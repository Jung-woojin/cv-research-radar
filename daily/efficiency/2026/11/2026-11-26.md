## 1. MNN — 제한된 CPU 예산과 무제한 host의 최적 thread 수는 다르다

**사실:** #27358 head `e317e3a0a48c7b8556fa3e9febeebae950cf1f8a`의 diff는 MNN thread 요청을 `cpu_threads()`로 제한한다. Linux affinity와 현재 cgroup 및 ancestor의 `cpu.max`를 읽는다. 공통 함수의 8-thread 상한은 제거하되 ONNX·NCNN은 호출부에 상한을 유지한다. [구현](https://github.com/ultralytics/ultralytics/pull/27358/files)

**저자 측정:** 2×AMD EPYC 9655·384 logical CPUs, MNN 3.6.2, FP32·640 입력에서 3회의 교대 fresh-process round median이다. 지표는 `YOLO().predict` wall ms/image다.

| 조건 | 요청 threads 전→후 | YOLO26n ms | YOLO26m ms |
|---|---:|---:|---:|
| `taskset -c 0-7` | 192→8 | 25.0→18.8 | 111.3→90.9 |
| `docker --cpus=4` | 192→4 | 294.2→77.6 | 850.4→239.2 |
| `taskset -c 0-31` | 192→32 | 28.8→29.3 | 90.6→92.2 |
| 제한 없음 | 192→192 | 29.1→29.9 | 89.1→84.7 |

**리뷰어 재현:** 같은 EPYC host model의 Docker 4-CPU 조건에서 YOLO26n 294→80ms, 같은 검출 결과를 보고했다. 반대로 무제한 환경에서 MNN을 8 threads로 고정하면 YOLO26x는 약 164→299ms로 느려졌다. 요청 thread 수는 실제 MNN worker 수와 같다고 가정하지 않는다. [리뷰 원문](https://github.com/ultralytics/ultralytics/pull/27358#issuecomment-7169099812)

**조건·한계:** main/PR의 정확한 benchmark base SHA, 명시적 batch·warm-up 횟수·OS/compiler 세부 버전·thermal mode는 미확인이다. 같은 검출은 holdout 정확도 동등성의 증거가 아니다. quota와 affinity, 서로 다른 모델의 결과를 합치면 **not strictly apples-to-apples**다. ARM board는 CI를 넘어선 성능 검증이 없고 cgroup v1도 미검증이다.

**진단→가설:** worker가 CPU quota보다 많으면 runnable thread 경합과 quota throttling이 지연을 늘릴 수 있다. 반면 CPU 예산이 충분하면 큰 모델의 병렬성을 과도하게 줄이는 것이 손해다. throttling counter가 없어 정확한 원인 귀속은 가설이다.

**최소 실험·GO/KILL:** 동일 weight·batch 1·640·commit에서 thread 1/2/4/8/기본 × quota/affinity/무제한을 교차하고 실제 worker 수, `cpu.stat` throttling, p50/p95, context switch, 출력 오차를 기록한다. 제한된 환경에서 지연·정합성이 함께 개선되면 GO. 모든 MNN 환경에 8-thread 상한을 일괄 적용하면 KILL.

## 2. LiteRT — 같은 두 CPU라도 quota와 pinning은 다른 실행 조건이다

**사실:** #27360 head `6502cb7f29a008a3c82dabb18dbae29224a9bfdf`는 interpreter의 `num_threads=NUM_THREADS`를 `cpu_threads(NUM_THREADS)`로 바꾼다. 모델 축소·INT8 전환이 아니다. [diff](https://github.com/ultralytics/ultralytics/pull/27360/files)

**저자 측정:** 같은 384-logical-CPU EPYC 구성, LiteRT FP32·640, 3회 교대 fresh-process round의 `YOLO().predict` wall median이다.

| 조건 | interpreter threads 전→후 | YOLO26n ms |
|---|---:|---:|
| Docker quota 0.5 CPU | 8→1 | 299.6→82.8 |
| Docker quota 2 CPUs | 8→2 | 86.1→24.0 |
| affinity 2 CPUs | 8→2 | 26.9→20.2 |
| 제한 없음 | 8→8 | 14.5→15.5 |

**리뷰어 재현:** EPYC quota 2 조건에서 84.1→24.0ms를 보고했고, Apple M-series host의 18-CPU Linux VM에서는 ai-edge-litert 2.4.0으로 thread 선택과 검출 결과를 확인했다. 이 VM의 버전 정보를 EPYC 측정의 확정 runtime 버전으로 옮기지 않는다. [리뷰](https://github.com/ultralytics/ultralytics/pull/27360#issuecomment-7167807379)

**조건·한계:** EPYC의 exact LiteRT 버전·base SHA·batch·warm-up·OS/compiler는 미확인이다. quota 2와 affinity 2는 실행 가능 코어 배치·throttling이 달라 **not strictly apples-to-apples**다. unrestricted 양쪽 8-thread 결과의 작은 차이는 코드의 thread 축소 효과로 해석할 수 없다. 공유 코드 경로라는 이유만으로 i.MX95 보드/NXP delegate 가속을 주장하지 않는다.

**진단→가설→실험:** quota 아래의 과도한 thread가 지연을 만들 수 있다. 같은 모델에서 quota 2/affinity 2를 분리하고 threads 1/2/8, delegate, 실제 export shape·batch를 고정한다. warm-up 이후 wall과 interpreter-only 시간을 별도로 측정한다.

**GO/KILL:** CPU 제한 container에는 우선 GO. MNN과 LiteRT의 서로 다른 모델·runtime 표로 backend 우열을 정하면 KILL. 두 사례는 같은 CPU 예산 원인의 별도 runtime 증거이며 독립된 알고리즘 가속 두 건으로 세지 않는다.

## 3. Core AI — asset이 같아도 실행 경로가 같지는 않다

**사실:** #27373은 package 수정이 아닌 미병합 문서 PR이다. 새 비교는 head `b9a2ba67ce51949ba0a8904d1b568dab4394aad8`에 있고, 기존 Mac mini·iPhone 측정은 그대로 옮긴 표라고 명시한다. [고정 문서](https://github.com/ultralytics/ultralytics/blob/b9a2ba67ce51949ba0a8904d1b568dab4394aad8/docs/en/integrations/coreai.md)

**저자 측정:** MacBook Air M4·macOS 27.2.1에서 coreai-core 1.0.0으로 export한 YOLO26n은 Python `val`에서 1.7~1.8초/image, 직접 Python runtime 호출에서도 1.7~2.0초였다. 같은 asset의 Swift 호출은 FP32 6.6ms, FP16 7.2ms였다. Swift 6.4.2, 첫 호출 이후 20회 median·기본 specialization 조건이다. `USE_OS_COREAI=1`도 Python 경로를 빠르게 만들지 못했다고 보고했다.

**조건·한계:** 새 Swift/Python 대조의 batch·정확한 input shape·Python warm-up 횟수는 해당 timing 문단에서 확정하지 못했다. Python `val`과 Swift function 호출은 측정 범위가 달라 **not strictly apples-to-apples**다. 따라서 이를 Swift 언어의 가속 배수로 제시하지 않는다. FP16이 FP32보다 빠르다는 결과도 아니다.

**반례와 교차확인:** 구버전 converter/core/PyTorch 조합으로 만든 FP32 asset은 Python에서 11ms였다고 하지만 export와 runtime이 함께 달라 단일 버전 회귀로 귀속할 수 없다. Apple은 specialization 결과가 device·OS에 의존하고 cache를 사용한다고 설명한다. 이는 cold load와 warm inference를 나눌 근거이며 위 지연 원인을 입증하지는 않는다. [Apple 공식 문서](https://developer.apple.com/documentation/CoreAI/managing-model-specialization-and-caching)

**진단→가설:** 새 asset 표현과 Python runtime의 실행·specialization 경로 사이에 비용이 있을 수 있다. direct Python에서도 느리다는 관찰은 Ultralytics 전후처리만으로 설명하기 어렵게 하지만 kernel/device profiler 증거는 없다.

**최소 실험·GO/KILL:** 동일 asset hash·입력 tensor·batch에서 Python direct/YOLO/Swift를 비교한다. load·specialization·첫 호출·warm function·전후처리를 분리하고 Instruments로 실제 device 배치와 동기화를 확인한다. 앱 경로의 warm latency가 목표를 통과하면 GO. Python 수치로 Apple hardware를 평가하거나, Swift 6.6ms를 카메라 end-to-end 지연으로 인용하면 KILL.

## 4. Intel Xe2 Vulkan — 큰 tile보다 실행 가능한 tile이 먼저다

**사실:** 미병합 #33076 head `99d99bef723fd6efb65d8f2f147a8de39677488b`는 Intel Xe2+Mesa ANV에 한해 non-coopmat2 matmul tile을 medium으로 제한한다. diff의 vendor·driver·architecture guard와 128×128 shape 시험 추가를 확인했다. Windows Intel·다른 vendor에 일괄 적용하는 변경이 아니다. [구현](https://github.com/ggml-org/llama.cpp/pull/33076/files)

**저자 제보:** Arc Pro B60(BMG G21), Thunderbolt 연결 aarch64 host, Linux 7.1.12, GuC 70.72.1, Mesa 26.2.4·ANV 26.2.6, Vulkan 1.4.354다. Qwen3-4B-Instruct-2507 Q4_K_M, `-ngl 99 -fa 1`에서 master는 m,n 모두 64를 넘는 large-tile dispatch에 16~19초 후 device-lost가 발생했다. prompt 길이보다 ubatch 경계와 일치했다고 보고한다. [제보·조건](https://github.com/ggml-org/llama.cpp/pull/33076)

**수정 후 측정:** `llama-bench -p <N> -n 128 -r 3 -dev Vulkan0`에서 pp512는 ub64 206.14±3.21, ub512 729.32±19.02 tok/s였다. tg128은 각각 11.09±1.06, 10.66±0.09였다. 이는 **수정본 내 서로 다른 ubatch 비교**로 **not strictly apples-to-apples**다. master ub512는 완료하지 못했으므로 patch의 순수 속도 개선율을 계산할 수 없다.

**검증 한계:** 저자는 MUL_MAT 4,122건 통과를 보고했다. 전체 backend suite는 시간 제한으로 중간 종료했으므로 전부 통과한 것으로 쓰지 않는다. warm-up·명시적 logical batch·build compiler·clock/power mode는 미확인이다. 출력/연산자 시험은 full-model 품질 검증과 다르다.

**진단→가설→실험:** 특정 큰 tile·subgroup 경로가 driver hang을 유발할 수 있다. 동일 stack에서 parent/patch × ub64/72/96/512를 대조하고 dispatch tile, device reset, 출력 오차, pp/tg, profiler 시간을 기록한다. 이후 driver만 바꿔 hardware·driver 경계를 분리한다.

**GO/KILL:** 해당 장비 보유자의 격리 재현은 조건부 GO. 기본 배포 채택은 리뷰·driver별 회귀 확인까지 보류한다. pp512 향상을 decode·전력 개선으로 확대하면 KILL.
