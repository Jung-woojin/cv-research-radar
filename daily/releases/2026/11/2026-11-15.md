## 1. Ultralytics v8.4.213 — 후처리 비용과 타일 recall의 분리

**배포 사실:** 11월 15일 03:48:08 KST 발행. annotated tag object는 `55d268e96a74c364dbe499da89562ca499c01e5a`, 대상 commit은 `d0cfceaf16f8d13dc3e62270744e8f8a44640448`다. release는 새 architecture가 없다고 명시한다. [Release](https://github.com/ultralytics/ultralytics/releases/tag/v8.4.213)

**저자 설명과 코드 변경:** [PR #27197](https://github.com/ultralytics/ultralytics/pull/27197)은 큰 mask stack을 각 box 내부에서 decode하고, outline·JSON·text export가 그 표현을 직접 사용하도록 한다. `masks.data` 접근 시에는 dense `(N,H,W)` tensor를 생성한다. 경로 전환 기준은 dense stack이 CPU에서 4M pixels, GPU에서 33M pixels를 초과하는 경우다. 이는 VRAM byte 한도가 아니다. 이 PR은 11월 14일 merge됐으며 이번 공개 사건은 후속 package release다.

**별도 correctness 신호:** [PR #27188](https://github.com/ultralytics/ultralytics/pull/27188)은 class-aware NMS 이후 fragment coverage 검사에도 class offset을 적용한다. 이전에는 다른 class의 큰 box가 tile seam의 fragment를 제거할 수 있었다. `agnostic_nms=True` 경로는 같은 수정 효과를 기대하는 대조군이 아니다. PR의 예제별 객체 수 변화는 개발자 재현이며 이 실행의 측정이 아니다.

**논문 claim과 artifact의 간극 — 추론:** 동일 weight의 segmentation 비용 감소는 representation 개선 없이 가능하다. 반대로 dense tensor를 즉시 읽는 consumer에서는 지연 생성 이득이 줄 수 있다. tile recall 증가도 NMS/coverage 수정의 효과일 수 있다. outline-only 시간과 dense-mask 소비 시간을 같은 latency로 비교하면 **not strictly apples-to-apples**다.

**공개물·라이선스·설치:** code는 AGPL-3.0이며 설치 후보는 `ultralytics==8.4.213`이다. Python package·torch·torchvision·export runtime을 함께 lock해야 하며 package pin만으로 전체 환경이 고정되지 않는다. 이번 release API의 별도 asset은 SBOM이고 새 pretrained weight나 dataset은 확인되지 않았다. 기존 weight의 license는 별도 확인 대상이다. CPU fixture부터 가능하며 full inference의 GPU/VRAM 최소값은 모델·해상도·mask 수에 따라 달라져 단일 수치를 확인하지 못했다.

**무결성·활동:** SBOM의 API SHA256은 `70cb262ecc52c271f8299e636d9426e1779da74b31acd624c0e4dc41d8d6fbfa`다. 이는 weight digest가 아니다. tag object의 서명 상태는 unsigned이며 웹 페이지가 표시하는 commit 서명과 구분한다. 파일 다운로드 checksum 대조·attestation 검증은 하지 않았다. 위 merged PR을 확인했으나 open Issue 전수 조사나 사용자 회귀 재현은 하지 않았다.

**진단 → 가설 → 최소 개입 → 10~30분 계획:** 준비된 환경에서 v8.4.212/v8.4.213에 동일 box·prototype tensor를 넣는다. 경로 전환 기준 양쪽의 크기를 선택하고 ① outline/JSON만 소비, ② dense tensor까지 접근하는 두 경로를 나눠 mask·polygon parity와 peak memory, warm-up 후 시간을 기록한다. 실제 GPU 사용 시 hardware·precision·batch·input shape·동기화 조건을 고정한다. 별도로 두 class의 box가 tile seam에서 겹치는 작은 fixture로 보존 여부를 검사한다. backbone 재학습은 필요하지 않다.

**GO/KILL:** 출력 동등성과 consumer 전체 경로의 비용 감소가 확인되면 후처리 migration은 GO. tile fixture가 기대한 class-aware 보존을 만족하면 해당 수정은 GO. dense materialization을 제외한 시간을 전체 inference 속도라고 부르거나 recall 변화를 새 모델 gain으로 설명하는 것은 KILL이다.

## 2. RF-DETR 1.12.1 — batch·tensor layout을 실험 계약으로 고정

**배포 사실:** 11월 12일 22:24:29 KST release. 정확한 tag는 `1.12.1`이며 commit은 `f29e2a8bbb7cdcb8920bf74a335062f88a35046d`다. release asset은 wheel과 sdist다. [Release](https://github.com/roboflow/rf-detr/releases/tag/1.12.1)

**관측과 저자 설명:** [PR #1695](https://github.com/roboflow/rf-detr/pull/1695)은 fixed-batch predictor에서 batch 인자 생략 시 directory·recorded video를 batch=1로 처리하던 경로를 고친다. release 설명에 따르면 마지막 불완전 batch는 padding하지 않고 계속 거부한다. PR merge는 11월 9일로 창 밖이지만 package 발행은 창 안이다.

[PR #1700](https://github.com/roboflow/rf-detr/pull/1700)은 값과 shape가 올바른 boolean mask도 noncontiguous stride이면 `view`에서 실패하는 경로를 수정한다. chunk를 먼저 자른 뒤 `reshape`하며 필요한 복사는 chunk 내부로 제한한다. 개발자의 CPU/MPS parity 및 test 통과 보고는 독립 검증이 아니다. PR merge는 11월 10일이며 오늘 채택 이유는 12일 package 공개다.

**논문 claim과 artifact의 간극 — 추론:** 같은 checkpoint라도 batching wrapper에서 실패하거나 evaluator가 layout 때문에 crash하면 공개 표의 재현에 도달하지 못한다. 이를 모델 표현력 한계로 분류해서는 안 된다. release의 segmentation 메모리 최적화도 model forward 전체의 속도 향상으로 일반화하지 않는다. batch·precision·evaluator·mask layout이 다른 성능 비교는 **not strictly apples-to-apples**다.

**공개물·라이선스·설치:** [tag 고정 pyproject](https://github.com/roboflow/rf-detr/blob/1.12.1/pyproject.toml)에서 Apache-2.0, Python ≥3.10, torch ≥2.2, torchvision ≥0.17, transformers ≥5.1,<6, supervision ≥0.29를 확인했다. 설치 후보는 `rfdetr==1.12.1`이다. 범위 dependency를 실제 resolve한 환경까지 lock해야 한다. training/evaluation extra는 기본 설치와 구분한다. 새 checkpoint·dataset dump는 이 release asset에 없고 기존 weight 다운로드는 별도다. evaluator fixture는 CPU에서 시작할 수 있다. full-model GPU/VRAM 최소값은 확인되지 않았다.

**무결성·활동:** wheel의 release API SHA256은 `d4671be83f9633f8f3de1a59ab3f9c25b320705175d93c8c788b8e1e8a401724`다. 실제 download/hash 대조와 attestation 검증은 하지 않았다. #1695·#1700의 merged 상태를 확인했으며, issue backlog 전수 감사나 새 release 이후 독립 사용자 재현까지 확인한 것은 아니다.

**진단 → 가설 → 최소 개입 → 10~30분 계획:** 1.12.0/1.12.1의 evaluator에 동일한 mask 값을 contiguous와 strided 형태로 각각 전달한다. prediction-only·target-only·양쪽 layout을 교차하고 chunk 경계에 걸친 score-ordered match flags와 IoU를 비교한다. 모델 load 없이 layout 가설부터 반증한다. 준비된 모델 환경이 있으면 fixed batch=4 predictor에 8장/9장 directory를 넣고 explicit batch와 생략 경로를 비교한다. 9장의 마지막 1장 거부를 새 회귀로 오인하지 않는다.

**GO/KILL:** layout만 바꾼 입력의 match flags·IoU가 같고 정상 batch가 처리되면 migration은 GO. fixture가 통과해도 full COCO AP 또는 TensorRT 전체 parity를 증명했다고 말하는 것은 KILL이다. 값이 달라지면 dtype·threshold·chunk 설정을 보존한 최소 반례부터 조사한다.

## 보류 후보의 새 확인: Iris-Z

어제의 card 조회 실패를 보완했다. [Hub history](https://huggingface.co/speridlabs/iris-z/commits/main)의 최초 `Iris-Z` commit은 `39cf884b84e14fb5bc44b2e6a06aaf7735a49c86`, 11월 11일 18:20:41 UTC다. 현재 revision `5d35ec0d3ebd55b7438cdaed93457a7231d6711f`의 11월 13일 변경은 arXiv 링크 추가다. 현재 tree에는 big 14개, small 4개 numbered transformer shard가 있다. 최근 수정 시각을 신규 weight 공개일로 쓰지 않는다.

[고정 card](https://huggingface.co/speridlabs/iris-z/blob/5d35ec0d3ebd55b7438cdaed93457a7231d6711f/README.md)는 weight metadata에 FLUX non-commercial license를 표시하고 코드에는 Apache-2.0을 안내한다. gated FLUX.2 autoencoder의 조건 동의·인증도 필요하다. 따라서 코드 license를 weight 이용권으로 확장하면 안 된다. card의 all-task GPU memory 안내는 big 약 112GB·small 약 33GB이며 독립 측정이 아니다. SDK 설치 안내는 Python 3.10·PyTorch 2.9.1/CUDA 13.0·NVIDIA driver 580 이상이다.

깊이 benchmark는 10-seed pixelwise median, speed 표는 기본 1 seed다. 이 두 표를 동일 budget의 성능·속도로 읽으면 **not strictly apples-to-apples**다. 이는 claim을 반박한 결과가 아니라 evaluator·seed budget을 고정해야 한다는 신호다. 이번에는 weight 초기 공개가 창 밖이고 새로운 weight 교체 근거가 없어 핵심 릴리스 수에 포함하지 않는다.
