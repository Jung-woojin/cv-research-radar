## 1. NCNN이 Linux 프로세스 CPU 제한을 무시해 과도한 thread 사용

**확인 사실:** #27244는 main의 `42891e21903ea2ece4f123ac3d188642fb537617`로 병합됐다. diff는 모델 로드 전에 Linux NCNN의 thread 수를 줄이고 ONNX와 공통 `cpu_threads(n)`을 사용한다. 사람 maintainer glenn-jocher가 별도 Linux container에서 thread-count 변화를 확인했다. [공식 PR·재현 댓글](https://github.com/ultralytics/ultralytics/pull/27244) · [diff](https://github.com/ultralytics/ultralytics/pull/27244/files)

- **실패 조건·구성:** Linux many-core host 또는 제한된 container, NCNN 1.0.20261020, YOLO26n FP32, 입력 640. NCNN 기본 thread 수가 host 기준이며 affinity·quota를 반영하지 않았다.
- **작성자 보고:** 384 logical CPU의 dual EPYC 9655에서 `taskset -c 0-3` 조건은 기존 352 threads·390~395 ms/image, 수정 4 threads·16.5~17.3 ms/image다. 극단적인 Docker quota 지연도 보고됐지만 일부는 단일 run이므로 안정적 배수 개선으로 일반화하지 않는다.
- **공식 인정·재현 수준:** maintainer는 Apple M-series host의 18-CPU Linux VM에서 기존 NCNN 18 threads가 무제한일 때 8, `--cpus=2`일 때 2, `--cpuset-cpus=0-3`일 때 4, `--cpus=0.5`일 때 1로 줄어드는 것을 확인했다. EPYC 지연시간은 maintainer가 재검증하지 않았다. 외부 독립 community 재현은 미확인이다.
- **진단 → 메커니즘:** 사용 가능한 CPU보다 큰 thread pool이 scheduling·quota throttling 비용을 만든다는 해석이다. 수정은 affinity와 mount root의 `/sys/fs/cgroup/cpu.max`만 읽는다. nested/ancestor cgroup의 더 작은 quota는 놓칠 수 있다.
- **남은 negative result:** 작성자는 nested systemd quota에서 8 threads·83 ms/image를 보고했다. maintainer도 한계를 인정했다. Linux ARM board·cgroup v1·실제 Vulkan GPU는 미검증이다. 8-thread 상한은 큰 모델의 무제한 host 성능을 낮출 수 있어 보편적 최적값이 아니다.
- **가설 → 최소 개입:** 같은 weight·입력에서 thread 수를 실제 CPU budget에 맞추면 출력 의미를 유지하면서 지연시간을 줄일 수 있다. quota 탐지는 별도의 후속 개입으로 분리한다.
- **최소 실험:** base `2f7d25228cec88be93aa3acf7de59d7765398575`와 병합 commit에서 동일 NCNN 모델·bus.jpg를 사용한다. fresh process마다 무제한, cpuset 4, quota 2, nested quota 조건을 분리하고 warmup 뒤 thread 수·median/p95 지연·cgroup throttling·box/class/confidence parity를 기록한다. ONNX를 thread 정책 대조군으로 둔다.
- **GO/KILL:** 실제 thread 감소와 latency 개선이 함께 보이고 예측이 유지되면 해당 환경에서 GO. nested quota를 못 읽으면 quota 완전 지원 주장은 KILL하고 탐지 범위를 축소한다. 서로 다른 host의 ms는 `not strictly apples-to-apples`다.
- **기존 주장과 충돌:** NCNN 모델 구조의 느림으로 단정할 수 없다. 자원 정책을 먼저 진단해야 한다. 모든 Linux 모델에서 8 threads가 최고 속도라는 주장도 근거가 없다.

## 2. RT-DETR CoreML 8-bit export가 inf anchor의 k-means 입력에서 실패

**확인 사실:** #27245는 `4252e33aa88eaa27e203434dc3eb4839ba290933`로 병합됐다. diff는 512개보다 큰 상수 중 non-finite 값이 있는 연산을 palettization 대상에서 제외한다. [공식 PR·maintainer 실험](https://github.com/ultralytics/ultralytics/pull/27245) · [diff](https://github.com/ultralytics/ultralytics/pull/27245/files)

- **실패 조건·구성:** macOS arm64, coremltools 9.0, RT-DETR-L, imgsz 640, `RTDETR("rtdetr-l.pt").export(format="coreml", quantize=8)`. 이 8-bit 설정은 k-means weight palettization이며 전 연산 INT8 실행을 의미하지 않는다.
- **작성자 주장·재현:** decoder의 inf-masked anchor가 상수로 접히고 scikit-learn k-means가 non-finite 입력을 거부했다. 작성자는 기존 102초 뒤 ValueError와 수정 후 32 MB package export를 보고했다.
- **공식 인정·community 수준:** maintainer가 기존 main에서 129초 뒤 같은 오류를 별도 재현했다. 수정 package의 bus.jpg confidence가 PyTorch와 0.01 이내이며 일반 YOLO26n INT8 package는 기존과 byte-identical이라고 보고했다. 외부 community 재현은 미확인이다.
- **진단 → 메커니즘:** inf는 anchor masking 의미를 가진 값인데 exporter가 일반 압축 weight처럼 처리했다. non-finite를 무조건 NaN 오류나 학습 불안정으로 해석하면 실패 소유 단계를 잘못 찾는다.
- **실패한 대안:** maintainer는 anchor의 inf를 큰 유한값으로 바꾸는 대안도 시험했다. PyTorch·ONNX·CoreML FP16에서는 bit-identical이었지만, 그 상수가 palettization되면서 INT8 coco8 mAP50-95가 원문 기준 0.7109에서 0.7040으로 낮아져 채택하지 않았다. 이는 작은 coco8의 원문 측정이며 전체 COCO의 일반적 정확도 차이가 아니다.
- **가설 → 최소 개입:** anchor 의미를 유지하면서 압축 단계만 건너뛰면 export 성공과 추론 의미를 함께 보존할 수 있다.
- **최소 실험:** base `4d254d8141e49dd85009e1ec7657ab3c4ee8c150`와 병합 commit, 같은 checkpoint·입력 크기·toolchain으로 기존/skip/finite-substitution 세 조건을 비교한다. export 성공·오류 단계·non-finite 상수 보존·package 크기·동일 이미지 box/confidence parity를 기록한다. coco8은 smoke test로만 사용하고 정확도 결론은 고정 COCO val split에서 별도 검증한다.
- **GO/KILL:** skip 조건만 export 오류를 제거하면서 FP16 기준 예측을 유지하면 진단 GO. export 성공만으로 정확도·Neural Engine 속도를 보장하는 해석은 KILL한다.
- **기존 주장과 충돌:** RT-DETR의 검출 능력 저하보다 export 최적화의 입력 계약 위반이다. 전일 LiteRT logit clipping과는 backend·실패 단계가 다르다. CoreML palettization과 LiteRT INT8 비교는 `not strictly apples-to-apples`다.
- **점수:** 심각도 **3/5** · 재현 신뢰도 **4/5** · 연구 아이디어 가치 **4/5**.

## 반증을 보존할 후보: 타일 NMS FP16 overflow

#27247의 작성자는 수동으로 ONNX graph output을 FP16으로 바꿔 class offset overflow를 재현했다. 산술 자체는 타당하지만 maintainer는 기본 YOLO/RT-DETR 경로에서 rows가 FP32로 승격되며 FP16 export도 FP32 I/O를 유지한다고 설명했다. MPS의 두 모델·두 canvas 크기에서 기존과 수정의 boxes가 같았다고 보고했고 PR은 미병합 종료됐다.

따라서 이를 일반 tiled prediction 회귀로 기록하지 않는다. 후속 검증의 첫 단계는 수정 없는 predict/val 호출에서 merge_tiles 입력 dtype을 직접 probe하는 것이다. 이 조건을 충족하지 못하면 학습 모델의 tiny-object 실패나 실제 배포 오류로 확대하지 않는다. 이 사례는 11월 15일 half-box utility 후보와 같은 “호출 경로 도달 가능성” 점검을 강화한다.

## 오늘의 실패 패턴 3개

1. **실행 budget과 runtime 기본값의 불일치:** container에 CPU 제한이 있어도 backend thread pool이 자동으로 따르지 않는다.
2. **의미 있는 특수값과 최적화 입력 계약의 충돌:** masking의 inf를 압축 알고리즘에 그대로 넘기거나 유한값으로 바꾸는 것 모두 검증이 필요하다.
3. **입력 locator와 출력 namespace의 혼동:** 정상 annotation 도구의 경로도 label 오저장을 유발할 수 있다.

## 논문 아이디어로 연결 가능한 빈틈

**추론:** aerial/UAV·maritime/CCTV deployment에서 같은 checkpoint의 실패를 모델·전처리·후처리·runtime·artifact 저장으로 분리하는 진단 benchmark를 만들 여지가 있다. 모델 재학습보다 먼저 thread budget, 상수 표현, 경로 mapping만 바꾸는 최소 개입을 평가한다. latency와 box parity, export와 예측 parity, label containment와 대응 무결성을 각기 짝지어 기록한다.

알려진 버그 세 개의 재현만으로 신규 논문이 되지는 않는다. 여러 backend·annotation 도구에서 재발하는 계약 위반과 실질 task 영향을 입증해야 한다. 타일 FP16 후보처럼 실제 기본 경로에 도달하지 않는 반례도 함께 공개해야 과장된 실패 집계를 피할 수 있다.

## 직접 재현해볼 최소 실험

첫 실험은 COCO converter의 합성 경로 matrix다. GPU 없이 작은 JSON과 임시 source fixture로 시작하고, label 위치·내용·충돌 예외를 base/merge 사이에서 비교한다. 실제 dataset 학습은 이 검사가 통과한 뒤에만 추가한다.

두 번째는 Linux container의 NCNN thread-count probe이며, 제한을 읽었는지와 예측 parity를 먼저 확인한 뒤 latency를 측정한다. CoreML은 별도 macOS 환경에서 export와 상수 보존부터 검사한다. Windows PC나 RTX 5060 Ti 8GB만으로 CoreML 재현이 가능하다고 보장하지 않는다.

**공통 GO:** 고정 base의 조건부 실패가 최소 개입 후 사라지고 정상 대조군이 유지된다. **공통 KILL/축소:** 실패를 재현하지 못하면 revision·입력 표현·호출 경로부터 확인한다. 이번 watch의 시간·VRAM·AP 측정은 없으며 /5 점수는 발생 확률이나 실측 성능이 아닌 조사자의 우선순위 판단이다.
