## Q1. 작은 객체 성능의 공백 중 얼마가 모델 실패가 아니라 metric 수집 실패인가?

**문제·Observation·왜 지금:** #27348은 evaluator가 계산한 크기별 AP를 `DetMetrics.area_ap`에 보관하고 `results_dict`에 합치며 실행마다 초기화한다. Maintainer는 CPU에서 기존 `model.val(save_json=True)`가 크기별 AP를 출력하지만 반환 객체에는 native key만 남는 현상을 재현했다고 보고했다. 학습·탐지 능력 개선의 증거가 아니다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27348) · [diff](https://github.com/ultralytics/ultralytics/pull/27348/files) · [maintainer 재현과 미검증 범위](https://github.com/ultralytics/ultralytics/pull/27348#issuecomment-7138478585)

**Gap·Diagnosis·Mechanism:** AP-small을 수집하지 못한 상태와 계산 결과 0을 같게 저장하면 작은 객체 실패 분포가 왜곡될 수 있다. 재사용 객체의 stale 값도 가짜 회복을 만들 수 있다는 추론이다. 기존 코드 버그 하나를 일반적인 모델 실패로 확대하면 안 된다.

**Hypothesis·최소 개입:** 값에 계산 여부·evaluator·run ID를 붙이고 누락을 0으로 채우지 않으면, 수집 경로에 따른 가짜 size gap을 제거할 수 있다.

**Experimental Design:** base `82f0bd146dc174306761be60521f2ccc378f3563`와 PR head `c0c0323132380f21aa0607e1cbe6a336e305becc`를 고정한다. 동일 predictions.json으로 direct evaluator·validator stats·반환 dict를 대조한다. 같은 객체로 save_json on→off→on을 실행하고 fresh 객체와 비교한다. callback 시점도 별도 기록한다. PR 본문은 `on_val_end`에 여전히 size key가 없다고 명시한다.

**Dataset·baseline·metric·판정:** coco8은 smoke test, 고정 COCO val2017 개발 subset은 실제 진단용이다. baseline은 직접 evaluator 결과다. 값 일치·key coverage·stale value 발생·native AP 보존을 측정한다. 계산된 값만 정확히 회수하면 GO. 누락을 0으로 보간하거나 callback 결과를 최종 반환값으로 취급하면 KILL한다. LVIS·DDP는 maintainer도 미검증이며 일반화하지 않는다.

**Expected Contribution·negative result:** 모델 능력과 연구 계측 오류를 분리하는 수집 계약이다. 수집 오류가 실험 결론을 바꾸지 않으면 영향 범위를 좁힐 수 있다. **Compute cost 1/5**, CPU 시작 가능. 1~2주 경로 검사, 3~4주 여러 evaluator, 5~8주 크기별 결론의 민감도를 평가한다. 알려진 API 버그 재현만으로 novelty는 낮고, 여러 연구 pipeline의 결론 변화가 있어야 논문화 후보가 된다.

## Q2. 영상 reasoning의 dependency 민감도는 시각 능력보다 입력 문법 변화로 설명되는가?

**문제·Observation·왜 지금:** #69599는 wrapped video triple을 bare placeholder로 정규화한 뒤 기존 replacement를 적용한다. 이미지 marker를 유지하는 테스트도 포함한다. 작성자는 CPU 재현을 보고했지만 GPU generation·video accuracy 비교는 실행하지 않았다고 명시했다. Maintainer는 원 제보에 end-to-end 답변 차이 근거를 요청했다. [수정안](https://github.com/vllm-project/vllm/pull/69599) · [diff](https://github.com/vllm-project/vllm/pull/69599/files) · [원 제보 댓글](https://github.com/vllm-project/vllm/issues/69473#issuecomment-7133101701)

**Gap·Diagnosis·Mechanism:** dependency가 바꾼 placeholder 확장과 모델의 시간 추론 실패를 구분할 필요가 있다. triple만 매칭하는 대안은 기존 bare 입력을 거부한다는 기여자의 CPU 반례가 있다. 정상 입력 한 종류만 복구하는 수정으로 전체 입력 계약이 보존됐다고 판단할 수 없다.

**Hypothesis·최소 개입:** frame·timestamp·weight·decoding을 고정하고 placeholder 문법만 개입하면, 일부 답변 차이는 중첩된 바깥 marker와 연결될 수 있다. token 구조 차이가 품질 차이를 반드시 만든다는 가정은 하지 않는다.

**Experimental Design:** 현재 head `8d8744e1e13278ee023a37be5b2e83411ea5b193`를 고정한다. 본문의 실행 보고는 이전 `0f11a6ae`와 동일 tree `95eba1ac` 기준임을 구분한다. CPU에서 wrapped/bare × dependency 전후 × cache on/off를 검사하고 이미지-only·image+video 대조군을 둔다. 이후 동일 자연 영상 응답을 비교하되 frame 수·sampling 시각·해상도·prompt를 바꾸지 않는다.

**Dataset·baseline·metric·판정:** 원문의 합성 4프레임은 문법 검사에만 사용한다. 후속은 E.T. Bench TVG의 고정 개발 subset과 동일 processor를 쓰는 소형 모델 후보로 수행한다. 정확한 checkpoint 실행 가능성은 미확인이다. baseline은 reference processor 구조이며 token sequence·placeholder 예외·캐시 일치·temporal IoU·답변 정확도를 기록한다. 문법 보존과 paired 품질 회복이 연결되면 GO. CPU 테스트만으로 reasoning 향상을 주장하면 KILL한다.

**Expected Contribution·negative result:** 입력 계약이 시간 추론 평가에 미치는 범위를 밝힌다. 구조가 달라도 품질이 유지되면 모델의 입력 문법 강건성 경계를 얻는다. **CPU cost 1/5, 실제 추론 3/5**의 계획 판단이다. 1~2주 계약 검사, 3~4주 소형 모델 paired 추론, 5~8주 다른 processor 계열로 확장한다. 알려진 marker 수정만으로 novelty는 낮으며 GPU 단계의 RTX 5060 Ti 8GB 적합성은 미측정이다.

## Q3. VQA의 0점에서 모델 오답과 judge 실패를 얼마나 식별할 수 있는가?

**문제·Observation·왜 지금:** CharXiv commit은 `-1` 등 비이진 점수를 0으로 바꾸고 전체 분모를 유지한다. 원본 통계 코드도 같은 규칙이다. 공식 점수를 바꾸지 않으면서 운영 실패를 따로 관측해야 한다. [최근 수정·테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/9134731f4f617e62ee80bcae9d0d5d9695ea55ef) · [원본 통계 코드](https://github.com/princeton-nlp/CharXiv/blob/main/src/get_stats.py)

**Gap·Diagnosis·Mechanism:** 집계 0점은 정상 오답만으로도, judge 실패만으로도 만들어진다. headline 하나로 원인을 식별할 수 없다는 산술적 사실이다. judge 오류가 특정 그림·답변 길이에 집중되는지는 아직 미확인이다.

**Hypothesis·최소 개입:** 공식 점수와 함께 유효 채점 coverage·실패 원인·그룹별 실패율을 기록하면, 모델 변화와 judge 운영 변화의 혼동을 줄일 수 있다. 유효 문항만의 정확도는 보조 진단값이며 공식 점수를 대체하지 않는다.

**Experimental Design:** 저장된 raw judge 출력과 모델 응답을 고정하고 이전/수정/원본 집계를 비교한다. mock judge에서 독립 실패와 그림·길이에 종속된 실패를 따로 주입해 식별 검사를 한다. 합성 주입 결과를 실제 장애 빈도로 보고하지 않는다. 실응답이 없으면 과거 점수 영향량 추정은 중단한다.

**Dataset·baseline·metric·판정:** CharXiv의 동일 split·figure ID를 사용한다. baseline은 원본 전체 분모 점수다. 전체 수·정상 오답·invalid 수, 그룹별 coverage, 재집계 차이를 측정한다. 0/1/-1만 있는 경우 수정–이전 평균 차이는 F/N이며 F는 실패 수라는 도출 관계이지 실측 향상량이 아니다. 실패율만 바꿔도 headline이 바뀌고 보조 로그로 이를 식별하면 진단 GO. judge를 교체하고 같은 조건 개선으로 주장하면 KILL한다.

**Expected Contribution·negative result:** judge 기반 VQA의 능력·운영 오류 분해다. 실패가 없으면 해당 run에서 집계 수정 영향이 없다는 결론을 얻는다. **Compute cost 1/5**, CPU 재집계부터 시작한다. 1~2주 로그 검사, 3~4주 실패 구조 분석, 5~8주 다른 evidence VQA로 확장한다. 단순 invalid counter는 기여가 작고, 실제 오류 집중과 연구 결론의 민감도가 필요하다. 신규 유료 judge 호출은 이번에 수행하지 않았다.

## Q4. 시간 구간 요약의 높은 점수는 정확한 grounding인가, 파싱 실패 표본의 제외 효과인가?

**문제·Observation·왜 지금:** E.T. Bench 원본과 고정 adapter의 TVG는 실패도 전체 분모에 남긴다. EVS는 파싱 가능한 응답만 평균하며 모두 실패하면 0이다. 최근 통합은 이 차이를 서로 다른 모델에 공통 적용할 기회를 만든다. [고정 adapter](https://github.com/open-compass/VLMEvalKit/blob/2f11dc888838404991214cce0358fff815be7ff6/vlmeval/dataset/etbench.py) · [원본 evaluator](https://huggingface.co/datasets/PolyU-ChenLab/ETBench/blob/main/evaluation/compute_metrics.py) · [공식 평가 안내](https://github.com/PolyU-ChenLab/ETBench/blob/main/docs/BENCHMARK.md)

**Gap·Diagnosis·Mechanism:** 어려운 영상 응답이 더 자주 파싱에 실패하면 EVS의 유효 표본 평균은 쉬운 표본에 치우칠 수 있다는 추론이다. 모든 실패가 어려운 표본이라는 증거는 아직 없다. 전일 judge 프레임 누락과 달리 이번 개입 대상은 응답 parser와 평균 분모다.

**Hypothesis·최소 개입:** 의미가 같은 구간 표현에서도 parse coverage가 다르면 공식 EVS 평균과 전체 표본 기준 진단값이 달라질 수 있다. 둘을 함께 보고하면 형식 호환성과 실제 시간 구간 정확성을 구분한다.

**Experimental Design:** 저장 응답의 구간 숫자는 유지하고 범위 표기만 바꾸는 paired fixture로 시작한다. 이후 자연 응답에서 실패 subset을 사람이 구간 추출 가능한지 검토한다. 공식 parser는 고정하고, 사람 확인 canonical span 재채점은 oracle 진단으로 분리한다. 성능 개선용 후처리로 발표하지 않는다.

**Dataset·baseline·metric·판정:** E.T. Bench의 동일 EVS sample ID·source·split과 TVG 대조군을 사용한다. baseline은 공식 점수다. parse coverage·유효 응답 평균·실패를 0으로 둔 전체 평균·사람 추출 가능률을 보고한다. coverage와 점수 변화가 연결되면 GO. 전체 평균을 공식 benchmark 점수로 바꿔 부르면 KILL한다. subset·1/2 FPS·timestamp prompt가 다른 결과는 **not strictly apples-to-apples**다.

**Expected Contribution·negative result:** 모델 grounding과 출력 형식 선택 효과의 분해다. 자연 응답에서 영향이 없으면 선택 편향의 상한을 해당 표본 안에서 정할 수 있다. **Compute cost 1/5**, 저장 응답 CPU 검사 가능. 1~2주 parser 검사, 3~4주 자연 응답 수작업 감사, 5~8주 task·source별 비교를 계획한다. 기존 format sensitivity 연구와 중복 위험이 높으며 실제 모델 순위 역전은 미확인이다.

## Q5. 제출 ID가 모두 맞아도 질문과 답변의 대응 오류가 평가를 통과할 수 있는가?

**문제·Observation·왜 지금:** OK-VQA commit은 제출 레코드의 이미지 문자열을 정수 `question_id`로 바꿨고 로컬 정확도 계산은 바꾸지 않았다. 원본 VQA `loadRes`는 질문 ID 집합을 annotation과 비교한다. 집합 일치는 답변이 올바른 질문에 붙었는지 증명하지 못한다. [최근 diff·테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/b151e05a8afcca759d7af7caa4eea7b877c8d4da) · [원본 loader](https://github.com/GT-Vision-Lab/VQA/blob/master/PythonHelperTools/vqaTools/vqa.py)

**Gap·Diagnosis·Mechanism:** schema 적합성, ID 유일성, 의미 대응은 별개다. 여러 질문이 한 이미지를 공유할 때 image ID를 질문 식별자로 오용하거나 join 순서를 잘못 쓰면 ID 집합이 정상이어도 답변이 바뀔 수 있다는 추론이다. 이번 수정에서 그런 추가 버그를 발견했다는 뜻은 아니다.

**Hypothesis·최소 개입:** `(question_id, image_id, question hash, raw answer hash)` 연결 기록은 schema 검사로 찾지 못하는 질문–답변 permutation을 탐지한다.

**Experimental Design:** 동일 저장 예측으로 올바른 keyed join, row-order join, 중복 ID, 같은 이미지 안 답변 교환의 통제 fixture를 만든다. 원본 loader와 별도 provenance 검사를 비교한다. 의도적으로 손상시킨 fixture임을 명시하고 실제 모델 결과로 취급하지 않는다.

**Dataset·baseline·metric·판정:** OK-VQA의 annotation이 있는 고정 개발 subset과 다중 질문 이미지를 사용한다. annotation revision·loader port는 고정해야 하며 원본 loader는 Python 2 문법이므로 현재 실행 환경 호환성을 별도 확인한다. baseline은 question ID keyed join이다. schema pass율·중복/누락 ID·손상 탐지율·공식 VQA 점수 변화, 동일 이미지 내 교환 오류율을 측정한다. schema가 통과한 손상을 provenance 검사가 잡으면 도구 MVP GO. 실제 raw 응답 연결 기록 없이 과거 모델 저하의 원인이라고 주장하면 KILL한다.

**Expected Contribution·negative result:** evidence VQA의 답변 귀속과 artifact 검증이다. 실제 pipeline에서 오류가 없으면 해당 결과의 대응 무결성을 확인할 수 있다. **Compute cost 1/5**, CPU 시작 가능. 1~2주 fixture, 3~4주 다중 질문·배치 export 감사, 5~8주 여러 평가 framework 비교를 계획한다. 일반 데이터 무결성 검사와 중복이 커 단독 논문 가능성은 낮으며, 시각 증거 귀속 오류의 실제 빈도·영향을 보여야 한다.

## 공통 비교 조건과 오늘의 선택

dataset revision·split·sample ID·입력 hash, backbone·checkpoint·pretraining·external data, resolution·TTA, runtime·processor·dtype, reasoning effort·context/frame budget·compute budget, evaluator commit·judge snapshot을 고정한다. 재집계만 하는 실험은 모델 조건을 보존하고 재추론하지 않는다. 미확인 조건은 미확인으로 기록한다. 모델·입력·evaluator가 함께 바뀐 비교는 **not strictly apples-to-apples**다.

| 질문 | Novelty /5 | Feasibility /5 | Compute efficiency /5 | Publication potential /5 |
|---|---:|---:|---:|---:|
| Q1 AP 수집 경로 | 3 | 5 | 5 | 3 |
| Q2 영상 입력 문법 | 3 | 4 | 4 | 4 |
| Q3 judge 실패 식별 | 3 | 5 | 5 | 3 |
| Q4 파싱 coverage 선택 | 3 | 5 | 5 | 4 |
| Q5 질문–답변 귀속 | 2 | 5 | 5 | 2 |

점수는 조사자의 우선순위 판단이며 실측치나 출판 보장이 아니다. Compute cost는 낮을수록 가볍고 compute efficiency는 높을수록 유리하다. 4~8주는 검증 계획이며 논문 완성을 보장하지 않는다.

- **오늘 가장 먼저 테스트:** Q1. 동일 predictions.json에서 direct evaluator·반환 dict를 대조하고 save_json on→off 전환에서 stale 값을 검사한다.
- **RTX 5060 Ti 8GB에서 시작 가능:** Q1·Q3·Q4·Q5의 CPU 검사와 Q2 processor 검사. Q2 실제 GPU 추론의 VRAM·호환성은 미측정이다.
- **장기 박사주제:** 영상 증거 → 입력 표현 → 답변 귀속 → parser → judge → metric 수집의 오류를 분해하는 안전 영상 평가. Q2·Q4를 중심으로 CCTV·해양 위험 사건의 Answer–Evidence Gap을 다룬다. 현재는 연구 방향이며 검증된 장기 추세가 아니다.

오늘의 변화는 평가 구현·입력 계약의 변화다. 중요한 미해결점은 그 변화가 자연 응답과 실제 연구 결론에 미치는 크기이며, 첫 단계는 새 architecture보다 보존된 예측과 CPU 검사다.
