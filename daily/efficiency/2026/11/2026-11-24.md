## 1. CoreML — 연산 가속보다 다음 batch 로딩을 겹칠 수 있는가

**사실:** #27335는 기본 compute unit으로 모델이 load되면 `prefetch=True`를 설정한다. `CPU_ONLY` fallback에는 적용하지 않는다. 가속기 사용을 허용하는 설정으로 load됐다는 사실만으로 실제 Neural Engine 실행을 확정하지 않는다. [구현 diff](https://github.com/ultralytics/ultralytics/pull/27335/files)

**저자 측정:** M5 Pro 18코어·48GB, macOS 27.2.1, Python 3.12.12, torch 2.15.0, coremltools 9.0, YOLO26n·export 640에서 COCO 384장 및 1080p H.264 384 frames를 사용했다. fresh process와 warm-up, main/PR 교대 측정이다.

| 조건 | main median | PR median |
|---|---:|---:|
| FP16·이미지·batch 1 | 2.741 s | 2.270 s |
| FP16·이미지·batch 16 | 1.697 s | 1.651 s |
| FP16·video·batch 1 | 2.327 s | 2.073 s |
| FP32·이미지·batch 16 | 3.905 s | 3.904 s |

표는 전체 workload 처리 시간이며 단일 image kernel latency가 아니다. PR의 개선율은 paired ratio의 median으로 계산돼 위 두 median의 비율과 정확히 같지 않다. 출력 hash는 각 precision 안에서 main과 같았고 peak memory는 최대 17MB 증가했다고 보고한다. [측정·반례](https://github.com/ultralytics/ultralytics/pull/27335)

**조건·한계:** warm-up 횟수와 baseline exact SHA는 미확인이다. FP32 기본 export는 해당 M5 Pro에서 CPU 경로라고 보고됐다. host load average 20–48인 과부하에서는 FP32 video가 6쌍 중 5쌍 느려졌다. 다른 Mac·precision·host load 간 비교는 **not strictly apples-to-apples**다. fanless Mac, RT-DETR, INT8은 미검증이다.

**진단→가설:** 직렬화된 decode/load와 inference가 병목이면 prefetch가 유효하지만, CPU가 이미 포화됐으면 추가 worker와 메모리 경합이 손해일 수 있다.

**최소 실험·GO/KILL:** 같은 Mac·weight·640 입력에서 prefetch on/off × batch 1/16 × 정상/과부하를 교차한다. loader 대기, 전체 p50/p95, RSS, output hash와 실제 device 배치를 기록한다. 배포 부하에서도 정합성과 지연 목표를 통과하면 GO. FP16 결과를 모든 CoreML 모델의 보장 가속률로 쓰면 KILL.

## 2. TensorRT INT8 — calibration 자료를 늘리면 왜 정확도가 나빠지는가

**사실:** #27340은 TensorRT 11 ModelOpt 호출의 명시적 `calibration_method="max"`를 제거해 기본 entropy를 사용한다. TensorRT 7–10 calibrator는 이 변경 대상이 아니다. [diff](https://github.com/ultralytics/ultralytics/pull/27340/files), [v8.4.217](https://github.com/ultralytics/ultralytics/releases/tag/v8.4.217)

**저자 측정:** RTX PRO 6000 Blackwell, TensorRT 11.5.0.63, ModelOpt 0.48.0, torch 2.15.0+cu132, static batch 1 엔진·batch 1 평가다. COCO val2017에서 128장 calibration의 YOLO26s-pose mAP50-95(P)는 FP16 0.6258, INT8 max 0.3130, entropy 0.6106이었다. YOLO26s-seg의 mask mAP는 0.3924 / 0.2241 / 0.3889였다. 추론 속도나 peak VRAM 개선 수치는 아니다. [측정표](https://github.com/ultralytics/ultralytics/pull/27340)

**교차확인·비용:** 최초 커뮤니티 제보는 Ultralytics 8.4.216, T4/L4, torch 2.14.1+cu126, driver 580.82.07, static 640×640·batch 1·`rect=False`다. YOLO26n은 COCO에서 FP16 0.4032, max 0.3843, entropy 0.3936, export는 max 176.5→entropy 251.4초였다. 이는 위 Blackwell 표와 hardware·software가 달라 **not strictly apples-to-apples**다. [원 제보 #27334](https://github.com/ultralytics/ultralytics/issues/27334)

**조건·한계:** PR의 모든 task별 input shape·warm-up·weight hash는 별도 확정하지 못했다. 4장 calibration에서는 OBB entropy가 max보다 0.3–0.9점 낮은 반례가 있다. PR은 다섯 번 rebuild에서 entropy가 0.6점 이내로 변했다고 보고한다. calibration/evaluation 중복 여부와 task별 분포 대표성은 추가 audit 대상이다.

**진단→가설:** 저자는 max가 outlier에 범위를 맞춰 일반 activation의 해상도를 잃는다고 설명한다. entropy의 clipping이 이를 완화할 수 있으나 작은 calibration set에서는 분포 추정이 불안정할 수 있다.

**최소 실험·GO/KILL:** 같은 weight·runtime·평가 split에서 max/entropy × calibration 4/128장 × 고정 image 순서를 비교한다. 별도 holdout의 task별 품질·outlier/scale 분포, export 시간, 엔진 p95·peak memory를 함께 기록한다. 정확도 관문과 export 예산을 통과하면 GO. “INT8이니 빠르다”거나 4장 결과로 모든 task의 entropy 우위를 선언하면 KILL.

## 3. CUDA BF16 KV — 매 token 전체 cache 변환이 숨어 있는가

**사실:** 미병합 #32905의 head는 `7615fa54ef3b8e46bab7939f11f1526f89e8d9ad`다. batch 1·지원 shape에서 BF16 KV의 vector 경로를 선택하되 GQA≤6과 compiled kernel 존재 여부를 확인한다. 저자는 GQA>6에서는 재독 traffic 때문에 convert+MMA가 더 빠르다고 설명한다. [코드·측정](https://github.com/ggml-org/llama.cpp/pull/32905)

**저자 측정:** Qwen2.5-1.5B-Instruct Q4_K_M, BF16 K/V, `-fa 1 -p 0 -n 128 -r 3`에서 context depth 16384의 decode는 RTX 3050 Laptop 4GB에서 58.58→76.11 tok/s, Tesla T4 16GB에서 81.35→94.22 tok/s였다. depth 0에서는 각각 114.32→115.76, 147.36→147.91 tok/s로 차이가 작다.

**조건·한계:** correctness 환경은 3050 CUDA 12.6, T4 CUDA 13.0이며 각 4430/4430 backend tests 통과 보고다. 성능 baseline exact SHA·driver·warm-up·명시적 ubatch는 미확인이다. `Q->ne[1]=1`, head size 128·KV heads 2·GQA 6·KV length 16384의 연산자 표는 scratch 16.78→0MB를 보고하지만 전체 모델 peak VRAM 감소로 환산하지 않는다. GPU 간, ncu kernel 시간과 cudaEvent p50 간 비교는 **not strictly apples-to-apples**다.

**진단→가설:** resident KV의 크기를 줄이지 않아도 token마다 BF16→F16 변환과 scratch traffic을 제거하면 긴 context에서 이득이 커질 수 있다. 전일 quantized sparse indexer의 결과와 합쳐 보편적 가속률을 만들지 않는다.

**최소 실험·GO/KILL:** 동일 장치에서 parent/patch × BF16/F16 KV × context depth × GQA 경계 6/8을 대조한다. conversion kernel 유무, scratch·peak allocated/reserved, decode p95, 출력/PPL을 기록한다. 경계 밖 회귀 없이 개선이 재현되면 GO. operator scratch 제거를 모델 전체 VRAM 절감이나 품질 동등성으로 단정하면 KILL.

## 4. V100 NVFP4 — kernel 5배가 모델 5배가 되지 않는 이유

**사실:** 미병합 #32875는 NVFP4 dequant의 thread 배치·decode·vector store를 바꾼다. head `2a946f9f8b618223e4cf0a5723bb745b161f3e12`의 11/23 보완은 store-loop 경고 수정이다. [diff](https://github.com/ggml-org/llama.cpp/pull/32875/files)

**저자 측정:** V100 32GB sm70, 250W limit·최대 1380MHz, driver 580.178.04, nvcc 12.8.93, Release CUDA build다. `m=4096,n=512,k=14336`, NVFP4×F32 연산자에서 dequant 평균은 1.436→0.284ms, 전체 MUL_MAT은 2292.57→1132.33µs였다. Qwen3.8-27B NVFP4 혼합 GGUF·14.72GiB, `-fa 1 -ngl 99 -r 3`, pp512·ub512는 238.43±0.53→272.26±0.70 tok/s였다. [단계별 표](https://github.com/ggml-org/llama.cpp/pull/32875)

**반례와 조건:** pp2048·ub1024는 271.79±0.13→275.67±7.27로 PR이 오차 범위 안이라고 명시한다. 교대 tg128에서는 사실상 변화가 없고 Qwen3.6-35B-A3B MoE도 ±1.5% 안이었다. Wikitext-2 40 chunks PPL은 양쪽 6.0327±0.14381로 보고됐다. baseline exact SHA·warm-up·전체 batch는 미확인이다. 250W는 설정 limit이며 실측 소비전력이 아니다.

**진단→가설:** 저자는 모델의 BF16 accumulation 요청이 V100에서 FP32 GEMM으로 이어져 병목을 남기고, MoE는 수정 kernel 대신 MMQ를 사용한다고 설명한다. op test의 FP16 tensor-core 경로와 모델의 FP32 경로는 **not strictly apples-to-apples**다. TFLOPS 증가도 모델 FLOPs 감소를 의미하지 않는다.

**최소 실험·GO/KILL:** 동일 V100·weight에서 parent/patch × dense/MoE × ub512/1024를 비교하고 dequant/GEMM/MMQ 시간 비중과 PPL을 기록한다. 실제 model trace에서 해당 kernel이 병목일 때만 GO. kernel 배수를 end-to-end 개선율로 쓰거나 미시험 Ampere·Ada에 일반화하면 KILL.
