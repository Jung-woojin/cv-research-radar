## Q1. 추적 상태의 좌표 정합성을 고쳐도 identity 성능이 악화되는 조건은 무엇인가?

**문제·Observation·왜 지금:** Deep OC-SORT 수정안은 GMC가 현재 상태뿐 아니라 observation history와 ORU 복원 상태도 변환하게 한다. Maintainer는 exact pan에서 오류를 별도로 재현했지만, 실제 MOT16 moving-camera 실험에서 imgsz=1280의 IDF1이 54.82→53.78로 낮아져 종료했다. ID switches는 254→229로 줄었다는 보고다. 기본 GMC none은 영향받지 않는다. [PR·diff](https://github.com/ultralytics/ultralytics/pull/27352/files) · [maintainer 실행과 종료 근거](https://github.com/ultralytics/ultralytics/pull/27352#issuecomment-7167727750)

**Gap·Diagnosis·Mechanism:** 좌표 정합성은 확인됐지만 실제 악화의 원인이 GMC noise, association 경계, ORU dynamics 중 무엇인지는 미확인이다. 합성 단위 테스트 성공은 시스템 성능 개선의 충분조건이 아니다.

**Hypothesis·최소 개입:** noisy GMC와 가림 길이의 상호작용이 수정의 이득을 상쇄할 수 있다. 정확한 warp와 추정 warp를 분리하고, 낮은 신뢰도에서만 보정 강도를 낮추는 개입을 검증한다. 원인 확정이나 검증된 해결책은 아니다.

**Experimental Design:** base `a0b816afb56c5df78df5a33a982a227f7ee00c05`, head `702775df3672a96b510b17d613988b91fbf16204`를 고정한다. 동일 cached detection에서 main/수정 × GMC none/exact/estimated × translation/rotation × 가림 길이를 비교한다. 먼저 합성 좌표·속도 잔차, 이후 MOT17의 고정 개발 구간을 사용한다. 이미 보고된 MOT16 네 구간만으로 개입을 선택하지 않는다.

**Baseline·metric·GO/KILL:** main과 GMC none을 baseline으로 IDF1·HOTA·ID switches·재연결률·warp 잔차를 기록한다. held-out sequence에서 identity 지표와 오류 감소가 함께 재현되면 GO. ID switches만 줄거나 static-camera 대조군이 악화하면 개입 KILL이다.

**Expected Contribution·Risk·negative result:** 좌표 정합성 복구가 유리한 조건을 예측하는 진단 지도다. 알려진 버그 수정만으로 novelty는 낮다. 효과가 없으면 정합성 개선의 적용 경계를 남긴다. **Compute cost 2/5**: cached detection은 CPU 시작 가능하며 새 검출 생성 비용은 별도다. 1~2주 합성 분해, 3~4주 실영상 검증, 5~8주 다른 tracker 확장을 계획한다. 여러 tracker에서 반복돼야 논문화 후보가 된다.

**Gap·Diagnosis·Mechanism:** 중복 recall과 sentinel 처리의 효과가 크기별 AP와 모델 간 차이에 균일한지는 미확인이다. GT가 적은 class·size bin은 recall 간격이 커져 경계 규칙의 영향을 다르게 받을 수 있다는 추론이다. 전일 반환 dict의 AP 누락 문제와 구별한다.

**Hypothesis·최소 개입:** 예측을 그대로 두고 evaluator만 교체하면 관측 AP 변화 일부를 recall 경계 밀도로 설명할 수 있다. 실제 모델 순위 역전은 아직 확인하지 않았다.

**Experimental Design:** base `fa3e7f8979f8a5ee65a3d3109d389df83f6dd640`, head `145655440e345c180d774781130f1a522c0eaccb`를 고정한다. perfect·FP→TP·TP 뒤 FP·미도달 threshold·빈 입력의 합성 배열부터 비교한다. 다음으로 동일 COCO val2017 prediction을 크기·class별 재채점한다. matching·category·max_det·area range를 고정하고 reference 차이가 남으면 집계 밖 원인을 따로 찾는다.

**Baseline·metric·GO/KILL:** COCO reference와 이전/수정 계산의 절대 차이, bin별 evaluator delta, 모델 차이의 부호 안정성을 기록한다. 고정 예측에서 경계 규칙만의 효과를 설명하면 진단 GO. evaluator delta를 P2나 architecture 개선으로 해석하면 KILL이다.

**Expected Contribution·Risk·negative result:** 작은 객체 연구의 평가 민감도와 실제 능력 차이를 분리한다. 산술 수정 자체는 novelty가 낮고 여러 보존 예측에서 결론 민감도를 보여야 한다. 순위가 유지되면 해당 조건에서 평가 변경에 대한 결론 강건성을 얻는다. **Compute cost 1/5**, CPU 재집계 가능. 1~2주 계약 검사, 3~4주 크기별 영향, 5~8주 여러 모델·dataset 분석을 계획한다.

## Q5. 같은 judge 이름에서 wrapper 선택만 달라져도 평가 결론이 바뀌는가?

**문제·Observation·왜 지금:** `0c658c2`는 `--judge-model-class`를 추가한다. 고정 코드에서 alias 또는 `LOCAL_LLM`으로 최종 model version을 정한 뒤 wrapper를 선택한다. override가 모델 버전 변환까지 우회하지는 않는다. [변경 diff](https://github.com/open-compass/VLMEvalKit/commit/0c658c28a129366252f7b906f87f3f22473f4716) · [고정 구성 코드](https://github.com/open-compass/VLMEvalKit/blob/0c658c28a129366252f7b906f87f3f22473f4716/vlmeval/dataset/utils/judge_util.py)

**Gap·Diagnosis·Mechanism:** judge 이름만 같으면 조건이 같다는 가정을 검사해야 한다. wrapper가 요청 형식·기본값·재시도·응답 해석을 바꿀 수 있지만 실제 점수 차이는 미확인이다. 전일 judge 실패를 0점으로 집계하는 문제와 개입 지점이 다르다.

**Hypothesis·최소 개입:** 최종 model ID와 payload·응답 처리까지 맞추면 wrapper에 따른 차이 일부가 사라질 수 있다. wrapper class 이름 차이 자체가 인과적 설명은 아니다.

**Experimental Design:** 저장된 CharXiv 응답과 동일 judge prompt를 이용해 자동/명시 wrapper × alias/직접 model ID × `LOCAL_LLM` 유무를 mock transport에서 비교한다. 비밀 값은 기록하지 않는다. payload가 다른 경우에만 원인을 좁힌다. 이후 실제 채점은 정확한 snapshot·endpoint·budget을 고정한 별도 실험으로 수행한다. 모든 dataset이 공통 builder를 쓰는지는 각각 확인한다.

**Baseline·metric·GO/KILL:** 기준 wrapper의 정규화 payload·응답 파서를 baseline으로 request 차이율·동일 fixture의 판정 불일치·failure coverage를 기록한다. transport나 parser 차이가 점수 차이를 매개하면 GO. mock 결과만으로 실제 judge 정확도 개선을 주장하면 KILL이다.

**Expected Contribution·Risk·negative result:** 평가 모델과 API 경로 효과를 분리하는 재현성 계약이다. 일반 API 테스트와 중복 위험이 높아 자연 응답의 실제 결론 민감도가 필요하다. 차이가 없으면 해당 wrapper 조합의 동등성 범위를 제시한다. **Compute cost 1/5**, CPU mock부터 가능하며 유료 judge 호출은 수행하지 않았다. 1~2주 계약 검사, 3~4주 raw response 감사, 5~8주 복수 benchmark 검증을 계획한다.

## 비교 조건·점수·오늘의 선택

dataset revision·split·sample ID, 입력·prediction hash, backbone·checkpoint·pretraining·external data, resolution·TTA, runtime·dtype·thread, reasoning effort·context/frame/compute budget, evaluator commit·judge snapshot·wrapper를 기록한다. 재채점은 예측을 고정한다. 미확인 항목은 미확인으로 남긴다. 입력·evaluator·장치가 함께 달라진 결과는 **not strictly apples-to-apples**다.

점수는 조사자의 판단이며 실측치·출판 보장이 아니다. Compute cost는 낮을수록 가볍고 compute efficiency는 높을수록 유리하다. 각 4~8주 일정은 검증 계획이다.

- **오늘 가장 먼저 테스트:** Q3. GPU·weight 없이 합성 recall/precision과 COCO reference의 계약을 검사한 뒤 보존 예측을 재채점한다.
- **RTX 5060 Ti 8GB에서 시작 가능:** Q1 cached detection, Q3 재집계, Q4 입력 감사, Q5 mock은 CPU로 시작한다. Q2는 지원되는 Paddle CPU 환경을 먼저 확보해야 하며 Windows 재현은 미확인이다.
- **장기 박사주제:** Q1의 시간 상태 정합성과 Q4의 증거 완전성을 중심으로, CCTV·UAV·해양 안전 영상에서 관측·상태·평가의 오류를 분해하는 진단 연구. 현재 제안이지 검증된 장기 추세는 아니다.

오늘 달라진 것은 모델 규모보다 실행·입력·평가 계약이다. 남은 핵심은 자연 데이터에서의 영향 크기이며, 첫 행동은 작은 통제 실험으로 모델 능력과 계측 효과를 분리하는 것이다.
