## 1. 캐시 적용 순서: warm-up이 숨은 재현 조건이 된다

**Claim / 커뮤니티 재현.** #15371 작성자는 모델을 먼저 `cache_context("cond")` 안에서 실행한 뒤 `apply_first_block_cache`를 적용하면, 다음 호출도 context로 감쌌는데 `No cache context is set`이 발생한다고 보고했다. 같은 흐름의 `enable_cache`는 작동한다고 설명한다. 환경은 Diffusers main `ed3267270`, PyTorch 2.15.0, Python 3.12, CPU다. tiny FluxTransformer의 random weights·입력을 사용하며 공개 checkpoint 품질 평가가 아니다. [재현 코드](https://github.com/huggingface/diffusers/issues/15371)

**확인한 사실.** 고정 revision의 [HookRegistry](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/hooks/hooks.py)는 child registry 목록을 재사용하고, subtree hook 변경 뒤 이를 무효화하는 메서드를 제공한다. [enable_cache](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/models/cache_utils.py)는 새 hook 적용 뒤 무효화를 호출한다. 반면 읽은 [apply_first_block_cache 전체 함수](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/hooks/first_block_cache.py)는 child hook을 등록하지만 같은 무효화 호출이 없다.

**Observed gap / 한계.** 예외 재현 외에 작성자는 MagCache의 cond/uncond 상태 공유와 fresh pipeline 대비 출력 차이도 주장한다. 해당 MagCache 경로의 독립 실행·전체 소스 검증은 하지 않았으므로 그 수치를 확정 결과로 사용하지 않는다. 읽은 이슈는 open이며 댓글이 없고, 수정 병합을 확인하지 못했다.

**진단 → 가설.** warm-up이 만든 registry 목록에 나중에 추가한 hook이 없으면 context 전파가 누락될 수 있다. 이때 같은 checkpoint·seed라도 캐시 적용 순서가 숨은 조건이 된다.

**최소 실험.** 같은 state dict와 입력으로 ① 적용 후 첫 실행, ② 실행 후 적용, ③ 실행 후 `enable_cache`, ④ 실행 후 적용하고 registry만 무효화하는 조건을 비교한다. hook별 context 이름·등록 목록·예외·출력을 저장한다. cond/uncond를 분리하고 fresh pipeline 대조를 둔다. 처음부터 서로 다른 random initialization을 비교하지 않는다.

**GO/KILL.** registry 무효화만으로 context 전파가 복구되고 fresh 설정과 출력이 일치하면 이 원인 가설로 GO. 예외만 사라지고 cond/uncond 상태가 섞이면 KILL. 기존 one-block MagCache 버그의 수정 여부와 합쳐 판단하지 않는다.

## 2. TCD: 문서 계약과 reference 호환성을 먼저 구분한다

**Claim / 재현 조건.** #15370은 `set_alpha_to_one=True/False`를 바꿔도 terminal output이 같다고 보고한다. Windows, Python 3.12.8, PyTorch 2.9.0+cu126, Diffusers 0.44.0.dev0에서 CPU만 사용했다. `prediction_type="sample"`, one-step, ones sample·zero model output의 fixture다. 모델 weights·dataset·GPU가 필요하지 않다. [원문](https://github.com/huggingface/diffusers/issues/15370)

**Observed gap / 사용자 보고.** 두 설정 모두 약 `0.0292233`을 반환하며 문서상 의미라면 True 조건은 0이어야 한다는 제보다. 이는 해당 scalar fixture의 보고값이며 이미지 품질 차이나 논문 성능 차이가 아니다.

**확인한 사실.** [고정 TCD 소스](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/schedulers/scheduling_tcd.py)는 설정에 따라 `final_alpha_cumprod`를 생성하지만 terminal 경로에서 timestep을 0으로 두고 `alpha_prod_s`를 배열에서 읽는다. [PR #15292](https://github.com/huggingface/diffusers/pull/15292)의 diff는 terminal 경로에서 final alpha를 쓰도록 바꾸고 회귀 검사를 추가한다. PR은 11/14 생성, 11/22 수정됐으며 조회 당시 open, `merged_at=null`, head는 `0ef25799dbf28797919d5716f1ea8f8aab395681`이다. 최근 새 이슈·PR 갱신을 다루는 것이며 새로 유입된 버그라고 단정하지 않는다.

**호환성 한계.** 작성자는 TCD reference도 endpoint index 0을 사용한다고 명시했다. 이번에는 reference 원문까지 별도 대조하지 않았으므로 저자 주장으로 남긴다. 문서대로 바꾸면 기본 설정의 terminal 출력도 바뀐다는 PR 설명은 중요하다. 이 변경을 보편적인 재현성 개선으로 승인할 수 없다.

**진단 → 가설 → 최소 실험.** 설정 불변성인지 reference 호환 의도인지 분리한다. 현 소스와 PR head에서 True/False × eta 0/0.3/1 × 지원 prediction type을 비교하고 마지막 alpha·sample·RNG state를 저장한다. 이후 reference의 고정 revision을 확보해 같은 식과 입력을 대조한다.

**GO/KILL.** 문서 계약 회귀 검사는 GO. reference와의 수치 동등성을 확인하기 전 기본 동작 변경을 “논문 재현 수정”으로 적용하는 판단은 KILL. 테스트 기대값이 바뀌었다는 사실만으로 이미지 품질 개선을 주장하지 않는다.

## 3. LCM: 마지막 step의 RNG와 반환 sample을 함께 검사한다

**Claim / 재현 조건.** #15368은 custom `timesteps=[999,499,19]`, `strength=0.5`에서 실제 schedule은 `[19]`인데 `num_inference_steps`는 3으로 남아 마지막 step에서도 RNG가 진행된다고 설명한다. [PR #15364](https://github.com/huggingface/diffusers/pull/15364)는 CPU·torch 2.14의 회귀 테스트를 제시한다. 환경 전체는 이슈에 없으므로 미확인으로 남긴다. [이슈](https://github.com/huggingface/diffusers/issues/15368)

**확인한 사실.** [고정 LCM 소스](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/schedulers/scheduling_lcm.py)는 마지막 step 판정에 원래 `num_inference_steps`를 쓴다. 문제 분기는 noise를 뽑은 뒤 `prev_sample = sqrt(alpha_prev) * denoised + sqrt(beta_prev) * noise`를 반환한다. 정상 terminal 분기는 `prev_sample = denoised`다. 제안 diff는 판정을 `len(self.timesteps)-1`로 바꾼다. PR은 open, `merged_at=null`, head `735e3a77819e761519cb36c539dced7bf768df90`이다.

**원문과의 불일치.** 이슈의 “sampled noise is never used” 설명을 함수 반환값 전체에 그대로 적용하면 안 된다. 읽은 소스상 noise는 `prev_sample`에 들어간다. downstream pipeline이 어느 반환 필드를 사용하는지는 별도 검사해야 한다. 또한 원문이 TCD #15301을 “fixed”라고 부르지만 API에서는 해당 PR도 open, `merged_at=null`이었다. 제안된 수정과 병합된 수정은 구분한다.

**진단 → 가설.** strength가 schedule 길이만 바꾸고 종료 판정 기준은 바꾸지 않으면 RNG와 terminal sample 계약이 동시에 어긋날 수 있다. 같은 generator를 재사용하는 다음 요청에도 영향이 이어질 가능성이 있다. 실제 생성 이미지의 변화 크기는 미측정이다.

**최소 실험.** single-step truncation과 multi-step truncation, truncation 없는 control을 둔다. 매 step의 RNG state, 다음 random draw, `prev_sample`, `denoised`를 모두 저장한다. 수정 전후 terminal 반환과 비terminal 경로를 각각 비교하고 pipeline이 소비하는 필드도 추적한다. epsilon/v_prediction과 동일 dtype·seed·입력을 유지한다.

**GO/KILL.** 실제 마지막 step에서 RNG가 보존되고 `prev_sample`이 의도한 denoised와 일치하며 비terminal 결과가 보존되면 GO. RNG 검사만 통과시킨 뒤 출력 동등성을 선언하거나, TCD PR 병합까지 완료됐다고 보고하는 판단은 KILL.

## 4. MiniMax-H3 Image: adapter 등록 성공은 학습·scale 작동의 증거가 아니다

**Claim / 재현 조건.** #15367은 image transformer에서 `add_adapter`가 `AttributeError`로 실패한다고 보고했다. Diffusers main `c215605` 및 0.43.0, macOS arm64, Python 3.11.18, torch 2.15.0 CPU, PEFT 0.22.0 조건이다. tiny one-layer 모델과 rank-4 `to_q` adapter를 사용했다. 실제 checkpoint의 benchmark 재현 결과는 아니다. [원문](https://github.com/huggingface/diffusers/issues/15367)

**확인한 사실.** [고정 image transformer 소스](https://github.com/huggingface/diffusers/blob/ed3267270/src/diffusers/models/transformers/transformer_minimax_h3_image.py)의 클래스 상속에는 `PeftAdapterMixin`이 없다. [PR #15366](https://github.com/huggingface/diffusers/pull/15366)은 mixin 외에도 `apply_lora_scale`, forward의 `attention_kwargs`, modular denoiser의 인자 전달을 추가한다. 조회 당시 open, `merged_at=null`, head는 `09d1ff8275b90a9ccb87cecca23dd76d78cc54dd`이다.

**Observed gap / 증거 수준.** 이슈의 두 댓글은 모두 같은 작성자다. 별도 독립 재현 두 건으로 세지 않는다. 작성자의 [추가 설명](https://github.com/huggingface/diffusers/issues/15367#issuecomment-7055917889)은 mixin만으로 지원이 완성되지 않으며 pipeline-level `load_lora_weights`와 checkpoint 변환은 별도 작업이라고 명시한다. PR의 테스트 통과 주장은 작성자 실행 보고이지 이번 실행의 실측이나 릴리스 보증이 아니다.

**진단 → 가설.** 로컬 compatibility subclass로 API 오류만 해결하면 요청별 scale 전달이 빠질 수 있다. 학습이 돌아가는 것처럼 보여도 intended adapter intervention이 실제 출력에 반영되는지 확인해야 한다.

**최소 실험.** 동일 tiny 모델에서 base → 비영 초기화 adapter → scale 0/0.5/1 → disable/enable 순서를 검사한다. zero 초기화가 만드는 처음의 무효 효과와 scale 전달 실패를 혼동하지 않는다. base weight를 freeze하고 backward·optimizer 한 step 뒤 LoRA gradient·parameter 변화와 base 불변을 확인한다. model 직접 호출과 modular pipeline의 scale 전달을 별도로 검사한다.

**GO/KILL.** scale 0이 base를 복구하고 scale 1이 adapter 경로와 일치하며 gradient·lifecycle·pipeline routing을 통과하면 해당 경로를 GO. 상속 추가·로드 성공만으로 full training reproduction이나 외부 checkpoint 호환을 승인하는 판단은 KILL.
