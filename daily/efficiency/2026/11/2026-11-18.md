## 1. NCNN — CPU quota와 thread pool의 불일치

**사실:** merge commit은 `42891e21903ea2ece4f123ac3d188642fb537617`이다. Linux NCNN에서 모델 load 전에 thread 수를 기존 선택값·8·affinity·cgroup v2 quota 중 작은 값으로 제한하고 최소 1을 보장한다. quota는 `/sys/fs/cgroup/cpu.max`만 읽어 parent/nested quota를 놓칠 수 있다. ONNX의 기존 로직을 공유 함수로 옮겼다. [구현 diff](https://github.com/ultralytics/ultralytics/pull/27244/files)

**저자 측정:** dual EPYC 9655·384 logical CPUs, NCNN 1.0.20261020, YOLO26n FP32·imgsz 640에서 whole-host는 352 threads·156–244 ms/image → 8 threads·29–33 ms/image였다. 4-CPU affinity는 352 threads·390–395 → 4 threads·16.5–17.3 ms였다. 반면 raw NCNN·16-core mask의 YOLO26x는 8 threads·176–179 ms, 16 threads·153–155 ms로 상한의 손해를 보였다. [조건·표](https://github.com/ultralytics/ultralytics/pull/27244)

**비교 조건:** 85분 간격 두 series, 각각 fresh-process 3회 교대, process당 timed calls 30회이며 quota 행은 15회다. detections는 각 pair에서 같았다는 저자 보고다. 고정 입력 640이며 NCNN은 batch 이미지를 순차 처리한다. timed calls 앞 warm-up 횟수·정확한 torch/OS version은 미확인이다. Docker quota의 기존 210,000/430,000 ms는 각 1회라 대표 개선 배수로 사용하지 않는다. ARM 보드·실제 Vulkan GPU는 미측정이며 x86 결과의 edge 전이는 **not strictly apples-to-apples**다.

**진단→가설:** 모델 FLOPs보다 thread oversubscription·quota throttling이 wall-clock을 지배할 수 있다. 그러나 큰 모델의 병렬성까지 8로 제한하면 연산량이 큰 구간에서 이득을 잃는다.

**최소 실험:** 보유 Linux 환경에서 동일 weight·input·build로 thread 1/2/4/8/16 × affinity/quota를 대조한다. quota throttled time·context switch·p50/p95·품질을 기록하고 load 전후 thread 변경을 구분한다.

**GO/KILL:** quota와 pool 크기를 맞춰 전체 추론 지연이 반복 개선되면 GO. 8을 모든 모델·ARM 보드의 최적값으로 채택하는 것은 KILL.

## 2. Intel i915 — 완료 시간이 짧아도 계산이 완료됐는가

**커뮤니티 재현:** b12374 `9183a552e`, GNU 11.4.0, Linux, Core Ultra 5 125H·Arc Xe-LPG·96GB DDR5-5600 UMA, Mesa 26.0.3-1ubuntu1·Vulkan 1.4.335에서 긴 queued work 뒤 출력 손상을 보고한다. 원문은 i915의 20초 request timeout이 작업을 취소하고 ANV가 성공을 반환하는 경로를 원인으로 제시한다. 아직 open이며 최초 bad commit은 미확인이다. [원문·로그](https://github.com/ggml-org/llama.cpp/issues/32370)

**보고된 대조:** Qwen3.6-27B IQ2_XS, context 1024·batch/ubatch 512·sequence 1·FA off·1 PPL chunk에서 기본 watchdog은 PPL 248320과 fence timeout, watchdog을 끈 같은 binary는 PPL 5.2887과 timeout 로그 0건이었다. 해당 로그의 pass 시간은 56.28→66.89초다. 이는 수정 후 감속 배수가 아니라 잘못된 계산을 포함한 결과와의 비교다. KV precision·warm-up·반복 오차는 미확인이다.

**진단→가설:** async 유무 자체보다 아직 실행되지 않은 queue 작업의 대기 시간과 watchdog의 관계가 문제일 수 있다. 작은 ubatch도 누적 queue가 길면 안전을 보장하지 못한다. serialization의 약 28% penalty는 작성자 보고이며 다른 장치·모델과는 **not strictly apples-to-apples**다.

**최소 실험:** kernel 설정 변경에 앞서 동일 prompt·weight hash로 async on/off·submission serialization·ubatch를 대조한다. CPU reference, PPL/output parity, fence timeout, 실제 완료와 p95를 함께 확인한다. 손상 후 KV 상태는 재사용하지 않고 각 arm을 fresh load한다.

**GO/KILL:** 정상 출력과 완료 로그를 함께 확인한 경로만 성능 측정에 GO. 실패 계산의 짧은 시간을 throughput 이득으로 쓰거나 watchdog 해제를 일반 배포 기본값으로 채택하는 것은 KILL. 원문도 해제의 추가 영향을 검증하지 않았다.

## 3. AMD Vulkan — driver 경계에 맞춘 shader 제외

**사실:** `8f647f1fdb0c3bf72bf36e23641da2a28cea993f`로 #32415가 병합됐다. diff는 AMD RDNA3/4의 flip 경로에서 proprietary driver를 제외한다. 작성자는 Windows 11·R9700·driver 26.10.1에서 cooperative-matrix 배열을 여러 loop에서 indexing하는 최소 shader로 compiler crash를 설명한다. driver 수정 자체는 아니다. [PR](https://github.com/ggml-org/llama.cpp/pull/32415), [diff](https://github.com/ggml-org/llama.cpp/pull/32415/files)

**신규 커뮤니티 근거:** 11/17 RX 7600 XT·Windows 10 22H2·Adrenalin 26.10.1·b12445 `ef3848f9d` 제보는 prompt 63은 통과, 64는 crash로 경계를 좁혔다. `GGML_VK_DISABLE_FA_FLIP=1`에서 시험 모델들이 통과했으나 PR을 포함한 build의 직접 검증과는 구분한다. 모델별 precision·head shape가 다르고 warm-up·반복 수가 부족해 throughput 순위를 만들지 않는다. [댓글의 조건·표](https://github.com/ggml-org/llama.cpp/issues/32353)

**진단→가설:** 모델 크기보다 shader 선택 임계점이 실패를 유발할 수 있다. 같은 crash signature도 overlay 주입 등 다른 원인이 가능하므로 이 guard가 모든 AMD 오류를 해결한다고 볼 수 없다. OS·GPU·driver 간 비교는 **not strictly apples-to-apples**다.

**최소 실험:** 같은 GPU·driver·weight에서 parent/merge build × prompt 63/64/512를 비교한다. FA는 유지하고 flip 선택만 격리하며 pipeline compile·prefill·decode·output parity를 따로 기록한다. batch/ubatch·KV precision·warm-up을 고정한다.

**GO/KILL:** fixed build의 반복 생존과 정합성 확인 후 지연 측정에 GO. 우회 성공을 새 shader 가속 실측이나 범용 RDNA 안정성으로 표현하면 KILL.

## 4. STM32 — compile 근거가 생겼지만 보드 측정은 남았다

**사실:** #27211은 `39f5cc13639f42d71e806469bd6965382a78c478`로 병합됐다. ST 기여자는 11/16 댓글에서 head `96f1d7d`의 YOLO26n 7-task INT8 export를 ST Edge AI Core 4.1.0-20732·STM32N6 Neural-ART target으로 compile해 exit 0·warning 없음을 보고했다. 11/17 최종 review는 INT8 graph가 compile 당시와 byte-identical이라고 명시한다. 첨부 ZIP 내부는 이번 실행에서 독립 검증하지 않았다. [compile·최종 review](https://github.com/ultralytics/ultralytics/pull/27211#issuecomment-6915845160)

**수치 정정:** 작성자는 이전 표가 재현되지 않아 현재 main 기준으로 다시 측정했다고 밝혔다. 최종 host 표의 segmentation mask mAP50-95는 float 0.540→INT8 0.401, pose는 0.459→0.267이다. 어제 인용한 0.541→0.365와 0.449→0.265를 신규 방법의 개선폭으로 계산하지 않는다. detect는 0.686→0.639다. [최종 표](https://github.com/ultralytics/ultralytics/pull/27211)

**조건:** ORT CPU·batch 1·YOLO26n, detect/segment/pose는 imgsz 640, 작은 기본 datasets의 host 평가다. CPU SKU·ORT exact version·warm-up은 미확인이다. semantic 1024·depth 768·classify 224를 같은 조건으로 합치지 않는다. on-device accuracy·latency·memory는 미검증이며 board·host 비교는 **not strictly apples-to-apples**다.

**진단→가설:** ST 측 설명은 float segmentation head의 activation buffer 부담과 INT8 품질 간 trade-off다. NMS/TopK를 graph 밖에 둔 비용까지 포함해야 배포 효율을 판단할 수 있다.

**최소 실험:** immutable final export와 별도 calibration/holdout을 고정한다. 전체 INT8 대 최소 head-float의 task별 품질·compiler memory report를 먼저 비교하고, 이후 실제 보드에서 전후처리 포함 p95·peak SRAM/외부 RAM·energy/frame을 측정한다.

**GO/KILL:** 지금은 compile artifact와 품질 경계 검증에 GO. compile 성공·파일 3–3.5배 축소를 보드의 속도·전체 RAM·전력 배수로 바꾸는 판단은 KILL.
