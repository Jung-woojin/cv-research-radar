## 1. WebGPU Plugin EP 0.6.0 — RGB smoke test의 사각지대

**배포 사실.** 정확한 tag는 `plugin-ep-webgpu/v0.6.0`, 대상 commit은 `2b68ec0faadd6bdb0c8121f3bc16e4551e9975ff`다. 11월 17일 07:44:35 KST 발행됐다. release API의 assets 배열은 비어 있다. 따라서 이 tag의 존재를 다운로드 가능한 별도 plugin binary 검증으로 확장하지 않는다. 새 weight·dataset 배포도 아니다. [Release](https://github.com/microsoft/onnxruntime/releases/tag/plugin-ep-webgpu/v0.6.0)

**코드와 개발자 검증.** [PR #33432](https://github.com/microsoft/onnxruntime/pull/33432)의 diff는 Conv2dMM의 vec3 경로에서 scalar storage 채널 좌표를 4로 나누던 처리를 교정한다. 입력 채널 6·9·15에서 잘못된 채널을 읽을 수 있고, 3채널은 시작 좌표가 0이어서 오류를 가린다는 설명이다. FP32/FP16, dynamic/initializer weight, CPU fallback 금지 fixture가 추가됐다. 개발자는 Windows/D3D12 검증 통과를 보고하지만 macOS Metal은 미검증이라고 명시한다. PR merge는 **10월 19일**이다. 오늘의 신규 사건은 이 교정을 포함한 **0.6.0 release**이며 버그 최초 발견일이 아니다.

**호환성·설치 조건.** source license는 MIT다. 최소 core 1.24.4와 별개로 concurrent independent Session 지원은 1.28.3 이상인 1.28 계열, 1.30.1 이상인 1.30 계열, 1.31 이상으로 제한된다. 1.29.x 등은 serialized compatibility이고 같은 device의 생성·할당·전송·Run 등을 호출자가 직렬화해야 한다. 같은 Session의 I/O binding과 Run 중첩은 concurrent mode에서도 허용되지 않는다. 1.26.0은 host의 plugin-version 검사로 거부된 제보가 release에 명시돼 있다.

Windows preview Agility SDK 활성화에는 호환 Windows·loader·Developer Mode·driver 조건이 있다. 설치 surface는 core/plugin build·Dawn backend·driver·provider option이며, 단일 pip package 번호만으로 고정할 수 없다. [SDK 안내](https://github.com/microsoft/onnxruntime/blob/2b68ec0faadd6bdb0c8121f3bc16e4551e9975ff/docs/BuildWithDawnAgilitySDK.md). GPU/VRAM 최소값은 확인하지 못했다. 작은 fixture로 메모리 사용을 제한할 수 있지만 측정값은 없다. binary checksum·attestation도 검증하지 않았다.

**활동과 claim gap.** #33432는 Issue #32928을 해결하는 merged PR이다. 이는 저자 검증이며 전체 Issue 해결률이나 독립 재현을 뜻하지 않는다. release의 “성능·안정성 개선”을 모든 CV graph의 품질 향상으로 일반화하면 안 된다. 특히 README의 three-channel 설명보다 PR의 6·9·15채널 조건이 진단에 중요하다.

**진단 → 가설 → 10~30분 최소 실험.** 모델·weight를 배제하고 batch=2, 8×8 입력, 3×3 Conv에 채널별 구별 가능한 값을 넣는다. 입력 채널 3·6·9·15와 scalar/vec4 대조군을 구성하고 FP32/FP16·dynamic/initializer weight를 나눈다. CPU reference와 WebGPU의 오차, provider 배정, fallback 여부를 기록한다. backend·driver·core/plugin commit·precision·shape를 고정한다.

**GO/KILL.** 다중 채널 fixture가 CPU reference와 사전 정의한 dtype별 허용오차 안에서 일치하면 실제 CV graph subset으로 GO. RGB 한 장 통과만으로 backend parity를 선언하거나 Metal까지 검증됐다고 쓰는 것은 KILL이다.

## 2. vLLM v0.34.0 — 같은 weight라도 기본 실행 예산이 달라진다

**정확한 배포.** tag object는 `0c57b4195da4a6b69a7725908e428053e51e51b8`, 대상 commit은 `62d4bc3c7e33b1b6c906e233e6af2d3506c482ca`이며 tag verification은 unsigned다. tagger 시각은 11월 16일 04:27:15 UTC, release 발행은 23:22:00 UTC로 다르다. source license는 Apache-2.0이다. [Release](https://github.com/vllm-project/vllm/releases/tag/v0.34.0)

**배포 변화와 저자 주장.** Model Runner V2만 남고 기본 block size는 16→64로 바뀐다. backend override가 있으므로 모든 GPU에서 64라고 단정하지 않는다. extensible KV cache는 capture·warm-up 이후 실제 여유 메모리로 크기를 정하며 기본 utilization은 1.0이다. release는 높은 동시성의 throughput 개선과 일부 조건의 token latency 악화를 함께 보고한다.

[PR #56492](https://github.com/vllm-project/vllm/pull/56492)는 virtual address 예약과 physical mapping을 설명한다. PR 비교의 기존 utilization은 **0.92**이고 release의 업그레이드 안내는 **0.9**를 제안한다. 이를 같은 baseline으로 합치지 않는다. [PR #63231](https://github.com/vllm-project/vllm/pull/63231)은 block size에 묶인 connector 가정과 ROCm 경로 문제를 설명한다. 두 PR은 각각 11월 2일·5일 merge됐으며 오늘 처음 발견된 문제는 아니다.

**artifact·설치 조건.** release에는 source tarball과 CUDA 13.0·CPU·XPU wheel이 있다. CUDA x86_64 wheel의 API SHA256은 `79ca4b3cd74aec08c4bf476bdf0cb15735b605ae5368526a2faae1e30f044ca2`다. 직접 다운로드 검산·서명 검증은 하지 않았다. pin 후보는 `vllm==0.34.0` 또는 `vllm/vllm-openai:v0.34.0`이며 image digest는 별도로 확보해야 한다. ROCm 배포는 10.0이고 Hub ≥2.0.0·tokenizers ≥0.23.3·timm ≥1.0.30 요구가 있다. 새 model integration은 weight 배포·weight license의 증거가 아니다. 새 dataset/evaluator artifact도 확인하지 않았다.

**진단 가설.** weight를 고정해도 cache budget·block size·runner가 함께 달라지면 성능 차이의 원인을 하나로 귀속할 수 없다. 기본값끼리의 전후 비교는 **not strictly apples-to-apples**다. PR의 통과 보고는 개발자 검증이며 VLM별 독립 재현은 아니다. GPU/VRAM 필요량은 target·context·precision·동시성에 따라 달라져 단일 최소값을 확정하지 않았다.

**10~30분 계획.** 이미 weight와 환경이 준비된 경우에만 동일 VLM revision·이미지 해상도/patch 수·prompt·출력 제한·greedy·batch·동시성을 고정한다. 0.34.0 안에서 cache on/off와 block 16/64를 가능한 조합으로 나눠 실제 resolved setting, cache capacity, TTFT·TPOT·throughput·peak memory·출력 token을 기록한다. cold start와 warm run을 분리한다. 먼저 동시성 1로 correctness를 확인하고 높은 동시성은 별도 단계로 둔다.

**GO/KILL.** 출력과 자원 예산을 확인한 후 migration 검토로 GO. throughput 증가만으로 latency도 개선됐다고 결론내리거나 구 PR 수치를 최종 tag의 새 실측값으로 쓰는 것은 KILL이다.

## 3. LongCat-Video-Avatar 1.6 — weight·LoRA·cache 경로를 분리해야 한다

**사실.** [PR #156](https://github.com/meituan-longcat/LongCat-Video/pull/156)은 11월 15일 11:57:51 KST merge됐고 고정 code commit은 `58eb336edc5c8c63389838727e40b8c18434e54e`다. [공식 README](https://github.com/meituan-longcat/LongCat-Video/blob/58eb336edc5c8c63389838727e40b8c18434e54e/README.md)는 같은 Avatar 1.5 architecture에 DMD LoRA A와 OPSD LoRA B를 안내한다. code·weight는 MIT로 명시된다. [공식 Hub metadata](https://huggingface.co/meituan-longcat/LongCat-Video-Avatar-1.6)도 MIT이나 updated는 11월 13일이다. Hub history/tree 조회 실패로 immutable weight revision·checksum·최초 공개 시각은 미확인이다. **11월 15일 신규 weight 업로드라고 쓰지 않는다.**

**주장과 간극.** 저자는 입 움직임·장시간 안정성 개선을 주장한다. 실제 diff에는 RoPE 적용 뒤 K cache 저장, LoRA mixing·FP8·통신·VAE 최적화가 함께 있다. 어느 변경이 품질을 개선했는지는 분리되지 않았다. 기본 `mix_steps=4, mix_alpha=1.0`은 README상 mixing 비활성·단일 LoRA 경로다.

**조건·활동.** Python 3.10, torch 2.6.0/cu124, FlashAttention 및 avatar requirements가 설치 surface다. PR은 ORT CPU 1.16.3을 GPU 1.20.2로 바꾼다. FP8는 Transformer Engine이 필요하고 INT8과 동시 사용하지 않는다. 예시는 2 GPU지만 최소 VRAM은 미확인이다. 공개 dataset·독립 evaluator·binary attestation은 확인하지 못했다. 최근 Issue 제목만으로 사용자 재현 성공을 판정하지 않았다.

**진단 → 가설 → 10~30분 계획.** 먼저 CPU에서 checkpoint manifest와 LoRA 선택·mixing 분기를 audit한다. 환경이 있으면 동일 latent·seed·shape·precision에서 cached/uncached attention을 비교해 RoPE/cache 계약을 확인한다. 이후 같은 짧은 audio/image로 LoRA만 바꾼다. 장시간 안정성은 이 smoke test로 증명할 수 없다.

**GO/KILL.** weight revision 확보와 cache parity 확인 후 짧은 clip으로 GO. 전체 1.5/1.6 차이를 architecture gain으로 해석하거나 FP8·compile까지 바꾼 속도를 LoRA 효과로 쓰는 것은 KILL이다.

## 오늘의 GO/KILL

1. **GO — 최우선:** WebGPU 다중 채널 Conv fixture로 모델 정보와 backend 인덱싱 오류를 분리한다.
2. **GO — 조건부:** vLLM은 weight·입력·cache budget을 고정한 뒤 기본값 변경을 분해한다.
3. **GO — manifest 먼저:** Avatar는 weight revision·LoRA 선택·cache 계약부터 확인한다.
4. **KILL:** 최근 논문 링크·card 수정·release 설명만으로 새 weight·독립 재현·SOTA 달성을 선언하지 않는다.
5. **KILL:** 조건이 다른 throughput·품질 수치를 같은 실험으로 묶거나 검증하지 않은 숫자를 채우지 않는다.

오늘 선정한 것은 공개 artifact와 실행 계약의 변화다. 논문 성능을 독립 검증한 보고서는 아니며, 모든 smoke test는 미실행 계획이다.
