## 1. ONNX Runtime WebAssembly `MatMulNBits` — 피크 메모리와 decode 비용

**[사실]** ONNX Runtime 공식 저장소의 issue #33795는 WebAssembly build에서 `MatMulNBits`가 매 호출마다 weight matrix 전체를 FP32 scratch buffer로 dequantize한다고 보고합니다. 작성자가 제시한 `K=2,048`, `N=128,000` 4-bit 예에서는 scratch가 1,048 MB이며, LFM3-1.7B-ONNX에서 WebAssembly memory가 session load 후 1,363 MB에서 첫 prompt 후 2,366 MB로 늘었다고 적었습니다. 재현용 모델 생성·브라우저 실행 코드와 package version `onnxruntime-web@1.31.1`도 포함합니다.  
출처: https://github.com/microsoft/onnxruntime/issues/33795

**[커뮤니티 재현]** issue 작성자는 M3 Ultra/Chrome에서 3.8 tokens/s, iPhone 16 Pro Max/Safari에서 0.3 tokens/s를 관찰했으며, 64 MB 이하 column chunking으로 peak memory를 1,644 MB로 낮췄다고 보고합니다. 이는 maintainer가 검증한 benchmark가 아닙니다.

**[해석]** 4-bit weight 파일 크기만 보고 browser-memory suitability를 판단하면 안 됩니다. dequantization scratch와 WebAssembly memory growth가 input resolution이나 model parameter보다 먼저 mobile deployment를 막을 수 있습니다.

**진단 → 가설 → 최소 실험:** target vision/embedding ONNX model에서 `MatMulNBits` shape, 최초 prompt 전후 WebAssembly memory, p50/p95 token 또는 frame latency를 기록합니다. N-axis tiled export와 원본 export를 동일 device·browser·thread 수에서 비교합니다. GO는 peak memory가 tab budget 아래이면서 output equivalence를 만족하는 경우이고, KILL은 first-run peak가 budget을 넘거나 accuracy/retrieval parity가 깨지는 경우입니다.

## 2. ONNX Runtime Linux arm64 FP16 MatMul — 메모리 절감과 수치 drift

**[사실]** 공식 issue #33798은 Linux arm64 CPU Execution Provider에서 ONNX Runtime 1.29.0부터 FP16 MatMul이 FP16 accumulation을 사용한다고 보고합니다. 작성자가 Azure Standard_D8ps_v6(Neoverse-N2), Ubuntu 24.04.5, Python 3.12.3에서 고정 revision의 `Qwen3-Embedding-0.6B-ONNX`를 비교한 표에 따르면, FP16 대 FP32 embedding의 최대 `1 − cosine`은 1.28.0의 `1.5e-6`에서 1.31.1의 `2.7e-4`로 변했습니다. 같은 issue는 peak memory가 2.54 GB에서 0.98 GB로 줄었다는 관찰도 제공합니다.  
출처: https://github.com/microsoft/onnxruntime/issues/33798

**[커뮤니티 재현]** 작성자는 34 documents/12 queries retrieval test에서 두 query의 4위·5위 순서가 바뀌었다고 보고했습니다. 이는 공개 issue의 작성자 측정이며 maintainer의 결론은 아닙니다.

**[해석]** edge device에서 FP16 path를 켜면 memory는 줄어도 ranking/threshold decision처럼 작은 embedding drift에 민감한 downstream 결과가 달라질 수 있습니다. 속도·메모리만의 Pareto 비교는 충분하지 않습니다.

**진단 → 가설 → 최소 실험:** 동일 model revision·corpus·query·CPU에서 ORT 1.28.0과 최신 버전을 비교하고, peak RSS, p50/p95 latency, cosine drift, top-k rank changes를 함께 수집합니다. FP32 fallback·FP16 path는 별도 조건으로 기록합니다. GO는 정확도/순위 guardrail 내에서 memory target을 만족할 때, KILL은 deployment metric이 허용 오차를 넘을 때입니다.

## 3. ONNX Runtime iOS WebGPU single-pass prefill — dispatch 크기 guardrail

**[사실]** ONNX Runtime 공식 issue 목록은 #33758을 iOS 27 iPhone에서 약 900 tokens의 single-pass WebGPU prefill이 Safari GPU process를 crash시키며, smaller submissions/dispatches로 나눌 것을 요청한 issue로 표시합니다.  
출처: https://github.com/microsoft/onnxruntime/issues/33758

**[커뮤니티 제보]** 이 항목의 상세 issue 본문은 이번 실행에서 캐시로 다시 불러오지 못했으므로, crash 메커니즘·GPU memory 수치·fix 상태는 미확인입니다.

**[해석]** edge prefill은 token count 하나만으로 일반화할 수 없습니다. model graph, browser, iOS build, GPU memory pressure, concurrent tab, dispatch partitioning이 함께 작동할 수 있습니다.

**진단 → 가설 → 최소 실험:** iPhone target에서 256·512·768·900 token 길이와 single-pass 대 partitioned prefill을 비교합니다. success rate, GPU-process termination, p50/p95 prefill latency, browser memory를 기록합니다. GO는 partitioned plan이 crash 없이 latency budget을 만족하는 경우, KILL은 release candidate가 반복 종료되는 경우입니다.
