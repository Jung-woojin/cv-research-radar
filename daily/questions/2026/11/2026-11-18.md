## Q1. 다중 이미지 VLM의 관계 추론 실패 중 얼마가 이미지와 참조 문장의 대응 오류인가?

**문제·Observation·왜 지금:** 공식 변경은 자동 chat 변환에서 `<image>` 표식 위치에 실제 이미지를 배치한다. 이전 경로는 이미지를 앞에 모으면서 literal 표식도 남겼다. maintainer 설명은 일부 processor의 image token 수 불일치를 지적한다. 수정은 표식 수와 이미지 수가 같은 경우에만 적용되며, 불일치 입력은 기존 경로를 유지한다. [공식 변경·테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/7e25868c14dab6e8a5c2d69463f4d9b2f906d231)

**Gap → Diagnosis → Mechanism:** 실행 오류를 없애는 것과 각 문장이 올바른 이미지를 가리키는 것은 별개다. 이미지 수가 같아도 대응 관계가 어긋날 수 있다. CCTV 전후 장면 비교에 같은 문제가 생길 수 있다는 연결은 추론이며, 이 수정이 video memory를 개선한다는 근거는 없다.

**Hypothesis·최소 개입:** 이미지와 참조 문장의 대응을 보존하면, 모델을 바꾸지 않아도 입력 조립 때문에 발생한 관계 판단 오류를 줄일 수 있다. 단순한 이미지 순서 민감성과 의미 대응 오류는 분리한다.

**MVP·baseline·dataset:** parent `60a79fb270e5c712460c533e0a3664c7081c0a7f`와 수정 commit을 공식 RED/BLUE fixture에서 비교한다. 이미지 ID, content 순서, literal marker 수를 CPU에서 기록한다. 그다음 영향받는 실제 task의 표본과 정답이 명확한 두 이미지 합성 쌍을 사용한다. ①원래 대응, ②이미지와 지시문을 함께 교환해 의미 보존, ③이미지만 교환해 정답이 바뀌는 대조군, ④marker 불일치 조건을 분리한다. 자체 `doc_to_messages`를 사용하는 task는 별도 대조군이다.

**판정 metric·GO/KILL:** 입력 계약 위반율, processor 완료율, 전체 요청 기준 정답률, 완료 표본 기준 정답률, 의미 보존 교환의 답 일관성을 함께 기록한다. 대응 복구와 오류 감소가 같은 표본에서 연결되면 GO. 완료율만 오르면 adapter 복구로 범위를 줄인다. 직렬화가 같거나 코드 경로를 호출하지 않으면 해당 task 영향 주장은 KILL한다.

**Expected Contribution·negative result:** 입력 대응 감사와 관계 추론 평가를 연결하는 작은 진단 세트. 변화가 없어도 모델 실패가 입력 조립으로 설명되지 않는 범위를 좁힐 수 있다.

**Compute·Risk·4~8주:** CPU fixture는 cost **1/5**. 후속 모델 추론 비용은 checkpoint에 따라 미확인이다. 알려진 버그 재현 자체의 novelty는 낮다. 여러 processor에서 대응 보존과 task 실패의 인과관계를 확인하면 4~8주 내 진단 논문 후보이며, 그렇지 않으면 재현 노트가 적합하다.

## Q2. 같은 예측을 저장하고도 표본 순서 때문에 평가 결론이 달라지는 경로가 있는가?

**문제·Observation·왜 지금:** 공통 median 구현이 정렬 없는 `arr[len(arr)//2]`에서 표준 중앙값으로 수정됐다. 같은 commit은 power analysis의 잘못된 입력을 명시적으로 거부한다. 모든 accuracy나 mAP에 영향을 주는 변경은 아니다. [공식 diff·테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/c33a160d7d08168897051091029aee2d88229232)

**Gap → Diagnosis → Mechanism:** 분산 실행의 병합 순서나 dataset 순서가 집계기까지 전파되면 모델을 재실행하지 않아도 점수가 달라질 수 있다. 실제 영향을 받은 task·leaderboard 목록은 미확인이다. 11월 16일 질문의 이미지 단위 불확실성과 달리 오늘은 집계 함수의 순열 불변성을 검사한다.

**Hypothesis·최소 개입:** median을 실제 호출하는 평가에서는 저장 출력의 순서 의존성이 수정 후 사라진다. 입력을 미리 정렬한 홀수 표본처럼 영향이 없는 대조군도 존재한다.

**MVP·baseline·dataset:** 먼저 보유 task 설정과 실행 trace에서 median 호출을 확인한다. 없으면 실제 benchmark 실험을 중단하고 합성 계약 검사로만 남긴다. 호출이 있으면 같은 per-sample 값에 원래 순서·역순·고정 seed 순열을 적용해 이전 식과 수정 구현을 비교한다. 짝수/홀수 표본, shard 병합 순서, 동일값 입력을 ablation으로 둔다. mean은 순서 불변 대조군으로 사용한다.

**판정 metric·GO/KILL:** 순열별 집계 범위, 표준 median과의 차이, 동일 두 모델의 우열 부호 변화를 기록한다. 수정 전 순서 영향이 실제 호출 경로에서 확인되면 GO. 유효한 표본 결과가 모두 같으면 해당 평가에서 영향 없음으로 기록한다. power analysis는 별도 입력 유효성 감사로 남기며 중앙값 수정과 효과를 합치지 않는다.

**Expected Contribution·negative result:** 평가 집계의 재현성 감사 규약. 모델 순위가 유지되는 negative result도 “구현 오류가 있었으나 이 비교 결론은 유지됨”이라는 유용한 경계다.

**Compute·Risk·4~8주:** 저장 출력 재집계는 CPU cost **1/5**. 알려진 통계 구현 오류 하나만으로 논문화하기 어렵다. 여러 집계기·shard 병합 경로와 실제 비교 결론의 영향을 확보하면 4~8주 내 평가 도구 연구 후보다. 실제 호출 자료를 얻지 못하면 확장하지 않는다.

## Q3. VLM이 이미지 속 오류를 고치는 원인은 시각 증거 손실인가, 언어적 교정 성향인가?

**문제·Observation·왜 지금:** PINK 저자들은 필기 전사에서 학생의 오류를 모델이 임의로 고쳐 교육상 필요한 증거를 숨기는 over-correction을 지적한다. 이는 저자 주장이다. 오늘 확인한 신규 변경은 FERMAT-PINK의 lmms-eval 통합이며, 코드는 전사·oracle를 rubric으로 채점한다. [논문 소개](https://aclanthology.org/2026.emnlp-main.476/) · [통합 코드·YAML](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/6dcf31da7b92970fd91a2a7a37f03b36ec112f0c)

**Gap → Diagnosis → Mechanism:** 점수가 더 올바르게 보인다는 사실만으로 원인이 언어 prior인지 작은 기호의 시각적 손실인지 알 수 없다. 공식 scorer는 성공 표본 교집합을 기본 사용하므로 judge 실패가 표본 선택도 바꿀 수 있다. [공식 scorer](https://github.com/9115jin/PINK/blob/main/src/pink/score.py)

**Hypothesis·최소 개입:** 같은 오류의 시각적 가독성을 바꿨을 때 교정이 크게 달라지면 지각 경로를, 가독성을 확보해도 “그대로 전사” 지시의 명확화에 민감하면 교정 성향을 후속 원인 후보로 볼 수 있다. 이 실험만으로 내부 기전이나 인과적 분리를 확정하지 않는다.

**MVP·baseline·dataset:** 접근 약관을 충족한 FERMAT `train` 평가 split에서 사람이 원본 오류를 확인한 표본을 고른다. dataset revision과 sample ID를 고정한다. 같은 모델·decode 설정에서 원본/내용 손실 없는 오류 영역 확대와 공식 전사 prompt/오류 보존을 명시한 prompt를 교차한다. 확대 crop은 원문 맥락도 함께 제공하고 전체 해상도 증가 대조군을 둬 context 제거와 pixel budget 영향을 구분한다. 새로운 이미지·prompt 조건에는 새 추론이 필요하다. 저장 출력만 있으면 우선 사람이 오류 보존 여부를 감사하고 scorer 분모를 재검사한다.

**판정 metric·GO/KILL:** 오류 기호 보존율, 정상 기호 손상률, PINK·raw ratio, judge 성공률과 전체 요청 수를 함께 기록한다. 공식 drop 점수와 동일 요청 subset에 제한한 oracle의 누락 0점 민감도 분석을 분리한다. oracle judge 실패는 임의 점수로 채우지 않는다. 사람이 확인한 오류 은폐가 개입에 따라 달라지고 정상 전사가 유지되면 GO. judge 선택이나 crop 맥락 손실만으로 차이가 설명되면 기전 주장을 KILL한다.

**Expected Contribution·negative result:** 증거 충실도 실패를 지각·교정·채점 단계로 나누는 진단. 변화가 없어도 단순 prompt와 확대가 해결책이 아니라는 결론을 얻는다. 해양 안전 VQA로의 확장은 별도 데이터와 rubric 검증이 필요하다.

**Compute·Risk·4~8주:** 저장 출력·분모 감사 cost **1/5**, 후속 추론·judge cost **3/5**의 계획상 추정이다. 실제 비용·VRAM은 미측정이며 8GB judge 실행을 보장하지 않는다. over-correction과 PINK 자체는 이미 연구됐다. 요인 분리·사람 감사가 여러 모델에서 재현돼야 4~8주 논문 가능성이 생긴다.

## Q4. 작은 검출 모델의 속도 우위는 모델 구조보다 CPU budget 정책에 얼마나 의존하는가?

**문제·Observation·왜 지금:** Linux NCNN의 thread 수를 affinity·cgroup v2 quota와 상한 8로 제한하는 수정이 병합됐다. 작성자는 많은 CPU가 보이는 host에서 과도한 thread가 지연을 키웠다고 보고한다. 문서와 코드 모두 nested/ancestor quota 탐지 한계를 남기며, 큰 모델에는 상한 8이 오히려 느릴 수 있음을 인정한다. [공식 PR·측정 조건](https://github.com/ultralytics/ultralytics/pull/27244) · [diff](https://github.com/ultralytics/ultralytics/pull/27244/files)

**Gap → Diagnosis → Mechanism:** 작은 모델과 큰 모델의 latency를 runtime 기본값으로 비교하면 thread scheduling과 quota throttling이 구조 효과에 섞일 수 있다. 이는 UAV·CCTV edge 연구와 관련되지만 해당 장치에서 입증한 결과는 아니다.

**Hypothesis·최소 개입:** 모델 크기와 thread 정책 사이 상호작용이 있어 자원 조건을 고정하면 속도 차이의 크기가 달라질 수 있다. 기존 순위 역전을 관측했다고 주장하지 않는다.

**MVP·baseline·dataset:** base `2f7d25228cec88be93aa3acf7de59d7765398575`와 merge `42891e21903ea2ece4f123ac3d188642fb537617`에서 동일 NCNN artifact·640 입력·고정 이미지 집합을 사용한다. YOLO26n과 더 큰 모델을 같은 host에서 비교한다. 무제한·cpuset·quota·nested quota를 분리하고 fresh process에서 모델 로드 전 thread 수를 고정한다. ONNX Runtime은 정책 대조군으로 둔다. CPU budget 조건의 순서를 교차해 시간대 부하 영향을 줄인다.

**판정 metric·GO/KILL:** 실제 thread 수, warmup 후 median/p95 latency, throttling, 처리량, box/class/confidence parity를 기록한다. 의미 보존 상태에서 모델 크기×thread 정책의 상호작용이 반복되면 GO. 예측이 달라지면 속도 비교와 정확도 영향을 분리한다. 차이가 사라지면 해당 host에서 구조 비교가 정책에 견고하다는 negative result다.

**Expected Contribution·Risk·4~8주:** edge 검출의 자원 조건을 포함한 비교 프로토콜. 알려진 thread 수정 재현만으로 novelty는 낮다. 복수 backend·복수 CPU에서 기전과 결론 변화를 검증하면 4~8주 시스템 진단 연구 후보다.

**Compute:** GPU 없는 Linux 실험 cost **2/5**. 현재 Windows에서 fixture 감사는 가능하지만 Linux cgroup 측정은 별도 Linux 환경이 필요하다. RTX 5060 Ti의 메모리와 무관하게 host·container 준비가 제약이다.

## Q5. 모델 압축에서 의미 있는 특수 상수를 보존하면 export 성공과 예측 의미를 함께 지킬 수 있는가?

**문제·Observation·왜 지금:** RT-DETR CoreML 8-bit export에서 inf-masked anchor가 k-means 입력에 들어가 실패했다. 수정은 512개보다 큰 non-finite 상수를 palettization 대상에서 제외한다. 여기서 8-bit는 weight palettization이며 모든 연산의 INT8 실행을 뜻하지 않는다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27245) · [압축 제외 diff](https://github.com/ultralytics/ultralytics/pull/27245/files)

**Gap → Diagnosis → Mechanism:** non-finite가 mask 의미를 담는 경우와 학습·수치 오류인 경우를 같은 정책으로 처리하면, export를 성공시켜도 의미를 바꿀 수 있다. 전일 분류 logit 양자화와 달리 오늘은 변환 graph의 상수 역할과 압축 대상 선별을 묻는다.

**Hypothesis·최소 개입:** 값의 유한성만 보는 일괄 치환보다 mask 상수의 의미를 보존하는 선택적 압축이 정확도 손상을 줄일 수 있다. 모든 NaN/inf를 허용하자는 주장은 아니다.

**MVP·baseline·dataset:** base `4d254d8141e49dd85009e1ec7657ab3c4ee8c150`와 merge `4252e33aa88eaa27e203434dc3eb4839ba290933`의 같은 RT-DETR-L checkpoint·640 입력·coremltools 9.0 조건을 고정한다. 기존 압축, non-finite 상수 제외, 큰 유한값 치환, FP16 기준을 비교한다. 작은 고정 이미지 집합과 coco8은 smoke test로만 사용하고, 정확도 일반화는 고정 COCO val에서 확인한다. graph 상수의 값과 consumer 연산도 저장한다.

**판정 metric·GO/KILL:** export 성공 여부·실패 단계, package 크기, 상수 보존, box/confidence parity, AP와 작은 물체 AP를 구분해 기록한다. 제외 정책이 오류를 없애고 FP16 대비 task 손상을 줄이면 GO. export만 성공하고 예측이 변하면 성공으로 묶지 않는다. 작은 물체 AP 개선은 현재 미확인이며 유한값 치환도 동등하면 단순 정책을 배제하지 않는다.

**Expected Contribution·negative result:** 압축의 수치적 적법성과 semantic 보존을 분리하는 감사 방법. 차이가 없으면 검증한 상수·backend에서 단순 변환도 충분하다는 경계를 제시한다.

**Compute·Risk·4~8주:** 실제 CoreML 실험은 macOS 환경이 필요하고 cost **3/5**의 계획상 판단이다. Windows·8GB GPU만으로 실행 가능하다고 보장하지 않는다. backend 특수 버그에서 끝날 위험이 크다. 복수 graph·모델 계열에서 상수 역할과 task 영향을 연결해야 4~8주 논문 후보가 된다.
