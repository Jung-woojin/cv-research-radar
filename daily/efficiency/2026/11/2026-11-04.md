## 1. LMCache ROCm 7.2.4 wheel — 호환성 tuple을 성능 수치와 분리

- **출처:** [LMCache releases](https://github.com/LMCache/LMCache/releases), [LMCache Docker README](https://github.com/LMCache/LMCache/blob/dev/docker/README.md).
- **사실:** `v0.5.7rc4-rocm-torch210` wheel은 11월 3일 공개됐습니다. release는 `rocm/pytorch:rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.10.0`의 digest `sha256:4449f856653602317e4101a76fce599c7fcd58ccec2e539951fce5f73083179e`, Torch `2.10.0+rocm7.2.4.git3d3aa833`, HIP runtime `7.2.53211`, CPython 3.12 manylinux 2.39 x86_64, C++11 ABI 및 gfx942/gfx950 code object를 고정합니다.
- **저자/릴리스 주장:** 이 정확한 환경에서 build·test했고 해당 wheel이 release integration을 포함한다고 명시합니다.
- **해석:** 이 정보는 재현 가능한 설치 기준선이지 latency, throughput, VRAM 또는 전력 결과가 아닙니다. 특히 다른 ROCm container, Torch patch 또는 다른 GPU architecture에서 설치가 된다는 사실만으로 cache transfer 성능을 비교할 수 없습니다.
- **진단 → 가설 → 최소 실험:** 타깃 AMD GPU에서 image digest와 `torch.__version__`, HIP version, GPU arch를 먼저 manifest로 남깁니다. 동일 모델·prompt 길이·cache hit/miss 비율·concurrency에서 baseline과 wheel을 각각 cold 5회/warm 20회 실행해 TTFT p50/p95, decode tokens/s, peak VRAM, host RSS, cache hit rate를 비교합니다.
- **GO/KILL:** manifest가 정확히 일치하고 tail latency와 memory guardrail을 통과하면 GO입니다. “gfx942/gfx950 지원”을 다른 AMD GPU 또는 edge throughput 보증으로 바꾸는 것은 KILL입니다.

## 2. vLLM MoE top-k PDL gate — graph replay 회귀의 architecture 조건

- **출처:** [merged PR #65059](https://github.com/vllm-project/vllm/pull/65059), [관련 성능 issue #65055](https://github.com/vllm-project/vllm/issues/65055).
- **사실:** PR #65059는 11월 2일 vLLM `main`에 병합됐습니다. 수정은 PDL launch attribute를 SM90+에만 설정합니다. PR은 pre-SM90에서 해당 attribute가 capture된 CUDA graph에 programmatic edge로 기록돼 replay를 늦출 수 있다고 설명하며, SM90+ 경로는 의도적으로 바꾸지 않았습니다.
- **저자 측정:** A100-PCIE-40GB, driver 590.48.01, CUDA 13.0, Torch 2.14.0+cu130, vLLM 0.33.0에서 standalone 48-edge harness를 21회 교대 측정했습니다. PDL attribute는 A100에서 128.7→181.8 µs, RTX A4000에서 83.6→113.5 µs, RTX 4090에서 79.0→108.9 µs graph replay를 보였습니다. 이는 각각 약 1.1/0.62/0.63 µs per edge 관측입니다.
- **저자 측정:** 같은 PR은 1× A100의 op-chain에서 세 MoE shape에 대해 6.9–9.0% 빠른 replay를, end-to-end batch 1에서는 0.7%와 1.2% 개선을 보고하지만 batch 16은 noise 범위라고 기록합니다. PR은 GPU 밖 범위와 Hopper/Blackwell은 측정하지 않았다고 명시합니다.
- **해석:** kernel microbenchmark의 큰 비율 개선은 serving 개선과 같지 않습니다. edge 수·capture 여부·MoE layer 수가 맞을 때만 활용 가능한 신호이며, batch 16 결과가 noise라는 사실은 production concurrency에서 재측정이 필요함을 뜻합니다.
- **진단 → 가설 → 최소 실험:** pre-SM90 장비에서 동일 vLLM revision으로 PDL-gated build와 base를 A/B/B/A 순서로 비교합니다. input 128/output 256 및 실제 workload 두 종류에서 warm-up 5회 뒤 15회 이상 실행하고 graph replay time, TTFT p50/p95, decode tokens/s, peak memory, task output hash를 기록합니다. SM90+는 regression guard만 별도로 측정합니다.
- **GO/KILL:** pre-SM90 target의 p95와 throughput이 함께 개선되고 output hash/quality guardrail을 통과하면 GO입니다. A100의 per-edge µs를 Jetson, Hopper, Blackwell 또는 eager-only serving FPS로 외삽하는 것은 KILL입니다.

## 3. TensorFold GB10 cache churn — “여유 메모리”가 tail latency의 반증은 아님

- **출처:** [TensorFold issue #1856](https://github.com/ashhart/TensorFold/issues/1856).
- **사실:** 공개된 11월 1일 issue는 official `tensorfold-1.2.0-linux-aarch64` archive의 SHA256, release commit, GB10 sm_121 1대, Ubuntu 24.04.4, driver/실제 loaded `libcuda` 580.173.02, CUDA toolkit/container 13.3.1을 기록했습니다. test launch는 131,072 context, 8 GiB prompt cache, BF16 KV, MTP enabled, 4개의 public chat fixture와 3회 client invocation을 사용합니다.
- **작성자 관측:** 65,583–65,584-token prompt를 섞은 cache churn 동안 136회의 `NV_ERR_NO_MEMORY` kernel message, 최소 26.51 GiB `MemAvailable`, 82 failed internal allocation trace를 기록했고, 세 client invocation은 모두 종료 코드 0으로 끝났다고 보고합니다. 8 GiB cache 상태에서 최대 TTFT는 115–117초였다고 관측합니다.
- **작성자의 제한:** 이 기록은 fatal OOM이나 allocator retry가 latency 원인이라는 사실을 주장하지 않으며, stripped binary라 allocation caller를 cache object로 귀속하지 못한다고 명시합니다.
- **해석:** “시스템 여유 메모리”만으로 serving tail latency나 allocator 안정성을 판정할 수 없습니다. 특히 131k context, mixed prefill/decode, cache evict/reuse는 request-state 및 driver allocation path와 따로 분리해 관찰해야 합니다.
- **진단 → 가설 → 최소 실험:** 동일 binary hash·driver·model revision으로 (a) cache off, (b) fixed hit, (c) forced eviction 세 arm을 만들고 public fixture를 3회 이상 반복합니다. 각 arm에서 TTFT p50/p95/max, decode tokens/s, cache hit/resume tokens, `MemAvailable`, GPU memory, driver allocation error count를 time-aligned trace로 저장합니다.
- **GO/KILL:** error count가 0으로 수렴하고 fixed-hit 대비 eviction arm의 p95 guardrail이 통과하면 GO입니다. 단일 issue의 115–117초를 GB10 일반 성능 또는 TensorFold의 공식 allocator 결함으로 단정하는 것은 KILL입니다.

## 오늘의 실행 규칙

1. 성능 표에는 GPU architecture, driver와 실제 loaded runtime, container/image digest, model revision, precision/KV dtype, context, cache size·hit policy, concurrency, graph mode, warm-up 및 반복 횟수를 함께 기록합니다.
2. compatibility, model-load memory, peak VRAM, compute time, TTFT, end-to-end decode tokens/s와 error count를 하나의 “speed” 지표로 합치지 않습니다.
3. 공개 issue의 수치는 작성자 관측으로 표시하고, merged upstream change·release artifact와 독립적인 성능 검증을 구분합니다.
