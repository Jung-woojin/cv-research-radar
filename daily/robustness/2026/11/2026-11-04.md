## 1. T4 CUDA deployment shift — 동일 GPU 이름이 동일 실행 환경을 뜻하지 않음

- **출처:** [llama.cpp issue #31503](https://github.com/ggml-org/llama.cpp/issues/31503).
- **사실:** issue 작성자는 같은 `b12030` image (`03dc44df4107`)와 Tesla T4, 동일 kernel driver 610.43.02에서 한 host는 XL model load와 262k context/MTP smoke test를 통과했고 다른 host는 `unsupported PTX toolchain`을 냈다고 기록했습니다. 동작한 host는 kernel 6.8.0-111, Docker 28.0.4, nvidia-container-toolkit 1.19.1-1을 사용했습니다.
- **작성자/배포팀 관측:** image의 `/usr/local/cuda/compat/libcuda.so.615.71.09`가 CUDA 13.4 UMD를 제공하며, toolkit 1.19.1+ host는 이를 inject해 PTX JIT가 성공한 반면 1.17.5 host는 older host UMD 13.3을 주입해 첫 kernel load에서 실패했다고 보고합니다. old-toolkit host에서 `LD_LIBRARY_PATH=/usr/local/cuda/compat`와 host UMD 13.4 upgrade가 load를 통과시켰다는 관측도 있습니다.
- **해석:** 이것은 sm_75 model kernel 자체의 안정성 판정이 아니라 container runtime/UMD compatibility cell의 failure입니다. GPU SKU와 kernel-driver major만 일치하는 환경은 **not strictly apples-to-apples**입니다.
- **진단 → 가설 → 최소 실험:** 같은 image digest·model·prompt로 T4 host마다 kernel, driver, `nvidia-container-toolkit`, container 내 실제 `libcuda.so`, `LD_LIBRARY_PATH`, CUDA runtime을 manifest에 저장합니다. cold model load와 256k-context smoke를 3회 반복하고 load success, first-kernel error, first-token latency, exit code를 비교합니다.
- **GO/KILL:** target host의 loaded UMD가 image/toolkit 요구와 일치하고 반복 load가 통과하면 GO입니다. 한 T4 host에서의 성공을 모든 T4 또는 모든 CUDA 13 image의 compatibility claim으로 쓰는 것은 KILL입니다.

## 2. Strata model-switch vision state — capability artifact와 active modality state의 분리

- **출처:** [Strata issue #4926](https://github.com/Niko1221/Strata/issues/4926).
- **사실:** 공개 issue는 Strata app 0.2.9/control-engine 0.1.55, Windows 11, RTX 3090 24GB에서 installed GGUF와 local-folder GGUF를 바꿀 때 picture reading이 꺼지는 sequence를 기록합니다. shared `mmproj` vision encoder는 이미 내려받아져 있었고, 양방향 model switch에서 같은 현상을 보고합니다.
- **작성자 관측:** switch 및 첫 off/on 재활성화가 `--vision no`로 setup을 실행해 `--vision` launch option을 잃었고, 두 번째 off/on에서야 `--vision yes`가 되어 복구됐다고 합니다. 공개 log는 context 131072, int8 KV와 `vision encoder already downloaded` 상태를 함께 보입니다.
- **해석:** vision encoder 파일의 존재, UI toggle, 실제 runtime capability는 서로 다른 상태입니다. 이를 분리하지 않으면 이미지 모델이 grounding/OCR을 실패했다고 잘못 진단하거나, model switch 뒤 image request가 text-only path로 떨어진 것을 model robustness 문제로 오인할 수 있습니다.
- **진단 → 가설 → 최소 실험:** model A→B와 B→A 각각에서 clean image fixture와 text control을 5회 교대 실행합니다. UI state, setup command의 `--vision`, engine capability probe, image task success, invalid-format/error, first-response latency를 한 row에 저장합니다. vision artifact hash는 고정하고 switch 전후 capability probe가 다르면 workload score 비교를 무효화합니다.
- **GO/KILL:** 첫 switch 뒤 capability probe와 image control이 모두 통과하면 GO입니다. encoder file 존재 또는 UI ON만으로 vision pipeline이 활성화됐다고 판정하는 것은 KILL입니다.

## 3. Gemini image observability shift — 성공 응답이 telemetry 성공을 보장하지 않음

- **출처:** [LiteLLM issue #49567](https://github.com/BerriAI/litellm/issues/49567).
- **사실:** 공개 issue는 LiteLLM v1.106.6 Docker deployment에서 Gemini image request가 200 OK, native response id, usage를 반환했지만 이후 15분 이상 `LiteLLM_SpendLogs`에 해당 row가 없었다고 보고합니다. 해당 run의 usage는 prompt 1,108 tokens 중 image 1,089 tokens였고 응답 latency는 2.47초로 기록됐습니다.
- **작성자 관측:** 동일 key·deployment로 seconds apart text-only control을 실행하면 success spend row가 생성됐고, request id·response id·model group을 포함한 query로 image row가 지연 또는 다른 label로 저장된 경우도 확인하지 못했다고 합니다. issue는 image spend와 Prometheus success count가 undercount될 수 있다고 주장하지만 maintainer fix는 아직 확인되지 않았습니다.
- **해석:** client success와 cost/traffic telemetry success는 별개 failure cell입니다. image workload만 dashboard에서 빠지면 multimodal deployment의 비용, reliability, error rate가 text traffic으로 희석되어 calibration·capacity 판단까지 틀어질 수 있습니다.
- **진단 → 가설 → 최소 실험:** 동일 deployment·key·timeout에서 1×1 public image와 text-only control을 번갈아 10회 실행합니다. response id, HTTP status, provider usage, `LiteLLM_SpendLogs` row count, Prometheus counter delta, model group, write delay를 time-aligned하게 저장합니다. 실제 secret이나 사용자 이미지는 쓰지 않습니다.
- **GO/KILL:** image/text 모두 response-id 기준 telemetry row와 counter delta가 일치하고 지연 한계 안에 들어오면 GO입니다. 200 OK만으로 spend/usage dashboard가 정확하다고 결론내리거나, 단일 issue로 모든 Gemini deployment에 같은 결함이 있다고 선언하는 것은 KILL입니다.
