## Q1. OBB evaluator provenance sensitivity를 어떻게 score와 rank uncertainty로 바꿀 것인가?

### 관측된 사실

Supervision 0.31.5는 OpenCV 환경의 OBB IoU·NMS·metric을 exact convex clipper로 변경했고, 공식 원문은 거의 collinear한 edge 또는 매우 작은 rotated box에서 기존 OpenCV 경로가 IoU 0 또는 1을 낼 수 있었다고 설명한다. 같은 원문은 OBB precision/recall/F1/mAR의 corner precision도 수정됐으며, stored IoU·NMS·mAP reference 재생성을 권고한다.

출처:
- https://github.com/roboflow/supervision/releases/tag/0.31.5
- https://github.com/roboflow/supervision/pull/2882
- https://github.com/roboflow/supervision/pull/2887

### 연구 질문

**동일 prediction·annotation에서 evaluator implementation/version만 바꿨을 때, 어떤 OBB geometry slice가 mAP·mAR 및 model ranking reversal을 유발하며, 그 불확실성을 leaderboard에 어떻게 표시해야 하는가?**

### 가설

작은 box, 큰 coordinate origin, near-collinear overlap이 많은 slice일수록 old/new evaluator 간 IoU·NMS keep-set 차이가 커지고, 전체 score 변화보다 per-class 또는 per-domain rank reversal이 먼저 나타날 수 있다. 일반적인 axis-aligned 또는 충분히 큰 box slice에서는 차이가 제한적일 수 있다.

### 최소 실험

1. 최소 3개 detector의 **동일한** frozen prediction/ground truth를 보관한다.
2. `supervision==0.31.4`/`0.31.5`, OpenCV 유무, 동일 IoU threshold와 NMS 설정의 4개 evaluator condition을 실행한다.
3. IoU matrix, NMS retained index, AP/mAR, runtime을 geometry slice별로 기록한다.
4. model pair별 rank agreement와 bootstrap confidence interval을 계산하고, evaluator 간 rank reversal이 있는 slice만 별도 leaderboard column으로 표시한다.

### 판정

**GO:** 사전 정의한 geometry slice에서 evaluator 간 ranking 차이가 재현되면 evaluator hash/version을 leaderboard 필수 metadata로 삼는다.  
**KILL:** 모든 slice에서 score·rank 차이가 measurement noise 범위라면 evaluator provenance를 경고 수준 metadata로만 유지한다.

## Q2. Tracker occlusion retention은 count benchmark의 model quality와 얼마나 독립적인가?

### 관측된 사실

같은 Supervision 0.31.5에서 `LineZone`의 default side-state retention은 `max(2, minimum_crossing_threshold + 1)`에서 `max(30, minimum_crossing_threshold + 1)` absent frame으로 바뀌었다. 공식 예시는 5-frame occlusion 뒤 재등장한 같은 tracker가 새 기본값에서는 count되지만 기존 값에서는 count되지 않음을 보인다.

출처:
- https://github.com/roboflow/supervision/releases/tag/0.31.5
- https://github.com/roboflow/supervision/pull/2873

### 연구 질문

**occlusion gap length와 FPS를 명시했을 때, retention policy를 조정하는 것만으로 recovered true crossing과 false crossing의 trade-off를 model/tracker 변경과 독립적으로 예측할 수 있는가?**

### 가설

2–30-frame occlusion bucket에서는 retention 증가가 missed crossing을 줄이지만, identity reuse·반대 방향 재진입이 있는 traffic/maritime 영상에서는 false crossing도 증가할 수 있다. 동일한 frame threshold는 FPS가 달라지면 다른 시간 정책이 된다.

### 최소 실험

1. tracker output을 고정하고, crossing event와 occlusion interval을 수동 annotation한다.
2. `max_absent_frames`를 2, 5, 10, 30으로 바꾸고 동일 clip에서 count한다.
3. gap length(0, 1–2, 3–5, 6–30, 31+)와 FPS별로 true positive, false positive, false negative를 집계한다.
4. detector/tracker를 바꾸지 않은 policy curve와 tracker를 바꾼 curve를 분리해 비교한다.

### 판정

**GO:** 같은 tracker output에서 policy curve가 stable하고 domain별 optimum가 재현되면, count benchmark는 model score와 retention score를 별도 축으로 보고한다.  
**KILL:** optimum가 annotation convention 또는 scene마다 무작위로 바뀌면 단일 default threshold를 일반 benchmark claim으로 쓰지 않는다.

## Q3. Dataset·judge provenance가 interactive VLM benchmark의 ranking stability를 보장할 수 있는가?

### 관측된 사실

V-Thinker 저장소는 2026-11-07에 Perception, Instruction-Guided Interaction, Interactive Reasoning의 세 과제로 구성된 VTBench를 공개했고, 1,500 QA pair라고 설명한다. 이후 저장소 공지는 Hugging Face의 Instruction-Guided Interaction subset이 실험에 사용한 final version과 일치하지 않는 non-final export였다고 밝히고, judge prompt와 dataset을 다시 공개했다. 이는 공개 artifact revision과 evaluator/judge revision이 결과 해석의 일부임을 보여 주는 저자 공지다.

출처:
- https://github.com/We-Math/V-Thinker
- https://huggingface.co/datasets/We-Math/VTBench

### 연구 질문

**interactive VLM benchmark에서 dataset revision, judge prompt revision, task subset을 manifest로 고정하면, 공개 leaderboard의 rank correlation과 score confidence를 충분히 안정화할 수 있는가?**

### 가설

text-only answer scoring보다 image editing·interaction task에서 judge prompt와 subset revision의 영향이 클 수 있다. artifact hash와 judge prompt hash가 없는 aggregate score는 same model·same sampling이라도 revision 간 rank reversal을 보일 수 있다.

### 최소 실험

1. VTBench artifact를 revision/hash별 snapshot으로 분리하고 task별 item ID, sample count, media checksum을 manifest에 기록한다.
2. 최소 3개 VLM을 동일 model revision, prompt, decoding parameters, seed로 각 snapshot에 실행한다.
3. 공개 judge prompt와 revision별 judge prompt를 독립 condition으로 실행해 task별 score, Kendall rank correlation, item-level disagreement를 계산한다.
4. Perception, Instruction-Guided Interaction, Interactive Reasoning을 aggregate 전에 각각 보고한다.

### 판정

**GO:** artifact·judge hash를 고정한 조건에서 rank correlation과 item-level agreement가 사전 기준을 넘으면 revision별 leaderboard를 유지한다.  
**KILL:** hash를 고정해도 task별 rank가 불안정하면 단일 aggregate ranking을 철회하고 task-specific result만 공개한다.

## Q4. Multi-forward distributed training의 gradient correctness를 자동 release gate로 만들 수 있는가?

### 관측된 사실

Transformers issue #50424은 `GradientCheckpointingLayer`와 FSDP2 `fully_shard` 및 `use_reentrant=True` 조합에서, 하나의 backward 전에 같은 layer를 여러 번 실행하면 마지막 forward 외 gradient contribution이 사라질 수 있다고 보고한다. 연결된 PyTorch issue는 오류 없이 optimizer step이 진행되는 조건에서 full gradient sum과 relative error 0.605, last-forward-only와 0.000이라는 관측을 제시한다. 이는 원문 작성자의 재현 보고이며, VLM 학습 전체에 독립 검증된 일반 법칙은 아니다.

출처:
- https://github.com/huggingface/transformers/issues/50424
- https://github.com/pytorch/pytorch/issues/203482

### 연구 질문

**여러 forward를 한 backward로 합치는 multimodal/RL 학습에서, reference gradient-sum probe가 reentrant checkpoint·FSDP nesting 오류를 실제 training run 전에 충분히 검출할 수 있는가?**

### 가설

작은 representative subgraph에서 만든 gradient-sum probe는 production-scale memory/throughput을 재현하지 않아도 silent last-forward-only gradient를 검출할 수 있다. 다만 MoE routing, mixed precision, heterogeneous sequence length가 추가되면 false negative가 생길 수 있다.

### 최소 실험

1. production VLM의 visual encoder/projector/decoder를 포함한 작은 representative graph와 2개의 서로 다른 microbatch를 준비한다.
2. checkpoint 없음, reentrant, non-reentrant, FSDP outside/inside checkpoint 조건을 동일 초기화에서 실행한다.
3. separate backward sum을 reference로 삼아 parameter group별 relative gradient error, global norm, optimizer update 차이를 계산한다.
4. 조건별 memory, wall-clock과 numerical error를 함께 기록하고, CPU/gloo smoke test 뒤 target accelerator에서도 반복한다.

### 판정

**GO:** probe가 known-bad nesting을 검출하고 known-good condition에서 reference와 일치하면 CI release gate로 넣는다.  
**KILL:** probe가 production failure를 놓치거나 normal condition을 지속적으로 fail시키면 model-family별 probe로 축소하고 universal gate claim을 하지 않는다.
