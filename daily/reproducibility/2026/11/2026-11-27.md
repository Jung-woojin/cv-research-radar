## 사례 1 — grayscale 변환 요청이 입력 layout을 바꾼다

**Claim·재현 조건.** Diffusers 0.44.0.dev0, macOS arm64·Apple M1 Max, Python 3.13.7, torch 2.15.0 CPU에서 8×8×3 float32 NumPy RGB 배열을 VaeImageProcessor에 전달했다는 보고다. do_resize=False, do_normalize=False, do_convert_grayscale=True이며 weights가 필요 없다. [원문](https://github.com/huggingface/diffusers/issues/15414)

**Observed gap·작성자 보고.** 기대한 한 장의 grayscale 출력 (1,1,8,8) 대신 (8,1,8,3)이 반환돼 assertion이 실패했다. PIL 입력에서는 기대한 단일 grayscale 출력이 나온다는 설명이 있으나, 게시된 실행 코드는 NumPy 실패 경로다. 댓글은 없으며 독립 재현은 확인하지 못했다.

**Mechanism·소스 사실.** 고정 revision 16eb5cc4fd8262fd33b3c9119a12977c25cc4985는 grayscale flag가 켜진 3차원 NumPy 입력의 마지막 축이 1이 아니면 마지막에 축을 추가한다. 따라서 HWC RGB를 (H,W,C,1)로 만든 뒤 batch 배열처럼 처리할 수 있다. 실제 grayscale 변환 호출은 PIL 분기에 있다. [소스](https://github.com/huggingface/diffusers/blob/16eb5cc4fd8262fd33b3c9119a12977c25cc4985/src/diffusers/image_processor.py#L644-L725)

**진단 → 가설 → 최소 실험.** 실패 위치는 seed·VAE decoding 이전의 layout 해석이다. RGB 패턴과 서로 다른 H·W를 가진 작은 fixture를 PIL/HWC/명시적 batch 형태로 넣고 shape·채널·pixel 값을 기록한다. 수동 grayscale 변환한 HWC1을 기준으로 비교하며 BHW grayscale의 기존 의미도 보존해야 한다. 단순 reshape로 오류를 감추지 않는다.

**GO/KILL.** 지원된 입력 표현에서 이미지 수·공간 축·grayscale 값이 보존되거나 모호한 입력을 명시적으로 거부하면 GO. shape만 맞춘 후 색 변환 의미와 기존 batch 경로를 검사하지 않는 수정은 KILL. 생성 품질 격차나 학습 영향 크기는 미측정이다.

## 사례 2 — 같은 checkpoint 값이어도 학습 가능한 parameter 집합이 달라진다

**Claim·조건.** Transformers 5.25.0.dev0 및 5.22.0, Linux·Python 3.12.12·torch 2.14.0+cu130 조건의 보고다. tiny Laguna 모델을 저장한 뒤 AutoModelForCausalLM으로 다시 읽으면 frozen router bias의 requires_grad가 False에서 True로 바뀐다. 작성자는 D-FINE·DEIMv2의 decoder.reg_scale/up, Ernie 4.5 VL MoE도 영향 목록에 포함했다. 해당 CV 모델별 학습 성능은 독립 검증하지 않았다. [이슈](https://github.com/huggingface/transformers/issues/51286)

**사실·기전.** 고정 base 3d2d3b3f7bed13f858da128cd932a2f8d36e1490의 두 loader 경로는 tensor의 부동소수점 여부로 requires_grad를 설정하며 기존 module의 freeze 상태를 참조하지 않는다. 이는 weight 값 일치만으로 학습 재현성을 보장할 수 없다는 근거다. [loaded 경로](https://github.com/huggingface/transformers/blob/3d2d3b3f7bed13f858da128cd932a2f8d36e1490/src/transformers/core_model_loading.py#L1580-L1595), [missing 경로](https://github.com/huggingface/transformers/blob/3d2d3b3f7bed13f858da128cd932a2f8d36e1490/src/transformers/modeling_utils.py#L515-L524)

**수정 범위·한계.** PR #51287은 기존 requires_grad와 float 여부를 함께 확인하고 loaded/missing frozen parameter 테스트를 추가한다. 조회 시 open, merged_at=null, head fb52eaad9b0928491d4db354f07c3b8bff1561f0이다. 테스트는 flag 보존을 검사하며 task 품질·DDP 복구를 직접 보증하지 않는다. [PR](https://github.com/huggingface/transformers/pull/51287)

**가설·최소 실험.** checkpoint 왕복 전후 이름별 weight hash·requires_grad·optimizer 포함 여부를 비교한다. loaded/missing 경로를 분리하고 한 optimizer step의 frozen parameter 변화와 gradient를 검사한 뒤 DDP 두 step으로 확장한다.

**GO/KILL.** 원래 freeze 계약과 intended trainable parameter가 모두 보존되면 GO. 로딩 성공이나 weight hash 일치만으로 동일 학습 recipe라고 승인하는 것은 KILL.

## 사례 3 — 재현되지 않은 MoE 실패를 cache 버그나 수정 완료로 단정하지 않는다

**Claim·시간 구분.** 11/26 게시된 Qwen3-VL-MoE 조사 기록은 11/20 CI에서 한 번 발생한 cached/cacheless logit 불일치를 다룬다. 모델 task 정확도나 pretrained checkpoint의 seed 분산 연구가 아니라 tiny random config·FP32 CPU 테스트다. [조사 원문](https://github.com/huggingface/transformers/issues/51312)

**확인된 사실.** 공식 run API에서 해당 merge-group 실행의 failure 상태와 tested head 47f65ea3020ba2cfcba73ceacc0e258f8e856bca를 확인했다. queue branch 이름의 base SHA와 실제 tested head는 다르다. 이 API만으로 개별 logit 오류를 독립 검증한 것은 아니다. [실패 run](https://github.com/huggingface/transformers/actions/runs/44786420520)

**Observed gap·작성자 보고.** 최초 실패는 step 2 max_diff 약 0.346이었다. 작성자는 같은 실패 commit·Intel CI 하드웨어에서 310,000회, main에서 210,000회, AMD에서 24,000회 재시도했으나 실패가 없었다고 기록했다. 이 숫자는 작성자의 실행 집계다. 추정 실패율은 관측 확률로 인용하지 않는다. 재시도는 단독 테스트였고 원래 shard의 선행 테스트 상태 영향은 조사되지 않았다.

**기전·불확실성.** 고정 소스의 router는 FP32 softmax 뒤 top-k를 선택하고 재정규화한다. 작은 경로별 수치 차이가 k/k+1 경계를 넘으면 expert 집합이 바뀔 수 있다는 설명은 코드와 부합한다. 그러나 작성자도 실제 flip은 관측하지 못했다. “cache 버그가 아니다”는 작성자 결론이며, 이번 분석은 원인 확정으로 취급하지 않는다. [router 소스](https://github.com/huggingface/transformers/blob/47f65ea3020ba2cfcba73ceacc0e258f8e856bca/src/transformers/models/qwen3_vl_moe/modeling_qwen3_vl_moe.py)

**상태·최소 실험.** 이슈는 의도적으로 closed이며 재발 전 수정 계획이 없다는 댓글이 있다. weights seed와 input RNG를 각각 기록해 정확히 replay하고, cached/cacheless의 token별 router gap·선택 expert·logit을 수집한다. 단독 실행과 원래 shard 문맥을 분리하고 all-expert routing을 진단 대조로만 쓴다. [종료 설명](https://github.com/huggingface/transformers/issues/51312#issuecomment-7190716544)

**GO/KILL.** 원래 조건에서 재발을 replay하고 경계 flip 또는 context effect를 분리하면 해당 기전 검증으로 GO. 무실패 반복을 실패 확률 0으로 해석하거나 all-expert 테스트를 실제 sparse routing 재현성의 보증으로 쓰는 것은 KILL.
