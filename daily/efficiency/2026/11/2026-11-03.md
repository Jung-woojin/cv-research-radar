## 1. BEVFormer ONNX PTQ — 시간 순서와 엔진 조건을 고정한 비교

- **출처:** [ModelOpt 0.48.0 release](https://github.com/NVIDIA/Model-Optimizer/releases/tag/0.48.0), [BEVFormer workflow](https://github.com/NVIDIA/Model-Optimizer/blob/e2f328a/examples/onnx_ptq/bevformer/README.md).
- **사실:** release는 temporal calibration data 생성, INT8/FP8 quantization, TensorRT engine build, nuScenes accuracy evaluation을 포함한 BEVFormer ONNX PTQ 예제를 추가했습니다. 문서는 TensorRT 10.14, RTX 6000 Ada validation system, GPU별 plugin 재컴파일, 순서 보존 calibration 600개와 `prev_bev` 전파를 명시합니다.
- **문서의 과거 기준값:** 동일 GPU에서 600 calibration samples와 6,019 nuScenes validation samples를 사용한 과거 TensorRT 10.14 기준으로 FP16 대비 INT8/FP16은 1.87×, FP8/FP16은 1.18× speedup입니다. 문서 자체가 DL4AGX-container 통합은 3 sample만 검증했고 NDS/mAP를 재실행하지 않았다고 밝힙니다.
- **해석:** 시간 상태를 가진 BEV 모델에서는 static calibration만 맞춰도 충분하다고 볼 수 없습니다. scene boundary에서 state와 CAN-bus delta를 초기화하는지, engine과 plugin을 대상 GPU에서 다시 빌드했는지가 정확도·wall-clock보다 먼저 비교 가능성을 좌우합니다.
- **진단 → 가설 → 최소 실험:** 동일 checkpoint·6,019 validation·동일 GPU에서 FP16/INT8/FP8을 각각 5회 interleaved 실행하고 NDS/mAP, GPU compute median, peak memory, cold/warm latency를 기록합니다. 600개 ordered calibration과 무작위 순서 calibration을 분리해 state-reset 규칙도 대조합니다.
- **GO/KILL:** FP16 대비 speedup과 정확도 guardrail을 함께 만족하면 GO입니다. 3-sample integration 성공 또는 다른 GPU의 engine을 full-validation 결과로 사용하는 것은 KILL입니다.

## 2. GGML 저비트 weight-only 형식 — 파일 크기와 배포 가능성의 분리

- **출처:** [ModelOpt 0.48.0 release](https://github.com/NVIDIA/Model-Optimizer/releases/tag/0.48.0).
- **사실:** release는 Q8_0(32-value block), IQ1_S/IQ2_XS(256-value block), IQ2_XXS(2.0625 bits/weight), IQ2_S(2.5625 bits/weight), IQ1_M(1.75 bits/weight) weight-only quantization과 PTQ recipe/export를 추가했습니다. IQ 계열은 weight 마지막 차원이 256으로 나누어떨어져야 하며, Megatron export에는 tensor·pipeline parallel size 1 조건이 명시돼 있습니다.
- **저자/릴리스 주장:** GPTQ가 GGML block 전체를 양자화하고 이후 column error를 보상하며, 일부 IQ recipe는 calibration data를 필요로 한다고 설명합니다.
- **해석:** bits/weight는 저장·전송량의 지표이지 VRAM peak, prefill/decode latency, NPU kernel 지원의 대용물이 아닙니다. shape padding이나 runtime dequantization이 더 큰 병목이 될 수 있습니다.
- **진단 → 가설 → 최소 실험:** 목표 vision encoder 또는 VLM linear weight의 마지막 차원과 실제 packed artifact 크기를 검사하고, FP16·Q8_0·지원 IQ 형식을 동일 device/driver/runtime/batch/input shape에서 비교합니다. model-load RSS, peak VRAM, p50/p95 latency, task metric을 함께 남깁니다.
- **GO/KILL:** 모든 형상·runtime 제약을 만족하면서 memory/latency와 metric guardrail이 통과하면 GO입니다. “1.75 bits/weight”만으로 edge throughput 향상을 주장하는 것은 KILL입니다.

## 3. Sparse-attention calibration — calibration recipe와 serving recipe의 불일치

- **출처:** [ModelOpt 0.48.0 release](https://github.com/NVIDIA/Model-Optimizer/releases/tag/0.48.0).
- **사실:** release는 FlashAttention/FlashInfer용 vLLM skip-softmax calibration을 추가하며, calibration은 validation prompts file을 요구하는 single-sequence·unchunked·eager 실행이라고 밝힙니다. serving은 calibrated 128-token KV tile과 128-row prefill Q tile을 유지하고 execution schedule만 autotune하며 one-token decode에는 더 작은 Q tile을 사용합니다.
- **사실:** sparse-only vLLM 설치에서는 일부 DCP, DBO/ubatching, speculative decoding, FULL mixed-batch CUDA graph를 거부하고 calibrated decode도 FULL decode graph를 거부합니다.
- **해석:** calibration에서 얻은 sparsity 이득이 production batching/graph mode로 자동 이식된다고 볼 수 없습니다. 실제 serving 옵션이 calibration 가정과 달라지는 순간 throughput·tail latency·quality의 비교가 깨집니다.
- **진단 → 가설 → 최소 실험:** 고정 prompt set에서 eager single-sequence와 production-like prefill/decode를 분리하고, 128-token 경계 전후의 p50/p95 latency, tokens/s, peak VRAM, task quality를 기록합니다. 지원되지 않는 graph/batching 조합은 성능 비교가 아니라 configuration rejection으로 별도 기록합니다.
- **GO/KILL:** 지원 조합에서 held-out prompt 품질과 tail-latency guardrail을 통과하면 GO입니다. calibration 결과를 비지원 serving 조합에 외삽하거나 rejected configuration을 우회해 benchmark에 포함하는 것은 KILL입니다.

## 오늘의 실행 규칙

1. 비교 표에는 GPU/NPU, driver, TensorRT·CUDA·runtime, precision, batch, stream 수, input shape, warm-up·measurement window를 모두 적습니다.
2. temporal model은 scene-boundary state reset과 input order를 artifact로 보존합니다.
3. “압축률/bit 수”, “엔진 load memory”, “peak memory”, “compute latency”, “end-to-end latency”를 한 지표로 합치지 않습니다.
