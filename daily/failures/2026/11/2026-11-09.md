## 1. Mixed-precision `compressed-tensors` checkpoint가 dense module을 무작위 초기화할 수 있음

### 사실

- Transformers issue #50426은 `transformers` 5.22.1 및 2026-11-05 기준 main, `compressed-tensors` 0.20.1 환경에서 pre-quantized mixed-precision checkpoint를 `from_pretrained`로 불러올 때의 문제를 보고한다.
- 보고된 조건에서는 quantized MoE expert와 dense BF16 attention causal convolution이 공존하는 `RedHatAI/GLM-5.3-Flash-NVFP4`가 사례다.
- issue 저자는 serialized companion key가 없는 dense module에도 conversion rewrite가 적용되어 `.weight`가 unexpected로 처리되고, 대상 parameter가 조용히 random initialization된다고 설명한다.
- 연결된 open PR #50466은 dense converter를 보존하는 수정이라고 명시하며, 해당 문제를 해결한다고 표기한다. 아직 upstream `main`에 merge된 release fix라는 근거는 확인하지 못했다.

출처:
- https://github.com/huggingface/transformers/issues/50426
- https://github.com/huggingface/transformers/pull/50466

### 진단

load가 성공하고 inference가 시작되더라도 일부 dense parameter가 checkpoint 값이 아닐 수 있으므로, smoke test 통과·메모리 사용량·단순 output shape만으로 checkpoint integrity를 보장할 수 없다. 이 신호는 checkpoint loading failure가 아니라 **silent parameter corruption 위험**이다.

### 가설

mixed checkpoint에서 packed companion key가 없는 converter source가 존재하면, 영향 module의 `state_dict` coverage가 낮아지고 같은 prompt의 logits/generation이 정상 dense reference와 달라질 수 있다. 완전히 quantized이거나 완전히 dense인 checkpoint에서는 이 조건이 발생하지 않을 수 있다.

### 최소 실험

1. production과 같은 Transformers·compressed-tensors 버전에서 target checkpoint를 CPU `from_pretrained`로 한 번 load한다.
2. load report의 `UNEXPECTED`와 missing key를 module별로 저장하고, 영향 후보 dense parameter의 shape·finite ratio·checksum을 reference checkpoint와 비교한다.
3. 고정 prompt 20개, greedy decoding, 동일 tokenizer로 normal/reference load와 output token·first-step logits을 비교한다.
4. PR #50466이 merge/release되기 전까지 unexpected dense `.weight`가 하나라도 나오면 해당 checkpoint를 serving promotion에서 제외한다.

**GO:** 모든 expected dense parameter가 checkpoint에서 로드되고 fixed-prompt diff가 허용 기준 안이면 배포한다.  
**KILL:** unexpected dense weight 또는 random-init 흔적이 있으면 load 성공 여부와 관계없이 차단하고, fixed version/patch로 재검증한다.

## 2. FSDP2 + reentrant checkpoint에서 silent gradient loss

### 사실

- Transformers issue #50424은 `GradientCheckpointingLayer.__call__`이 `super().__call__`을 checkpoint하므로 forward hook까지 checkpoint 영역에 들어간다고 설명한다.
- issue 저자는 layer가 FSDP2 `fully_shard` unit이면서 `use_reentrant=True`이고, 하나의 `backward()` 전에 같은 layer가 여러 번 forward되면 마지막 forward의 gradient만 남을 수 있다고 보고했다. 예외 없이 `optimizer.step()`이 진행되는 조건이다.
- 연결된 PyTorch issue #203482도 같은 failure mode를 보고한다. 해당 원문은 2개의 forward에서 full gradient sum 대비 relative error 0.605, last-forward-only 대비 0.000이라는 관측을 제시하며, 2.11.0·2.15.0·2.16 dev에서 오류 없이 발생한다고 적었다.
- 두 원문 모두 CPU와 2 gloo rank로 재현 가능하다고 적어 GPU 특이 failure로 한정할 근거는 없다.

출처:
- https://github.com/huggingface/transformers/issues/50424
- https://github.com/pytorch/pytorch/issues/203482

### 진단

RL, DPO 또는 gradient accumulation 변형처럼 여러 forward의 loss를 한 backward로 합치는 학습에서는 loss가 감소해도 일부 forward의 gradient contribution이 빠질 수 있다. 따라서 step 성공·loss finite·optimizer state 갱신만으로 학습 correctness를 판단하면 안 된다.

### 가설

FSDP2 per-layer sharding과 reentrant checkpoint의 nesting이 함께 있고 동일 layer를 backward 이전에 두 번 이상 실행하면, aggregate gradient가 full-reference sum 대신 마지막 forward 쪽으로 치우친다. non-reentrant checkpoint 또는 checkpoint/FSDP nesting 변경 시 차이가 줄어들 수 있다.

### 최소 실험

1. production model의 작은 layer와 동일한 FSDP2 wrapping을 사용해 두 개의 서로 다른 microbatch를 하나의 backward에 넣는다.
2. checkpoint 없음, reentrant checkpoint, non-reentrant checkpoint 세 조건에서 parameter gradient를 저장한다.
3. “두 microbatch를 별도 backward로 합산한 reference”와 각 조건의 L2/relative error를 비교한다.
4. rank별 gradient, global norm, optimizer update도 함께 기록하고 2-rank와 production world size에서 반복한다.

**GO:** reentrant 조건의 gradient가 reference sum과 허용 오차 안에서 일치하면 해당 wrapping을 유지한다.  
**KILL:** step가 성공해도 full-sum reference가 아닌 last-forward-only gradient와 일치하면 reentrant 조합을 중지하고 training run을 재시작 또는 재평가한다.

## 3. vLLM GPT-J compressed-tensors FP8 KV-cache scale이 1.0으로 fallback될 수 있음

### 사실

- vLLM issue #65945은 GPT-J `compressed-tensors` checkpoint에서 저장된 FP8 KV-cache `k_scale`/`v_scale`가 attention layer로 전달되지 않는다고 보고한다.
- 보고 환경은 vLLM `0.33.0rc1.dev848+g14d147a7a`, `compressed-tensors==0.17.0`, CUDA 13.0/H20-3e였다. load는 error나 warning 없이 성공하고, calibrated value 대신 `k_scale = v_scale = 1.0`으로 실행된다고 적혀 있다.
- 연결된 open PR #65949는 GPT-J 전용 name mapping을 추가하는 수정이며, 새 test 7개 중 수정 전 4개가 실패하고 수정 후 7개 모두 통과했다고 보고한다.
- 같은 PR의 self-contained repro 결과는 layer 0의 0.5/0.25, layer 1의 0.75/0.375 scale이 1.0/1.0 대신 attention layer에 적용됐다고 적는다. 이는 PR 작성자 보고이며, upstream release 반영은 확인하지 못했다.

출처:
- https://github.com/vllm-project/vllm/issues/65945
- https://github.com/vllm-project/vllm/pull/65949

### 진단

checkpoint load와 serving startup이 성공해도 FP8 KV cache의 calibration scale이 무시되면 long-context quality·numerical behavior 비교가 의도한 quantization 조건을 대표하지 않을 수 있다. 단순 throughput benchmark는 이 오류를 발견하지 못할 수 있다.

### 가설

GPT-J의 HF key naming을 쓰는 compressed-tensors FP8 checkpoint에서 vLLM version이 해당 mapping을 포함하지 않으면 attention module의 effective KV scale은 1.0이 된다. mapping patch가 있는 build에서는 checkpoint-specified scale이 layer에 주입된다.

### 최소 실험

1. target checkpoint metadata에서 expected per-layer `k_scale`/`v_scale`를 추출해 manifest로 남긴다.
2. vLLM load 직후 attention layer의 effective scale을 layer별로 dump하고 checkpoint metadata와 비교한다.
3. scale이 1.0인 baseline과 calibrated-scale build에서 동일 prompt·seed·context length로 logits, token sequence, NaN/Inf count, peak memory를 비교한다.
4. direct issue 환경과 다르면 GPU·CUDA·vLLM commit을 manifest에 분리해 일반화하지 않는다.

**GO:** 모든 target layer의 effective scale이 checkpoint metadata와 일치하고 fixed-prompt outputs가 안정적이면 FP8 KV-cache 결과를 채택한다.  
**KILL:** load 성공에도 scale이 1.0 fallback이거나 layer coverage가 불완전하면 해당 benchmark/serving 결과를 invalid로 표시하고 version patch 전 배포하지 않는다.

## 즉시 운영 규칙

1. Quantized 또는 mixed checkpoint는 “load 성공” 대신 parameter-key coverage, scale coverage, fixed-prompt diff를 release gate로 삼는다.  
2. Distributed training은 step/loss 외에 multi-forward gradient-sum reference를 최소 한 번 비교한다.  
3. open issue/PR의 test는 upstream release fix를 뜻하지 않는다. 재현 manifest에 repository commit, package version, accelerator, prompt/seed를 함께 보존한다.  
4. 동일 문제가 다른 model family·hardware·quantizer에 일반화된다는 증거가 없으면, 보고된 조합 밖으로 실패 범위를 확대 해석하지 않는다.
