## 핵심 사례

### 1. 장문 prefill 뒤의 상태 오염 — SGLang #48964

- **사실(공개 이슈):** GLM-5.3-Flash, v0.5.23-cu130, 4×H100 80GB/TP4에서 약 1.04M-token 요청을 한 번 처리한 뒤 이후 요청이 빈 응답 또는 반복 token을 반환하고 MTP acceptance가 0.00이 된다는 제보다. `/flush_cache`로 회복되지 않고 process restart가 필요했다고 한다.
- **대조군/metric:** 같은 cluster와 needle test에서 v0.5.22는 5/5 recall·79.8 s 뒤 healthy, v0.5.23은 5/5 recall·117.7 s 뒤 poisoned으로 보고됐다. nightly는 0/5 recall이었다. 이는 작성자 측정이며 독립 재현이 아니다.
- **shift cell / 악화 cell 수:** context length 약 1M, 127개 chunked-prefill chunk 뒤의 subsequent short request·tool call·JSON-schema request. 셀 수는 공개된 한 long-context cell뿐이며, calibration/coverage는 보고되지 않았다.
- **진단:** long-request 품질만 보면 통과해도, 시간 순서가 추가된 “long prefill → later query” 축에서 server state가 손상될 수 있다.
- **가설:** 작성자는 speculative prefill에서 KDA state-pool layout이 바뀐 경로의 out-of-bounds write를 의심한다. 이는 저자/이슈 작성자 가설이며 확정 원인이 아니다.
- **최소 실험:** 동일 checkpoint와 pod에서 `(v0.5.22,v0.5.23) × (16K,1.04M prompt) × (spec prefill on/off)`를 실행하고, 각 long prompt 뒤 20개 고정 short probe의 exact-match·acceptance·JSON-schema 오류율을 기록한다.
- **GO/KILL:** v0.5.23만 long-prefill 후 short-probe failure가 반복되면 canary gate를 GO; off 상태도 같은 결과면 speculative-path 가설은 KILL하고 cache/KDA 경로를 분리한다.
- **출처:** https://github.com/sgl-project/sglang/issues/48964

### 2. Ragged batch에서 AMD MLA decode NaN/오답 — SGLang #48967

- **사실(공개 이슈):** gfx1151(Strix Halo)에서 `has_mla=True`, Lk 576/Lv 512, long sequence와 ragged batch 조합이 NaN 또는 큰 오답 행을 낸다는 제보다. fp32 reference와의 error가 약 4, bf16 rounding 단독은 약 1e-2이며 실패 행이 동일 입력에서도 매 run 달랐다고 한다.
- **shift cell / 악화 cell 수:** AMD gfx1151 × ragged batch × long sequence의 한 시스템 cell이다. 보고서가 제시한 것은 failing rows이지 benchmark dataset의 악화 cell 수가 아니며, calibration/coverage도 미보고다.
- **진단:** 균일 batch·짧은 sequence의 average latency/accuracy는 통과해도 request-length heterogeneity에서 kernel read/race류 오류를 가릴 수 있다.
- **가설:** 작성자는 uninitialized/racing memory read 가능성을 제시했다. 프로젝트의 확정 진단은 아니다.
- **최소 실험:** fixed seed와 동일 K/V에서 `{uniform, ragged}` batch를 100회 반복하고 fp32 reference 대비 max error, NaN rate, failing row index 분포를 수집한다. `has_mla=False`와 별 GPU backend를 negative control로 둔다.
- **GO/KILL:** ragged 조건에서만 반복적인 NaN/오답 또는 row-distribution 변화가 있으면 request bucketing/fallback을 GO; uniform과 ragged 모두 reference-bound면 raggedness 가설을 KILL한다.
- **출처:** https://github.com/sgl-project/sglang/issues/48967

### 3. NVFP4 subnormal scale 소실 — SGLang #48906

- **사실(공개 이슈):** SGLang의 기본 FP4 Marlin path(SM80–SM9x)에서 bf16 activation일 때 E4M3 subnormal block scale이 사실상 0으로 복호화되어 해당 16-weight block이 0이 될 수 있다는 구체적 제보다. float16 경로는 같은 bytes를 정확히 복호화한다고 설명한다.
- **작성자 측정:** `nvidia/Llama-3.3-70B-Instruct-NVFP4`의 H20 offline Engine/WikiText-2 16,376 positions에서 현 경로 PPL 3.5664, 수정 kernel PPL 3.5558, next-token prediction이 3.35% 위치에서 바뀌었다고 보고한다. GSM8K 5-shot은 93.2→92.9%였다. 이들은 작성자 측정이며 apples-to-apples 일반 성능 비교가 아니다.
- **shift cell / 악화 cell 수:** SM80–SM9x × bf16 × NVFP4 tail-scale blocks. 예시 checkpoint에서 165,266개 subnormal scale, 5,409/10,240 qkv output rows가 영향을 받는다고 이슈는 주장한다. calibration/coverage는 미보고다.
- **진단:** 평균 task score가 유사해도 serialization된 scale tail과 runtime dequantization의 불일치가 발생한다. 따라서 model-card 수치만으로 checkpoint fidelity를 검증할 수 없다.
- **가설:** subnormal exponent의 bf16 construction이 잘못되어 작은 scale을 0으로 만든다는 이슈 작성자 분석이다.
- **최소 실험:** 동일 layer에서 `{fp16,bf16} × {subnormal scale retained, zeroed}`를 비교하고 dequantized weight checksum, layer output max/mean error, next-token divergence를 기록한다. 0.5–6 E2M1 identity-input repro를 그대로 사용한다.
- **GO/KILL:** bf16만 fp16 대비 tail-block checksum/출력이 달라지면 float16 fallback 또는 patched kernel canary를 GO; checksum이 일치하면 host preprocessing 가설을 우선 재검토한다.
- **출처:** https://github.com/sgl-project/sglang/issues/48906

### 4. Memory profiling 밖의 graph-capture OOM — vLLM #65907

- **사실(공개 이슈):** vLLM v0.33.0에서 DeepSeek-V4.1-Flash/DSpark speculative decode가 `--gpu-memory-utilization 0.97`에서 startup 중 OOM을 낸다는 제보다. 같은 deployment는 v0.32.0에서 며칠간 안정적이었다고 한다.
- **관측 조건:** 2 node×4 H100, TP8/EP8, bf16, 1,048,576 max model length이며, speculator CUDA graph capture 도중 약 4 GiB `sparse_attn_indexer` workspace allocation이 실패했다고 보고됐다. 이것은 8-GPU 조건의 특정 deployment이며 다른 hardware·batch에는 **not strictly apples-to-apples**다.
- **shift cell / 악화 cell 수:** version v0.32→v0.33 × DSpark capture × high utilization의 한 startup cell. calibration/coverage와 dataset error는 해당하지 않으며 미보고다.
- **진단:** reserved-memory budget만으로는 graph capture dummy run의 peak workspace를 보장할 수 없다. 따라서 “0.97이 뜬다”는 capacity evidence가 아니라 overload risk signal이다.
- **가설:** memory profiler가 DSpark speculator graph capture allocation을 반영하지 않는다는 것이 작성자 가설이다.
- **최소 실험:** 동일 image에서 `{v0.32,v0.33} × {DSpark on/off} × {0.85,0.90,0.95,0.97}` sweep을 하고, capture 직전/중/후 `allocated`, `reserved`, free memory 및 startup success를 기록한다.
- **GO/KILL:** v0.33+DSpark에서만 threshold가 유의하게 낮고 trace에 capture peak가 보이면 production headroom cap을 GO; DSpark off에서도 동일하면 model/base allocation 경로로 재분류한다.
- **출처:** https://github.com/vllm-project/vllm/issues/65907

## 오늘의 진단 → 가설 → 최소 개입

| 진단 | 가설 | 최소 개입 |
|---|---|---|
| 평균 품질은 정상인데 순차 workload 후 응답이 붕괴 | hidden state/cache가 long prefill에 의해 오염 | long-prefill 뒤 fixed probe suite와 restart gate |

| profile 상 여유가 있는데 warm-up에서 OOM | capture workspace가 budget 밖 | utilization sweep과 capture-phase peak accounting |

## 오늘의 GO/KILL

- **GO:** 장문 요청을 쓰는 VLM/agent serving은 “첫 long request 성공”만 보지 말고 `long prefill → 20 short probes`를 release canary에 넣는다.
- **GO:** NVFP4 deployment는 bf16 vs fp16 layer-output differential과 weight checksum을 release acceptance에 넣는다.
- **GO:** AMD/heterogeneous serving은 request length bucketing 전후의 ragged-batch NaN rate를 별도 KPI로 기록한다.
- **KILL:** 네 공개 이슈를 일반적인 모델 정확도 하락 또는 모든 GPU의 오류로 해석하지 않는다. 모두 특정 version·backend·shape·hardware의 미독립 재현 신호다.
