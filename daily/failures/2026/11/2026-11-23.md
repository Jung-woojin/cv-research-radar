## 1. DOTA 재분할이 이전 실행의 객체 라벨을 보존

**확인 사실:** #27322는 미병합이다. Diff는 타일 이미지 쓰기의 반환값을 검사하고, 성공적으로 저장된 배경 타일의 기존 라벨을 삭제한다. 회귀 테스트에는 변경·미변경 이미지와 이미지 저장 실패 조건이 포함돼 있다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27322) · [수정 및 테스트](https://github.com/ultralytics/ultralytics/pull/27322/files)

- **실패 조건·모델·dataset·configuration:** DOTA 형식 입력을 동일 output directory로 두 번 분할한다. 첫 실행의 foreground annotation을 제거한 뒤 배경 타일을 허용해 재실행하면, 이미지는 덮어써도 이전 `.txt` 객체 라벨이 남을 수 있다. 모델과 weight는 무관한 전처리 단계다.
- **작성자 재현:** 64×64 이미지의 경량 harness에서 annotation 제거 후 기존 코드는 stale label 하나를 남기고 수정은 남기지 않았다고 보고했다. NumPy·OpenCV·Shapely를 사용했지만 geometry wrapper를 대체했고 로컬 PyTorch가 없어 전체 package 실행은 하지 못했다. 여러 OS의 CI 통과도 작성자 보고이며 이번 watch가 CI 전체 로그를 독립 검증한 것은 아니다.

## 2. Unicode TIFF 쓰기의 성공 반환이 예상 파일 보존을 보장하지 않음

**확인 사실:** #27323은 미병합이다. 수정은 `cv2.imwritemulti` 대신 Pillow의 multipage TIFF 저장을 사용한다. 테스트는 ASCII·Unicode 파일명과 1·5·10 channel 출력의 frame 수·pixel 일치 및 원본 제거를 확인한다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27323) · [diff](https://github.com/ultralytics/ultralytics/pull/27323/files)

- **실패 조건·모델·dataset·configuration:** Windows, Python 3.13, OpenCV 4.13.0.92에서 `convert_to_multispectral(directory, replace=True)`와 비ASCII 파일명을 사용한다. 모델 추론이 아닌 RGB 기반 변환 utility의 파일 I/O 문제다.
- **작성자 재현:** `photo_测试.jpg` 입력에서 OpenCV가 true를 반환했으나 깨진 이름으로 TIFF를 쓰고 directory loop가 원본을 삭제했다고 보고했다. 수정 후 예상 경로가 보존됐고, 별도 1·3·10 page 비교에서 두 writer가 생성한 TIFF를 OpenCV로 읽었을 때 pixel이 같았다고 한다. 경량 harness는 reader와 imports를 공급했으며 전체 로컬 환경에는 PyTorch가 없었다.
- **공식 인정·community 수준:** 자동 리뷰가 승인했다. 사람 maintainer pderrenger는 이전 write safeguard가 “실패 반환”만 감지하고 “잘못된 경로에 성공”하는 경우는 잡지 못한다고 설명했다. `replace=False`로 변환하고 예상 이름의 TIFF가 열리는지 확인하라는 우회법을 제시했다. 사람의 별도 Windows 실행 재현은 확인하지 못했다. [maintainer 설명·우회법](https://github.com/ultralytics/ultralytics/pull/27323#issuecomment-7084872153)
- **진단 → 메커니즘:** writer의 성공 신호와 원하는 파일 경로·읽기 가능성의 계약이 다르다. 상위 loop는 성공 반환을 원본 삭제 조건으로 사용한다. 단, 모든 산출물이 사라졌다는 뜻은 아니며 다른 이름의 TIFF가 남을 수 있다.
- **가설 → 최소 개입:** Python 경로 처리를 사용하는 writer로 교체하면 해당 Unicode 경로 실패가 사라지고 page 내용은 보존될 것이다.
- **최소 실험:** base `96041a27bf4f258fd3bff511ee24cfb1661b21fb`와 head `78e0fc949046158959e2a691f30523cb7df6123d`를 고정한다. 원본의 복사본만 임시 폴더에 넣고 ASCII·한글·중문 이름, 1·5·10 channel을 비교한다. 예상 경로 존재, 재열기, page 수·pixel, 원본 보존 여부를 기록한다. 강제 저장 예외에서도 원본이 남는지 확인한다.
- **GO/KILL:** 예상 경로와 모든 page가 맞고 저장 실패 때 원본이 보존되면 GO. 다른 이름으로만 저장되거나 예외 이후 원본이 사라지면 KILL한다. 실제 연구 원본으로 삭제 동작을 시험하지 않는다.
- **기존 주장과 충돌·한계:** 이전 safeguard가 모든 쓰기 손실을 방지한다는 해석은 지지되지 않는다. 실제 센서 multispectral 데이터의 spectral 정확도나 일반 TIFF 전체의 호환성 검증을 뜻하지 않는다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **3/5**.

## 3. Axelera `nms=True`가 export head와 metadata를 불일치시킴

**확인 사실:** #27304는 11월 22일 00:40 KST에 main의 `c747ded440c5bf8d7a4da40f33f084976c60da9e`로 병합됐다. 지원하지 않는 `nms=True`를 head 선택 전에 `None`으로 정규화하고, Axelera의 one-to-one head 선택 조건을 수정했다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27304) · [exporter 수정](https://github.com/ultralytics/ultralytics/pull/27304/files)

- **실패 조건·모델·dataset·configuration:** YOLO26n, `export(format="axelera", nms=True)`. 작성자는 x86 Linux의 axelera-devkit·axelera-rt 1.9.0과 COCO128을 사용했다. `imgsz=640`에서 export output은 기존 `(1,84,8400)`, 수정 후 `(1,300,6)`이었다고 보고했다.
- **작성자 주장·재현:** 기존 `metadata.yaml`의 end2end는 false인데 `.axm`은 true였다고 한다. COCO128 mAP50–95는 0.171→0.471, precision은 0.213→0.640으로 보고했다. 실제 backend/runtime을 사용하되 AIPU 호출은 FP32 head output으로 에뮬레이션했다. Metis 장치에서는 실행하지 않았다.
- **공식 인정·독립 검증:** maintainer glenn-jocher는 macOS에서 `imgsz=320`의 잘못된 head 선택을 재현하고, 수정 후 세 `nms` 값의 output shape가 같음을 확인했다. Linux 전용 compile 단계 전에 멈췄으며 `.axm` metadata와 AP는 작성자 Linux 실행에서 가져왔다고 구분했다. ONNX·ExecuTorch·NCNN 대조 artifact가 byte-identical이었다고도 보고했다. [독립 확인 범위](https://github.com/ultralytics/ultralytics/pull/27304#issuecomment-7065063547)
- **진단 → 메커니즘:** 지원하지 않는 옵션을 너무 늦게 정규화해 head 선택에 이미 영향을 준다. 이후 metadata와 decoder는 다른 output 계약을 전제한다.
- **가설 → 최소 개입:** 옵션을 head 선택 전에 정규화하면 export tensor와 metadata·decoder가 일치하며 기본 export와 같은 예측을 얻을 것이다.
- **최소 실험:** base `78623e668a25a9e87908b3ffd0d581b5b0389f93`와 병합 commit에서 동일 checkpoint·입력·해상도·compiler를 고정한다. `nms=True/None/False`의 shape와 양쪽 metadata를 먼저 검사하고 동일 head output을 decoder에 넣어 box·class·confidence를 비교한다. 실제 Metis 정확도·지연시간 검증은 별도 단계다.
- **GO/KILL:** 세 옵션이 같은 head·metadata·예측을 만들고 다른 format 대조군이 보존되면 GO. Metadata만 같고 decoder 결과가 다르면 KILL하고 compile/runtime 경계를 추가 조사한다.
- **기존 주장과 충돌·한계:** 과거 문서의 낮은 정확도를 “one-to-many head 자체의 Metis 성능”으로 해석하기 어렵다. 전후 AP는 head와 처리 계약이 달라 `not strictly apples-to-apples`이며 모델 학습 개선이 아니다. 호스트 에뮬레이션 정확도를 실제 NPU 성능·전력으로 일반화하지 않는다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **4/5** · 연구 아이디어 가치 **4/5**. 신뢰도는 head 선택 재현 기준이며 하드웨어 AP 검증 점수가 아니다.

## 제외 사례: SILog의 합성 수치 오류와 실제 보고 지표의 차이

#27315는 float32에서 두 모멘트의 차로 분산을 계산할 때 생기는 cancellation을 centered 계산으로 바꾸려 했다. Maintainer는 `align="none"`인 합성 상수 비율 예제의 차이를 재현했다. 그러나 일반 `model.val()`은 median alignment를 사용하고, depth8·NYU validation에서는 수정 전후 차이가 출력 정밀도상 구분되지 않는다고 보고했다. 실제 모델에서 보고되는 SILog가 바뀌는 근거를 요구하며 미병합 종료했다.

따라서 “SILog leaderboard가 오염됐다”는 사례로 선정하지 않는다. 수치 분석상 맞는 수정과 실제 연구 결론을 바꾸는 수정은 구분해야 한다. 이 watch는 해당 검증을 직접 실행하지 않았다. [종료 근거와 실제 데이터 대조](https://github.com/ultralytics/ultralytics/pull/27315#issuecomment-7069009591)

## 오늘의 실패 패턴 3개

1. **산출물의 실행 이력 의존:** 동일 annotation으로 분할해도 재사용 폴더의 과거 라벨이 결과를 바꿀 수 있다.
2. **성공 신호와 의미적 완료의 불일치:** 쓰기 true만으로 예상 경로·읽기 가능성·원본 대체의 안전성이 보장되지 않는다.
3. **옵션 정규화 순서와 출력 계약 불일치:** export 옵션이 head·metadata·decoder에 일관되게 적용되지 않으면 정확도 저하로 나타난다.

## 논문 아이디어로 연결 가능한 빈틈

**조사자의 추론:** aerial/UAV 파이프라인에서 모델을 바꾸기 전에 산출물 불변성을 검사하는 진단 연구가 가능하다. 재실행의 결과가 새 폴더와 같은지, 파일명만 바꿔도 변환 내용이 같은지, 같은 의미의 export 옵션이 같은 decoder 결과를 만드는지를 각각 검사한다.

최소 개입으로 회복되는 오류와 모델 자체의 tiny-object failure를 분리하는 것이 핵심이다. 여러 converter·splitter·runtime으로 확장하고 실제 연구 결과의 변화까지 측정해야 알려진 버그 하나를 고친 수준을 넘어설 수 있다. 현재 근거만으로 domain shift·seed variance·tiny-object 특이 실패를 주장할 수 없다. SILog 제외 사례는 합성 반례가 실제 지표에 도달하는지를 먼저 확인해야 한다는 연구 설계상의 대조군이다.

## 직접 재현해볼 최소 실험

**첫 순위는 CPU DOTA 재분할 불변성 검사다.** 두 합성 이미지에서 annotation 하나만 제거하고, 재사용 output과 깨끗한 output의 파일 집합·라벨·hash를 비교한다. Dataset 전체 다운로드나 GPU가 필요 없는 작은 fixture부터 시작한다. 다음으로 임시 복사본의 Unicode TIFF 경로·page 검사를 수행하고, Axelera는 compile 이전 head·metadata 검사부터 시작한다.

실험마다 source revision, dependency 버전, 입력 및 artifact hash, 실행 명령, 대조군을 보존한다. 실제 AP 비교에서는 dataset revision·split·weight·해상도·TTA·외부 데이터·evaluator·runtime·compute 조건을 고정한다. 이번 실행은 조사만 수행했으며 AP·VRAM·지연시간을 측정하지 않았다. 모든 /5 점수와 연구 연결은 조사자의 판단이다.
