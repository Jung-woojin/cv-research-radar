## 3. Paddle: 요청 장치와 실제 실행 장치가 달라 전일 수정이 우회됨

**확인 사실:** #27379는 `elif` 기반 CPU 분기 대신 `not config.use_gpu()`를 확인해 기존 oneDNN workaround를 적용한다. 전일 #27367의 새 누락 조건을 고친 병합이다. [공식 diff](https://github.com/ultralytics/ultralytics/pull/27379/files) · [maintainer 재현·전체 비교](https://github.com/ultralytics/ultralytics/pull/27379#issuecomment-7198125723)

- **실패 조건·configuration:** PyTorch는 CUDA를 인식하고 `device=0`을 요청하지만 Paddle 3.2.2 CPU wheel만 설치된 환경. Paddle은 경고를 출력하고 `config.use_gpu()`를 false로 남긴다. 실제 실행은 CPU이며 OBB·depth oneDNN 우회가 빠진다.
- **저자·공식 인정·재현:** community 작성자의 수정에 maintainer가 RTX PRO 6000 Blackwell 환경에서 fallback을 재현했다. 동일 FP32 export, 640, batch 1로 DOTAv1 val 전체 458장과 NYU Depth V2 val 전체 654장을 비교했다.
- **보고된 결과:** YOLO26n OBB mAP50–95는 0.072092→0.357689, depth RMSE는 0.551806→0.546539. n/s/m/l/x 모두 개선됐다고 보고했다. 정상 CUDA 13.0 GPU wheel과 명시적 CPU 대조군은 점수가 같았다. 정상 GPU의 dota8·depth8 수치를 전체 dataset 결과와 직접 비교하지 않는다.
- **비용:** EPYC 9655의 8개 core, 다섯 번 교대 fresh-process 실행에서 depth inference median은 49.7→84.9 ms, OBB는 32.7→35.4 ms다. 공유 host 측정이며 GPU latency가 아니다.
- **진단 → 가설:** 요청 상태를 실제 실행 상태로 취급한 분기 오류다. CPU 연산의 수치 오류 원인은 전일과 같지만, 장치 fallback 때문에 안전장치가 적용되지 않았다.
- **최소 개입·실험:** base `c5f18da4e1c069d7c527a52ee3bfefe095b89f9e`, merge `8e593ffc89c1265c38d40617731a08c706be635e`를 고정한다. CPU/GPU wheel × 요청 cpu/0 조합에서 실제 `use_gpu`, oneDNN·제거 pass, raw output hash를 기록한다. CUDA가 없는 host의 `device=0` 거부도 대조한다. 같은 export의 명시적 CPU와 fallback을 우선 비교하고 정상 GPU를 음성 대조군으로 둔다.
- **GO/KILL:** fallback이 명시적 CPU와 같은 pass·출력을 사용하고 정상 GPU가 보존되면 GO. 요청 문자열만 맞췄거나 정확도 개선을 GPU 가속으로 설명하면 KILL.
- **기존 주장과 충돌·한계:** `device=0` 로그만으로 GPU 실행·CPU 수정 적용 여부를 증명할 수 없다. Paddle upstream 자체의 수정이나 모든 장치의 해결을 확인한 것은 아니다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **4/5** · 연구 아이디어 가치 **4/5**.

## 오늘의 실패 패턴 3개

1. **AP가 놓치는 계약 위반:** 중복 box·class 순서·후처리 정밀도 문제는 평균 AP가 거의 변하지 않아도 존재한다.
2. **출력 표현 사이의 수치 간섭:** 서로 다른 범위의 출력을 하나의 quantization scale에 묶으면 특정 task가 다른 task의 정밀도를 잠식한다.
3. **요청과 실제 상태의 불일치:** 장치 선택과 evaluator 이름만으로 실행 경로·평가 조건을 추정하면 수정 적용과 비교가 어긋난다.

## 논문 아이디어로 연결 가능한 빈틈

**조사자의 추론:** “동일한 의미의 출력이 serialization·dtype·class 순서에 따라 얼마나 달라지는가?”를 metamorphic audit로 연구할 수 있다. 고정 raw prediction에서 prompt 순서·좌표 단위·dtype·출력 packing만 바꾸고, 중복률·count error·작은 객체 AP·latency를 측정한다. encoder를 바꾸기 전에 출력 계약의 취약점을 분리하는 접근이다.

알려진 버그 하나의 수정은 novelty가 부족하다. 여러 segmentation·grounding wrapper와 export backend에서 같은 진단이 반복되고, 수치 오차가 downstream 피해로 이어지는 조건을 예측해야 한다. GO는 여러 시스템에서 재현되는 메커니즘과 작은 개입의 유효 범위 확인이다. KILL은 특정 구현 한 줄의 회귀 테스트로만 끝나는 경우다. 음성 결과도 “AP 저하 없는 출력 계약 위반의 범위”를 제한하는 근거가 된다.

## 직접 재현해볼 최소 실험

첫 순위는 **CPU NMS 계약 검사**다. 공식 issue의 두 box 예제에 class·좌표 단위·dtype·순서 대조군을 추가한다. weight 다운로드 없이 산술 실패와 keep index를 먼저 검증할 수 있다. 수정판에서도 class 0 잔여 IoU가 0.702로 보고됐으므로 모든 출력을 엄격히 0.7 이하로 만든다고 가정하지 않고 FP16 원출력·좌표 변환의 잔여 오차도 기록한다.

다음은 고정 raw output의 reciprocal scaling·INT8 오차 검사, 마지막은 Paddle 실제 장치 matrix다. 모든 실행은 코드·dependency·evaluator revision, weight·입력·prediction·calibration hash, dataset revision·split, backbone·pretraining·외부 데이터·해상도·TTA·hardware·precision·batch·compute budget을 기록한다. 미확인 조건은 미확인으로 둔다. 위 실험과 연구 방향은 제안이며 이번 실행의 측정 결과가 아니다.
