## 1. VLMEvalKit — 로그 설정 독립화와 기본 채점 변경을 함께 본다

**실제 변경.** commit `79140a6eaff749f6298cf27e6907f0e68b778819`는 `can_infer_option`의 긴 A 답변 guard를 `verbose` 조건 밖으로 옮겼다. 이전에는 환경변수가 없으면 통과하던 경로가 있었고, 문자열 `VERBOSE=0`도 참으로 취급됐다. 수정 후 `0`, `false`, `no`, `off` 등은 로그를 끄며, guard의 거부 여부는 로그 설정과 무관하다. [공식 diff](https://github.com/open-compass/VLMEvalKit/commit/79140a6eaff749f6298cf27e6907f0e68b778819).

**코드·테스트 대조.** 단독 `A`, `The answer is A` 같은 명시적 최종 행은 앞단 parser에서 인정된다. 반면 테스트의 `The answer is A because it looks like a horse.`와 `Looking at the image, the answer is A`는 가능한 관사·긴 답변으로 거부한다. 따라서 “모든 명시적 A를 그대로 보존하는 수정”은 아니다. 장황한 정답 A의 recall을 희생할 가능성도 확인해야 한다. `can_infer`는 option 추출 실패 후 선택지 텍스트 매칭을 시도하므로, option 단계 거부가 모든 호출에서 최종 오답을 뜻하지도 않는다. [전체 구현](https://github.com/open-compass/VLMEvalKit/blob/79140a6eaff749f6298cf27e6907f0e68b778819/vlmeval/utils/matching_util.py), [회귀 테스트](https://github.com/open-compass/VLMEvalKit/blob/79140a6eaff749f6298cf27e6907f0e68b778819/tests/test_matching_option_boundaries.py).

**maintainer 설명과 수치의 지위.** commit은 MMBench dev mini에서 Qwen2.5-VL-7B-Instruct의 기대 기준을 42/55에서 41/55로 바꿨다고 설명하고 CI workflow의 baseline도 수정한다. 이는 저장소의 기대값 변경과 maintainer 진술이다. 이번 실행에서 CI 로그·해당 응답·동일 모델 설정을 독립 재현하지 않았으므로 새 측정치나 전체 MMBench 하락으로 제시하지 않는다.

**호출 경로.** MCQ의 `extract_answer_from_item`은 `can_infer`를 먼저 실행한다. 해결되지 않았고 judge가 없으면 `exact_matching` 경로에서 Z를 반환하며, judge가 있으면 추가 매칭을 시도한다. parser 변경은 정확도뿐 아니라 judge 이관률에도 영향을 줄 수 있다. [MCQ 호출 구현](https://github.com/open-compass/VLMEvalKit/blob/79140a6eaff749f6298cf27e6907f0e68b778819/vlmeval/dataset/utils/multiple_choice.py).

**관측 → 진단 → 기전.** 관측은 로그 옵션과 정답 판정의 결합이다. 진단은 모델 차이로 보이던 변화에 실행 환경이 섞일 수 있다는 것이다. 새 guard는 환경 의존성을 없애면서 기본 채점도 더 보수적으로 만든다. “버그 수정이므로 점수가 올라야 한다”는 가정은 성립하지 않는다.

**가설 → 최소 개입 → 실험.** 동일 raw 응답·선택지·정답을 고정하고 이전/수정 commit에 `VERBOSE` 미설정·1·0·false를 각각 적용한다. option 추출, 텍스트 fallback, 미해결, 최종 hit를 따로 기록한다. A/B/C/D와 짧은/긴 답변 subgroup을 나누고, 불일치는 실제 최종 결론과 대조한다.

**GO/KILL.** 수정본에서 로그 설정 간 판정이 같아지고 실제 관사 오인이 줄면 migration 근거가 된다. 정답 A 산문의 손실이 나타나면 손실을 함께 보고한다. 저장 응답 없이 fixture만 사용하면 구현 검증에 한정하고 benchmark 개선량은 주장하지 않는다. GPU와 신규 judge 호출 없이 시작할 수 있다.

## 2. Omni-DuplexEval — 질문의 시각과 judge가 보는 시각 증거를 고정한다

**실제 변경 시점.** lmms-eval commit `573a89504132afb6371a43de526b52ed8151b004`가 real-time description과 proactive reminder 평가 adapter를 추가했다. 이는 이번 창의 통합이며 benchmark 자체의 최초 발표가 아니다. [공식 변경](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/573a89504132afb6371a43de526b52ed8151b004).

**입력 교차검증.** 공식 데이터 카드는 `question_audio`가 영상 전체 길이와 정렬돼 있고 PR 질문은 임의 시각에 나타날 수 있다고 명시한다. adapter는 질문을 영상 앞에 별도 재생하는 대신 원래 영상 음성과 같은 시각에 합산한다. 따라서 질문 선행 노출 여부가 temporal reasoning 평가 조건에 포함된다. split 이름만 같다고 같은 입력은 아니다. [공식 데이터 카드](https://huggingface.co/datasets/Hothan/Omni-DuplexEval), [adapter 설명](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/omni_duplexeval/README.md).

**채점 교차검증.** 원본은 temporal sensitivity와 content accuracy를 분리한다. adapter의 temporal 평균은 relevant로 판정된 문장 점수에 기반한다. 모든 문장·모든 실패를 일률적으로 0으로 평균하는 지표가 아니다. content 호출 실패·읽을 수 없는 점수는 0으로 처리한다. PR 역시 별도 성공 판정 경로다. 오류율·relevance 비율을 숨긴 채 지표 이름만 비교하면 안 된다. 확인한 원본 파일 blob은 RTD `b529dd02ecaaa68f0e00468ce290e36d7201993f`, PR `30564b42afe4aa0d764569e0a30f308bfb135d51`이다. [원본 RTD](https://github.com/OpenBMB/Omni-DuplexEval/blob/main/real_time_description.py), [원본 PR](https://github.com/OpenBMB/Omni-DuplexEval/blob/main/proactive_reminder.py), [adapter 전체 구현](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/omni_duplexeval/utils.py).

**새 비교 위험.** content judge의 기본 auto 모드는 local-path video part를 보낸다. endpoint가 HTTP 400/415/422로 거부하고 frame 요청이 성공하면 8개 균등 추출 프레임으로 전환한다. 한 번 영상 요청이 수락되면 이후에는 video를 유지한다. 요청 수락 자체가 endpoint의 실제 영상 독해를 입증하지는 않는다. transient 오류는 재시도 대상이며 그 이유만으로 입력 모드를 바꾸지는 않는다.

**추론.** 짧은 위험 이벤트는 8프레임 관측에서 빠질 수 있다. 영상 입력 run과 frame fallback run은 **not strictly apples-to-apples**다. 반대로 점수가 낮다는 이유만으로 모델의 영상 이해 실패라고 단정하면 endpoint·입력 처리 실패를 혼동할 수 있다.

**가설 → 최소 실험.** 먼저 한 샘플의 질문 파형이 annotated 시각에 들어오는지와 preamble 보정 후 chunk 시각을 감사한다. 보존된 영상·응답이 있다면 content 입력을 auto에 맡기지 말고 video/frames로 명시해 judge·prompt를 고정한 paired 비교를 설계한다. judge 호출이 필요한 단계는 이번 실행에서 수행하지 않았다.

**GO/KILL.** 사건을 담은 프레임의 포함 여부와 판정 차이가 연결되면 frame budget 민감도 연구로 진행한다. endpoint가 local video를 읽는지 확인되지 않으면 video-mode 점수의 의미 해석을 보류한다. 합성 음성·영상은 정렬 구현 검사에만 쓰고 실제 모델 성능 근거로 사용하지 않는다.

## 3. Full-Duplex-Bench — 동일 이름 아래 시간 근사와 분모 차이가 있다

**변경과 범위.** 같은 lmms-eval commit은 FDB v1.5의 interruption·backchannel·talking-to-other·background-speech adapter를 추가한다. 순수 음성 상호작용 평가로, 영상 능력의 직접 근거는 아니다. 위 영상 adapter와 같은 duplex wrapper를 공유하므로 시간·실패 처리의 비교 대상으로 선정했다. v1.5 자체를 이번 주 새 benchmark로 부르지 않는다. [adapter 설명](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/full_duplex_bench/README.md), [원본 v1/v1.5](https://github.com/DanielLin94144/Full-Duplex-Bench/tree/main/v1_v1.5).

**사실과 maintainer 명시 차이.** 원본 pipeline은 생성 음성에 ASR 단어 시각을 붙인다. adapter는 모델이 한 초 chunk에 출력한 텍스트의 단어를 그 구간에 균등 배치한다. 원본의 stop/response latency도 계산하지 않는다. 이는 adapter 문서가 인정한 편차이며 원 논문 표와 직접 비교할 수 없다.

**judge 교차검증.** 원본 `eval_behavior.py`와 adapter는 기본 judge `gpt-4o-2024-08-06`, system/user payload 및 seed 기반 재시도 구조를 공유한다. 다만 원본 반복은 무제한이고 adapter는 기본 최대 5회다. 이번 실행은 해당 API의 현재 이용 가능성을 시험하지 않았다. 원본 확인 blob은 `f00ae67d8a5ae946a56872e40cb8e88d5e24f850`이다. [원본 evaluator](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/main/v1_v1.5/evaluation/eval_behavior.py), [adapter scorer](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/full_duplex_bench/utils.py).

**metric와 실패 분모.** adapter는 C-tag 비율 외에 자체 요약 지표 `fdb_expected_behavior`와 `fdb_scoring_failed`를 제공한다. 생성 오류·재시도 후 judge 실패는 다른 점수에 None을 반환하고 집계에서 제외한다. 빈 정상 출력과 명시적 생성 오류도 같은 취급이 아니다. key 부재·일부 인증/endpoint 오류는 run을 중단한다. 따라서 “실패는 모두 0” 또는 “모든 실패를 제외”라는 요약 모두 부정확하다.

**데이터 한계.** 자동 다운로드는 community mirror를 사용한다. 문서는 원본과 같은 v1.5 archive라고 설명하지만 이번 실행에서 archive hash를 대조하지 않았다. 원본 release 복사본과 mirror의 동등성은 검증할 항목으로 남긴다.

**진단·가설.** 시간 근사가 overlap 전후 의미 구간의 위치를 바꾸거나, 채점 실패가 어려운 표본에 몰리면 동일 모델에서도 C-tag와 성공률이 달라질 수 있다. 이는 코드에서 도출한 가설이며 발생 빈도는 미측정이다.

**최소 실험과 GO/KILL.** 출력 음성·chunk 로그가 함께 보존된 샘플에 한해 ASR 단어 시각과 균등 배치 시각을 paired 비교하고 overlap 경계 전후의 차이를 먼저 찾는다. 이후 같은 judge로 C-tag를 비교한다. 동시에 전체 수·채점 성공 수·실패 사유를 기록한다. 경계 판정과 label 차이가 연결되면 진행하고, 생성 음성이 없으면 원본 시간 정밀도와의 동등성 주장은 중단한다.

## 동조건 비교와 미확인 항목

오늘 확인한 것은 parser 수정과 adapter 추가다. 새로운 backbone·pretraining·external data·input resolution·TTA·reasoning effort·frame/context/compute budget을 통일한 모델 비교는 확보하지 않았다. dataset revision과 정확한 sample ID, evaluator commit, prompt, decoding, judge snapshot·API wrapper·입력 모드를 저장해야 한다.

MiniCPM duplex wrapper는 미디어를 chunk별로 offline 재생한다. 이 결과로 실제 서비스의 wall-clock latency를 입증할 수 없다. FDB의 근사 단어 시각, Omni의 content 입력 모드, judge 실패 분모가 다르면 **not strictly apples-to-apples**다. 공식 테스트는 검토했지만 실행하지 않았으며, 이번 수정으로 실제 순위가 얼마나 변하는지는 미확인이다. [duplex wrapper](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/models/simple/minicpm_o_45_duplex.py).

## 오늘의 benchmark signal 3개

1. **로그 설정도 채점 provenance다.** 환경 독립화 여부와 기본 판정 변경을 별도로 감사한다.
2. **시간 정렬과 judge의 시각 증거를 평가 조건으로 기록한다.** 질문 노출 시각·preamble·video/frames를 함께 고정한다.
3. **성공률에는 분모와 시간 정밀도가 필요하다.** 채점 성공 표본 비율과 실제 시간 측정을 병기한다.

## 내 연구에 바로 연결되는 포인트

- 해양·CCTV 안전 VQA는 “위험을 맞혔는가”와 “위험 시점에 반응했는가”를 분리한다. 균등 프레임에 짧은 사건이 들어왔는지도 확인한다.
- Answer–Region Gap에서는 A 답변의 형식 손실을 grounding 실패로 분류하지 않도록 parser 불일치를 먼저 제거한다.
- video memory 연구는 chunk 순서 성능과 실제 처리 지연을 별도 측정한다. offline replay 성능을 실시간 서비스 능력으로 확대하지 않는다.
- **오늘 가장 먼저 할 실험:** 저장된 MCQ 응답의 이전/수정 parser × `VERBOSE` 설정 감사. 새 모델 학습·GPU·유료 judge 호출 없이 시작할 수 있다.
- 이 보고서의 실험·GO/KILL은 제안이다. 실행 결과나 미확인 향상 수치는 만들지 않았다.
