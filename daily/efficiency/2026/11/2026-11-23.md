## 1. Vulkan — 연산량보다 CPU 왕복이 병목인가

**사실:** #32735는 `8a97fa98ab1a454709bbf5ac979661feaeadec40`으로 병합됐다. non-contiguous SCALE의 지원 거부를 없애고 shader가 source/destination stride를 사용하게 바꿨다. [구현 diff](https://github.com/ggml-org/llama.cpp/pull/32735/files)

**저자 측정:** Radeon AI PRO R9700, Inkling-2-Mini-UD-Q8_K_XL에서 master `b019be0c`→수정 `0ea4ffd0`의 pp512는 507.3→1604.8 tok/s, tg128은 19.1→53.8 tok/s였다. graph split은 194→2로 보고됐다. [측정 원문](https://github.com/ggml-org/llama.cpp/pull/32735)

**비교 조건:** `-ngl 99 -fa 1 -ctk q8_0 -ctv q8_0 -p 512 -n 128 -d 0,16384 -r 3`. weights는 Q8_K_XL, KV는 q8_0이다. 별도 batch/ubatch·warm-up·OS·driver/compiler version·power mode는 미확인이다. coding task 완료는 저자의 smoke test이며 정량 품질 동등성 검증은 아니다. CUDA·다른 AMD GPU와는 **not strictly apples-to-apples**다.

**진단→가설:** strided view의 지원 판정이 매 layer CPU fallback을 유발해 왕복·동기화가 누적됐을 수 있다. FLOPs 감소가 원인이라는 근거는 없다.

**최소 실험·GO/KILL:** 같은 장치·weight·driver에서 parent/merge를 비교하고 SCALE 배치 위치, split 수, 전송 시간, PP/TG와 출력 오차를 기록한다. split·전송 감소와 성능 회복이 함께 재현되면 GO. 다른 backend의 저하까지 해결됐다고 주장하는 것은 KILL.

## 2. Metal — concat 대역폭 개선이 전체 지연을 얼마나 바꾸는가

**사실:** #32824는 미병합이며 head는 `84519ad7434ac416db596b45433d0530e5b86c8c`다. 넓은 row의 vector copy와 threadgroup 배치를 조정한다. [diff](https://github.com/ggml-org/llama.cpp/pull/32824/files)

**저자 측정:** F16, `a=[512,1,256,2]`, `b`는 `[640,1,8192,2]`의 strided view, `dim=2`, 5회 median에서 0.333→0.185 ms, 104→187 GB/s였다. CONCAT 정합성 시험은 236/236 통과했다고 보고한다. [조건·결과](https://github.com/ggml-org/llama.cpp/pull/32824)

**비교 조건:** local Metal backend다. PR의 AI 작업 메타데이터에는 Mac Studio M5 Ultra 256GB가 있지만 측정표와 동일 환경인지 별도 확정하지 않았다. benchmark baseline SHA·macOS/Metal/compiler version·warm-up·추론 batch는 미확인이다. 이는 명시된 tensor shape의 연산자 대조이며 모델 end-to-end·다른 Mac 비교는 **not strictly apples-to-apples**다.

**진단→가설:** FLOPs가 거의 없는 복사 연산도 실행 배치·정렬 때문에 대역폭을 충분히 쓰지 못할 수 있다. 전체 추론 이득은 concat의 원래 시간 비중에 제한된다.

**최소 실험·GO/KILL:** 동일 Mac에서 aligned/unaligned·transposed·작은/큰 row를 sweep하고 scalar/vector 경로의 정합성과 시간을 대조한다. 실제 모델 trace에서 concat 비중과 전체 p95도 측정한다. 병목 구간과 전체 지연이 함께 줄면 GO. microbenchmark 배수를 모델 가속률로 쓰면 KILL.

## 3. CUDA quantized indexer — 작은 cache와 적은 traffic은 다르다

**사실:** #32795는 미병합이며 head는 `bcc592ebdc7f75a8dfbe42a8c96ca2e02b697e5c`다. fused sparse indexer에서 quantized K의 F32 cast를 생략한다. [한 줄 diff](https://github.com/ggml-org/llama.cpp/pull/32795/files)

**저자 측정:** RTX 4000 Ada 4장·tensor split·np1·context 65k·q8_0 KV·cold boot 조건에서 약 48k prompt의 PP는 265.9→304.6 tok/s, TG는 34.79→39.86 tok/s였다. 약 7k prompt에서는 각각 약 2% 차이였다. 저자는 VRAM은 변하지 않았다고 명시한다. [측정·품질 원문](https://github.com/ggml-org/llama.cpp/pull/32795)

**비교 조건:** baseline `e6d624b9a`, 동일 prompts/build flags, Coder IQ2_XXS 계열이다. 정확한 CUDA/driver·batch/ubatch·warm-up·반복 오차는 미확인이다. F32 vec→half MMA로 산술 경로가 바뀌므로 bit-identical하지 않다. 16k greedy 예시의 출력 차이를 인정한다. 서로 다른 382B 모델의 PPL을 위 속도표와 합치면 **not strictly apples-to-apples**다.

**진단→가설:** 긴 context의 반복 cast와 indexer 읽기 traffic이 병목일 수 있다. resident allocation이 그대로여도 지연은 줄어든다.

**최소 실험·GO/KILL:** q8_0/f16 × parent/patch를 고정 context sweep으로 대조한다. cast traffic·kernel 선택·PP/TG·peak VRAM과 top-k 선택/PPL을 함께 본다. 품질 허용치 안에서 개선이 재현되면 GO. 속도만 보고 품질 동등성을 선언하거나 다른 backend에 바로 적용하면 KILL.

## 4. Android — native GPU offload가 모든 구간을 이기지는 않는다

**사실:** #32261은 미병합이다. 11/22 commit `acbf0c12c9d0c5e3e39b0b5f4fc766fb50079998`과 새 측정이 추가됐다. 유지보수자가 이전 Vulkan 1.1 장치 사용을 지적한 뒤 Vulkan 1.3.305 장치 결과가 게시됐다. [PR·댓글](https://github.com/ggml-org/llama.cpp/pull/32261)

**저자 대조:** Mali-G610 MC2, A55 4개+A78 4개, driver 54.1.0, build `acbf0c12c`, Qwen3.5 0.8B Q4_K_M, 4 threads에서 `-ngl 99`의 pp512/tg128은 17.78/4.02 tok/s, `-ngl 0`은 18.09/2.57 tok/s였다. CPU control 행도 backend 열은 Vulkan으로 표시되므로 실제 대조는 `ngl` 설정으로 식별해야 한다. [11/22 측정 댓글](https://github.com/ggml-org/llama.cpp/pull/32261#issuecomment-)

**비교 조건:** 동일 build·모델 이름·thread 수지만 weight hash·Android/Termux/compiler version·KV precision·batch·warm-up·열/전력 상태는 미확인이다. 다른 SoC나 CPU/GPU 자원량을 같게 맞춘 효율 비교는 **not strictly apples-to-apples**다.

**진단→가설:** 작은 GPU의 offload 이득은 decode와 prefill에서 다르며 UMA·전송·kernel overhead의 비중에 좌우될 수 있다.

**최소 실험·GO/KILL:** 같은 기기의 thermal steady state에서 CPU affinity와 clocks를 기록하고 ngl 0/부분/전체를 교대로 반복한다. PP/TG·TTFT·출력 정합성·RSS를 측정한다. decode 위주 목표에만 조건부 GO. GPU 지원만으로 prefill·energy 개선까지 선언하면 KILL.
