## 2. Paddle CPU: 런타임 최적화가 OBB와 depth의 의미를 바꿈

**확인 사실:** #27367은 metadata를 먼저 읽고 CPU OBB에서 `inplace_pass`, depth에서 `onednn_placement_pass`를 제거하도록 변경했다. GPU 경로는 변경하지 않는다. upstream #79984·#79985는 조회 시 open이며 댓글이 없었다. [공식 수정](https://github.com/ultralytics/ultralytics/pull/27367/files) · [검증 조건·결과](https://github.com/ultralytics/ultralytics/pull/27367) · [OBB 최소 재현](https://github.com/PaddlePaddle/Paddle/issues/79984) · [보간 최소 재현](https://github.com/PaddlePaddle/Paddle/issues/79985)

- **실패 조건·모델·dataset·configuration:** Linux x86-64 AMD EPYC 9655, Paddle 3.2.2와 PIR `.json` 모델, 기본 oneDNN 활성화. 작성자는 3.0.0·3.1.1에서도 재현했다고 보고했다. YOLO26n/YOLO11n OBB는 dota8, YOLO26n-depth는 depth8, val batch=1로 비교했다.
- **공식 인정과 community 수준:** Ultralytics maintainer glenn-jocher가 작성·병합한 수정과 직접 upstream 제보가 근거다. Paddle maintainer의 인정·수정 또는 독립 community 재현은 확인하지 못했다. 자동 리뷰 승인은 별도 수치 재현으로 세지 않는다.
- **메커니즘에 관한 작성자 보고:** OBB에서는 layout 변환의 공유 buffer를 in-place `cos`·`sin`이 덮어써 angle이 `sin(cos(angle))`처럼 변한다. depth에서는 oneDNN bilinear interpolation이 `align_corners=True`를 반영하지 않는다.
- **최소 재현 근거:** upstream은 OBB를 concat/cos/sin의 작은 그래프로, depth를 보간 한 연산으로 축소했다. depth 예제는 oneDNN과 dygraph 사이 최대 오차 1.2983, oneDNN off에서는 0을 보고했다. 모두 원문 작성자의 측정값이다.
- **정확도와 비용:** 작성자 표에서 YOLO26n-OBB dota8 mAP50-95는 ONNX/main/수정이 0.894/0.383/0.894, depth RMSE는 0.205/0.260/0.205다. 같은 표의 depth latency는 main 82.9→수정 148.2 ms다. 소규모 dataset 결과이며 전체 DOTA·depth benchmark 성능으로 일반화하지 않는다.
- **진단 → 가설:** 학습된 표현의 손실보다 런타임 최적화 pass가 tensor alias·보간 계약을 바꾼 문제다. 영향을 받는 pass만 제거하면 전체 oneDNN 비활성화보다 기능을 좁게 복구할 수 있다.
- **최소 실험:** base `4a5ad7ca78f4b70147b6167c0b2eb5edd3d11c6d`, merge `fa3e7f8979f8a5ee65a3d3109d389df83f6dd640`를 고정한다. CPU에서 upstream 두 합성 모델의 default/task별 pass off/oneDNN off를 비교한다. OBB 중간 angle tensor의 값·공유 여부와 depth 출력 오차를 기록하고 `align_corners=False`를 음성 대조군으로 둔다. 이후 동일 weight·입력·전처리·thread 수로 실제 모델의 raw output과 latency를 대조한다.
- **GO/KILL:** 최소 연산 오차와 실제 raw output 차이가 함께 줄고 무관한 task가 보존되면 GO다. AP만 좋아지고 연산 동치가 복구되지 않으면 원인 설명은 KILL한다.
- **기존 주장과 충돌·한계:** export 성공과 CPU 실행 성공은 수치 동치를 보장하지 않는다. Intel CPU·Windows·NVIDIA GPU는 미검증이고 ARM64 실제 실행도 확인되지 않았다. 다른 장치의 속도와는 not strictly apples-to-apples다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **4/5**. 신뢰도는 구체적 재현 코드가 있으나 독립 재현이 부족함을 반영한다.

## 3. AP 계산: 완벽한 예측의 0.995와 evaluator 변경에 따른 가짜 성능 향상

**확인 사실:** #27368은 보간 후 사다리꼴 적분을 COCO의 101 recall threshold에서 precision envelope를 선택해 평균하는 방식으로 바꾸는 open PR이다. Diff와 자동 리뷰는 확인했지만 사람 maintainer의 독립 재현·승인·병합은 확인하지 못했다. [공식 PR·작성자 측정](https://github.com/ultralytics/ultralytics/pull/27368) · [계산 코드와 회귀 테스트](https://github.com/ultralytics/ultralytics/pull/27368/files)

- **실패 조건·모델·dataset·configuration:** 최대 recall이나 중복 recall이 평가 threshold와 일치하는 `compute_ap` 입력. 작성자는 YOLO26n coco8·coco128, YOLO26n-OBB dota8 및 mask·pose 경로를 검사했다.
- **작성자 주장·재현 근거:** 완벽한 검출은 AP 0.995 대신 1.0이어야 한다. 같은 `predictions.json`, bbox, max_det=100을 pycocotools로 평가한 coco8 mAP50-95는 기존 0.6693, 수정 0.6750, COCOeval 0.6750이었다. coco128은 0.4834/0.4865/0.4867로 작은 잔여 차이가 있다. 전체 evaluator 동치를 입증한 표가 아니다.
- **공식 인정·community 수준:** 테스트 두 개와 작성자의 실행 보고, 자동 승인만 확보했다. 새로운 모델의 성능 개선이나 독립 community 재현으로 해석하지 않는다.
- **진단 → 메커니즘:** 중복 recall에서 `np.interp`가 뒤쪽 precision 또는 sentinel을 선택하고 적분 규칙도 COCO threshold 평균과 다르다. 수정안은 `searchsorted(..., side="left")`로 첫 도달 지점을 선택한다.
- **가설 → 최소 개입:** 예측을 바꾸지 않고 scoring만 교체해 생기는 AP 변화는 학습 효과가 아니라 평가 프로토콜 효과다.
- **최소 실험:** base `fa3e7f8979f8a5ee65a3d3109d389df83f6dd640`, head `145655440e345c180d774781130f1a522c0eaccb`를 고정한다. 완벽한 검출, FP→TP, TP 뒤 FP, 도달하지 못한 recall threshold, 빈 입력을 포함해 기존·수정·COCO reference를 비교한다. 실제 비교는 predictions hash·IoU matching·category filtering·max_det·area range를 고정한다.
- **GO/KILL:** 합성 기대값과 reference가 일치하고 고정 예측의 차이를 설명하면 계산 수정 GO다. 잔여 차이가 남으면 matching·category·area 처리까지 진단한다. scoring 변경으로 얻은 AP를 architecture gain으로 주장하면 KILL한다.
- **기존 주장과 충돌·한계:** 동일 모델·dataset이라도 evaluator revision이 다르면 not strictly apples-to-apples다. 전일 #27348의 AP 반환값 누락과는 다른 문제다. pycocotools·dataset revision, 해상도·TTA·seed 등 전체 조건은 본문만으로 확인되지 않았다.
- **점수:** 심각도 **3/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **4/5**.

## 논문 아이디어로 연결 가능한 빈틈

**조사자의 추론:** “추적기의 좌표 정합성 복구는 언제 실제 identity 성능을 해치는가?”를 진단 연구로 만들 수 있다. exact/estimated GMC, 가림 길이, 카메라 회전, cached velocity 정합성을 분리하고 고정 detection으로 association 효과만 측정한다. 합성 정합성·실제 IDF1·HOTA가 어디서 갈라지는지가 핵심 결과다.

알려진 구현 버그 하나를 고치는 것만으로 novelty는 부족하다. 여러 tracker·서로 다른 카메라 조건에서 원인이 반복되고 작은 개입의 적용 범위를 예측해야 한다. 결과가 음성이어도 “상태 정합성은 필요하지만 성능 개선의 충분조건은 아니다”라는 경계를 제시할 수 있다. 실제 성능 악화의 원인을 현재 근거만으로 GMC noise라고 확정하지 않는다.

## 직접 재현해볼 최소 실험

첫 순위는 **CPU AP scoring 계약 검사**다. weight 다운로드 없이 원문 두 회귀 입력과 추가 경계 입력을 비교하고, 이후 작은 고정 prediction JSON으로 외부 evaluator와 대조한다. AP 변화가 evaluator에서만 발생함을 먼저 확인한다.

다음은 Paddle 최소 연산 두 개, 마지막은 cached detection 기반 tracking 실험이다. CPU 검사부터 시작할 수 있지만 실제 tracking detection 생성 비용은 별도다. 모든 실행에서 코드·dependency·evaluator revision, 입력·weight·prediction hash, 명령, dataset revision·split을 기록한다. 모델 성능 비교에서는 backbone·pretraining·외부 데이터·해상도·TTA·compute budget도 고정한다. 이번 보고서의 실험들은 제안이며 실행 결과가 아니다.
