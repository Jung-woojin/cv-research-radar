## 1. MTEB 2.27.25 — 낮은 시각 이해 점수의 원인이 정답 이미지 배선일 수 있다

**정확한 버전.** [공식 tag metadata](https://api.github.com/repos/embeddings-benchmark/mteb/git/tags/ecc2e6b701088111967b364023e3322d58f480df)는 commit `9c5cbdae52f3139321488b77841480243333bd73`을 가리킨다. 발행은 27일 13:32:17 KST다. tag signature는 unsigned이며, 이를 artifact 손상 증거로 해석하지 않는다.

**사실 — 데이터와 평가 코드.** [PR #5957](https://github.com/embeddings-benchmark/mteb/pull/5957)은 27일 04:23:44 UTC merge됐다. 이미지 ID가 파일의 정렬되지 않은 순서로 부여돼 caption의 정답 ID가 다른 프레임을 가리키던 문제를 다룬다. [공식 diff](https://github.com/embeddings-benchmark/mteb/pull/5957/files)는 원본 파일의 숫자 순서에 맞춰 corpus를 재구축하는 script와 새 task를 추가한다. 기존 task는 유지하고 `superseded_by`로 v2를 안내한다.

정확한 새 dataset pin은 다음과 같다.

- `ImageCoDe.v2`: `mteb/imagecode-multi` revision `b343a10c1d029b71f0a281a7027588268bc59ace`
- `ImageCoDeT2IRetrieval.v2`: `mteb/imagecode` revision `55f8bae423bdcba7de14017e3f3f66130ea19d87`

새 image-text pair task와 기존 task는 공통 loading 함수를 사용한다. 따라서 package만 올리고 옛 task 이름을 유지하면 새 corpus를 평가한다고 보장할 수 없다. task 이름·dataset revision·결과 cache key를 함께 기록해야 한다.

**저자 주장과 논문 간극.** PR 작성자는 CLIP ViT-B/16을 이용한 전후 검증과 원본 corpus 재구축의 byte-level 일치를 보고한다. 이는 개발자 검증이며 이번 실행의 측정이 아니다. 기존 낮은 점수 일부가 모델의 compositional reasoning 실패보다 이미지–정답 대응 오류에서 왔을 수 있다는 신호다. 이를 모든 ImageCoDe 결과나 원 논문 전체의 오류로 확대하지 않는다. 원 논문과의 preprocessing·split·checkpoint 완전 일치도 이번에 확정하지 않았다.

**라이선스·공개물·설치.** [고정 pyproject](https://github.com/embeddings-benchmark/mteb/blob/9c5cbdae52f3139321488b77841480243333bd73/pyproject.toml)상 code는 Apache-2.0, task metadata상 dataset은 CC-BY-SA-4.0이다. 신규 model weight 배포는 아니다. pin 후보는 `mteb[image]==2.27.25`이며 Python ≥3.11,<3.15, datasets ≥2.19.0, torch ≥2.0, transformers ≥4.40,<6 등의 범위 의존성을 실제 lock으로 고정해야 한다. package pin만으로 전체 환경을 고정한 것은 아니다. corpus revision은 확인했지만 다운로드 checksum·attestation 검증은 미실행이다.

**활동·자원.** 공식 Issue #5499를 해결하는 merged PR을 확인했다. benchmark 목록의 v1→v2 전환 범위는 PR에서도 후속 질문으로 남아 있으므로 모든 leaderboard가 이동했다고 단정하지 않는다. CPU manifest·정답 대응 감사에는 GPU가 필요 없다. CLIP 전체 평가의 최소 VRAM·소요 시간은 미확인이다.

**추론 — 진단 → 가설 → 10~30분 최소 실험 계획.**

1. 준비된 소규모 원본 이미지 집합에서 숫자 파일 순서, corpus ID, qrels 정답을 나란히 확인한다. 재학습은 하지 않는다.
2. 구·신 revision에 동일 caption·동일 이미지 집합을 대응시켜 잘못 연결된 정답의 변화만 센다. ID 문자열이 같다는 이유로 이미지가 같다고 가정하지 않는다.
3. 다음 단계에서 고정 CLIP checkpoint·processor·resolution·precision으로 paired subset 평가를 한다. corpus가 바뀌면 image embedding cache도 content 기준으로 무효화한다.

**GO:** 이미지 내용과 정답 연결을 먼저 감사한다. **KILL:** 데이터 교정 후 점수 상승을 새 representation의 성능 향상으로 보고하지 않는다. v1/v2 corpus가 다른 비교는 **not strictly apples-to-apples**다.

## 2. LingBot-Map 2.0 — 공개 causal base로 GCR 성능을 재현할 수 있는가

**새 사건의 범위.** [27일 commit](https://github.com/Robbyant/lingbot-map-v2/commit/078b54485830c74ab1d3797667073e3e8353f3b9)은 README에 `(without GCR)`를 추가한다. 정확한 code pin은 `078b54485830c74ab1d3797667073e3e8353f3b9`, package metadata는 `lingbot-map2-streaming 0.1.0rc1`이다. formal GitHub release 목록은 비어 있다. README의 초기 code 공개 news는 21일, benchmark 추가는 23일이다. **오늘의 채택 이유는 새 weight가 아니라 최근 공개 범위 명시 변경**이다.

**사실 — 논문 기능과 artifact 계약.** [고정 README](https://github.com/Robbyant/lingbot-map-v2/blob/078b54485830c74ab1d3797667073e3e8353f3b9/README.md)는 현재 저장소를 causal Online Streaming용 geometric base로 설명한다. [공개 config](https://github.com/Robbyant/lingbot-map-v2/blob/078b54485830c74ab1d3797667073e3e8353f3b9/configs/base-streaming.json)도 `training_mode: causal`이며 width 512, height 288을 지정한다. 공개 base를 technical report의 GCR 포함 결과와 동일 모델로 취급하면 안 된다.

config의 weight SHA256 선언은 `d3ae62a09d3caaeb0947c4372f6fb23a4c0e85304867fa9702948ba030310e27`이다. 이는 기대 hash metadata이며 실제 파일 검산 결과가 아니다. README는 paired config·weight와 접근 권한 있는 계정을 요구하고 모델 저장소가 private이라고 안내한다. 이번 Hub 조회는 해당 ID를 찾지 못했으므로 실제 public weight 접근 가능 여부와 immutable Hub revision은 확정하지 못했다. 모델이 존재하지 않는다고 단정하지 않는다.

**커뮤니티 제보.** [Issue #1](https://github.com/Robbyant/lingbot-map-v2/issues/1)과 [Issue #2](https://github.com/Robbyant/lingbot-map-v2/issues/2)는 27일 GCR weight·mixed-mode checkpoint의 공개 여부를 묻는다. 독립적인 정량 실패 재현은 아니다. 현재 범위 판단은 사용자 추측보다 공식 README의 명시를 근거로 한다.

**라이선스·설치·자원.** 저장소는 CC-BY-NC-4.0을 안내하고 third-party notices를 별도로 둔다. 1.0의 조건을 그대로 적용하지 않는다. [고정 pyproject](https://github.com/Robbyant/lingbot-map-v2/blob/078b54485830c74ab1d3797667073e3e8353f3b9/pyproject.toml)는 Python ≥3.10, torch ≥2.8와 FlashInfer 등을 요구한다. README recipe는 Python 3.11·torch 2.8.0/CUDA 12.8, BF16 가능 CUDA GPU를 안내한다. dependency 전체가 pin된 환경은 아니며 최소 GPU/VRAM은 미확인이다. 예제 dataset 링크와 benchmark 안내는 있지만 실제 파일 접근·전체 training data 공개는 검증하지 않았다.

**추론 — 진단 → 가설 → 10~30분 최소 실험 계획.**

1. CPU에서 config·loader가 요구하는 causal mode, hash, parameter key·shape의 계약을 먼저 정리한다.
2. 접근 권한과 weight가 이미 준비된 환경에서만 짧은 RGB sequence를 실행한다. frame manifest·입력 순서·keyframe 정책·해상도·precision을 기록한다.
3. GCR 포함 checkpoint·실행 경로를 확보하기 전에는 drift correction ablation을 계획 단계로 유지한다. base의 drift가 남는다는 사실만으로 논문의 GCR 기여를 반증할 수 없다.

**GO:** 공개 기능 범위와 loader 계약 감사. **KILL:** causal base 실행을 GCR 재현 완료로 표시하거나, 논문의 GCR 수치를 현재 artifact가 보장한다고 소개하지 않는다. checkpoint·memory policy가 다른 비교는 **not strictly apples-to-apples**다.

## 3. MTEB 2.27.26 — cleaning script 수정과 dataset 복구 완료를 구분

**정확한 버전.** [공식 release](https://github.com/embeddings-benchmark/mteb/releases/tag/2.27.26)는 28일 04:37:43 KST 발행됐다. [tag metadata](https://api.github.com/repos/embeddings-benchmark/mteb/git/tags/78c1f4c0034d047f05fc65f5237ba8bbdc088fd0)의 대상은 commit `78fca945999b4c981b399e21d3b9c92e5a3f5213`이며 unsigned다. ImageCoDe 교정과 별개의 script 오류다. CV 전용 사례는 아니지만 공통 평가 데이터 파이프라인의 실패 패턴으로 포함했다.

**사실 — 한 줄의 저장 대상.** [PR #6016 diff](https://github.com/embeddings-benchmark/mteb/pull/6016/files)는 `scripts/data/clean_and_update_tasks.py`에서 `ds["test"] = filter_leakage(...)`를 `ds[split] = filter_leakage(...)`로 바꾼다. loop가 현재 처리하는 평가 split에 결과를 되써야 하는데 항상 test에 기록하던 문제다.

**저자 주장.** release는 여러 평가 split이 있으면 원래 test가 filtered validation으로 대체되거나, validation만 평가하는 task에서는 평가에 쓰이지 않는 test가 새로 만들어질 수 있었다고 설명한다. 일부 published `.v2` dataset과의 일치도 보고한다. 독립 검증은 하지 않았다. 이번 code 수정만으로 모든 영향을 받은 Hub dataset이 새 revision으로 복구되고 leaderboard가 재평가됐다고 볼 근거는 확보하지 못했다.

**공개물·설치·license·활동.** 이 사건은 새 weights/data 공개 확정이 아닌 cleaning script 교정이다. code license는 Apache-2.0이며 개별 dataset 조건은 별도다. pin 후보는 `mteb==2.27.26`과 해당 source commit이다. script는 저장소의 `scripts/` 경로에 있으므로 wheel 설치만으로 그 파일이 포함된다고 가정하지 않는다. PR diff와 release 포함은 확인했고, 전체 Issue 해결률·수정 dataset의 새 hash는 미확인이다. checksum·attestation 검증은 미실행이다.

**추론 — 진단 → 가설 → 10~30분 최소 실험 계획.**

1. 작은 train·validation·test fixture에서 각 eval split에 train 중복을 하나씩 넣는다.
2. parent와 수정 script를 분리해 호출하고 split 이름, row identity, 삭제된 중복, 원래 test의 보존을 확인한다. validation-only 조건도 별도로 검사한다.
3. 준비된 실제 dataset audit를 확장할 때는 old/new revision과 split fingerprint를 기록한다. script 수정 결과와 기존 Hub artifact를 혼동하지 않는다.

CPU fixture이므로 GPU/VRAM이 필요 없다. **GO:** split별 보존·중복 제거 계약 검사. **KILL:** cleaning code merge만으로 기존 benchmark leakage가 모두 사라졌다고 선언하지 않는다.
