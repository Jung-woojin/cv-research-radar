## 핵심 사례 1 — FP16 좌표 변환과 annotation 저장

**Claim / 재현 조건.** 커뮤니티 작성자는 Ultralytics 8.4.211, commit `a47b02d0d6f17922df3322382fd86cc5a700ba54`, Windows 11, Python 3.14.5, PyTorch 2.15.0+cpu에서 명시적 `Results.to(float16)` 뒤 큰 좌표의 중심이 `inf`로 저장된다고 보고했다. 일반 FP32 inference 전체의 실패 주장은 아니다. [제보](https://github.com/ultralytics/ultralytics/issues/27166)

**Observed gap / 사실.** 같은 예제의 FP32 경로는 유한한 중심을 내지만 FP16 경로는 그렇지 않다는 작성자 결과다. 고정 revision의 `xyxy2xywh`가 중심 계산에 `(x1 + x2) / 2`를 쓰는 점을 직접 확인했다. maintainer는 FP32 좌표·저장을 권고하고 이슈를 “not planned”로 닫았다. 종료를 수정 완료로 해석하면 안 된다. [소스](https://github.com/ultralytics/ultralytics/blob/a47b02d0d6f17922df3322382fd86cc5a700ba54/ultralytics/utils/ops.py), [처리 상태](https://github.com/ultralytics/ultralytics/issues/27166)

**진단 → 가설.** 최종 중심값이 표현 가능해도 중간 합이 FP16 범위를 넘으면 실패할 수 있다. 대형 원격탐사 영상의 후처리에 관련될 가능성은 추론이며, 실제 발생 빈도는 미확인이다.

**최소 실험.** weights 없이 이슈 fixture의 FP32/FP16 좌표 변환과 저장 후 재로딩을 비교한다. 입력·변환·직렬화 각 단계에 finite assertion을 둔다.

**GO / KILL.** FP32 저장과 재로딩이 유한성을 유지하면 GO. 좌표에 `inf`가 생긴 파일은 evaluator 입력에서 제외한다(KILL). FP16 confidence 사용과 좌표 dtype을 별도로 관리한다.

## 핵심 사례 2 — 기본 config로 만든 모델과 checkpoint 모델은 다르다

**Claim / 재현 조건.** 커뮤니티 제보는 Transformers `5.23.0.dev0`, commit `863d2620210d72fc0a9a03fdfe200bc9699154f6`, Linux, Python 3.13, torch 2.12.1+cu130에서 여러 기본 config의 생성·forward 실패를 제시한다. 작성자는 Hub checkpoint config로 로드하는 경로는 구분했다. [제보](https://github.com/huggingface/transformers/issues/50601)

**Observed gap / 사실.** Molmo2 adapter의 기본 `text_hidden_size=3584`와 text 기본 `hidden_size=4096`을 고정 소스에서 확인했다. 모델 전체 실행 실패는 작성자의 재현 보고다. maintainer들은 기본 config 생성뿐 아니라 forward 검사 필요성과 기존 checkpoint 호환성 위험을 논의했으며, 이슈는 open이다. [config 소스](https://github.com/huggingface/transformers/blob/863d2620210d72fc0a9a03fdfe200bc9699154f6/src/transformers/models/molmo2/configuration_molmo2.py), [토론](https://github.com/huggingface/transformers/issues/50601)

**진단 → 가설.** 서로 다른 sub-config의 기본값이 연결부의 차원 계약을 깨뜨릴 수 있다. 이 실패를 weights 손상이나 논문 성능 불일치로 설명할 근거는 없다.

**최소 실험.** 기본 config, checkpoint에서 읽은 config, 차원을 명시적으로 맞춘 tiny config를 각각 생성·forward·save/load한다. config diff와 projector 출력·text embedding 차원을 저장한다.

**GO / KILL.** 연결 차원이 맞고 저장 전후 forward가 유지되면 해당 config를 GO. 기본 config만 실패하면 공개 checkpoint 전체의 재현 실패라는 결론은 KILL한다. 기본값 수정으로 기존 checkpoint 동작이 달라지는지도 별도 검사한다.

## 핵심 사례 3 — LTX block offload의 decode 호출 경로

**Claim / 재현 조건.** Diffusers `main`의 `f598e6e`, Python 3.12, torch `2.13.0+rocm10.0.0` 제보는 LTX-2.5 BF16, VAE tiling, block-level group offload 및 stream 사용 시 decode에서 CPU/GPU tensor mismatch가 난다고 설명한다. GPU 모델은 미제공이다. [제보·최소 코드](https://github.com/huggingface/diffusers/issues/15250)

**Observed gap / 사실.** 작성자의 traceback은 입력과 weight 장치 불일치다. 해당 revision의 LTX2 video VAE 파일에 `_group_offload_block_modules` 선언이 없는 점을 확인했다. 다만 이것만으로 오디오·vocoder·중복 hook에 관한 모든 진단을 독립 검증한 것은 아니다. 조회 시 이슈는 open이고 댓글이 없었다. [고정 소스](https://github.com/huggingface/diffusers/blob/f598e6e/src/diffusers/models/autoencoders/autoencoder_kl_ltx2.py)

**진단 → 가설.** 직접 `decode()`를 호출하는 경로가 `forward()` 중심 offload hook을 우회하면 weight가 CPU에 남을 수 있다는 작성자 진단이다. seed 변경으로 해결할 유형이라는 근거는 없다.

**최소 실험.** 동일 latent·checkpoint에서 no-offload, 현재 block offload, VAE를 offload 대상에서 제외한 조건을 비교한다. decode 입구의 input/weight/buffer 장치와 hook 실행을 기록하고, 실행이 끝난 조건끼리만 출력 차이를 확인한다.

**GO / KILL.** 장치 정합성과 decode 완료가 확인된 조건만 GO. decode 전 실패한 run의 품질·속도 비교는 KILL한다. ROCm 제보를 NVIDIA CUDA 전체의 실패로 일반화하지 않는다.

## 핵심 사례 4 — LeRoPE의 학습 가능 변수 누락

**Claim / 재현 조건.** Transformers `28ec08c4`, Python 3.12.13, torch 2.13.0+cu130의 CPU tiny-model 제보는 full-parameter training에서도 LeRoPE `alpha`에 gradient와 update가 없다고 보고한다. 이미지 입력을 평가한 실험은 아니다. [제보](https://github.com/huggingface/transformers/issues/50622)

**Observed gap / 사실.** 읽은 Transformers 코드에서 `alpha`는 `nn.Buffer`이고 RoPE forward는 `@torch.no_grad()`다. NeMo AutoModel의 고정 revision은 `alpha`를 `nn.Parameter`로 두고 differentiable forward를 사용한다. 이 구현 차이는 직접 확인했지만 full-model 학습 품질 차이는 미확인이다. [Transformers 소스](https://github.com/huggingface/transformers/blob/28ec08c4/src/transformers/models/mistral_large4/modeling_mistral_large4.py), [NeMo 소스](https://github.com/NVIDIA-NeMo/Automodel/blob/1298a2e143db3be03ecaff80c72ac727afec9d0e/nemo_automodel/components/models/mistral_large4/rope_utils.py)

**진단 → 가설.** optimizer 등록과 autograd 경로를 모두 만족해야 학습된다. 한쪽만 바꾸면 충분하지 않을 수 있다. 최신 maintainer 댓글은 core 정책 검토를 요청했으며 확정된 수정 지침은 아니다. [토론](https://github.com/huggingface/transformers/issues/50622)

**최소 실험.** 기존 코드, Parameter만 변경, no_grad만 제거, 둘 다 변경하는 네 조건에서 동일 초기값·입력으로 optimizer membership, gradient, update, 첫 update 전 logits parity를 검사한다.

**GO / KILL.** 의도한 변수만 gradient/update를 얻고 초기 forward가 유지되면 후속 학습 실험으로 GO. tiny test 통과만으로 checkpoint 품질 향상이나 논문 재현 완료를 주장하는 것은 KILL한다.

## 공통 비교 조건과 오늘의 판단

사례 간 데이터·모델·hardware·precision·batch·evaluator가 다르므로 성능을 서로 비교하는 것은 **not strictly apples-to-apples**다. FP16 좌표·기본 config 사례는 학습 dataset, split, TTA에 대한 성능 실험이 아니며, LTX와 LeRoPE 사례도 benchmark 점수 차이를 제공하지 않는다. seed 분산은 측정하지 않았다.

- **GO — 가장 먼저:** weights가 필요 없는 FP32/FP16 좌표 저장 fixture로 결과 파일의 유한성을 검사한다.
- **GO — 학습 전:** resolved config, checkpoint revision/hash, optimizer parameter 이름, gradient 유무, framework/runtime·precision을 manifest로 보존한다.
- **GO — 생성 전:** offload 설정과 실제 decode 장치 배치를 함께 기록한다.
- **KILL:** closed issue를 해결 완료로, tiny fixture를 full-model reproduction으로, 기본 config 오류를 공개 weights 오류로 바꾸어 서술하지 않는다.
- **후속 연구 가설:** seed sweep에 앞서 dtype·config·hook·gradient 계약을 검사하면 일부 재현 실패를 더 작은 실험으로 분리할 수 있다. 검증하려면 동일 fixture의 계약 검사 결과와 이후 end-to-end 실패 여부를 함께 수집해야 한다. 현재는 제안이며 실측 결론이 아니다.
