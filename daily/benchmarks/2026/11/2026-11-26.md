## 1. ZeroBench — 같은 dataset 이름 아래 입력 이미지가 달라진다

**확인 사실.** VLMEvalKit commit `ae086d83b2272d9cbb1087a328c23f6b28994390`는 `ZEROBench`와 `ZEROBench_sub`의 URL 및 MD5를 바꾸고 `_v3` 두 variant를 추가했다. 기존 소문자 파일명을 `ZEROBench*.tsv` 대소문자로 수정한다. 코드 diff는 데이터 등록 부분에 한정되며 prompt·exact-match evaluator·기본 반복 횟수의 수정은 없다. [공식 변경](https://github.com/open-compass/VLMEvalKit/commit/ae086d83b2272d9cbb1087a328c23f6b28994390).

| variant | 이전 MD5 | 새 MD5 |
|---|---|---|
| ZEROBench | `600d5e89325f1dab5ad3fa2ea200cea6` | `5a04a75da6258dd558e89002925db456` |
| ZEROBench_sub | `2d2131bffb7f09ca099fdd0f3ad0392b` | `7775abf7da9c85a24d42d0e4ed25c2d2` |
| ZEROBench_v3 | 신규 등록 | `ea980a05d8a6ad8058693aea42a3c4de` |
| ZEROBench_sub_v3 | 신규 등록 | `848347e947adcb24c28aeaaa4b5505e3` |

**작성자 보고.** PR #1890은 기존 export가 질문별 첫 이미지만 저장해 main의 7문항에서 이미지 8개, sub의 26문항에서 이미지 29개를 누락했다고 설명한다. 복구 후 main은 100문항·108이미지, sub는 334문항·363이미지라고 보고한다. 원래 두 variant는 질문·정답·attribution을 유지한 v2이고, v3 main에는 두 문항의 문구 변경, sub에는 세 문항의 문구와 두 문항의 답변 형식 변경이 포함된다는 설명이다. 이는 작성자의 전수 대조 보고이며 이번 실행의 독립 데이터 측정이 아니다. [PR 설명과 검증 내역](https://github.com/open-compass/VLMEvalKit/pull/1890).

**원본 교차검증.** ZeroBench 공식 저장소는 main 100문항·sub 334문항을 명시하며, 이미지 배열을 입력으로 사용한다. 공식 README는 v3가 2025년 12월의 문구 명확화이고 v2 branch가 유지된다고 설명한다. 따라서 이번 adapter 등록을 새 benchmark·새 split의 최초 공개로 해석하지 않는다. “문구 수정이 점수에 거의 영향을 주지 않는다”는 것도 원저자의 주장이지 모든 모델에서 검증된 불변성이 아니다. [공식 README와 평가 예시](https://github.com/jonathan-roberts1/zerobench/blob/main/README.md), [공식 데이터 카드](https://huggingface.co/datasets/jonathan-roberts1/zerobench/blob/main/README.md).

PR 작성자는 원본 v2를 `9153b1fdb028ecf58ee55a9204c609745df53ea0`, v3를 `8fcdfd9138c802cac52b774b36946e70f738f500`에 고정해 대조했다고 기록했다. 이 revision은 후속 재현의 출발점이며, 이번 실행에서 두 Parquet와 TSV를 byte 단위로 재대조하지 않았다.

**실제 실행 가능성은 미확인.** PR의 11월 25일 hosting check에는 main v3 URL이 404이고 나머지 세 파일은 200이었다고 적혀 있다. 병합됐다는 사실만으로 그 문제가 해결됐다고 볼 수 없다. 이번 실행의 네 URL HEAD 요청은 모두 `The SSL connection could not be established, see inner exception.`으로 실패했고 HTTP status를 얻지 못했다. 웹 도구도 main·v3 URL에 접근하지 못했다. 따라서 현재 404 여부·파일 크기·실제 checksum 일치는 미확인으로 남긴다. SSL 실패를 서버의 404로 바꾸어 기록하지 않는다. [등록 URL과 checksum](https://github.com/open-compass/VLMEvalKit/blob/ae086d83b2272d9cbb1087a328c23f6b28994390/vlmeval/dataset/image_vqa.py).

**진단과 기전.** 공통 loader는 image 목록을 다룰 수 있고, ZeroBench prompt도 `dump_image`가 반환한 모든 경로를 메시지에 넣는다. 따라서 작성자 보고대로 export 단계에서 이미지가 빠졌다면 모델은 질문이 요구하는 시각 증거 일부를 처음부터 받지 못했을 수 있다. 이는 모델의 multi-image reasoning 실패와 구별해야 한다. 다만 실제 run에 들어간 메시지와 이미지가 없으면 과거 실패 원인을 확정할 수 없다. [공통 loader](https://github.com/open-compass/VLMEvalKit/blob/ae086d83b2272d9cbb1087a328c23f6b28994390/vlmeval/dataset/image_base.py), [ZeroBench prompt·채점](https://github.com/open-compass/VLMEvalKit/blob/ae086d83b2272d9cbb1087a328c23f6b28994390/vlmeval/dataset/image_vqa.py).

**가설 → 최소 개입 → 실험.** 가설은 누락 이미지가 있었던 문항의 실패 일부가 representation/readout보다 입력 손실에서 발생했다는 것이다. 먼저 과거 TSV와 실제 message 로그를 보존하고, 원본 revision별 question ID·이미지 개수·순서·hash·질문·정답을 대조한다. v2 이미지 복구와 v3 문구 변경을 한 번에 섞지 않는다. 복구만 비교할 때는 같은 checkpoint·prompt·decoding·도구·반복 횟수를 고정한다.

**GO/KILL.** 과거 run에서 입력 누락이 확인되면 해당 문항과 정상 입력 문항을 나눠 제한 재추론한다. 실제 메시지에 이미 모든 이미지가 있었다면 입력 손실 가설은 해당 run에서 기각한다. 파일을 확보하지 못하면 성능 차이 추정은 중단한다. 데이터 감사는 GPU 없이 가능하지만 재추론 비용은 사용하는 모델에 달려 있다.

**동조건 판정.** 기존 이름의 전후 결과라도 checksum이 다르면 자동으로 동일 입력 비교가 아니다. v2↔v3 또는 이미지 복구 전↔후 비교는 **not strictly apples-to-apples**다. 공식 leaderboard의 현재 점수만으로 이 복구가 순위를 얼마나 바꿨는지 계산할 수 없다.

## 2. Judge API 클래스 선택 — 모델 문자열 외에 wrapper도 평가 조건이다

**확인 사실.** commit `0c658c28a129366252f7b906f87f3f22473f4716`는 `--judge-model-class`를 추가했다. 명시하면 `run.py`가 `model_class`를 judge kwargs에 넣고, `build_judge`가 `vlmeval.api`에서 해당 이름을 찾아 `is_api`를 확인한 뒤 wrapper를 구성한다. 없거나 API wrapper가 아니면 ValueError다. 미지정 시 기존 자동 선택 경로를 유지한다. [공식 diff](https://github.com/open-compass/VLMEvalKit/commit/0c658c28a129366252f7b906f87f3f22473f4716).

**실제 적용 범위.** 클래스 override보다 먼저 모델 alias를 snapshot 이름으로 변환하며 `LOCAL_LLM`이 있으면 그 값을 `model_version`으로 사용한다. 따라서 이 옵션이 모델 버전 선택까지 우회하는 것은 아니다. CLI의 명시적 클래스는 `--judge-args`의 같은 키보다 뒤에서 대입된다. 다만 개별 dataset이 공통 `build_judge`를 이용해야 이 경로를 거친다. 모든 benchmark가 이 옵션으로 동일하게 바뀐다고 일반화하지 않는다. [judge 구성 코드](https://github.com/open-compass/VLMEvalKit/blob/0c658c28a129366252f7b906f87f3f22473f4716/vlmeval/dataset/utils/judge_util.py), [CLI kwargs 경로](https://github.com/open-compass/VLMEvalKit/blob/0c658c28a129366252f7b906f87f3f22473f4716/run.py).

**주장과 추론.** 변경 제목은 judge API 클래스의 명시적 선택 기능을 설명한다. 특정 judge의 정확도 향상이나 API 호환성 성공은 이 diff로 증명되지 않는다. wrapper가 달라지면 요청 형식·기본값·오류 처리가 달라질 수 있다는 것은 감사해야 할 가설이다. 같은 모델 이름만 적은 평가 기록으로 완전한 조건 일치를 보장할 수 없다는 운영 신호로 해석한다.

**진단 → 최소 실험.** 저장된 raw prediction과 평가 prompt를 고정하고, 먼저 mock transport에서 자동/명시 wrapper가 만드는 요청을 비교한다. 실제 model ID, endpoint 경로, 메시지 역할·이미지 표현, token budget·temperature·retry를 기록한다. alias 및 `LOCAL_LLM` 적용 후 최종 값을 확인한다. 이 검사는 구현 계약 검증이며 실제 judge 성능 시험은 아니다.

**GO/KILL.** payload가 달라지면 차이를 통제한 뒤 소규모 paired regrading으로 진행한다. payload와 응답 처리까지 같으면 wrapper 선택만으로 점수가 바뀐다는 가설을 지지하지 않는다. 유료 API 채점과 성능 변화량은 이번 실행에 포함하지 않았다. wrapper·endpoint·judge snapshot이 다르면 기존 결과와 **not strictly apples-to-apples**다.

## 비교 조건과 검증 한계

오늘은 backbone·pretraining·external data·input resolution·TTA·reasoning effort·context/frame/compute budget을 통일한 새 모델 비교를 확보하지 않았다. 학습 데이터나 split의 새 변경도 확인하지 않았다. ZeroBench의 v3 등록과 기존 원본 revision을 구분해야 한다.

후속 run에는 dataset revision·checksum·sample ID, 입력 이미지 순서와 resize, evaluator commit, raw response, 최종 prompt, 도구 사용, decoding, 반복 횟수, judge snapshot·wrapper·endpoint를 함께 보존한다. ZeroBench의 기본 다섯 번 반복과 단일 run 정확도, pass@5, pass^5를 섞어 읽지 않는다. 이 기본값은 이번 commit에서 새로 도입된 변화가 아니다. [공식 metric 설명](https://github.com/jonathan-roberts1/zerobench/blob/main/README.md).

이번 실행은 코드·문서 정적 검토와 HTTP 접근 시도다. PR에 적힌 테스트 통과 수는 작성자의 보고이며 직접 테스트를 실행한 결과로 제시하지 않았다. 현재 hosted TSV의 완전성과 최종 API 요청의 동등성은 후속 검증 대상이다.

## 오늘의 benchmark signal 3개

1. **dataset 이름보다 checksum과 실제 입력을 본다.** 같은 이름 아래 누락 이미지 복구가 들어가면 전후 run의 평가 조건이 달라진다.
2. **입력 복구와 문구 revision을 분리한다.** multi-image 증거 복구와 질문 명확화를 섞으면 원인을 해석하기 어렵다.
3. **코드 등록과 실행 가능성을 따로 검증한다.** 병합·URL 등록·HTTP 접근·checksum 일치·judge payload는 각각 확인할 계약이다.

세 signal은 선정한 두 변경에서 도출한 교훈이며, 독립된 신규 benchmark 세 건을 의미하지 않는다.

## 내 연구에 바로 연결되는 포인트

- Answer–Region Gap과 evidence-grounded VQA에서는 정답 실패를 해석하기 전에 실제 전달된 이미지·crop·panel의 누락부터 검사한다.
- CCTV·해양 안전 multi-view VQA는 프레임 수뿐 아니라 순서·중복·누락을 sample별로 기록한다. 정답률 변화가 temporal reasoning 개선인지 입력 복구인지 분리한다.
- **오늘 가장 먼저 할 실험:** 기존 ZeroBench 데이터와 message 로그의 이미지 개수·순서·hash 대조. RTX 5060 Ti 8GB에서도 GPU 없이 시작할 수 있다.
- 장기 연구로 확장하려면 동일 문항의 증거 일부 누락/전체 제공을 통제하고, 답변 변화와 근거 사용을 함께 측정한다. 이번 관측만으로 새로운 architecture나 논문화 가능성을 주장하지 않는다.
