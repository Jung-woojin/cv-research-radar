## 1. Supervision 0.32.1 — 모델보다 평가기와 split을 먼저 고정

**새 내용·시각 — 사실:** 2026-11-24 10:31:30 UTC, 즉 19:31:30 KST에 배포됐다. confusion matrix의 정규화 축, 빈 target의 mAR, dataset split 반올림, BGRA annotation, Windows 비ASCII 경로를 수정했다. 새 모델 논문이 아니라 CV 평가·입출력 도구 업데이트다. [릴리스](https://github.com/roboflow/supervision/releases/tag/0.32.1).

**코드 품질·재현성:** confusion matrix PR은 true-on-rows 구조에 column 정규화를 적용했던 원인과 sklearn 대조 테스트를 제시한다. PR #2954의 실제 병합은 11월 19일 19:58:26 UTC다. 작성자의 테스트 통과 보고는 독립 재현과 구분한다. normalized plot 변화가 raw confusion counts 자체의 개선을 뜻하지 않는다. [원인·수정·테스트 PR](https://github.com/roboflow/supervision/pull/2954).

**라이선스·가중치·설치:** 코드는 MIT, 이 patch에 새 pretrained checkpoint는 없다. Python ≥3.10이며 NumPy·SciPy·Pillow·PyAV 등을 사용한다. 설치 난이도는 낮음~중간으로 판단한다. core dependency와 별도로 COCO 평가 extras를 확인해야 한다. [tag 고정 manifest](https://github.com/roboflow/supervision/blob/0.32.1/pyproject.toml).

**GPU·호환성:** 아래 metric·split 검사는 CPU로 설계할 수 있어 8GB GPU를 요구하지 않는다. 전체 detector 실행의 VRAM은 별도다. Ultralytics·Transformers 출력 adapter가 있으며 이번 release는 Transformers bfloat16 변환도 수정한다. MMDetection·timm의 모든 출력에 대한 직접 호환은 미확인이다.

**유지보수:** 0.32.0과 0.32.1의 연속 배포 및 여러 수정 PR은 활동 근거다. 응답 시간이나 장기 유지보수 품질을 수치로 추정하지 않았다.

**진단 → 가설 → 최소 실험 — 제안:** 작은 물체 recall 개선처럼 보이는 변화가 빈 bucket의 0→-1 전환과 집계 방식에서 생길 수 있다. 0.32.0/0.32.1에 동일한 저장 prediction·target을 넣고, 비대칭 오분류 예제와 small target이 없는 예제를 각각 평가한다. raw counts, normalized diagonal, bucket별 target 수, mAR, 음수 제외 집계를 기록한다. split 함수는 고정 seed에서도 버전 간 구성원이 달라질 수 있으므로 image ID 목록을 파일로 고정한다.

**GO/KILL:** raw counts를 보존하면서 normalized plot이 true-class 기준 계산과 일치하고 빈 bucket을 undefined로 처리하면 GO. split 구성원이나 evaluator 버전이 섞인 기존 성능 비교는 보류하고 다시 계산한다. 이 조건에서는 **not strictly apples-to-apples**다.

**점수:** 실험 가치 5/5 · 재현성 5/5 · 신규성 2/5 · 실용성 5/5.

## 2. Ultralytics 8.4.217 — 타일 기하와 INT8 calibration 분리

**새 내용·시각 — 사실:** 2026-11-23 19:49:22 UTC, 즉 11월 24일 04:49:22 KST 배포. 직사각 `tile=[h,w]`와 `tile_overlap`을 train/val/predict에서 설정할 수 있다. 관련 PR #27300은 11월 21일 05:22:48 UTC에 병합됐다. release 날짜와 구현 병합일을 구분한다. [릴리스](https://github.com/ultralytics/ultralytics/releases/tag/v8.4.217), [타일링 PR](https://github.com/ultralytics/ultralytics/pull/27300).

**코드 품질·재현성:** 타일 PR은 공통 window 생성과 CPU 회귀 검사를 설명하지만 GPU/MPS·DDP는 미검증이라고 명시한다. 기본 overlap은 0.2다. 이 PR에 SAHI 방식의 merging 추가까지 포함됐다고 해석하지 않는다.

**배포 변경 — 사실과 저자 주장:** PR #27340은 TensorRT 11의 ModelOpt 경로에서 명시적 `max` calibration 설정을 제거해 기본 `entropy`를 사용한다. TensorRT 7–10 경로는 유지된다. 작성자는 지정한 128장 calibration 조건에서 정확도 회복을 보고하지만, 작은 기본 calibration set에서는 일부 OBB·semantic 결과가 악화되기도 했다. 따라서 모든 조건의 일괄 향상으로 요약할 수 없다. [구현·환경·비교표](https://github.com/ultralytics/ultralytics/pull/27340).

**라이선스·가중치·설치:** package는 AGPL-3.0이다. 이번 변경을 위해 새 가중치가 필요한 것은 아니며 기존 checkpoint를 고정해 비교해야 한다. Python ≥3.8, torch·torchvision·OpenCV 의존성이 있다. 일반 추론은 중간 이하, TensorRT 11·ModelOpt export 환경 구성은 높음으로 판단한다. [tag 고정 manifest](https://github.com/ultralytics/ultralytics/blob/v8.4.217/pyproject.toml).

**GPU·호환·유지보수:** 최소 VRAM은 미확인이다. 타일을 순차 처리하는 batch=1 검사부터 제안하지만 RTX 5060 Ti 8GB 적합성은 측정해야 한다. Ultralytics 내부 API에 직접 적용되며 MMDetection·timm·Hugging Face의 공통 plugin은 아니다. 연속 patch와 병합 PR은 활동 근거다.

**진단 → 가설 → 최소 실험 A — 제안:** UAV·CCTV의 작은 물체 미검출이 해상도 손실과 tile 경계 절단에서 생기는지 검사한다. 고정 val image ID 20장과 동일 checkpoint로 whole-image, 정사각 tile, 직사각 tile을 비교한다. tile 입력 해상도·overlap·총 tile 수·중복 제거 규칙·confidence·NMS·precision을 기록한다. small-object recall/AP와 경계 근처 recall, 총 wall time, peak VRAM을 함께 측정한다. 20장은 진단용이며 전체 benchmark 성능으로 일반화하지 않는다.

**최소 실험 B — 제안:** export가 필요한 경우에만 동일 weight·calibration ID·전처리·TensorRT/ModelOpt 버전·batch로 FP16, INT8 max, INT8 entropy를 비교한다. engine을 반복 빌드해 AP·latency·export 시간의 변동을 기록한다. 버전 전체를 바꾸면 evaluator 수정도 섞이므로 calibration 인자만 바꾸는 대조를 우선한다.

**GO/KILL:** 동일 추론 예산에서 경계 recall 개선이 유지되면 타일 실험 GO. tile 수 증가 효과만 보이면 기하 효과 주장은 보류한다. INT8은 동일 calibration에서 FP16 대비 손실과 비용이 허용 범위일 때만 채택한다. 다른 입력·calibration·GPU 결과끼리는 **not strictly apples-to-apples**다.

**점수:** 실험 가치 5/5 · 재현성 4/5 · 신규성 3/5 · 실용성 5/5.

## 3. Kraken 7.2 — segmentation 후처리와 가중치 교체를 분해

**새 내용·시각 — 사실:** 2026-11-20 10:51:14 UTC, 즉 19:51:14 KST 배포. 기본 BLLA 모델 교체, Sato filter·polygonization 변경, 이미지 경계 ROI 수정, `segtest` 채널·merged-class 집계 수정을 포함한다. 문서 OCR/HTR segmentation 도구이므로 UAV·해양에 바로 전용할 후보로 보지는 않는다. [7.2 릴리스](https://github.com/mittagessen/kraken/releases/tag/7.2), [공식 changelog](https://kraken.re/main/changelog.html).

**가중치 공개일 — 사실:** 연결된 BLLA 모델 카드의 Version v2 공개일은 2026-09-21이다. 이번 주 새 weight 공개가 아니라 release의 기본 모델 채택이다. 모델 파일과 train/val/test 목록이 제공된다. 모델 카드는 Latin·Arabic·Greek 중심 자료와 기울어진 글씨·세로쓰기 등 한계를 명시한다. 코드의 Apache-2.0과 모델·원 데이터 이용 조건은 별도로 확인해야 하며 가중치 라이선스는 이번 확인에서 확정하지 못했다. [모델 카드·파일·split](https://zenodo.org/records/22879549).

**코드 품질·재현성:** 평가 명령과 split 자료가 있어 코드·가중치·평가기 효과를 분리할 단서가 있다. 후처리 속도 향상과 extractor 간 예측 차이에 관한 설명은 저자 주장이다. 본 실행에서 재현하지 않았다.

**설치·GPU·호환:** 코드 Apache-2.0. Python ≥3.10,<3.15, torch ≥2.9,≤2.14, lightning 2.6.6 등이 tag manifest에 명시된다. 의존성이 많아 난이도 중간~높음이며 Windows에서는 Linux/WSL 환경부터 검토할 것을 제안한다. 최소 VRAM은 미확인이고 작은 모델 파일 크기를 peak memory로 환산하면 안 된다. 자체 Kraken CLI·모델 형식이며 MMDetection·Ultralytics·timm·Hugging Face 직접 adapter는 확인하지 못했다. [7.2 manifest](https://github.com/mittagessen/kraken/blob/7.2/pyproject.toml), [공식 저장소](https://github.com/mittagessen/kraken).

**유지보수:** 7.1→7.2 배포와 release에 연결된 수정 PR이 활동 근거다. 여러 달의 배포 간격을 장기 안정성 보장으로 해석하지 않는다.

**진단 → 가설 → 최소 실험 — 제안:** 경계 segmentation 개선이 encoder보다 polygonization 또는 evaluator 수정에서 생겼을 수 있다. 문서 segmentation이 필요한 경우 고정 20페이지에서 7.1/7.2 코드 × 이전/현재 weight의 2×2 대조를 설계한다. weight 로딩 호환을 먼저 검사하고 불가능하면 비교를 중단한다. 동일 raw segmentation map을 두 후처리에 넣어 line F1, region IoU, 경계 누락, 전처리/forward/polygonization별 시간을 기록한다. evaluator는 하나로 고정하고 별도 대조에서만 교체한다.

**GO/KILL:** 동일 map·weight에서도 경계 오류나 후처리 시간이 개선되면 코드 효과 가설을 지지한다. 개선이 weight 교체에서만 나타나면 후처리 기여 주장은 기각한다. 문서 segmentation 수요가 없으면 clone 우선순위를 낮춘다.

**점수:** 실험 가치 3/5 · 재현성 3/5 · 신규성 3/5 · 실용성 3/5.

## 이번 주 바로 clone할 우선순위

1. **Supervision 0.32.1:** CPU 평가기 회귀 검사부터 진행한다. 8GB GPU 환경에서도 가장 부담이 적은 첫 실험이다.
2. **Ultralytics 8.4.217:** UAV·CCTV 고정 소표본에서 타일 기하를 검사한다. INT8 export는 별도 환경에서 수행한다.
3. **Kraken 7.2:** 문서 segmentation·후처리 진단이 필요할 때만 조건부 clone한다.

이 세 후보는 서로 다른 프로젝트다. Ultralytics의 타일링과 calibration을 별도 저장소 후보처럼 중복 계산하지 않았다. 세 번째 후보의 분야 적합성이 낮다는 한계를 유지하며 추가 후보를 억지로 채우지 않았다.

실험 전 code commit, weight hash/revision, dataset revision·split ID, evaluator, 해상도, tile/pass 수, batch, precision, seed, GPU·driver·CUDA, package lock을 남긴다. 비교표에서 backbone·pretraining·외부 데이터·TTA·compute가 달라지면 표시한다. 이번 주 첫 질문은 **“모델을 바꾸지 않아도 평가기·입출력·후처리를 고정하면 관측된 변화가 사라지는가?”**다.
