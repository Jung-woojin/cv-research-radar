- 가장 먼저 할 실험은 Surya 2와 2.5의 표 geometry 계약 검증이다. 8GB GPU 없이도 출력 JSON 비교와 소규모 주석으로 시작할 수 있다.

## Q1. OCR 표의 HTML 정확도는 좌표 기반 표 이해를 대체할 수 있는가?

**문제 정의 / 왜 지금 가치가 있는가**  
Surya `v0.23.0`은 기본 Surya 2.5로 전환하면서 table HTML을 기본 출력으로 제공하지만 row/column geometry를 제공하지 않는다. 표 구조 복원이 좋아 보여도 좌표 기반 셀 정렬·검증·downstream extraction이 가능한지는 별도 질문이다.

**직접 근거 — [사실]**  
공식 릴리스와 README는 Surya 2.5가 row/column geometry 없이 HTML을 출력하며, `--mode simple` 및 geometry가 필요하면 Surya 2 checkpoint를 사용해야 한다고 명시한다. 릴리스의 1.7× throughput 및 OmniParseBench 85.9는 단일 H100·공개 scorer 조건의 결과다. [release](https://github.com/datalab-to/surya/releases) · [README](https://github.com/datalab-to/surya)

**Gap**  
현재 benchmark headline은 table HTML의 semantic validity와 geometry schema compatibility를 분리해 보고하지 않는다.

**핵심 가설 — [추론]**  
HTML similarity가 높아도 merged cell·불규칙 표·multi-line cell에서 geometry-dependent pipeline의 schema pass rate는 떨어질 수 있다.

**최소 실험(MVP)**  
복잡도별 표 50개를 Surya 2(simple)와 2.5(full)로 처리해 HTML→cell reconstruction을 동일 규칙으로 만든다.

**Baseline / 데이터 / metric / ablation**  
- baseline: Surya 2 geometry, Surya 2.5 HTML reconstruction  
- 데이터: 공개 PDF 표 50쪽 + 직접 정의한 cell polygon 소표본  
- metric: schema pass rate, cell boundary IoU, merged-cell F1, text-to-cell assignment accuracy  
- ablation: regular/irregular, merged-cell 유무, DPI 150/192/300

**성공/실패 판정**  
2.5 reconstruction이 Surya 2 대비 merged-cell F1에서 10%p 이상 낮거나 schema pass rate가 15%p 이상 낮으면 GO; 모두 근접하면 geometry gap 주장은 KILL한다.

**Compute 난이도**: 2/5  
**Novelty 위험**: output-schema conversion 연구와 중복 가능성. 문서 OCR의 downstream contract를 명시해야 한다.  
**4–8주 논문화 가능성**: 중간 — 여러 OCR/VLM에 같은 계약 검사를 확장할 때.  
**Negative result도 남는 결론**: HTML에서 geometry를 안정적으로 복원할 수 있음을 보이면 기존 호환성 위험을 정량적으로 축소할 수 있다.  
**평가**: novelty 3/5 · feasibility 5/5 · compute efficiency 5/5 · publication potential 3/5

## Q2. OCR benchmark의 평균 점수는 출력 API 변경에 둔감한가?

**문제 정의 / 왜 지금 가치가 있는가**  
Surya 2.5의 OmniParseBench headline은 Surya 2보다 높지만, JSON schema와 table mode의 기능 집합은 동일하지 않다. 평균 점수 지표가 사용자-facing breaking change를 놓치는지 검사할 필요가 있다.

**직접 근거 — [사실]**  
공식 README는 Surya v1→v2에서 output schema가 바뀌었고, Surya 2.5 `simple` table mode는 error를 낸다고 설명한다. 표 성능표는 192 DPI, `surya-ocr` 0.23.0, public scorer, 모델당 1회 실행 조건이다. [README 및 benchmark 조건](https://github.com/datalab-to/surya)

**Gap**  
OCR benchmark는 text/table/layout quality를 측정하지만 API consumer가 요구하는 field availability·type stability·error behavior를 보통 점수화하지 않는다.

**핵심 가설 — [추론]**  
모델 점수의 평균 개선과 API contract completeness는 약한 상관만 보이며, 특히 niche downstream task에서 contract loss가 더 큰 운영 비용을 낸다.

**최소 실험(MVP)**  
세 가지 consumer(표 좌표 추출, 검색용 HTML indexing, layout overlay)를 정의해 Surya 2/2.5 output에 schema validator를 실행한다.

**Baseline / 데이터 / metric / ablation**  
- baseline: quality-only ranking, contract-aware ranking  
- 데이터: Surya 공개 예제와 30개 문서  
- metric: required-field coverage, parser exception rate, task completion rate, quality score  
- ablation: consumer type, strict/relaxed schema, fallback converter on/off

**성공/실패 판정**  
quality-only 순위와 task completion 순위의 Spearman 상관이 0.5 미만이면 GO; 모든 consumer에서 순위가 보존되면 KILL한다.

**Compute 난이도**: 1/5  
**Novelty 위험**: 소프트웨어 호환성 연구에 가까워질 수 있다. vision benchmark protocol로 일반화해야 한다.  
**4–8주 논문화 가능성**: 중간 — 다수 document VLM의 version transition을 추가할 경우.  
**Negative result도 남는 결론**: quality leaderboard가 실제 consumer outcome의 좋은 proxy라는 반증 근거가 된다.  
**평가**: novelty 4/5 · feasibility 5/5 · compute efficiency 5/5 · publication potential 3/5

## Q3. Video SR에서 같은 가중치는 attention 구현이 달라도 같은 방법인가?

**문제 정의 / 왜 지금 가치가 있는가**  
FlashVSR의 공식 README는 일부 제3자 구현이 LCSA를 dense attention으로 대체해, 특히 고해상도에서 눈에 띄는 품질 저하를 낼 수 있다고 밝힌다. “같은 checkpoint”라는 표현이 파이프라인 등가성을 보장하는지 검증할 질문이다.

**직접 근거 — [유지보수자 주장]**  
FlashVSR는 공식 pipeline에서 768×1408, 단일 A100의 약 17 FPS를 제시하며, community testing에서 LCSA 누락 구현의 고해상도 품질 저하 가능성을 안내한다. 동일 README는 제3자 서비스가 v1/v1.1 또는 full pipeline을 쓰는지 불명확하다고 명시한다. [official README](https://github.com/OpenImagingLab/FlashVSR)

**Gap**  
VSR 결과는 checkpoint label 위주로 비교되는 반면, custom attention·pre/post-processing·해상도·aspect-ratio 전환이 구분되어 보고되지 않는다.

**핵심 가설 — [추론]**  
LCSA를 dense attention으로 바꾼 영향은 low-resolution 평균 PSNR보다 1440p 이상, motion 경계, 긴 clip에서 temporal artifact와 peak VRAM으로 먼저 드러난다.

**최소 실험(MVP)**  
공식 구현과 LCSA 대체 경로를 10개 clip, 720p/1440p, short/long 조건으로 비교한다. 8GB GPU에서는 full 1440p 대신 720p 짧은 clip과 profiling만 수행한다.

**Baseline / 데이터 / metric / ablation**  
- baseline: official LCSA, dense replacement, 가능하면 windowed baseline  
- 데이터: 공개 VSR clip 10개  
- metric: PSNR/SSIM, temporal warping error, artifact preference(블라인드), peak VRAM, p50 latency  
- ablation: resolution, clip length, aspect-ratio switch, attention implementation

**성공/실패 판정**  
고해상도에서 temporal error가 10% 이상 악화하거나 OOM/latency profile이 역전되면 GO; 모든 조건에서 차이가 작으면 operator-parity claim은 KILL한다.

**Compute 난이도**: 4/5  
**Novelty 위험**: implementation ablation만으로는 약하다. reproducibility metadata 표준으로 확장해야 한다.  
**4–8주 논문화 가능성**: 낮음–중간 — 여러 streaming VSR 모델의 operator substitution을 포함할 때.  
**Negative result도 남는 결론**: LCSA가 해당 조건에서는 재현·품질에 핵심 병목이 아니라는 유용한 구현 결과가 된다.  
**평가**: novelty 3/5 · feasibility 3/5 · compute efficiency 2/5 · publication potential 3/5

## Q4. 3D 공간 VLM의 성능 이득은 frame budget과 geometry revision에 얼마나 의존하는가?

**문제 정의 / 왜 지금 가치가 있는가**  
R2R은 novel-view semantic prediction으로 spatial understanding을 개선한다고 제시하지만, 4B/8B 평가의 frame budget과 VGGT 설치 조건이 다르고 학습 코드·데이터 준비 스크립트는 아직 공개되지 않았다.

**직접 근거 — [사실]**  
공식 R2R 저장소는 4B/8B 체크포인트, 추론·평가 코드를 공개했고 Python 3.12, CUDA 13 계열 PyTorch, flash-attn 2.8.2, patched VGGT를 요구한다. README는 학습 코드와 data-preparation scripts를 “coming soon”으로 명시한다. [official repository](https://github.com/yuqunw/R2R)

**Gap**  
체크포인트 평가 성능에서 frame budget, VGGT revision, base model, evaluator version의 기여가 분리되어 있지 않으면 method mechanism을 단정하기 어렵다.

**핵심 가설 — [추론]**  
공간 질의 성능은 새로운 view-rendering supervision뿐 아니라 frame budget과 geometry encoder revision의 상호작용에 민감하며, low-frame regime에서 이득 순위가 달라질 수 있다.

**최소 실험(MVP)**  
공식 inference/evaluation 경로만 고정해 4B와 8B를 각각 frame budget 16/32/64(가능한 범위)에서 실행하고 revision manifest를 남긴다.

**Baseline / 데이터 / metric / ablation**  
- baseline: R2R-4B/8B 및 base Qwen3-VL 가능 범위  
- 데이터: 공식 VSIBench 또는 공개 evaluation subset  
- metric: spatial QA accuracy, calibration, frame당 marginal gain, latency, VRAM  
- ablation: frame budget, model size, VGGT revision, seed

**성공/실패 판정**  
frame budget 통제 뒤 R2R 이득이 유지되고 calibration도 개선되면 GO; 이득이 특정 budget 또는 revision에만 묶이면 mechanism claim은 KILL/축소한다.

**Compute 난이도**: 5/5  
**Novelty 위험**: evaluation confound analysis가 이미 존재할 수 있다. exact release manifest를 중심 기여로 삼아야 한다.  
**4–8주 논문화 가능성**: 낮음 — 하드웨어·모델 접근성이 핵심 위험.  
**Negative result도 남는 결론**: 공개 checkpoint가 어떤 조건에서만 재현되는지 명확한 reproducibility map을 남긴다.  
**평가**: novelty 4/5 · feasibility 2/5 · compute efficiency 1/5 · publication potential 4/5

## Q5. “공개된 추론 코드”는 학습 기여의 재현 증거가 될 수 있는가?

**문제 정의 / 왜 지금 가치가 있는가**  
R2R처럼 inference/evaluation과 checkpoint가 먼저 공개되는 경우, 재현 성공이라는 말이 checkpoint replay인지 학습 과정 재현인지 혼재한다.

**직접 근거 — [사실]**  
R2R README는 추론·평가 코드 및 모델 checkpoint 공개를 안내하는 동시에 training code와 data-preparation scripts는 미공개라고 적는다. [R2R release status](https://github.com/yuqunw/R2R)

**Gap**  
CV/VLM release checklist는 실행 가능성은 확인해도 data transform, sampling, pseudo-label, curriculum 같은 학습 인과 요소의 공개 상태를 정량화하지 않는 경우가 많다.

**핵심 가설 — [추론]**  
추론 replay 가능성과 학습 claim auditability는 별도 축이며, artifact completeness score가 낮은 연구일수록 architecture advantage의 인과 설명도 약해진다.

**최소 실험(MVP)**  
최근 공개된 CV/VLM 20개를 대상으로 checkpoint, inference, evaluator, training code, data recipe, exact revision의 공개 여부를 이진/등급으로 audit한다. R2R은 현재 공개 상태의 사례로만 분류한다.

**Baseline / 데이터 / metric / ablation**  
- baseline: GitHub stars/README completeness 같은 표면 proxy  
- 데이터: 공개된 최근 CV/VLM 저장소 20개  
- metric: artifact completeness, runnable replay rate, claim-audit coverage, documentation-to-execution mismatch  
- ablation: model size, domain, institution, release age

**성공/실패 판정**  
artifact score가 runnable replay와 claim-audit coverage를 stars/README length보다 잘 설명하면 GO; 설명력이 없으면 score 설계를 KILL한다.

**Compute 난이도**: 1/5  
**Novelty 위험**: open-science checklist와 중복 가능성. CV/VLM의 geometry/data-prep 특수성을 입증해야 한다.  
**4–8주 논문화 가능성**: 중간 — 표본과 rubric의 사전등록이 필요하다.  
**Negative result도 남는 결론**: 간단한 공개 체크리스트가 이미 auditability를 충분히 설명한다는 실증이 된다.  
**평가**: novelty 4/5 · feasibility 5/5 · compute efficiency 5/5 · publication potential 4/5
