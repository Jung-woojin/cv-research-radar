## 1. CountBenchQA — 형식 준수와 계수 정확도를 분리한다

**확인 사실.** `countbenchqa_process_results`는 strip한 응답과 정답 문자열의 exact match에서 `parse_count` 결과와 정답 정수의 비교로 바뀌었다. 반환되는 `acc`와 `exact_match`에는 같은 새 score를 넣는다. 따라서 `exact_match`라는 키가 남아 있어도 과거의 원문 문자열 일치와 같은 정의가 아니다. [공식 변경](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/09920f2cfbb667d5278e18354e4ab9034c9806c0).

**maintainer 설명과 테스트.** `3.`처럼 계수는 맞지만 형식이 다른 답을 0점으로 처리하던 문제를 수정한다. 추가 테스트는 숫자만 있는 답, 마침표, 문장 속 숫자, `seven`, 오답·빈 응답을 포함한다. 이는 테스트 fixture이며 모델의 실측 점수가 아니다. [공식 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/09920f2cfbb667d5278e18354e4ab9034c9806c0/test/tasks/test_countbenchqa.py).

**교차확인과 한계.** 재사용되는 CountQA helper는 마지막 `</think>` 이전을 버리고 남은 텍스트의 첫 정수 match를 찾으며, 없으면 zero~twenty의 영어 수 단어를 찾는다. 숫자와 수 단어가 함께 있으면 숫자 검색이 우선이다. 이를 일반적인 의미 이해나 마지막 결론 추출이라고 해석하면 안 된다. CountBenchQA 설정은 `vikhyatk/CountBenchQA`의 `test`, temperature 0, 최대 32 new tokens, “single number” 후속 지시를 사용한다. dataset revision은 YAML에 고정되지 않는다. CountQA의 집중/비집중 subset metric이 CountBenchQA에 새로 추가된 것은 아니다. [helper 원문](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/09920f2cfbb667d5278e18354e4ab9034c9806c0/lmms_eval/tasks/countqa/utils.py), [평가 YAML](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/09920f2cfbb667d5278e18354e4ab9034c9806c0/lmms_eval/tasks/countbenchqa/countbenchqa.yaml), [데이터셋 원문](https://huggingface.co/datasets/vikhyatk/CountBenchQA).

**관측 → 진단 → 기전·추론.** 이전 score에는 시각적 계수 오류와 출력 형식 위반이 섞여 있었다. 새 채점은 일부 형식 위반을 완화하지만 여러 숫자를 설명하는 응답에서 잘못된 수를 고를 가능성은 남는다. 실제 영향 비율·모델 순위 변화는 미측정이다.

**가설 → 최소 개입 → 실험 제안.** 모델을 다시 호출하지 않고 같은 sample ID·정답·원응답을 parent `ec8c326c56b123be8139bbfd53ac492ab71eb02c`와 수정 commit으로 재채점한다. 전환된 표본을 마침표·문장·수 단어·여러 숫자·추론 태그로 나누고 사람이 최종 의도를 감사한다. 전체 분모, parse 실패율, old/new accuracy, 전환 방향을 함께 기록한다. 여러 숫자·소수·부정 수 표현은 별도 경계 fixture로 점검한다.

**GO/KILL.** 형식만 다른 정답이 회복되면 채점 복구로 기록한다. 모호한 응답의 오수락이 발견되면 해당 범주를 별도 보고하고 파서 하나로 모델 우열을 확정하지 않는다. 변화가 없으면 보유 결과에서 영향 없음으로 종료한다.

**비교 판정.** 동일 저장 응답의 paired 재채점은 evaluator 효과를 분리한다. old/new headline accuracy를 모델 향상량으로 비교하는 것은 **not strictly apples-to-apples**다. 새로운 backbone·학습 데이터·작은 물체 인식 개선의 근거는 아니다.

## 2. 영상 구간 — 질문이 지정한 시간만 실제로 보았는가

**확인 사실.** 자동 message 변환은 `video_start/video_end` 또는 `start_time/end_time`을 video content의 시간 필드로 옮긴다. Gemini chat·simple 경로는 해당 구간을 video metadata로 전달한다. Phi-4 chat은 bounds를 풀어 loader에 넘기고 loader는 전체 영상 대신 지정 구간의 frame index 범위에서 균등 샘플링한다. [공식 변경](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/8e07e581a8d967990b22fe1c13428e99d5173156).

**maintainer 설명.** 구간 정보가 중첩 media URL 안에 남아 Qwen에 전달되지 않거나 Gemini에서 전체 파일을 처리하고, Phi-4에서는 전체 파일의 index를 샘플링하던 문제를 설명한다. 수정 후 모든 backend와 모든 task의 시간 처리가 동등하다고 독립 확인한 것은 아니다.

**공식 테스트와 외부 문서.** 추가 테스트는 색이 다른 프레임을 가진 합성 영상으로 2~4초 metadata, 0초 시작, 무구간 입력, legacy dict, Phi-4 구간 index를 검사한다. Gemini 부분은 fake SDK type과 upload 함수로 metadata를 검사하므로 실제 서비스가 그 구간을 처리했다는 end-to-end 증거는 아니다. Google 공식 문서도 start/end offset에 의한 clipping을 설명하지만 현재 문서 예시는 Interactions API다. 이 commit의 `types.Part` 경로와 현재 예시의 API 차이를 남긴다. [공식 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/8e07e581a8d967990b22fe1c13428e99d5173156/test/models/test_video_interval.py), [Google 영상 처리 문서](https://aistudio.google.com/docs/video-understanding).

**관측 → 진단 → 기전·추론.** 지정 구간 밖의 증거가 유입되거나 제한된 frame budget이 전체 영상에 흩어지면 temporal reasoning 결과가 달라질 수 있다. 결과 방향은 단정할 수 없다. 구간 제한이 관련 프레임 밀도를 높일 수도 있고, 이전에 보던 외부 단서를 제거할 수도 있다. 파일 전체 upload와 모델이 관측하는 전체 구간도 구분해야 한다.

**가설 → 최소 개입 → 실험 제안.** 먼저 모델 없이 request→chat→backend payload의 start/end를 감사한다. Phi-4에서는 같은 영상·frame 수로 parent `7d932d24561dcee6c34d5abec267401b0d1bd21b`와 수정 버전의 선택 frame timestamp를 비교한다. CFR 합성 영상에서 시작 0, 열린 경계, 역전 구간, 영상 밖 시각, frame 수보다 짧은 구간을 점검한다. 범위 보정·중복 index도 기록한다. 이후 실제 사용 task에 시간 구간이 있는 표본만 고정 checkpoint·prompt·frame budget·resolution·decode budget으로 paired 추론한다.

**GO/KILL.** metadata 소실 또는 구간 밖 샘플링이 확인되면 그 경로의 기존 결과부터 재평가한다. 구간을 지정하지 않거나 별도 loader를 쓰는 task에는 자동으로 영향 있다고 하지 않는다. 서비스 호출 검증 없이 mock 성공을 API 재현 성공으로 보고하지 않는다.

**비교 판정.** 전체 영상과 지정 구간 입력은 **not strictly apples-to-apples**다. 동일 frame 수라도 유효 시간 범위와 중복 비율을 보고해야 한다. 지난 보고서의 uint8/THWC 변환과는 별개의 시간 증거 수정이다.

## 3. VLMEvalKit MCQ — 최종 답과 실제 라벨 집합을 맞춘다

**확인 사실.** `can_infer_last_option`은 마지막 비어 있지 않은 줄에서 bare label, answer/option/choice 형식, 일부 화살표 형식을 인식한다. boxed·강조 표시를 정리하고 실제 choices에 속한 경우에만 반환하며 기존 option/text 추정보다 우선한다. 기존 실패 문자열·거부 처리는 그보다 앞에 남아 있다. 따라서 “언제나 마지막 글자를 선택”하는 구현이 아니다. [공식 diff](https://github.com/open-compass/VLMEvalKit/commit/c0f938b32f2a7a2ab93e9d42fb21ad09f5d50470), [전체 matching 코드](https://github.com/open-compass/VLMEvalKit/blob/c0f938b32f2a7a2ab93e9d42fb21ad09f5d50470/vlmeval/utils/matching_util.py).

**두 번째 변경·확인 사실.** 일반 영어·중국어 judge prompt는 고정 A~D 대신 `build_choices`에서 얻은 실제 라벨을 받는다. BLINK·WeMath·LEGO 전용 prompt 경로는 그대로이므로 이 개선을 모든 dataset에 일반화하지 않는다. local inference로 답을 얻으면 judge 호출 없이 반환한다. [호출 경로](https://github.com/open-compass/VLMEvalKit/blob/c0f938b32f2a7a2ab93e9d42fb21ad09f5d50470/vlmeval/dataset/utils/multiple_choice.py).

**maintainer 설명과 검증 수준.** commit 제목은 최종 선택지 우선과 유효 judge 라벨 사용을 수정 의도로 명시한다. 해당 commit의 변경 파일은 두 개이며 새 회귀 테스트는 포함되지 않는다. 본 실행에서는 함수와 호출자를 읽어 정적 확인했고 실제 judge 호출이나 benchmark 재채점은 하지 않았다. 지난 lmms-eval 파서 수정과 같은 구현이라고 간주하지 않는다.

**관측 → 진단 → 기전·추론.** reasoning에 등장한 중간 선택지와 최종 답이 다를 때 파서가 중간 답을 고르면 능력 평가가 출력 구성에 오염된다. 또한 E 이상 선택지가 있는 문제에서 고정 A~D 지시는 judge의 응답 공간을 왜곡할 수 있다. 수정은 local parse와 judge prompt 양쪽을 바꾸므로 두 효과를 따로 분해해야 한다.

**가설 → 최소 개입 → 실험 제안.** 저장된 원응답·choices로 parent `6a49a8e2a496a314f5267be715c75c0aef93f4f7`와 수정 버전의 local parse만 먼저 비교한다. 중간 A·마지막 B, boxed 답, trailing 설명, 없는 라벨, 거부 문구, E 이상 라벨을 포함해 label 전환과 judge 필요 여부를 기록한다. 그다음 같은 judge·seed 정책·유효 choices를 고정하고 prompt 변경만 별도 비교한다. 기존 judge 결과 cache를 새 protocol과 섞지 않는다.

**GO/KILL.** 최종 답 복구와 judge 호출 감소가 확인되면 accuracy·parse coverage·judge 호출 수를 따로 보고한다. 애매한 마지막 줄의 오수락이 늘면 인간 감사 후 범위를 제한한다. 코드에 남은 judge 재시도 소진 후 무작위 fallback도 별도 집계해야 한다. label 처리 개선이 judge 불확실성 전체를 제거하지는 않는다.

**비교 판정.** evaluator와 judge prompt가 다른 점수는 **not strictly apples-to-apples**다. 새 학습·시각 encoder 변경을 증명하지 않으며 실제 영향 dataset·변화량은 아직 미확인이다.

| compute budget | 계수·local MCQ는 저장 응답 재채점 가능. 영상 재추론·judge API 비용은 별도이며 VRAM·비용 실측 없음 |
| evaluator version | 각 고정 commit과 parent로 비교. dataset·processor·SDK·judge revision도 추가 기록 필요 |
| 논문·code·leaderboard | 코드의 실제 변화는 확인. 논문 headline·공식 순위의 새 상승을 검증한 보고서는 아님 |

detection·segmentation·OVD·aerial/UAV·remote sensing·maritime 전용 순위 변화는 충분한 직접 근거를 확보하지 못했다. 관련 없는 수치와 placeholder로 항목을 늘리지 않았다. 보조 탐색의 `roboflow/benchmarks` commit 조회는 404였으며 해당 저장소에 대한 근거로 사용하지 않았다.

## 오늘의 benchmark signal 3개

1. **계수의 형식 효과:** 숫자를 맞혔는지와 “숫자만 출력”을 지켰는지 분리하고 metric 이름보다 실제 구현을 기록한다.
2. **시간 증거의 범위:** 구간 metadata가 실제 backend와 선택 프레임까지 도달했는지 확인한 뒤 temporal reasoning을 평가한다.
3. **답·라벨 계약:** 마지막 의도와 유효 선택지 집합을 고정하고 local parser 효과와 judge 효과를 분리한다.

## 내 연구에 바로 연결되는 포인트

- **오늘 먼저:** 저장된 계수 원응답을 재채점하여 시각적 계수 오류와 형식 오류를 분리한다. 정확도 차이가 없으면 그 결과를 그대로 남긴다.
- **CCTV·해양 안전 video VQA:** 사고 전후 구간을 지정한 평가에서 실제 선택 timestamp와 질문 구간을 함께 보존한다. 전체 영상을 본 결과를 짧은 clip의 추론 능력으로 표현하지 않는다.
- **Answer–Region Gap:** 맞는 선택지를 추출한 것과 올바른 영상·영역 증거를 본 것은 별개다. 채점 복구만으로 grounding 정합성을 인정하지 않는다.
- **small/tiny object·P2:** 계수 파서 수정은 작은 객체 AP 개선 근거가 아니다. 물체 크기별 연구에는 별도 size annotation·localization 지표가 필요하다.
- **RTX 5060 Ti 8GB:** 저장 응답 감사와 metadata·frame index 검사는 대형 모델 적재 없이 설계할 수 있다. 영상 모델·외부 judge가 8GB에서 실행된다는 보장은 하지 않는다.

모든 최소 실험은 후속 제안이다. 본 실행에서 새 모델 성능이나 회귀 테스트 통과를 측정하지 않았다.
