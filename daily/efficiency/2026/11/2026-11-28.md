## 1. TensorFlow — CPU 지정과 실제 GPU 배치는 달랐다

**사실:** #27401 head `248169e5dd9d5d70c0abbf9e1eeca513a2b349bd`는 SavedModel/GraphDef 로딩 시 TensorFlow의 GPU visibility를 비운다. 이미 사용자 코드가 TensorFlow GPU를 초기화했다면 예외를 억제하므로 기존 배치는 그대로일 수 있다. `device=0`도 이 경로를 GPU로 전환하지 않는다. [구현](https://github.com/ultralytics/ultralytics/pull/27401/files)

**리뷰어 재현:** RTX PRO 6000 Blackwell, Linux, Python 3.12, TensorFlow 2.19.0, CUDA 12 torch에서 기존 코드는 `device="cpu"`여도 GPU kernel 오류가 나고 약 95GB를 점유했다. 수정본은 SavedModel/GraphDef·CPU/GPU 요청 네 경우 모두 5개 box를 반환하고 GPU를 건드리지 않았다고 보고했다. [리뷰 원문](https://github.com/ultralytics/ultralytics/pull/27401#issuecomment-7218652985)

**수용한 비용:** 같은 카드에서 TensorFlow 2.21과 별도 import-order 수정 #27400으로 GPU가 정상 동작할 때 YOLO26n은 5.5~8.4ms였고, 8개 CPU core에서는 12.0ms였다. 기본 threads를 사용한 384-thread host에서는 약 145ms라는 보고도 있다. 이를 95GB 제보가 나온 TF 2.19 실패 환경과 하나의 동일 조건 전후 표로 합치면 **not strictly apples-to-apples**다.

**조건·한계:** SavedModel은 FP32 경로다. `bus.jpg` 입력은 확인했으나 이 timing의 명시적 batch·resize shape·warm-up·반복 수·CPU 모델·정확한 torch build·clock은 미확인이다. COCO8 mAP50 0.900과 5개 box는 배포 정확도 동등성의 충분한 증거가 아니다. Python 3.13의 `UnknownError`는 리뷰어가 #27400 이후 재현하지 못했으므로 합의된 실패로 쓰지 않는다.

**진단→가설:** 상위 wrapper의 CPU 표기와 TensorFlow의 실제 placement가 어긋나면 숨은 GPU 할당·호환성 오류가 생길 수 있다. CPU 강제는 이를 제거하지만 GPU 가속 이득도 제거한다.

**최소 실험·GO/KILL:** 같은 artifact hash·batch 1·고정 입력으로 fresh process/TF 사전 초기화 × visibility 설정을 대조한다. 실제 device trace, GPU allocation, load/첫 호출/warm p50·p95와 출력 오차를 분리한다. CPU 배포 의도와 실제 placement가 일치하면 GO. `device="cpu"` 문자열만으로 device와 메모리를 판정하면 KILL.

## 2. OCR TensorRT — engine만 배송할 수 있게 됐다

**사실:** #27408 head `11cbc38e66635fb6b2f9fdd67971d183c5846d84`는 `.engine` 경로를 `TensorRTBackend`에 직접 넘긴다. 이전에는 engine 단독 경로가 ONNX로 해석돼 실패했고, build를 피하려면 cache 이름의 engine과 76.6MB ONNX를 함께 두어야 했다. GPU·TensorRT 버전에 맞는 engine이 필요하다. [구현](https://github.com/ultralytics/ultralytics/pull/27408/files)

**리뷰어 재현:** RTX PRO 6000 Blackwell, TensorRT 11.5.0.63, torch 2.15.0+cu132, Python 3.12에서 PP-OCRv6 medium recognizer의 FP16 engine을 시험했다. network가 없는 container의 빈 폴더에서 engine 단독 load는 0.30초, `engine=True`와 함께 주면 0.33초였다. 기존 코드는 각각 ONNX load 오류와 DecodeError였다. ONNX에서 처음 build하는 경로는 전후 30.6/31.1초로 유지됐다. 다섯 word crop의 읽기 결과도 같았다고 보고했다. [리뷰 원문](https://github.com/ultralytics/ultralytics/pull/27408#issuecomment-7230115687)

**조건·한계:** 이것은 build와 load의 서로 다른 작업이므로 **not strictly apples-to-apples**다. 31초→0.30초를 순수 inference 가속률로 계산하지 않는다. 실제 crop 크기·batch·warm-up·반복·OS/driver는 미확인이다. 코드의 engine build 상한은 dynamic batch 8, 높이 48, 폭 3200이지만 실제 timing의 입력 shape로 대체하지 않는다. Jetson·TensorRT 10.3·Python 3.10은 검증되지 않았다.

**진단→가설:** 배포 시작 비용의 일부가 kernel보다 불필요한 artifact 의존성과 build 경로에 있을 수 있다. 기존 cache hit도 build를 피하므로 모든 기존 배포가 31초를 절약하는 것은 아니다.

**최소 실험·GO/KILL:** 같은 target stack에서 ONNX+cache/engine 단독/최초 build를 분리한다. offline 시작, 실제 file read/write, load 시간, 첫 crop·warm inference, 전체 OCR 품질과 배포 용량을 측정한다. 동일 target에서 engine 단독 부팅과 품질을 통과하면 GO. Blackwell 성공을 Jetson 호환성 검증으로 간주하면 KILL.

## 3. WebGPU — prefill의 메모리·workgroup 비용을 줄였지만 decode는 그대로다

**사실:** 미병합 #33192 head `7ffdfdac7c820f1e6c5b902304c64eade6a1a353`는 RMS_NORM_MUL의 64행 이상 workgroup을 128 threads로 선택하고, Flash Attention tile K row를 padding하며, 완전히 masked된 tile 계산을 건너뛴다. `pow(x,2)`도 곱셈으로 바꾼다. 여러 변경이 함께 들어가 개별 기여는 분리되지 않았다. [구현](https://github.com/ggml-org/llama.cpp/pull/33192/files)

**저자 측정:** Chrome 156·Apple M5 Max, wllama WebGPU, unsafe flags 없음, 약 980-token prompt, 교대 3회 median이다.

| 모델·weight precision | prefill 전→후 tok/s | decode 전→후 tok/s |
|---|---:|---:|
| Qwen3-0.6B Q4_K_M | 1598→2717 | 157.1→157.7 |
| Qwen3-0.6B Q8_0 | 1650→2871 | 159.4→158.8 |
| Llama-3.2-1B Q4_K_M | 1584→1648 | 193.3→193.7 |
| Gemma-3-1B Q4_K_M | 1541→1919 | 116.9→117.0 |

**교차 조건:** RTX 5060 Ti·native Dawn Vulkan, subgroup-matrix off, `llama-bench -fa 1`, 교대 2회×5 repetitions의 median에서 Qwen3-0.6B Q4_K_M pp512는 2550→3453 tok/s였다. default subgroup-matrix on에서는 6103→8267이었다. 반면 Llama-3.2-1B default pp512는 5231→5214였다. Chrome과 Dawn, feature on/off를 직접 비교하면 **not strictly apples-to-apples**다. [측정 원문](https://github.com/ggml-org/llama.cpp/pull/33192)

**조건·한계:** 정확한 base SHA·wllama/Dawn commit·OS/driver·batch/ubatch·warm-up·power mode는 미확인이다. quant 이름은 weight 형식이며 모든 연산의 accumulator precision을 뜻하지 않는다. 저자는 masked tile 생략의 exact output을 주장하지만 공개 본문에는 전체 모델 품질 대조가 없다.

**진단→가설:** Q/K normalization과 tile memory access가 prefill 병목인 모델에서 효과가 클 수 있다. decode와 다른 모델의 작은 변화는 범용 가속이라는 해석을 제한한다.

**최소 실험·GO/KILL:** 고정 browser/runtime·weight·batch·prompt에서 workgroup/padding/mask skip을 하나씩 켜고 pp·tg, first-token latency, timestamp profile, 출력 오차를 비교한다. 실제 사용하는 모델의 prefill과 정확도가 개선되면 GO. Qwen 결과를 모든 모델·decode·전력 개선으로 확대하면 KILL.

## 4. Inkling — 공유 weight와 독립 상태의 위치가 throughput을 바꿨다

**사실:** 미병합 #33198 head `601e4f51af6735965c7d84860824b5a55effa8d0`는 Inkling loop pass의 독립 KV/recurrent state를 공유하는 physical layer의 device에 배치한다. full offload·layer split·다중 GPU·tensor override 없음에만 적용된다. cache를 공유하거나 모델 크기를 줄이는 변경은 아니다. [구현](https://github.com/ggml-org/llama.cpp/pull/33198/files)

**저자 측정:** Tesla T4 두 장, Inkling 2 Mini UD-Q4_K_XL, upstream `a386950` 기반 같은 binary에서 placement만 toggle한 A/B/A다. CUDA Flash Attention on, 동일한 uncached prompt 32,768 tokens, 생성 128 tokens·temperature 0이다. 설정은 `-ngl 999 -sm layer -ts 1,3 -fa on -b 2048 -ub 64 -c 33280 -np 1`이다.

| run | prefill tok/s | decode tok/s | 상태-device 불일치 KV/recurrent | graph splits |
|---|---:|---:|---:|---:|
| 기존 A1 | 222.56 | 12.09 | 14/14 | 283 |
| placement 수정 | 261.95 | 25.33 | 0/0 | 7 |
| 기존 A2 | 212.57 | 11.43 | 14/14 | 283 |

저자는 A1/A2 평균 대비 prefill +20.4%, decode +115.3%를 보고했다. 128개 greedy token ID는 같았지만 일부 top-10 순위와 확률은 달랐다. [측정 원문](https://github.com/ggml-org/llama.cpp/pull/33198)

**조건·한계:** CUDA toolkit·driver·OS·compiler·warm-up·GPU interconnect topology·clock은 미확인이다. A/B/A는 drift 점검에 유용하지만 seed·요청 길이·split 비율을 바꾼 반복은 없다. 상태가 특정 GPU에 집중되면 그 장치 메모리 여유가 줄 수 있다는 것은 배치 코드에서 도출한 **추론**이며 실측 peak 수치는 없다. 자동 코드 리뷰는 독립 성능 재현으로 세지 않는다.

**진단→가설:** 연산량이 같아도 state와 weight의 device 불일치가 graph 분할과 전송을 늘릴 수 있다. split 감소와 throughput 회복은 이 가설을 지지하나 profiler의 전송량 측정이 더 필요하다.

**최소 실험·GO/KILL:** 같은 binary A/B/A를 유지하면서 짧은/긴 context·여러 split 비율을 대조한다. GPU별 peak memory, cross-device bytes, graph splits, pp/tg, token·logit 오차를 측정한다. 메모리 한도와 품질을 유지하며 전송·지연이 함께 줄면 GO. partial offload·다른 loop 모델에도 같은 이득을 보장하면 KILL.
