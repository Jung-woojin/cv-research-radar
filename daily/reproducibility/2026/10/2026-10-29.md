## 사례 1 — MoI-Bench: evaluator와 샘플 artifact를 먼저 고정해야 하는 모바일 편집 benchmark

**확인 사실.** MoI-Bench는 64개 하위과제와 1,150개 샘플, 16개 operation 및 8개 visual target category를 제시하며, MoI-Eval에서 instruction following·visual quality·detail preservation의 과제별 기준을 사용한다고 설명합니다.  
**저자 주장.** Operation × Target 분석과 Quality–Deployability map이 compact model 개선 지점을 더 세밀하게 드러낸다고 주장합니다.  
**관찰된 gap.** 오늘 확인한 공식 arXiv 원문에는 sample-level evaluation question, exact prompt/image preprocessing, aggregation 구현, 공개 artifact 위치를 검증할 수 있는 링크가 보이지 않았습니다. 이는 artifact가 존재하지 않는다는 뜻이 아니라, 현재 원문만으로 동일 evaluator를 재구성할 수 없다는 뜻입니다.  
**가능한 mechanism.** 편집 benchmark의 순위는 질문 문구, judge 설정, image resize/crop, aggregation weight에 민감할 수 있으므로, 이들이 고정되지 않으면 모델 차이와 evaluator 차이를 분리하기 어렵습니다.  
**최소 반증 실험.** 저자가 제공하거나 명시한 20개 샘플과 evaluation question을 고정하고, 두 evaluator 구현에서 operation별 점수·전체 순위의 Spearman 상관을 측정합니다.  
**GO/KILL.** GO: 원본 질문·전처리·집계 코드가 공개되고 구현 간 순위 상관이 높을 때. KILL: 이 요소들이 확인되지 않거나 소수 구현 변경만으로 순위가 크게 바뀔 때.  
**해석.** 지금은 모델 성능 재현보다 evaluator artifact 확보가 선행 조건입니다.

## 사례 2 — GameVerse: long-horizon claim은 split과 연속 시퀀스 계보가 핵심

**확인 사실.** GameVerse는 69.7K clips, 1,655시간, 349.6M frames와 1,358시간의 연속 2분 시퀀스를 보고하며, scene-consistent segmentation·quality filtering·camera pose estimation·event-based caption annotation을 설명합니다.  
**저자 주장.** 이 데이터로 학습하면 interactive world model의 temporal horizon이 크게 확장된다고 주장합니다.  
**관찰된 gap.** 원문 초록만으로는 train/validation/test의 게임·episode·연속 sequence 단위 분리, 같은 원본 playthrough의 근접 중복 차단, 데이터 manifest 및 download/license artifact를 확인할 수 없었습니다. 따라서 현재는 보유 시간 수치만으로 독립적인 generalization 주장을 재현할 수 없습니다.  
**가능한 mechanism.** 같은 게임·맵·playthrough의 인접 구간이 split을 가로지르면, 장기 coherence 향상이 환경 기억 또는 중복 프레임 회수의 영향일 수 있습니다. 반대로 episode-level split은 실제 난이도를 올릴 수 있습니다.  
**최소 반증 실험.** video/episode/group ID가 있는 manifest를 바탕으로 (a) clip-level, (b) episode-level, (c) game-level split을 만들고, 동일 checkpoint의 long-horizon metric을 각각 비교합니다. 모든 split에서 camera trajectory와 caption 생성 버전도 고정합니다.  
**GO/KILL.** GO: game/episode disjoint split에서도 주장이 유지되고 manifest가 공개될 때. KILL: clip-level에서만 이득이 유지되거나 group leakage를 audit할 수 없을 때.  
**해석.** 이는 leakage가 확인됐다는 주장이 아니라, long-horizon 결과를 해석하기 위한 최소 split audit입니다.

## 사례 3 — ScIntBench: simulator·action interface가 없는 동적 상호작용 수치는 재현 사양이 아니다

**확인 사실.** ScIntBench는 12개 시스템과 10개 room type에서 physical interaction을 평가하며, 초록은 평균 11.54% 성공, 12개 시스템 중 7개는 zero-interaction, 최고 결과는 36.92%라고 보고합니다.  
**저자 주장.** 기존 spatial intelligence 평가가 정적 감지에 치우쳤고, ScIntBench가 dynamic physical interaction을 측정한다고 주장합니다.  
**관찰된 gap.** 오늘 확인 가능한 공식 초록에는 simulator/version, action-space discretization, observation reset, success evaluator, seed, timeout/retry policy가 명시되지 않았습니다. 정확한 code release가 별도로 존재할 수 있으나 현 점검에서 검증하지 못했습니다.  
**가능한 mechanism.** embodied interaction은 action step 수, camera/physics reset, retry budget의 작은 차이로 success rate가 달라질 수 있어, 모델의 spatial reasoning과 environment controller의 차이를 분리해야 합니다.  
**최소 반증 실험.** 동일 모델·prompt를 고정한 채 seed 5개 이상에서 (1) official action space, (2) action granularity 절반, (3) retry budget 고정 조건을 비교하고, per-room success와 confidence interval을 기록합니다.  
**GO/KILL.** GO: environment build hash, evaluator, seeds, reset/retry policy가 제공되고 조건 변화에도 결론 방향이 유지될 때. KILL: 핵심 사양 부재로 동일 environment를 만들 수 없거나 retry policy에 따라 결론이 역전될 때.  
**해석.** 초록의 수치는 baseline 신호로는 유용하지만, 현재 공개 확인 범위에서는 독립 비교의 완결된 specification은 아닙니다.

## 공통 진단 → 가설 → 최소 개입

**진단.** 세 사례 모두 결과 수치나 데이터 규모는 제시하지만, 독립 실행자가 결과를 다시 만들기 위한 artifact 계층—data manifest/split, evaluator·environment version, preprocessing·aggregation, seed·timeout policy—은 현재 확인 범위에서 완결적으로 연결되지 않았습니다.

**가설.** 재현성 실패의 큰 비중은 모델 코드 자체보다 “평가 구성의 미고정”에서 발생하며, artifact manifest와 10–30분 smoke test를 release gate로 삼으면 나중의 성능 분쟁을 줄일 수 있습니다.

**최소 개입.** 각 프로젝트에 \`repro/\` 아래 (1) 환경 lockfile, (2) 10–20개 canonical sample manifest, (3) 단일 command evaluator, (4) fixed-seed expected output hash 또는 tolerance, (5) split/group-overlap audit를 추가합니다.

**오늘의 GO/KILL.**  
- GO: 위 다섯 artifact를 받는 프로젝트만 재현 실험 우선순위에 올립니다.  
- KILL/보류: 코드 설치 전에도 evaluator 또는 split 계보를 확인할 수 없으면 성능 비교를 진행하지 않습니다.

## 재현성 체크리스트

- seed뿐 아니라 Python/NumPy/PyTorch RNG, DataLoader worker, deterministic algorithm, cuDNN benchmark, precision/TF32, PyTorch·CUDA·driver 버전을 함께 기록한다.
- PyTorch는 동일 seed라도 release·platform·CPU/GPU가 다르면 완전한 재현을 보장하지 않는다고 안내한다. 단일 seed score를 범용 결과로 해석하지 않는다.
- benchmark는 data hash, sample/group ID, split 생성 코드와 evaluator commit을 함께 고정한다.
- 비교 조건이 다르면 **not strictly apples-to-apples**로 표기한다.
- 오늘은 위 논문의 code/data를 설치·실행하지 않았으므로, 실행 성공·실패나 성능 격차를 주장하지 않는다.
