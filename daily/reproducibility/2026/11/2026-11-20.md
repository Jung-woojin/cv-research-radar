## 1. PRX: callback 호출과 intervention 적용은 다르다

**Claim / 관측 보고.** #15355는 11/20 02:49 UTC에 게시됐다. 작성자는 마지막 step callback에서 latent를 0으로 바꿔 반환해도 결과가 0이 되지 않는다고 보고했다. tiny fixture의 callback 테스트 실패와 수정 후 통과를 제시했으며, 실제 `Photoroom/prx-512-t2i-sft` checkpoint는 실행하지 않았다고 명시했다.

**재현 조건.** Diffusers `0.44.0.dev0`, main `4f78832`, Python 3.12.16, PyTorch 2.15.0, macOS arm64 CPU, Transformers 5.23.0. 실제 학습 데이터·benchmark split·GPU·배치별 품질 수치는 없다.

**소스로 확인한 사실.** [PRX latent pipeline](https://github.com/huggingface/diffusers/blob/4f78832/src/diffusers/pipelines/prx/pipeline_prx.py#L802-L807)과 [pixel pipeline](https://github.com/huggingface/diffusers/blob/4f78832/src/diffusers/pipelines/prx/pipeline_prx_pixel.py#L638-L643)은 callback을 호출하지만 반환값을 받지 않는다. [공식 테스트](https://github.com/huggingface/diffusers/blob/4f78832/tests/pipelines/prx/test_pipeline_prx.py#L23-L30)는 이 동작을 이유로 strict xfail을 선언한다. 조회 시 이슈는 open, 댓글은 없다. 수정 병합·릴리스는 확인하지 못했다.

**Observed gap.** 작성자가 보고한 격차는 반환 latent의 미적용이다. 이미지 품질 하락이나 논문 점수 미달을 측정한 결과는 아니다. Tensor를 제자리에서 수정하는 callback까지 모두 무효라고 일반화할 근거도 없다.

**진단 → 가설.** 반환 dict를 읽지 않으면 callback 기반 ablation이 실제 intervention 없이 baseline처럼 실행될 수 있다. 이때 결과 차이가 작다는 관측은 intervention의 무효성을 뜻하지 않을 수 있다.

**최소 실험.** 같은 초기 latent·scheduler·step 수로 identity callback과 마지막 step의 latent를 새 zero tensor로 교체해 반환하는 callback을 비교한다. 먼저 latent 출력 경로에서 검사하고, 두 PRX pipeline 모두에서 `--runxfail`로 관련 테스트를 노출한다. 반환 dict 적용만 바꾼 뒤 동일 검사를 반복한다.

**GO/KILL.** 반환 전후 latent가 실제로 달라지고 identity 경로가 보존되면 실제 checkpoint 실험으로 GO. callback 전달 자체가 없거나 출력이 zero와 무관한 후처리를 포함하면 fixture를 먼저 수정한다. 반환 적용 후에도 intervention이 반영되지 않으면 단일 원인 가설은 KILL. `prompt_embeds` 변경의 유효성은 별도 데이터 흐름 검사가 필요하다.

## 2. Kolors PAG: IP-Adapter 입력 오류와 LoRA loader 수정은 별개다

**Claim / 관측 보고.** #15347은 11/19 03:29 UTC에 게시됐다. 작성자는 raw image 입력에서 `NoneType` 순회 오류, 두 adapter의 사전 계산 embedding 입력에서는 projection 목록 길이 불일치를 보고했다. #15348은 UNet-only LoRA도 `text_encoder_2` 참조에서 실패한다고 보고했다. 두 이슈는 같은 작성자의 조사이며 독립 재현 두 건으로 세지 않는다.

**재현 조건.** 보고된 revision은 `2bb9468`, Diffusers `0.44.0.dev0`, Windows, Python 3.12.16, PyTorch 2.14.1+cu130, Transformers 5.16.1, PEFT 0.21.3이다. 최소 코드는 CPU tiny/random components를 사용한다. 작성자는 RTX 5090에서 실제 Kolors fp16 weights, 1024×1024로도 같은 오류를 봤다고 추가 설명했다. 실제 weights의 수정 후 품질 동등성은 제시되지 않았다.

**소스로 확인한 사실.** [고정 소스](https://github.com/huggingface/diffusers/blob/2bb9468/src/diffusers/pipelines/pag/pipeline_pag_kolors.py#L971-L992)는 준비된 embedding을 `image_embeds`에 저장한 뒤 다른 변수 `ip_adapter_image_embeds`를 순회한다. [UNet 전달부](https://github.com/huggingface/diffusers/blob/2bb9468/src/diffusers/pipelines/pag/pipeline_pag_kolors.py#L1040-L1045)는 목록 대신 loop의 `image_embeds`를 전달한다. 같은 클래스는 SDXL LoRA loader mixin을 상속한다.

**수정 상태.** [PR #15350](https://github.com/huggingface/diffusers/pull/15350)은 Kolors PAG LoRA loading 수정으로 11/19 06:38:27 UTC main에 병합됐다. merge commit은 `47e9b10bbe0e9951089db66d541d98a4d6ca28ba`다. 이 사실을 IP-Adapter 수정이나 배포판 포함으로 확대 해석하지 않는다. #15347은 조회 시 open이고 댓글이 없다.

**Observed gap / mechanism.** IP-Adapter는 준비된 목록·입력 목록·최종 Tensor를 혼동하는 데이터 흐름 문제다. LoRA는 단일 text encoder pipeline에 두 encoder를 전제하는 loader를 적용한 계약 불일치다. 두 문제를 같은 patch 하나로 해결됐다고 처리하면 안 된다.

**최소 실험.** adapter 0/1/2개 × raw image/사전 embedding × CFG/PAG 켜기·끄기를 나눠 UNet 직전 목록 길이·각 Tensor shape·finite 여부를 검사한다. 동일 이미지에서 계산한 embedding과 사전 embedding 경로를 맞춰 비교한다. LoRA는 병합 전후 revision에서 동일 UNet-only state dict를 로드하고 adapter 등록 및 tensor 변경을 확인한다.

**GO/KILL.** IP-Adapter 목록 길이가 projection 수와 일치하고 두 입력 경로가 지정한 수치 허용오차 안에서 일치하면 GO. 예외만 사라지고 마지막 adapter만 반영되거나 CFG/PAG batch 배치가 어긋나면 KILL. LoRA 로드 성공 뒤에도 실제 품질·scale 효과는 별도 확인한다. tiny CPU와 실제 fp16 GPU 비교는 `not strictly apples-to-apples`다.

## 3. Surya OCR: weight보다 tokenizer 구현부터 고정해야 한다

**Claim / 관측 보고.** #50902는 11/18 00:08 UTC 게시, 마지막 댓글은 11/18 16:44 UTC다. 작성자는 `datalab-to/surya-ocr-2`가 Transformers 5.17.0에서는 generic backend를 쓰지만 5.18.0~5.23.0에서는 Qwen3.5 tokenizer를 사용해 `×`, `½`, 악센트 문자 등이 손상된다고 보고했다. Python 3.12, tokenizers 0.23.3 조건이다. 전체 OCR CER/WER·데이터 split·hardware 성능 비교는 없다.

**교차 근거.** [별도 사용자](https://github.com/huggingface/transformers/issues/50902#issuecomment-6965999923)는 작은 로컬 WordPiece artifact에서 `seconds` 토큰이 사라지는 예제를 제시했다. [다른 댓글](https://github.com/huggingface/transformers/issues/50902#issuecomment-6967498520)은 generic tokenizer class를 보존하면 두 사례가 복구된다고 보고했다. 이는 별도 사용자 보고이며 이번 실행의 독립 실측은 아니다. maintainer 응답은 있으나 이슈는 open이다.

**소스로 확인한 사실.** [v5.23.0 AutoTokenizer](https://github.com/huggingface/transformers/blob/v5.23.0/src/transformers/models/auto/tokenization_auto.py#L863-L898)는 override 대상 model type에서 등록된 specialized class를 우선할 수 있다. [Qwen3.5 tokenizer](https://github.com/huggingface/transformers/blob/v5.23.0/src/transformers/models/qwen3_5/tokenization_qwen3_5.py#L45-L80)는 BPE backend와 ByteLevel decoder/pre-tokenizer를 구성한다. generic class 선택과 실제 tokenizer 내부 구현을 함께 확인해야 한다.

**수정 상태.** 관련 [PR #49579](https://github.com/huggingface/transformers/pull/49579)는 조회 시 open, `merged_at=null`이다. pipeline stage 보존과 tokenizer model 자체 보존은 별개이므로 이 PR이 모든 사례를 해결한다고 단정하지 않는다. 댓글의 “PR을 열겠다”는 발언도 병합 증거가 아니다.

**진단 → 가설.** 같은 checkpoint와 seed라도 tokenizer class·model·decoder가 바뀌면 다른 token sequence를 입력하거나 동일 출력 ID를 다르게 읽는다. 따라서 일부 OCR 성능 하락은 vision representation 손실 없이도 발생할 수 있다. 실제 benchmark 하락의 원인으로 확정한 것은 아니다.

**최소 실험.** 같은 artifact revision과 checksum을 보존하고 5.17.0/5.23.0 환경을 분리한다. 원문의 문자 문자열과 로컬 WordPiece fixture에 대해 class 이름, tokenizer model, normalizer, pre-tokenizer, decoder, encode ID, decode 문자열을 저장한다. direct artifact load와 AutoTokenizer를 비교한 다음 동일 저장 prediction ID를 두 decoder로 해독한다. 이 단계에는 모델 weights나 GPU가 필요 없다.

**GO/KILL.** artifact 직접 로드는 보존되고 AutoTokenizer 경로에서만 손상되면 tokenizer 선택 가설로 GO. 두 경로가 동일하거나 artifact 자체가 바뀌었으면 버전 override 단독 원인 가설은 KILL. 이후 고정된 OCR 평가셋에서만 CER/WER를 측정하며, prediction ID와 image preprocessing까지 같게 해야 decoder 효과를 분리할 수 있다.

## 오늘의 GO/KILL과 후속 행동

- **첫 GO: tokenizer artifact 검사.** 모델 없이 문자 손상과 토큰 소실을 분리할 수 있다. 버전 pin은 해당 재현 조건의 우회책이며 다른 환경의 보편적 권장 버전으로 일반화하지 않는다.
- **두 번째 GO: PRX callback 불변식 검사.** intervention이 실제 latent를 바꾸는지 확인한 뒤 ablation 결과를 해석한다.
- **세 번째 GO: Kolors 입력 계약 검사.** LoRA 병합 revision과 IP-Adapter 미확인 수정 상태를 각각 기록한다.
- **오늘의 KILL:** seed sweep으로 tokenizer·callback·adapter 계약 오류를 설명하려는 접근, 이슈 closed를 release 완료로 처리하는 접근, 작은 fixture 결과를 논문 성능 재현 성공으로 보고하는 접근.
- 모든 후속 비교에서 backbone, data/split, input resolution, pretraining, hardware, precision, batch, TTA, evaluator/version을 고정하거나 미확인으로 기록한다. 이번 사례들은 논문 간 SOTA 비교가 아니다.
- 공식 reproduction 성공, checkpoint 대 논문 표 discrepancy, 누락 학습 hyperparameter에 대해서는 이번 조사 범위에서 충분한 새 근거를 확보하지 못했다. 기존 사례를 반복하거나 미확인 수치를 보충하지 않는다.
