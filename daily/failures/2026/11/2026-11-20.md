## 1. 클래스 제한과 외부 COCO/LVIS 평가 대상이 불일치

**확인 사실:** #27288은 미병합이다. Diff는 외부 평가 직전 `args.classes`를 `class_map`으로 변환해 `val.params.catIds`에 전달한다. custom JSON인 `gdict` 경로와 `single_cls` 경로는 개입에서 제외된다. [공식 PR·재현 보고](https://github.com/ultralytics/ultralytics/pull/27288) · [수정 코드](https://github.com/ultralytics/ultralytics/pull/27288/files)

- **실패 조건·구성:** YOLO26n, `data=coco.yaml`, `classes=[17]` 같은 부분 클래스 validation. Label과 prediction은 필터링되지만 `faster-coco-eval`은 annotation 파일의 모든 category를 평가한다고 작성자가 보고했다. LVIS도 같은 evaluator 경로를 사용한다.
- **작성자 재현:** COCO8 validation 네 이미지에서 label을 COCO 형식으로 변환한 fixture와 CPU prediction을 사용했다. 외부 box mAP50–95가 9.73%에서 58.38%로 바뀌어 COCO category 19로 제한한 직접 평가와 일치했다고 보고했다. 일곱 조건의 prediction JSON은 전후 byte-identical이었다고 한다. 이는 전체 COCO/LVIS benchmark 결과가 아니다.
- **공식 인정·community 수준:** 자동 리뷰는 승인했다. 사람 maintainer glenn-jocher는 standalone validation의 native `all` 행이 외부 평가보다 먼저 출력되므로 수정 후에도 그대로일 수 있다고 설명하고 수치를 외부 mAP로 명시하도록 요청했다. 독립 실행 재현·사람의 최종 승인·병합은 확인하지 못했다. [maintainer의 지표 구분](https://github.com/ultralytics/ultralytics/pull/27288#issuecomment-7018810391)
- **진단 → 메커니즘:** 같은 클래스 선택 요청이 데이터·prediction에는 적용되지만 외부 평가기 설정에는 전달되지 않는다. 서로 다른 category 집합의 평균을 같은 지표로 읽으면 모델 개선으로 오인할 수 있다.
- **가설 → 최소 개입:** 평가기 category 집합을 prediction의 dataset ID mapping과 일치시키면 weight와 prediction을 바꾸지 않고 직접 제한 평가와 같아질 것이다.
- **최소 실험:** base `5c10b12bc026608748fffe68427ce6ea56eb4ee0`와 head `df6160688fc86781574de7b900cd13c7ce441ff1`에서 prediction JSON·annotation·evaluator 버전을 고정한다. 단일 클래스·복수 클래스·전체 클래스 및 LVIS fixture를 비교하고 JSON hash, `catIds`, native 지표, 외부 지표를 각각 기록한다.
- **GO/KILL:** 부분 클래스 외부 점수가 직접 evaluator 기준과 일치하고 전체 클래스 대조군이 보존되면 GO. Prediction이 달라지거나 custom JSON·single_cls를 손상하면 KILL/범위 축소한다.
- **기존 주장과 충돌·한계:** 전후 수치는 평가 대상 변경이므로 `not strictly apples-to-apples`다. 개선된 모델 정확도로 인용하면 안 된다. 실제 COCO val2017 전체와 LVIS 전체의 손실 크기는 미확인이다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **4/5**.

## 2. 빠른 epoch가 학습 plot thread를 추월해 관측 자료가 누락

**확인 사실:** #27279는 main의 `e1ec8c3445a196a1da03f87ee0cba1d43939da6c`로 병합됐다. Detection·classification의 plot 생산자 두 곳에 `.join()`을 추가했다. [공식 PR·실험 보고](https://github.com/ultralytics/ultralytics/pull/27279) · [diff](https://github.com/ultralytics/ultralytics/pull/27279/files)

- **실패 조건·구성:** Platform은 epoch 0 종료 시 `trainer.plots`에 등록된 `train_batch0-2.jpg`를 업로드한다. 작은 데이터·빠른 학습에서 비동기 `plot_images`가 저장·등록을 끝내기 전에 callback이 실행된다.
- **작성자 재현:** 생산 환경 NVIDIA 학습에서 이미지가 전혀 업로드되지 않은 사례를 보고했다. COCO8, `batch=1`, `fraction=0.75`에서는 수정 전 CPU 3/3회와 MPS 3/3회에 마지막 plot이 누락됐고, 수정 후 세 이미지가 모두 등록됐다고 한다. 생산 실행의 정확한 GPU·weight revision은 확인하지 못했다.
- **공식 인정·반대 증거:** maintainer는 코드의 경쟁 조건을 인정했지만 자신의 Mac CPU/MPS 22회 실행에서는 누락이 없었다고 밝혔다. `val=False`, COCO128의 한 batch epoch에서 마지막 plot 등록과 callback 사이 여유가 29~54 ms였다고 보고했다. 다른 사람 리뷰도 runtime 환경에 PyTorch가 없어 실행 검증을 못 했다고 명시했다. [maintainer 검토](https://github.com/ultralytics/ultralytics/pull/27279#issuecomment-7011885708)
- **재현 수준:** 작성자 반복 실험과 사람의 코드 검토는 있으나 독립적인 누락 재현은 실패했다. 두 환경은 `not strictly apples-to-apples`이며 원문 횟수를 발생 확률로 일반화하지 않는다.
- **진단 → 메커니즘:** 비동기 생산자의 thread handle을 버린 채 소비자가 현재 등록 목록만 읽는다. 모델 학습 실패보다 실험 관측 자료의 불완전성 문제다.
- **가설 → 최소 개입:** 생산 지점에서 완료를 기다리면 callback 전에 저장·등록이 끝나 hardware 속도에 따른 누락을 없앨 수 있다.
- **최소 실험:** base `cb4b7fe8e742852a94ea2f041b6dd455518e6fb5`와 병합 commit에서 동일 소형 학습 조건을 고정한다. 먼저 plot 완료·등록·epoch callback 시각을 계측하고, 자연 실행과 의도적으로 plot을 지연한 통제 실행을 나눈다. Callback 시 파일 존재·등록 여부·live thread·총 학습시간을 기록한다.
- **GO/KILL:** 통제 지연에서도 예상 plot이 callback 전에 등록되고 정상 이미지가 같으면 순서 진단 GO. 자연 실행에서 누락이 없다는 이유만으로 버그 부재를 선언하지 않는다. Plot 자체가 실패한 경우까지 join이 해결한다고 주장하면 KILL한다.
- **기존 주장과 충돌·한계:** “빠른 run의 시각화 누락=학습 데이터가 사용되지 않음”을 지지하지 않는다. 학습 gradient·AP 손상은 보고되지 않았다. CUDA의 독립 재현과 이 watch의 실행은 없다.
- **점수:** 심각도 **2/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **3/5**.

## 3. AMD Xilinx INT8 export 성공과 aerial 정확도 보존은 별개

**확인 사실:** #27286은 문서 변경으로 병합됐으며 새로운 정확도 수정 코드를 추가한 PR은 아니다. 공식 문서는 CPU에서 PyTorch와 quantized ONNX를 비교하고 보드 추론은 실행하지 않았다고 구분한다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27286) · [변경된 원문](https://github.com/ultralytics/ultralytics/pull/27286/files)

- **실패 조건·구성:** `ultralytics` 8.4.215, AMD Quark 0.13, ONNX Runtime 1.32.0, PyTorch 2.15.0, x86-64 Linux EPYC 9655 CPU. INT8 calibration은 기본 소규모 데이터이며 정확도 보존 실패를 관찰한 조건이지 export crash가 아니다.
- **작성자 수치:** COCO val2017 5,000장, `imgsz=640`, `batch=1`, 양쪽 `rect=False`, 기본 COCO128 calibration에서 YOLO26n mAP50–95는 PyTorch 40.3, INT8 36.7이다. DOTAv1 val 458장, `imgsz=1024`, 기본 DOTA128 calibration의 YOLO26n-obb는 46.4 대 38.0이다. 이 watch가 측정한 값이 아니다.
- **공식 인정·재현 수준:** maintainer는 오류 메시지와 Hard-Swish weight transfer를 검증했지만 COCO/DOTA 수치·파일 크기는 Linux Quark가 필요해 재검증하지 않았다고 명시했다. 과거 8.4.173/Vitis AI 6.3 compile 결과는 복원됐으나 현재 8.4.215의 보드 정확도·지연시간 검증을 뜻하지 않는다. 외부 community 재현은 미확인이다. [검증한 항목과 하지 못한 항목](https://github.com/ultralytics/ultralytics/pull/27286#issuecomment-7011824286)
- **진단 → 메커니즘:** 보고된 손실은 quantization을 포함한 export 경로에서 발생한다. Calibration 대표성·activation 범위·민감 연산을 의심할 수 있지만 어느 요인이 주원인인지 원문은 분리하지 않았다. DOTA가 COCO보다 더 민감한 이유가 tiny object 때문이라는 결론도 아직 근거가 없다.
- **가설 → 최소 개입:** 같은 weight·평가 split에서 calibration 표본만 바꿔 손실이 회복되는지 검사하면 표본 부족과 연산 민감도를 분리할 수 있다.
- **최소 실험:** 먼저 동일 조건의 PyTorch·FP32 ONNX·기본 INT8를 비교해 export 자체와 INT8 효과를 나눈다. 이후 calibration을 평가 val과 분리된 train 이미지로 구성하고 크기·장면을 통제해 반복한다. DOTAv1의 전체 mAP와 크기별 recall을 같은 evaluator에서 기록하고 calibration 파일 목록·seed·artifact hash를 남긴다.
- **GO/KILL:** FP32 ONNX가 baseline을 보존하고 calibration 개입으로 INT8 손실이 일관되게 줄면 표본 가설 GO. FP32부터 손실이 크거나 calibration 변경 효과가 불안정하면 해당 가설을 KILL하고 export·연산별 진단으로 이동한다.
- **기존 주장과 충돌·한계:** Export 성공·compile의 높은 NPU 배치율은 task 정확도 보존을 보장하지 않는다. 두 dataset의 하락 폭은 모델·task·해상도·calibration이 달라 `not strictly apples-to-apples`다. CPU 정확도 검사는 실제 NPU latency·전력의 증거가 아니다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **4/5**.

## 오늘의 실패 패턴 3개

1. **평가 범위 전달 누락:** prediction이 같아도 evaluator의 category 집합이 다르면 점수가 달라진다.
2. **비동기 관측 순서 위반:** 학습이 정상이어도 기록 생산이 늦으면 보고되는 실험 증거가 불완전해진다.
3. **배포 성공과 task 보존의 분리:** export·compile 성공만으로 quantized 모델 정확도와 실제 장치 성능을 보장할 수 없다.

## 논문 아이디어로 연결 가능한 빈틈

**조사자의 추론:** aerial/UAV 실험에서 모델 능력과 평가·관측·배포 계약 위반을 분리하는 진단 프로토콜이 유용하다. 동일 prediction의 category 불변성, 동일 run의 plot 완료 순서, 동일 weight의 FP32→INT8 변환을 각각 독립 축으로 삼는다.

첫 연구 질문은 “부분 클래스 성능 차이 중 얼마가 모델이 아닌 evaluator 범위에서 발생하는가”다. 여러 평가 구현에서 같은 요청을 검사해야 알려진 버그 하나를 넘는 가치가 생긴다. 두 번째는 calibration 장면·크기 분포가 OBB의 크기별 recall 손실을 설명하는지다. 현재 수치만으로 tiny-object 특이 실패나 domain shift를 주장할 수 없다. 관측 자료 누락은 재현성 보조 연구로 다루며 학습 성능 저하와 구분한다.

## 직접 재현해볼 최소 실험

**첫 순위는 고정 JSON의 CPU category 검사다.** 네 이미지 fixture로 시작해 class 17→dataset category 19 mapping, 직접 제한 evaluator와 wrapper의 일치, 전체 클래스 대조군 보존을 확인한다. Weight 다운로드가 불필요하도록 기존 prediction을 fixture로 고정할 수 있다. Native `all` 행과 외부 평가 결과를 별도 수집한다.

두 번째는 plot thread의 통제 지연 실험이다. 세 번째는 Linux CPU의 FP32 ONNX 대조부터 시작하는 INT8 정확도 검사다. 초기 evaluator·순서 검사는 RTX 5060 Ti 8GB 없이도 가능하다. DOTA 전체 검증 시간·메모리는 측정하지 않았으므로 비용을 보장하지 않는다.

**공통 GO:** 고정 revision에서 관찰을 재현하고 최소 개입이 정상 대조군을 보존한다. **공통 KILL/축소:** 입력·평가 대상·runtime이 달라진 비교나 재현되지 않은 대규모 주장은 중단한다. 이번 실행에서 실험·AP·VRAM·지연시간을 직접 측정하지 않았으며 /5 점수는 조사자의 우선순위 판단이다.
