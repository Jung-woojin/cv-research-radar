## 5. 점검 도구 상태

### 확인된 사실

- `python -B scripts/radar_health.py`는 exit code 0으로 끝났지만 로컬 clone의 오래된 HEAD를 사용해 원격에 이미 있는 파일도 missing으로 표시했다.
- `python -B scripts/github_audit.py`는 두 저장소의 repository·commit·workflow·legacy Issue 조회에서 network timeout을 반환했다.
- 같은 실행에서 연결된 GitHub 앱은 repository, file, commit을 정상 조회하고 복원 파일도 생성했다.

### 진단과 가설

- **진단:** 현재 health 결과의 파일 존재 판정은 로컬 clone freshness에 민감하다.
- **가설:** `github_audit.py`의 raw network 경로는 현재 실행 환경에서 제한되지만 GitHub 앱 연결은 유효하다.
- **영향:** 로컬 결과만 믿으면 정상 보고서를 반복 복구하거나 중복 commit을 만들 위험이 있다.

### 다음 최소 실험

1. health script 출력의 missing candidate를 GitHub file API로 재검증한 뒤에만 실제 장애로 승격한다.
2. 다음 3회 health run에서 `local missing / remote exists` 건수를 기록한다.
3. 세 번 연속 발생하면 `radar_health.py`에 원격 SHA cache 또는 명시적 remote-verification 입력을 추가하는 변경을 별도 검토한다.
4. `github_audit.py`는 connector 기반 read path를 지원하기 전까지 network timeout을 전체 GitHub 장애로 해석하지 않는다.
