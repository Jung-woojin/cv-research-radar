## 사례 1 — 반환 dtype이 FP32여도 loss overflow는 이미 발생했다

**Claim·재현 조건.** [#15407](https://github.com/huggingface/diffusers/issues/15407)은 11/26 00:26 UTC 게시, 00:38 UTC 수정됐다. 작성자는 Diffusers `0.44.0.dev0`, revision `16eb5cc4fd8262fd33b3c9119a12977c25cc4985`, Python 3.12.13, torch 2.13.0+cu130의 Linux CPU에서 실제 FlowMatchEulerDiscreteScheduler와 공개 loss weighting 함수를 검사했다. weights·dataset은 필요 없다.

**Observed gap — 작성자 보고.** 기본 scheduler의 sigma를 FP16으로 바꾸고 `sigma_sqrt`를 선택하면 1,000개 중 3개 weight가 nonfinite다. 최소 sigma의 국소 목적함수에서 loss·gradient가 Inf이며, 역제곱 전에 FP32로 바꾸면 각각 1·2가 된다. 이는 pretrained GPU 학습 결과가 아니라 분석 가능한 단일 목적함수 검사다. 특히 **기본 scheduler 설정**과 **학습 스크립트 기본 weighting**을 혼동하면 안 된다. 작성자는 스크립트 기본값이 `logit_normal`이며 문제 조합은 FP16 + `sigma_sqrt`라고 명시한다.

**사실·진단.** [고정 helper 소스](https://github.com/huggingface/diffusers/blob/16eb5cc4fd8262fd33b3c9119a12977c25cc4985/src/diffusers/training_utils.py#L393-L408)는 `(sigmas**-2.0).float()`를 사용한다. [학습 호출 경로](https://github.com/huggingface/diffusers/blob/16eb5cc4fd8262fd33b3c9119a12977c25cc4985/examples/dreambooth/train_dreambooth_sd3.py#L1572-L1659)는 model input dtype으로 sigma를 얻고 weight를 loss에 곱한다. 최종 loss에서 다시 `.float()`해도 앞 연산의 Inf를 복원할 수 없다는 mechanism과 일치한다.

**수정 상태.** [PR diff](https://github.com/huggingface/diffusers/pull/15408/files)는 `sigmas.float().pow(-2.0)`로 바꾸고 실제 scheduler를 쓰는 loss=1·gradient=2 회귀 검사를 추가한다. 조회 시 head는 `a780cabf4f521acfe57c50563396d68a42c81679`, open·draft·`merged_at=null`이다. 이슈 댓글은 없으며 병합·release를 확인하지 못했다.

**가설 → 최소 실험.** cast 순서가 원인이면 동일 FP16 sigma tensor에서 cast 위치만 바꿔도 유한성이 회복되어야 한다. 기본 scheduler 전체 sigma와 작은 nonzero 경계값에 대해 FP16/BF16/FP32, 수정 전후의 weight·loss·gradient를 기록한다. 다른 weighting branch를 음성 대조로 두고, 이후에만 동일 batch·초기 noise·checkpoint로 짧은 학습을 비교한다.

**GO/KILL.** 국소 불변식 `weight × sigma.float()² ≈ 1`과 gradient 유한성이 회복되면 GPU 검증으로 GO한다. seed나 batch를 바꿔 문제 timestep을 피한 성공, 또는 반환 dtype만 검사한 성공은 KILL한다. 원문의 단일 seed sampling 표를 학습 seed variance나 실전 발산 확률로 일반화하지 않는다.

## 사례 2 — AP가 비슷해도 NMS의 중복 제거 계약은 깨질 수 있다

**Claim·재현 조건.** [#27371](https://github.com/ultralytics/ultralytics/issues/27371)은 11/26 01:47 UTC 게시됐다. 제보 환경은 Ultralytics 8.4.219/main `3a31e32f2`, Python 3.13.11, torch 2.13.0+cu130, torchvision 0.28.0, RTX 5090, SAM 3.1 weights다. LVIS 대조는 8.4.210에서 수행했다고 명시하므로 predictor 예제와 동일 실행으로 합치지 않는다.

**Observed gap — 작성자 보고.** FP16 정규화 box에 class offset 7680을 더하면 class 1의 좌표가 모두 7680으로 반올림되고 class 9는 Inf가 된다. 두 겹친 box의 CPU 산술 fixture에서 첫 class는 하나가 남지만 이후 class는 둘 다 남는다. 실제 bus 이미지에서도 높은 same-class IoU box가 살아남았다고 보고한다. LVIS minival에서 현재 경로와 FP32 batched NMS의 AP는 60.74 대 60.65로 비슷하지만, 낮은 confidence에서 반환 box 수는 줄었다는 주장이다. 이는 작성자의 단일 평가이며 독립 benchmark 재현이 아니다.

**사실·진단.** 전체 revision은 `3a31e32f2e254a13f86ea274d6331e19d0cb4d47`로 확인했다. [postprocess 소스](https://github.com/ultralytics/ultralytics/blob/3a31e32f2e254a13f86ea274d6331e19d0cb4d47/ultralytics/models/sam/predict.py#L2343-L2381)는 xywh→xyxy 후 class offset을 더하고 NMS를 실행한 뒤에야 원본 이미지 크기로 scale한다. [inference_features 경로](https://github.com/ultralytics/ultralytics/blob/3a31e32f2e254a13f86ea274d6331e19d0cb4d47/ultralytics/models/sam/predict.py#L2431-L2438)에도 같은 offset이 있다. normalized box의 작은 차이가 큰 offset 아래에서 소실되는 진단을 뒷받침한다.

**가설 → 최소 실험.** 모델 출력 자체를 고정하고, class 번호만 바꾸는 두-box fixture로 offset 전후 좌표·면적·IoU·keep index를 기록한다. FP16에서 먼저 offset을 더한 뒤 float로 바꾸는 조건과, 연산 전 FP32 변환 및 class별 NMS를 구분한다. class 순서를 바꿔도 같은 물체의 결과가 유지되는지 검사하고 두 predictor 경로를 모두 통과시킨다. 이후 고정 SAM checkpoint·입력·confidence·IoU로 확인한다.

**GO/KILL.** 서로 다른 class의 격리를 유지하면서 같은 class의 중복을 제거하고 prompt 순서 민감성이 사라지면 GO한다. agnostic NMS로 class 구분까지 없애거나 AP만으로 성공을 판단하는 것은 KILL한다. FP32에서도 큰 offset은 작은 normalized box의 정밀도를 해칠 수 있어 단순 dtype 변경만으로 충분하다고 단정하지 않는다. 이슈는 open·댓글 0개이며 이번 조사에서 병합 수정은 확인하지 못했다.

## 사례 3 — checkpoint 이름만 고정하면 processor 선택은 고정되지 않는다

**Claim·재현 조건.** [#51232](https://github.com/huggingface/transformers/issues/51232)는 11/25 10:48 UTC 게시, 13:09 UTC 수정됐다. Transformers 5.24.1, Windows 11, Python 3.12.4, torch 2.15.0+cpu 환경에서 `MCG-NJU/videomae-base`를 사용한다. 입력은 16×224×224×3 uint8 무작위 video다.

**Observed gap — 작성자 보고.** AutoProcessor는 VideoMAEImageProcessor를 반환해 `videos=` 호출이 필수 `images` 인자 누락 TypeError로 실패하지만, AutoVideoProcessor는 VideoMAEVideoProcessor를 반환해 처리에 성공한다. 작성자는 tiny checkpoint의 로컬 설정에 `processor_class`를 넣거나 video 설정 파일명으로 바꾸면 선택 클래스가 바뀐다고 보고했다. 원격 checkpoint 설정 revision·파일 hash와 실제 pixel tensor 동등성은 미확인이다.

**사실·진단.** 조사 시 main `f3b0be813bab0c3373a548106d9bce0c1a76efc7`의 [설정 탐색 코드](https://github.com/huggingface/transformers/blob/f3b0be813bab0c3373a548106d9bce0c1a76efc7/src/transformers/models/auto/processing_auto.py#L257-L278)는 image 설정 파일이 없을 때 video 설정 파일을 찾는다. [fallback](https://github.com/huggingface/transformers/blob/f3b0be813bab0c3373a548106d9bce0c1a76efc7/src/transformers/models/auto/processing_auto.py#L359-L373)은 AutoImageProcessor를 AutoVideoProcessor보다 먼저 시도한다. 이 순서는 보고된 선택 경로와 일치하지만, 해당 checkpoint가 반드시 그 경로로 들어가는지는 artifact를 고정해 별도 확인해야 한다. 유일한 member 댓글은 담당자 호출이며 해결 승인이 아니다.

**가설 → 최소 실험.** 입력 video를 저장하고 hash를 고정한 뒤 동일 checkpoint snapshot의 AutoProcessor·AutoVideoProcessor·명시적 VideoMAEVideoProcessor를 비교한다. 로컬 복사본에서 metadata만 한 항목씩 바꾸고 선택 클래스·shape·frame 순서·resize/crop·정규화 tensor 차이를 기록한다. config·code revision을 함께 남긴다. processor 검사를 통과한 뒤에만 동일 checkpoint logit을 비교한다.

**GO/KILL.** metadata 또는 factory 선택만으로 예외가 해소되고 의도한 frame 처리와 일치하면 GO한다. 클래스 이름이 바뀌었다는 사실만으로 video 정확도 복구를 선언하면 KILL한다. library 버그인지 checkpoint metadata 보완 사항인지는 아직 열린 질문이며, 이슈는 open이다.

## 오늘의 GO/KILL과 공통 manifest

- **첫 GO:** CPU loss weighting 검사 → synthetic NMS 검사 → 고정 snapshot의 processor 선택 검사 순서다. 모델 품질 측정 전에 연산·입력 계약을 분리한다.
- **보류 해제 조건:** MiniMax는 같은 checkpoint에서 text encoder block-level 조건의 수정 전후 device·hook 실행과 hidden-state parity가 필요하다. PR의 bitwise parity 및 성공 구성이 leaf-level이라는 사실만으로 이슈 조건이 검증됐다고 쓸 수 없다.
- **현재 KILL:** 작은 fixture의 수정 성공을 전체 학습 성능 회복, 논문 표 불일치 해소 또는 seed variance 감소로 확대하는 주장.
- backbone·dataset/split·resolution·pretraining·hardware·precision·batch·TTA·evaluator가 모두 같은 benchmark 비교는 아니다. 특히 FP16/FP32 및 NMS 구현 대조는 원인 분리 개입으로서 **not strictly apples-to-apples**다. weights 없는 함수 검사는 backbone·pretraining·split·TTA가 해당 없으며, checkpoint 평가로 확장할 때 고정한다.
- manifest에는 code/package·checkpoint·processor revision, config hash, 입력 hash, class/prompt 순서, dtype 변환 위치, CUDA/driver·CPU/GPU, batch, seed/RNG, evaluator와 raw tensor를 보존한다. 미확인 조건은 추정으로 채우지 않는다.
- **연구 질문:** seed sweep 전에 cast 순서·좌표계·factory 선택의 계약을 검사하면 재현 실패를 더 저렴하게 분리할 수 있는가? 오늘은 반증 가능한 실험을 제안했으며 효과 크기는 실측하지 않았다.
