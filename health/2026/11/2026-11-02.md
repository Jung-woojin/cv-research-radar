- 이 스크립트가 표시한 최근 날짜의 다수 “missing”은 로컬 clone의 10월 28일 기준 Git 상태를 보는 false positive다. 오늘 GitHub Files API로 검증한 3개 파일과 충돌한다.
- `github_audit.py`는 두 저장소에 대해 원격 HTTP timeout을 보고했다. 이는 파일 API 성공과 별개의 감사 경로 장애이며, 성공/실패를 추정하지 않았다.
- 원격 검증된 오늘 보고서는 복구 대상이 아니다. 미래 자료로 과거 날짜를 채우지 않았고, Issue를 만들지 않았다.

## 진단 → 가설 → 최소 실험

**진단 — [사실]** 로컬 Git 기준 최근 commit은 10월 28일로 남아 있고, 오늘 생성된 direct Files API commit을 보지 못한다. 이 때문에 health script가 원격에 실제 존재하는 보고서를 missing으로 표시한다.

**가설 — [추론]** health script가 로컬 filesystem/Git 기록과 Files API ledger를 우선 병합하지 않아 direct-file archive 이후 false positive를 만든다.

**최소 실험**  
검증된 3개 path에 대해 (a) local Git file 존재, (b) ledger의 verified SHA, (c) GitHub Files API fetch를 나란히 기록한다. Files API SHA가 ledger SHA와 일치하면 local missing 경고를 `remote-verified/local-stale`로 낮춰야 한다.

**성공 기준**  
오늘 검증한 세 파일이 missing 목록에서 제거되거나 최소한 false positive로 분류되고, 실제 원격 404만 recovery queue로 들어가면 통과다.

## 조치 및 보류

- 의도치 않게 disabled된 ID는 없어서 scheduler 변경을 하지 않았다.
- `issues` trigger가 없어서 workflow를 변경하지 않았다.
- 원격 HTTP audit timeout은 Files API 직접 검증으로 대체했지만, audit script 자체의 네트워크 실패는 별도 장애로 남긴다.
- CP949 출력 오류는 `PYTHONIOENCODING=utf-8`로 재현·우회 가능함을 확인했다. 스크립트 변경은 이번 health run의 저장 범위를 넘으므로 하지 않았다.
- 기존 원문·당시 근거 없는 과거 누락은 backfill하지 않았다.
