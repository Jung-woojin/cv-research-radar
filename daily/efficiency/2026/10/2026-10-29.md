## 사례 1 — Local formalizer는 latency와 task success를 동시에 볼 때만 의미가 있다

**확인 사실.** [Learning to Formalize](https://arxiv.org/abs/2610.36595)는 CALVIN-D validation annotation 1,011개에서 fine-tuned formalizer를 쓴 locally deployed decision model의 최고 task success 52.6%, formalizer가 없는 경우 11.8%를 보고합니다. 같은 실험 설정에서 end-to-end latency는 2.09 s, Qwen3.5-27B는 3.67 s라고 보고합니다.  
**저자 주장.** open-ended workload를 더 빠른 decision model로 formalize하는 방식이 성능과 응답 시간을 함께 개선할 수 있다고 주장합니다.  
**조건 감사.** 초록에서 확인 가능한 것은 “exact experiment setting”이라는 비교 설명뿐입니다. GPU/CPU·NPU 모델, batch size, precision, prompt length, warm-up, concurrency, network I/O, power는 확인하지 못했습니다. 따라서 일반적인 1.76× speedup이나 edge-device 보장으로 읽으면 안 됩니다.  
**진단.** 서로 다른 model class의 end-to-end latency는 model forward뿐 아니라 formalization 단계, controller loop, input/output serialization을 포함할 수 있습니다.  
**가설.** formalizer가 계산을 줄였다기보다 이후 decision model이 처리할 open-ended state를 압축했을 가능성이 있습니다.  
**최소 실험.** 동일 hardware·fixed input 100개에서 (a) formalizer, (b) decision model, (c) end-to-end controller를 따로 측정하고, batch 1/4, FP32/BF16/FP16, warm-up 20회 후 p50/p95 latency·peak VRAM·task success를 기록합니다.  
**GO/KILL.** GO: end-to-end p95가 유지되면서 task success가 올라가고 stage별 병목이 공개될 때. KILL: 지연 감소가 prompt 길이/원격 호출/재시도 정책 변화로만 설명되거나 edge target에서 재현되지 않을 때.  
**해석.** 이 결과는 유망한 system-level signal이지만, device-specific inference claim은 아직 **not strictly apples-to-apples**입니다.

## 사례 2 — Runtime compatibility가 고정되지 않으면 효율 비교 자체가 흔들린다

**확인 사실.** [PyTorch release compatibility matrix](https://github.com/pytorch/pytorch/blob/main/RELEASE.md)는 PyTorch 2.15의 stable CUDA 13.2와 cuDNN 9.26.0.51/NCCL 2.30.7, 2.14의 CUDA 12.6·13.0·13.2와 각각의 cuDNN/NCCL 조합, 2.13의 별도 CUDA/cuDNN/NCCL 조합을 명시합니다.  
**저자/공식 문서의 의미.** 이 표는 성능 우위를 주장하는 benchmark가 아니라, release별로 binary/runtime 조합이 다르다는 공식 호환성 사양입니다.  
**진단.** 같은 model·same precision·same GPU라도 PyTorch/CUDA/cuDNN/NCCL 조합이 바뀌면 kernel selection, graph compilation, memory allocator와 collective 동작이 달라질 수 있습니다. 이를 숨긴 throughput/VRAM 결과는 원인을 분리할 수 없습니다.  
**가설.** edge 배포에서 “모델이 빨라졌다”는 관찰의 일부는 model change가 아니라 runtime migration에서 생길 수 있습니다.  
**최소 실험.** model·weight·input shape·driver를 고정하고, 지원되는 두 PyTorch stack에서 warm-up 50회와 측정 200회로 p50/p95 latency, peak allocated/reserved VRAM, compile time, power를 비교합니다. compiler/runtime cache를 매 조건에서 분리합니다.  
**GO/KILL.** GO: runtime matrix와 container digest가 공개되고 지연 개선이 두 stack에서 같은 방향일 때. KILL: stack 정보를 복원할 수 없거나 개선이 한 조합에서만 발생할 때.  
**해석.** 이는 일반적인 runtime 차이의 가능성이지, 특정 논문의 성능 오류를 뜻하지 않습니다.

## 공통 진단 → 가설 → 최소 실험

**진단.** 오늘 조사창에서 확인된 신규 efficiency 근거는 제한적이었습니다. 특히 hardware, power, precision, batch, warm-up, input shape가 동시에 공개된 새 CV edge benchmark는 찾지 못했습니다.

**가설.** 효율 보고의 재현성은 FLOPs보다 measurement contract—하드웨어, software image, precision, input distribution, concurrency, cache state—의 공개 여부에 더 크게 좌우됩니다.

**최소 개입.** 모든 후보에 다음 manifest를 요구합니다: device SKU/driver, PyTorch·CUDA·cuDNN·TensorRT version, precision, batch/input shape, warm-up·iteration, latency percentile, peak memory definition, power 측정 위치, compiler cache/engine build 조건.

**오늘의 GO/KILL.**

- GO: local formalizer 논문을 위 stage-level profiling protocol로 재측정할 수 있을 때.
- KILL/보류: hardware 또는 runtime stack이 없는 숫자를 device-independent speedup으로 인용하지 않습니다.

## 측정 체크리스트

- latency는 p50/p95와 host↔device transfer 포함 여부를 함께 쓴다.
- throughput은 batch·concurrency·sequence/input shape와 함께 쓴다.
- peak VRAM은 allocated/reserved인지, engine build memory를 포함하는지 구분한다.
- power/energy는 장치·sampling interval·idle baseline·측정 경계를 공개한다.
- 다른 hardware, runtime, precision, input shape 조건은 **not strictly apples-to-apples**로 표기한다.
- 오늘은 실제 benchmark/컴파일을 실행하지 않았으므로, 위 수치를 독립 검증한 것은 아닙니다.
