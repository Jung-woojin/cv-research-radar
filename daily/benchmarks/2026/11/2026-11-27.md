### 원본 benchmark와의 일치 여부

원본 ZeroBench README의 공개 예시는 마지막 중괄호에서 답을 추출해 문자열을 비교한다. 공식 프로젝트는 공식 평가와 외부 보고를 구분하며 2026년 8월 red-teaming에 따른 채점 수정도 별도로 공지한다. 이번 VLMEvalKit의 새 hybrid judge가 그 공식 수정 절차와 동일하다는 근거는 확보하지 못했다. 원본의 과거 protocol 수정과 이번 adapter 변경을 하나의 사건으로 합치지 않는다. [원본 코드 예시](https://github.com/jonathan-roberts1/zerobench/blob/main/README.md), [공식 프로젝트와 결과 구분](https://zerobench.github.io/).

### 진단 → 기전 → 가설

**진단.** 공백이 있는 단위 표현이나 분수/소수 같은 의미상 같은 답이 문자열 비교에서는 실패할 수 있다. PR의 예시는 `15kg` 대 `15 kg`, `0.01` 대 `1/100`이다. 이 경우 점수 차이는 시각 reasoning의 변화가 아니라 답 표현과 판정 규칙 사이에서 발생한다.

**기전.** 새 채점은 비대칭이다. exact 정답은 judge가 재심사하지 않고, exact 실패에서만 추가 정답을 찾는다. 정상적으로 완료되는 동일 응답 집합에서 exact 정답 수를 줄이지 않는 구조이므로, 평균 점수 상승 자체는 judge 품질의 충분한 검증이 아니다.

**가설.** 상승분의 일부는 실제 표현 오류 복구지만, 일부는 전체 reasoning 내용·순서·reference 모호성에 대한 judge의 판단에 좌우될 수 있다. PR 작성자도 정답 값은 인정하면서 reasoning을 비판해 거부한 사례와 좌표 목록의 정렬 순서 때문에 거부한 사례를 기록했다. 이는 작성자의 사례 분석이며 독립 확인된 오류율은 아니다.

### 코드에서 확인한 추가 경계

- **시각 증거를 직접 검증하지 않는다.** ShortQA prompt에는 텍스트 질문·정답·응답이 들어간다. 이 경로는 이미지 근거가 맞는지 재검사하는 visual judge가 아니다.
- **리스트 의미를 자동으로 구조화하지 않는다.** `answer_type='exactMatch'`를 지정해 reference를 literal string으로 유지한다. 순서·개수 검증은 system instruction과 judge 판단에 의존한다.
- **parser의 유효 판정과 내용의 정확성은 다르다.** helper는 correctness tag 안에 yes 또는 no 중 하나만 포함되는지 검사하며, 재시도에서 temperature를 0, 0.5, 1로 바꾼다. parse 성공이 reference 해석의 정확성을 증명하지 않는다.
- **cache가 모든 조건을 고정하지는 않는다.** cache 경로에는 judge 이름, sample hash에는 index·질문·reference·전체 응답·system prompt가 반영된다. endpoint·wrapper·max_tokens·helper prompt template·실제 backend snapshot은 해당 hash의 구성 요소가 아니다. 동일 이름과 경로로 설정을 바꾸면 이전 성공 cache를 재사용할 수 있다는 정적 추론이며, 오염 발생을 실행으로 확인한 것은 아니다.
- **반복 결과 정렬은 명시적 index를 사용한다.** 새 detail의 `index`를 기존 repeat wrapper가 매칭한다. 이번 변경이 wrapper 알고리즘 자체를 새로 도입한 것은 아니다.

[ShortQA 호출·판정 parser](https://github.com/open-compass/VLMEvalKit/blob/9ffc2e37281a80729081fe52f977f088283783b3/vlmeval/dataset/image_shortqa.py), [judge prompt](https://github.com/open-compass/VLMEvalKit/blob/9ffc2e37281a80729081fe52f977f088283783b3/vlmeval/dataset/utils/shortqa.py), [cache 구현](https://github.com/open-compass/VLMEvalKit/blob/9ffc2e37281a80729081fe52f977f088283783b3/vlmeval/dataset/utils/judge_cache.py), [반복 집계와 정렬](https://github.com/open-compass/VLMEvalKit/blob/9ffc2e37281a80729081fe52f977f088283783b3/vlmeval/dataset/utils/repeat.py).

### 최소 개입과 첫 실험

1. 기존 응답 파일을 보존하고 SHA256·question ID·sample ID·reference를 고정한다. 데이터 이미지 복구 전후와 v2/v3를 섞지 않는다.
2. 네트워크 없이 exact 점수를 재계산하고 실패를 단위/공백, 수치 동치, 중괄호 추출, 순서/집합, 실제 오답, reference 모호성으로 분류한다. fatal·turn limit·정상 응답을 별도 집계하되 분모를 임의로 줄이지 않는다.
3. 분류된 작은 표본을 사람이 먼저 판정한다. 이후 judge 비교가 필요하면 전체 응답과 최종 답만 제공하는 두 조건을 같은 judge snapshot·prompt·budget에서 비교한다. cache namespace도 분리한다.
4. metric은 avg@5·pass@5·pass^5, exact→semantic 전환 수, 사람 기준 false acceptance/rejection, unavailable 수, judge 실패 수, 요청 수·비용이다. PR 수치를 자체 재현값처럼 사용하지 않는다.

**GO:** 사람이 확인한 표현 차이를 복구하면서 실제 오답의 오인정이 늘지 않는다면 평가 개선을 계속 조사한다. **KILL/보류:** reference 자체가 모호하거나 judge 결과가 reasoning 서술·cache 재사용에 좌우되면 모델 순위 주장을 중단하고 rubric부터 정리한다. 첫 두 단계는 GPU 없이 가능하다. 나머지는 judge API 비용이 들며 이번 실행에서는 수행하지 않았다.

## 비교 조건과 해석 한계

동일 저장 prediction의 두 채점 결과는 evaluator 변경의 효과를 보는 paired 비교다. 그러나 새 hybrid 점수와 기존 exact leaderboard를 모델 성능 순위로 합치는 것은 **not strictly apples-to-apples**다.

backbone·pretraining·external data·input resolution·TTA·도구·reasoning effort·context/frame budget·compute를 통일한 신규 모델 비교는 확보하지 않았다. PR 재채점은 같은 응답을 썼다는 작성자 보고이며, 원본 artifact의 checksum이나 500-slot mapping을 이번 실행에서 독립 감사하지 않았다.

후속 기록에는 dataset revision/checksum, evaluator commit, 생성 harness와 종료 상태, raw response hash, 반복 수, judge 실제 model ID·wrapper·endpoint·prompt·budget·cache namespace를 남긴다. 어제의 입력 이미지 복구와 오늘의 evaluator 변경을 동시에 적용한 점수 차이만으로 어느 요소가 원인인지 판정할 수 없다.

## 오늘의 benchmark signal 3개

1. **기본 judge 변경도 benchmark 이동이다.** 같은 데이터·응답이라도 evaluator가 달라지면 점수가 움직인다.
2. **generation 실패와 judge 실패를 분리한다.** 분모·fatal 상태·채점 완료 여부가 빠진 정확도는 headline에 쓰기 어렵다.
3. **점수 상승과 평가 타당성을 별도로 본다.** exact 정답 유지 구조의 상승분은 사람이 확인한 오류 복구와 함께 검증해야 한다.

세 signal은 신규 변경 한 건에서 도출한 해석이며 서로 다른 benchmark 세 건이 아니다.

## 내 연구에 바로 연결되는 포인트

- Answer–Region Gap 연구에서는 답 문자열의 정확성, 의미적 정답성, 이미지 근거의 정확성을 분리한다. text-only judge 통과만으로 grounding을 입증하지 않는다.
- 해양·CCTV counting/VQA는 단위·방향·순서에 민감하다. 의미 동치 normalization이 안전한 항목과 엄격한 순서 검사가 필요한 항목을 rubric에서 구분한다.
- **오늘 먼저 할 일:** 기존 VQA 저장 응답의 exact 실패를 분류하고, 실제 시각 실패와 표현 차이가 각각 얼마나 있는지 확인한다. RTX 5060 Ti 8GB에서도 첫 감사는 GPU 없이 시작할 수 있다.
- 장기 질문은 “judge를 강하게 하면 점수가 오르는가”보다 “어떤 응답 유형에서 자동 평가가 인간의 의미·증거 판정과 갈라지는가”다. 오늘의 관측만으로 새 architecture의 필요성을 주장하지 않는다.
