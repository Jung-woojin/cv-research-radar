## 1. FleXray — 범용 X-ray segmentation package

**새로 확인한 내용:** cutoff snapshot에 inference CLI, training, dataset/DRR 구조, config, documentation, tests, GitHub Actions CI와 release workflow가 함께 있었다. Python package 이름은 `flexray`, import는 `fxr`이며 Python 3.10+, PyTorch 2.3 이상 3 미만을 요구한다. [당시 snapshot](https://github.com/VictorButoi/FleXray/tree/064c89064e079a389de18d6566cea7361d0ef100)

**논문·프로젝트 연결:** 당시 README는 *FleXray: Universal Clinical X-ray Segmentation*과 프로젝트 페이지를 연결했다. 패키지는 일반 image format과 선택적 DICOM 입력을 받아 label별 threshold mask, probability, raw logits를 저장한다고 설명한다. 이는 임상적 유효성 검증을 의미하지 않는다. [공식 프로젝트](https://flexray.csail.mit.edu/), [논문](https://arxiv.org/abs/2609.26756)

**코드 품질·재현성:** 261개 파일, `tests/`, CI, 20개 이상의 문서, example config와 Colab이 존재한다. `pyproject.toml`은 기본 inference dependency와 `train`, `mcp`, `dicom`, `full`, `test` extras를 분리한다. 구조적 재현성은 좋지만 이번 백필에서 CI를 실행하거나 package를 설치하지 않았다.

**weights·라이선스:** model-zoo 문서는 다섯 member와 `model.safetensors`, config, label schema, preprocessing, checksum, ONNX 산출물 계약을 설명한다. 코드 MIT, public weights는 별도 model card가 없으면 CC-BY-NC-4.0이라고 명시한다. cutoff 당시 HF 파일 tree 전체와 실제 load 성공은 별도 검증하지 못했다.

**설치·자원·호환:** `python -m pip install flexray`가 기본 경로이며 DICOM은 extra다. MMDetection·Ultralytics·timm의 drop-in adapter는 확인하지 못했다. PyTorch와 safetensors 기반이므로 모델 wrapping은 가능하지만, 정확한 GPU/VRAM과 batch별 latency는 확인되지 않았다.

**진단 → 가설 → 최소 실험:** arbitrary X-ray라는 표현은 anatomy·촬영기기·view 변화에서 calibration이 유지된다는 증거와 다르다. 동일 image set에서 flagship single pass / 8-pass TTA / 5-member ensemble을 비교하고 Dice·small anatomy recall·ECE·P95 latency·peak VRAM을 기록한다. **GO:** TTA/ensemble이 작은 구조의 recall과 calibration을 일관되게 높인다. **KILL:** threshold tuning만으로 차이가 사라지거나 domain별 오류가 커지면 “universal” 일반화를 축소한다.

## 2. Glance Speedlab — local camera VLM의 측정 중심 latency harness

**새로 확인한 내용:** cutoff snapshot은 browser capture, transport, image-prefix, scoring, full-loop latency를 분리한다. Node 22+, pnpm 11, Vite/TypeScript frontend와 Python MLX backend를 포함하며 MIT license다. [당시 snapshot](https://github.com/yoheinakajima/glance-speedlab/tree/20af87b439a3ad6d16e69bae5767a7461e7b2cfa)

**저자 결과:** snapshot README는 native multi-question이 four cold sequential request보다 2.405배 빠르고, Qwen3-VL-2B가 4B보다 2.994배 빠르지만 per-question decision agreement는 83.3%라고 기록한다. selected-logit-only readout은 3.9%, fixed-shape MLX suffix compilation은 p50 0.6%, 224 대 320px capture는 0.999배라 채택하지 않았다. 이 수치는 한 Apple M5와 작은 고정 guardrail suite의 저자 측정이며 NVIDIA GPU 결과가 아니다.

**코드 품질·재현성:** 169개 파일에 experiment log, hypotheses, findings, decisions, reproducibility 문서, tests, CI, benchmark script가 있다. 성공하지 않은 최적화도 남겨 결과 선택 편향을 줄이려는 구조가 강점이다. 실제 camera/model validation이 남았다고 commit message가 명시한다.

**weights·설치·호환:** Glance의 open VLM checkpoint에 의존하며 Speedlab 자체 weight는 없다. Web stack과 local model service를 같이 준비해야 한다. Hugging Face 기반 VLM과 연결되지만 MMDetection/Ultralytics용 framework가 아니다.

**진단 → 가설 → 최소 실험:** UI 최적화보다 model forward와 질문 batch가 병목이라는 저자 해석을 Windows+NVIDIA에서도 검증한다. 같은 100 frame과 4개 질문에서 sequential / native multi-question / frame-reuse를 비교한다. capture-to-answer P50/P95, answer agreement, probability drift, dropped frame을 기록한다. **GO:** batch가 answer stability를 유지하며 end-to-end P95를 줄인다. **KILL:** browser scheduling이나 transport variance가 model 차이보다 크면 backend 최적화를 멈추고 capture pipeline부터 고친다.

## 3. OneJev — typed multimodal decision model과 API

**새로 확인한 내용:** cutoff snapshot은 screenshot·photo·video·text와 typed question을 받아 선택지별 probability를 한 forward에서 반환하는 API를 제공한다. `qev` package, FastAPI server, examples, benchmark, train config와 tests가 있었다. Python 3.10+, PyTorch 2.6+, Transformers 5+를 요구하고 Apache-2.0이다. [당시 snapshot](https://github.com/OmniJev/OneJev/tree/90a4584f17b42b8802da24324eb5318a45eb6e6b)

**모델·데이터·저자 결과:** 당시 README는 0.8B/4B/9B/27B 네 크기와 99,193 questions 학습 구성을 설명한다. 1280×720 screenshot에서 H200 latency를 제시하지만, prompt length·question 수·CUDA graph·preprocessing 조건을 그대로 맞추지 않으면 not strictly apples-to-apples다. HF model/data 링크가 있었으나 이번 백필에서 cutoff 당시 모든 weight/data 파일 tree와 checksum을 검증하지 못했다.

**코드 품질·재현성:** training module과 inference API가 함께 있고 pytest config가 있다. typed `Choice`, `Score`, yes/no 응답은 생성 text보다 평가가 단순해질 수 있다. 반면 candidate option 설계가 성능을 크게 좌우하므로 open-ended VQA와 직접 비교할 수 없다.

**설치·자원·호환:** PyTorch backend는 image/video를 지원하고 README는 llama.cpp 경로를 별도로 설명한다. 0.8B조차 실제 8GB GPU에서 지원되는지, quantization별 VRAM/latency는 확인하지 못했다. Hugging Face model interface와 API는 있으나 MMDetection/timm adapter가 아니다.

**진단 → 가설 → 최소 실험:** one-forward multi-question의 이득이 동일 image-prefix 재사용에서 오는지, typed option restriction에서 오는지 분리한다. 같은 image와 질문을 independent call / batched typed questions / generated answer+parser로 비교한다. accuracy, Brier score, calibration error, P95 latency, option-order sensitivity를 기록한다. **GO:** option permutation에도 calibration과 latency 이득이 유지된다. **KILL:** option wording이나 order가 대부분의 이득을 설명하면 agent decision 적용 범위를 제한한다.

## 4. Remote-Sensing-Image-Segmentation-Models — 투명한 RS baseline 묶음

**새로 확인한 내용:** cutoff snapshot은 remote-sensing segmentation paper/code/dataset index와 U-Net, SegFormer, SAM wrapper를 함께 제공한다. 23개 파일이며 MIT license다. [당시 snapshot](https://github.com/qi-fg/Remote-Sensing-Image-Segmentation-Models/tree/9bf0f8d27339061434a683e13b7d646032158827)

**코드 품질·재현성:** U-Net과 SegFormer에는 dataset·GPU 없는 synthetic CPU smoke test가 문서화돼 있다. U-Net demo는 base channel을 8로 낮추고, SegFormer tiny는 `embed_dims=(16,32,64,128)`, depth 1씩의 교육용 설정이다. 예시 mIoU는 synthetic demo 설명이며 실제 remote-sensing benchmark 성능이 아니다.

**weights·설치·호환:** U-Net과 compact SegFormer는 `torch` 중심의 단순 구현이며 pretrained weight가 없다. SAM wrapper는 별도 checkpoint와 dependency가 필요하다. 공식 NVlabs SegFormer나 MMSeg pretrained model과 weight-compatible하다고 가정하면 안 된다. MMDetection·Ultralytics drop-in도 확인되지 않았다.

**유지보수·실용성:** 작은 transparent baseline을 빠르게 읽고 data loader·loss·split validator를 붙이기 좋다. 60개 이상 방법을 정리했다는 README 표는 링크 큐레이션이며, 각 upstream code가 동일 라이선스·평가 조건이라는 뜻이 아니다.

**진단 → 가설 → 최소 실험:** 학술 baseline 이름이 같아도 구현·pretraining·crop·class mapping이 다르면 비교가 흐려진다. LoveDA 또는 작은 내부 tile subset에서 이 repo의 U-Net/SegFormer와 공식 pretrained implementation을 같은 split·resolution·augmentation으로 비교한다. mIoU, small-region recall, parameter 수, peak VRAM, wall time을 기록한다. **GO:** transparent baseline이 속도·실패 분석에 충분한 일관성을 보인다. **KILL:** 구현 격차가 architecture 효과보다 크면 leaderboard 비교에 사용하지 않고 smoke-test scaffold로만 유지한다.
