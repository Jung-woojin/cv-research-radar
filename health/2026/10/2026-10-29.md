```yaml

```

- **확인된 사실**: `issues` trigger는 두 파일 모두에 없다.

## 4) 새로 발견된 장애: 감사 도구의 원격 가시성

- `radar_health.py`는 당일 성공 ledger가 있는 6개 파일을 local clone 기준으로 `missing`이라 표시했다.
- 같은 출력에서 latest repo commit도 전날 값으로 머물렀다.
- `github_audit.py`는 두 저장소의 repository, commits, workflows, legacy issue 조회를 모두 `network unavailable or request timed out`로 반환했다.
- 반면 연결된 GitHub 파일 API는 같은 시점의 당일 6개 파일 및 두 workflow를 모두 성공적으로 읽었다.

### 진단

- **확인된 사실**: 로컬 clone/감사 스크립트의 remote read 경로가 stale 또는 timeout 상태다.
- **추론**: 이 상태에서 `missing_due_reports`를 복구 대상으로 그대로 사용하면 이미 존재하는 보고서를 중복 작성할 위험이 있다.
- **범위**: 보고서 저장 자체의 장애는 아니다. 직접 GitHub 파일 API의 당일 저장·본문 검증은 성공했다.

### 최소 개입

1. 다음 Health Check 전 `github_audit.py`의 네트워크/timeout 원인과 local clone fetch freshness를 분리 점검한다.
2. `radar_health.py`의 누락 복구 후보는 ledger만으로 확정하지 않고 GitHub 파일 API의 path 조회 결과로 교차확인한다.
3. 진단 도구가 원격 최신 commit과 파일 SHA를 읽을 수 있을 때까지, 오탐 missing에 대한 자동 복구 commit은 만들지 않는다.

### 판정 기준

- `github_audit.py`가 두 저장소의 repository·commits·workflow 조회를 timeout 없이 반환하고,
- `radar_health.py`의 오늘 6개 remote path 상태가 `missing`이 아니라 존재 상태가 되며,
- ledger SHA와 원격 blob SHA가 일치하면 해결로 판정한다.
