## 1. TensorRT — FP16 변환 뒤 compiler가 처리하지 못하는 graph

**확인 사실:** #4925는 열린 사용자 제보다. 11/14 댓글에 random-weight 최소 재현 graph와 실행 script가 추가됐다. maintainer의 원인 확정이나 fix는 확인되지 않았다. [최소 재현 보고](https://github.com/NVIDIA/TensorRT/issues/4925#issuecomment-6872323160).

**보고자 관찰:** BridgeDepth ViT-L, 고정 994×1482 입력의 FP16 ONNX는 build가 실패하고 FP32 export는 build·실행된다고 한다. 환경은 RTX 5060 Ti 16GB, TensorRT 11.4.0.106, CUDA 13.0, driver 595.99.02, Ubuntu 26.04다. 축소 graph는 opset 20·1,161 nodes이며 ONNX checker와 ORT 1.32.0 CPU를 통과하지만 TensorRT의 optimization level 0/1에서도 실패한다고 보고한다. 원래 full export의 opset 18과 축소본을 혼동하지 않는다. [환경·원문](https://github.com/NVIDIA/TensorRT/issues/4925), [축소본](https://github.com/NVIDIA/TensorRT/issues/4925#issuecomment-6872323160).

**비교 조건:** batch·warm-up·inference latency·peak VRAM·power는 미확인이다. build 시간은 inference latency가 아니다. FP16/FP32 export는 cast 구조도 달라 **not strictly apples-to-apples**다.

**진단→가설:** random weights에서도 실패한다는 보고는 값보다 cast/stride를 포함한 graph lowering 문제를 의심하게 한다. 특정 연산의 결함으로 확정할 수는 없다.

**최소 실험 제안:** 같은 GPU·runtime에서 축소본의 cast 경계와 precision만 단계적으로 바꾸고 build 성공·첫 실패 node·output finite 여부를 기록한다. build를 통과한 동일 의미 graph에만 batch 1, 고정 입력, 사전 정의한 warm-up으로 p50/p95 latency와 peak memory를 측정한다.

**GO/KILL:** 작은 변경으로 실패를 켜고 끌 수 있으면 compiler 원인 분리로 GO. engine이 없는 FP16 경로의 속도·전력 우월성 주장은 KILL.

## 2. Apple MPS — 실행 성공, 메모리 상주, 출력 품질을 따로 판정한다

**커뮤니티 측정:** 11/13 M3 Air 16GB 보고는 vLLM 0.33.0+cpu, torch 2.16.0.dev20261013, vllm-metal `3451a014`, Omni rc1에 #10071/#10072 cherry-pick을 사용한다. Z-Image-Turbo BF16/eager, VAE tiling/slicing 설정은 swap 증가와 디스크 여유 제한 때문에 weight load를 끝내지 못했다. 20.431 GiB는 실패한 load 중 process-tree footprint이며 성공한 inference peak가 아니다. [M3 상세 보고](https://github.com/vllm-project/vllm-omni/issues/10009#issuecomment-6848494027).

**측정 경계:** M3 지표는 0.5초 간격 PID footprint 합으로 shared page 중복 가능성이 있다. M5 Max 64GB 보고의 MPS allocated/driver 지표와 직접 비교할 수 없다. M5 Max 보고는 Z-Image 512²·1024² 실행을 보고하지만, torch build와 kernel이 다른 RTX 5090 대조군에서 hardware만의 효과는 분리되지 않는다. **not strictly apples-to-apples**다. [M5 Max 상세 보고](https://github.com/vllm-project/vllm-omni/issues/10009#issuecomment-6850198052).

**미확인 조건:** 두 보고를 통합한 공통 batch·warm-up·입력 manifest와 전력 측정은 없다. 로컬 evidence bundle을 직접 실행·감사하지 않았다.

**진단→가설:** unified memory 용량뿐 아니라 swap·디스크 여유·load 단계가 배포 가능성을 결정한다.

**최소 실험 제안:** 같은 model hash·runtime·prompt·BF16·batch 1·shape를 고정하고 load/warm-up/steady inference를 분리한다. allocated, driver, footprint, swap, free disk와 지연을 같은 시간축에 기록하고 이미지·음성 내용도 검사한다.

**GO/KILL:** 메모리·디스크 예산과 출력 품질을 함께 통과하면 GO. WAV/PNG 생성이나 HTTP 성공만으로 deployment 성공 처리하는 것은 KILL.

## 3. SoScale — FP4 payload보다 scale 선택의 손실을 진단한다

**확인 사실:** v1은 11/12 제출됐다. Hessian-aware scale-code search와 GPTQ식 error recovery를 결합하며 search는 offline이다. Qwen3-8B/14B에서 transformer linear를 W4A4로 양자화하고 embedding·LM head·normalization은 BF16으로 남긴다. [submission](https://arxiv.org/abs/2611.16426), [방법·실험](https://arxiv.org/html/2611.16426v1).

**저자 측정:** Qwen3-8B NVFP4의 7개 task 평균은 RTN 0.7262, SoScale 0.7356, SoScale+Hadamard 0.7308이다. 이 format에서는 Hadamard 추가가 평균을 낮춘다. calibration은 WikiText 128×2,048 tokens, 평가 batch는 64다. GSM8K는 5-shot, 나머지는 zero-shot이며 accuracy 단위도 구분해야 한다. [표·평가 설정](https://arxiv.org/html/2611.16426v1#S4).

**비교 조건:** task 평균은 tok/s가 아니다. 사용 hardware·정확한 software version·warm-up·실제 serving input shape·power는 인용 실험에서 미확인이다. 서로 다른 FP4 format이나 BF16과의 runtime 비교는 **not strictly apples-to-apples**다.

**진단→가설:** element-wise 오차보다 activation 분포에 따른 layer-output 손실이 scale 선택을 지배할 수 있다. 회전의 이득도 format에 의존한다.

**최소 실험 제안:** 동일 calibration·checkpoint에서 scale search on/off × error recovery on/off를 비교한다. layer-output 오차와 task별 정확도를 먼저 보고, 같은 native FP4 runtime에서 batch 1·동일 prompt/context로 TTFT·decode·peak memory를 별도 측정한다.

**GO/KILL:** 정확도 이득이 독립 calibration과 실제 kernel에서 유지되면 GO. W4A4 표기만으로 전체 모델 4-bit·4배 메모리 절감·wall-clock 가속을 주장하면 KILL.
