## 1. TensorRT 11 INT8: 보정 데이터를 늘리는 것이 정확도를 보장하지 않음

**확인 사실:** #27340은 TensorRT 11 ModelOpt 경로의 `calibration_method="max"`를 제거했고 v8.4.217로 병합됐다. TensorRT 7–10의 calibrator 경로는 바꾸지 않았다. [공식 제보와 재현 코드](https://github.com/ultralytics/ultralytics/issues/27334) · [maintainer PR 및 측정표](https://github.com/ultralytics/ultralytics/pull/27340) · [실제 diff](https://github.com/ultralytics/ultralytics/pull/27340/files)

- **실패 조건·모델·dataset·configuration:** 제보자는 Ultralytics 8.4.216, TensorRT 11.5.0.63, ModelOpt 0.48.0, Python 3.13, Colab T4/L4를 사용했다. YOLO11n·YOLO26n은 COCO128 보정과 COCO val2017 평가, static 640×640·batch 1·`rect=False` 조건이었다.
- **커뮤니티 재현:** 제보자는 보정 인자 하나만 바꿨다고 보고했다. T4의 YOLO26n mAP50–95는 FP16 0.4032, INT8 `max` 0.3843, `entropy` 0.3936이었다. 커스텀 모델 결과도 있지만 비공개 test 데이터의 일반화 가능성은 확인하지 못했다.
- **공식 인정·추가 검증:** maintainer glenn-jocher의 PR은 RTX PRO 6000 Blackwell, torch 2.15.0+cu132, TensorRT 11.5.0.63에서 여러 task를 추가 평가했다. 128장 보정의 YOLO26s-pose mAP50–95(P)는 `max` 0.3130, `entropy` 0.6106으로 보고됐다. 이는 **29.76 mAP 포인트** 차이다. 커뮤니티 T4와 maintainer Blackwell 결과는 하드웨어·torch가 달라 `not strictly apples-to-apples`다.
- **진단 → 메커니즘:** PR 설명은 `max`가 관찰된 최대 activation으로 범위를 정해 드문 outlier가 나머지 값의 양자화 해상도를 떨어뜨린다고 해석한다. 더 많은 보정 이미지가 더 큰 outlier를 포함할 수 있다. 이 메커니즘 설명은 maintainer의 해석이며, 이번 watch에서 tensor 분포를 직접 측정하지 않았다.
- **중요한 음성 결과:** 4장 보정에서는 `entropy`가 YOLO26s-OBB mAP를 0.6177→0.6088로 낮췄다고 보고됐다. 따라서 “entropy는 언제나 우월하다”는 결론은 성립하지 않는다. 반복 build에서 일부 변동과 별도 TensorRT build 이상치도 보고됐고 export 시간은 증가했다.
- **가설 → 최소 개입:** calibration 표본 수·구성에 따른 오류를 모델 표현력 문제와 분리한다. 동일 ONNX·weight·표본 순서를 고정하고 보정 방식만 바꾸면 activation outlier와 AP 손실의 관계를 진단할 수 있다.
- **최소 실험:** base `3d02699a6b7c8617f7e7d338f6052719dc3fda95`와 merge `bc52df894fafc9084977674a537bfd9d47185778`를 기준으로, 우선 YOLO26n 한 모델의 고정 보정 subset에서 `max/entropy`와 FP16을 비교한다. 이후 nested 4/128장 subset, 동일 평가 split, 반복 build로 확장한다. AP·export 시간·activation range를 기록하며 tiny-object 효과는 AP-small을 별도 측정하기 전에는 주장하지 않는다.
- **GO/KILL:** 같은 입력·설정의 반복 build에서 보정 방식 효과가 build 변동보다 일관되게 크면 GO. 효과가 재현되지 않거나 표본 구성 차이로만 설명되면 일반적인 보정 우열 주장을 KILL한다.
- **기존 주장과 충돌·한계:** “보정 이미지를 늘리면 안전하게 좋아진다”는 단순 운영 가정에 반례다. 모델 학습 성능 개선이나 모든 GPU에서의 동일 이득을 뜻하지 않는다.

## 2. OCR: 시각화가 다음 추론의 입력을 오염시킴

**확인 사실:** #27326은 detection 뒤 recognizer·drawing용 입력을 정규화하고 annotator에 복사본을 전달한다. 11월 24일 03:16 KST 병합됐다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27326) · [코드 diff](https://github.com/ultralytics/ultralytics/pull/27326/files) · [maintainer의 독립 실행 설명](https://github.com/ultralytics/ultralytics/pull/27326#issuecomment-7109921703)

- **실패 조건·모델·dataset·configuration:** 기본 `solutions.OCR()`의 `yolo26x-text.pt`와 PP-OCRv6, 실제 977×529 elevator-panel 사진을 사용했다. ASCII 라벨이 있는 BGR uint8 입력 배열을 재사용하거나 grayscale·BGRA·uint16을 recognizer에 전달하는 조건이다. 공개 benchmark split 결과는 아니다.
- **공식 인정·재현:** maintainer glenn-jocher는 원본 BGR 배열의 45,539 pixel이 바뀌고 두 번째 호출이 기존 25개 대신 58개 단어를 읽으며 그려진 confidence도 포함한다고 보고했다. Grayscale·BGRA는 detection 뒤 recognizer에서 예외가 발생했고 uint16은 23개를 읽었다. 수정 branch는 해당 입력들을 25개로 읽고 원본을 보존했다고 한다.
- **작성자·community 구분:** 작은 detector와 multispectral detector 관련 추가 결과는 작성자 실행이다. 실제 사진의 기본 모델 재현은 maintainer가 별도로 확인했다. 봇 승인과 coverage 댓글 자체를 독립 재현으로 세지 않는다.
- **진단 → 메커니즘:** detector가 입력을 받아들이는 것과 후단 recognizer가 같은 형식을 받아들이는 것은 다르다. 또한 annotation이 호출자 배열을 바꾸면 다음 호출은 원래 장면과 이전 출력이 합쳐진 이미지를 읽는다.
- **가설 → 최소 개입:** detector 입력은 유지하고 후단에서만 형식을 정규화하며 drawing을 copy에 수행하면 입력 형식 오류와 반복 호출 오염을 함께 줄일 수 있다.
- **최소 실험:** base `90248c4a16d7839895de596b7a14e573f36074ea`와 merge `87b1c92ff1b0fdaacfd369d4dc7f80dcc0caa671`에서 동일 ASCII 사진을 사용한다. 같은 배열 두 번 호출, 매번 새 복사본 호출, 비ASCII 대조군을 비교한다. 호출 전후 pixel hash, token·box·confidence, 두 번째 호출의 annotation 문자열 유입을 기록한다. 형식 테스트는 동일 장면의 grayscale·BGRA·uint16 변형으로 분리한다.
- **GO/KILL:** 원본 hash가 보존되고 반복 호출 결과가 새 복사본 대조군과 같으면 GO. 일반 BGR 결과를 바꾸거나 detector의 단일 channel 계약을 깨면 KILL한다. 원문에 나온 모든 형식에서 token 수가 같다는 사실만으로 일반 인식 정확도의 동등성을 선언하지 않는다.
- **기존 주장과 충돌·한계:** 같은 장면의 연속 OCR 차이를 temporal reasoning·hallucination·모델 불안정성으로 해석하기 전에 입력 mutation을 배제해야 한다. 이 사례만으로 VLM hallucination을 입증하지는 않는다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **4/5** · 연구 아이디어 가치 **4/5**.

## 3. OpenVINO GenAI: 반복 reload의 메모리 증가와 공유 plugin 수명 문제

**확인 사실:** #4993은 미병합이다. Diff는 tokenizer shared implementation의 마지막 참조 해제 시 cleanup, async warmup 대기, cache와 model runner의 해제 순서 변경 및 VLM 하위 모델 cleanup을 포함한다. [공식 PR](https://github.com/openvinotoolkit/openvino.genai/pull/4993) · [수정 diff](https://github.com/openvinotoolkit/openvino.genai/pull/4993/files)

- **실패 조건·모델·dataset·configuration:** 장기 서비스에서 `Tokenizer` 또는 `VLMPipeline`을 반복 생성·실행·파괴한다. 작성자는 Gemma-4-E4B와 Intel Arc B390 iGPU를 명시했다. `PrivateBytes`·CRT heap을 사용했지만 정확한 OS·driver·전체 dependency 조합과 공개 입력 fixture는 본문에서 확인하지 못했다.
- **작성자 주장:** 수정 전 reload당 약 240 KB 증가를 보고했다. 수정 후 tokenizer 300-loop와 VLM construct/destroy에서 heap 증가가 안정화되고, 50-loop generate 후에도 warmup 이후 PrivateBytes가 안정화됐다고 한다. 작성자의 측정이며 독립적인 메모리 profile 검증은 확보하지 못했다.
- **공식 인정·community 수준:** 공식 저장소에 PR이 존재하지만 사람 maintainer의 승인이나 별도 재현은 확인되지 않았다. 조회한 일반 댓글은 없고 리뷰는 작성자 응답과 자동 리뷰 중심이었다. 공식 limitation 확정으로 취급하지 않는다.
- **진단 → 메커니즘:** 작성자는 값 복사된 tokenizer 중 하나의 소멸이 공유 CPU plugin을 너무 일찍 unload하고, 살아 있는 InferRequest·RemoteTensor보다 먼저 plugin/model을 해제하는 순서를 원인으로 제시한다. 코드 변경은 이 설명과 연결되지만 인과성이 독립 검증된 것은 아니다.
- **수정의 남은 반례:** 자동 리뷰는 한 VLM instance의 소멸이 다른 live pipeline과 공유하는 plugin을 unload하면 후속 생성에서 자원이 중복될 수 있다고 지적했다. 작성자는 기존 lifecycle pattern과 일치하는 의도라고 답했다. 이는 해결된 합의가 아니다. [공유 plugin 지적](https://github.com/openvinotoolkit/openvino.genai/pull/4993#discussion_r4655838005) · [작성자 답변](https://github.com/openvinotoolkit/openvino.genai/pull/4993#discussion_r4662474963)
- **가설 → 최소 개입:** 단일 instance의 누수 감소와 여러 instance의 공유 자원 보존은 별도 속성이다. 마지막 참조에서만 cleanup하는 변경과 per-instance plugin unload를 분리해 검증해야 한다.
- **최소 실험:** base `2de7224b8031aaecf173ed98ecb890dbaac5b2b4`, head `1b694ec2cb76a3616b1fb4dfaa6972d70ae9b62c`를 고정한다. 먼저 CPU tokenizer 생성·encode/decode·파괴 loop를 수행하고 warmup 이후 heap slope를 본다. VLM에서는 A를 유지한 채 B를 반복 생성·파괴하고, 매회 A가 같은 입력으로 정상 generate하는지 확인한다. CPU와 GPU, SDPA와 paged attention은 별도 조건으로 기록한다.
- **GO/KILL:** 기존 반복 증가가 재현되고 수정 후 완화되며 살아 있는 A의 출력·실행이 보존되면 GO. 단일 instance 메모리만 안정화되고 다른 pipeline의 실패나 자원 중복이 나타나면 해당 teardown 전략을 KILL한다. allocator caching과 실제 live allocation 누수는 별도 측정으로 구분한다.
- **기존 주장과 충돌·한계:** 객체 scope 종료가 서비스 전체 자원 반환을 보장한다는 가정의 점검 대상이다. 모든 OpenVINO VLM에서 확정된 누수나 OOM이라는 주장은 근거가 부족하다.
- **점수:** 심각도 **3/5** · 재현 신뢰도 **2/5** · 연구 아이디어 가치 **4/5**.

3. **단일 객체 cleanup과 공유 자원 수명의 충돌:** 누수 완화가 여러 pipeline의 공존 안전성을 자동으로 보장하지 않는다.

## 논문 아이디어로 연결 가능한 빈틈

**조사자의 추론:** 반복 호출의 정확도 저하를 모델과 주변 상태로 나누는 진단 연구가 가능하다. OCR에서는 pixel 불변성, quantization에서는 고정 calibration tensor, VLM serving에서는 다른 live pipeline의 생존성을 대조군으로 둔다.

첫 연구 질문은 “반복 OCR 오류 중 입력 mutation 제거만으로 회복되는 비율은 얼마인가?”다. 여러 OCR·시각화 도구와 실제 CCTV·계기판 장면으로 확장하고 token 정확도·reading order·재호출 안정성을 함께 측정해야 한다. 알려진 버그 하나의 수정만으로 논문 novelty를 주장하기는 어렵다. 음성 결과라도 입력이 불변일 때 남는 오류를 모델·recognizer·layout 문제로 좁힐 수 있다.

## 직접 재현해볼 최소 실험

**첫 순위는 OCR 동일 배열 재호출 검사다.** CPU에서 한 사진과 기본 OCR로 시작해 입력 hash와 두 번의 token 결과를 비교한다. GPU가 없는 환경에서도 수행 가능하지만 weight·recognizer 의존성은 필요하다. 형식 변환과 copy를 별도 ablation으로 분리한다.

그 다음 CPU tokenizer loop로 자원 수명 문제를 좁히고, TensorRT 실험은 호환 NVIDIA GPU와 TensorRT 11 환경을 확보한 뒤 수행한다. 각 실험은 source revision, weight·입력 hash, dependency, 실행 명령, seed·build 반복, evaluator 조건을 보존한다. AP 비교 시 dataset revision·split·backbone·pretraining·외부 데이터·해상도·TTA·runtime·compute를 고정한다. 이번 보고서는 조사 결과이며 실제 실험 로그나 새 실측 수치를 생성하지 않았다.
