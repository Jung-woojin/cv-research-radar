## 1. CharXiv — 실패 페널티 수정과 judge 운영 가능성을 분리한다

**무엇이 바뀌었나.** lmms-eval commit `9134731f4f617e62ee80bcae9d0d5d9695ea55ef`는 descriptive/reasoning 집계에 공통 함수를 도입했다. 이전에는 judge 호출·파싱 실패가 반환한 `-1`도 평균에 들어갔다. 수정 후 0/1 이외 값은 0으로 바꾸며, 실패 표본을 분모에서 제외하지 않는다. invalid 개수를 warning으로 남긴다. [공식 변경과 회귀 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/9134731f4f617e62ee80bcae9d0d5d9695ea55ef).

**원본 대조.** 공식 CharXiv `src/get_stats.py`도 비이진 점수를 invalid로 기록하고 0으로 바꾼 뒤 전체 항목을 평균한다. 확인한 blob은 `12d1f1cd524225843d65b752326fe549fa8d55db`다. 따라서 이번 수정은 원본 집계 규칙에 맞추는 변화다. “실패를 빼서 정확도를 올린다”는 설명은 틀리다. [공식 통계 코드](https://github.com/princeton-nlp/CharXiv/blob/main/src/get_stats.py).

**maintainer 설명과 기전.** 작성자는 실패 한 건이 정상 오답보다 추가로 점수를 깎았다고 설명한다. 고정된 N개 결과가 0/1/-1뿐이고 실패가 F개라면, 새 평균과 이전 평균의 차이는 산술적으로 F/N이다. 이는 공식 구현에서 도출한 관계이며 실제 run의 향상량이 아니다. 다른 비이진 값이 섞이면 이 단순식은 적용하지 않는다.

**기본값의 새 문제.** 같은 commit은 placeholder endpoint/model 대신 OpenAI endpoint와 `gpt-4o-2024-05-13`을 기본값으로 사용한다. 공식 원본 reasoning grader도 이 snapshot을 지정한다. 하지만 OpenAI 공식 종료 목록은 이 모델의 종료일을 **2026-10-23**으로 표시한다. 따라서 기본값 복원이 현재 정상 채점을 보장하지 않는다. 종료 공지는 오늘 새 소식이 아니며, 오늘 adapter의 기본값 변경과 충돌한다는 점이 새 관측이다. [원본 grader](https://github.com/princeton-nlp/CharXiv/blob/main/src/reasoning_utils.py), [OpenAI 종료 목록](https://developers.openai.com/api/docs/deprecations).

**실패 경로의 한계.** 기본 endpoint에서 key가 없으면 client 생성 단계에 RuntimeError를 내지만, key가 존재하고 모델 호출이 실패하는 경우에는 helper의 재시도 후 `-1`이 반환될 수 있다. 새 집계는 이를 0으로 계산한다. 그러므로 전체 0점은 모델이 전부 틀렸다는 증거가 아니다. 명시적 endpoint/model override는 가능하지만 다른 judge로 바꾸면 기존 결과와 **not strictly apples-to-apples**다. 이번 실행은 유료 API 호출이나 실제 endpoint 가용성 시험을 하지 않았다. [수정 utils](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/9134731f4f617e62ee80bcae9d0d5d9695ea55ef/lmms_eval/tasks/charxiv/utils.py), [실패 반환 helper](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/9134731f4f617e62ee80bcae9d0d5d9695ea55ef/lmms_eval/tasks/charxiv/reasoning_utils.py).

**진단 → 가설 → 최소 실험.** 먼저 모델 응답·judge 결과를 고정하고 이전 평균, 수정 평균, 공식 통계 규칙을 나란히 적용한다. 전체 수·invalid 수·정상 오답 수를 분리하고 descriptive batch 실패도 개별 문항 단위로 센다. 가설은 과거 점수 차이 일부가 인지 능력보다 judge 실패율에 비례한다는 것이다.

**GO/KILL.** 보존 결과에서 집계 차이가 확인되면 기존 run을 재추론하지 않고 점수와 실패율을 함께 정정한다. 모두 유효한 0/1이면 이번 집계 수정의 영향은 없다고 결론낸다. 과거 raw judge 결과가 없으면 실제 과거 개선량 추정은 중단한다. GPU·신규 judge 호출 없이 시작할 수 있다.

## 2. OK-VQA — 제출 레코드 수정은 로컬 정확도 개선과 다르다

**확인 사실.** commit `b151e05a8afcca759d7af7caa4eea7b877c8d4da`는 제출 항목의 `image: "<question_id>.jpg"`를 `question_id: int(...)`로 바꿨다. 답변 정규화와 `exact_match` 계산식은 diff에서 변경되지 않았다. 작성자는 이전 형식을 VQA evaluator가 읽을 수 없었다고 설명한다. 회귀 테스트는 숫자 ID와 정규화된 답변 레코드를 검사한다. [공식 diff·테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/b151e05a8afcca759d7af7caa4eea7b877c8d4da), [전체 adapter](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/b151e05a8afcca759d7af7caa4eea7b877c8d4da/lmms_eval/tasks/ok_vqa/utils.py).

**외부 원문 대조.** VQA API의 `loadRes`는 각 레코드에서 `question_id`를 읽고 annotation의 질문 ID 집합과 일치하는지 검사한다. image ID는 이후 annotation에서 가져온다. 따라서 파일 이름과 질문 키는 대체 가능한 필드가 아니다. 확인한 VQA API blob은 `fa0abeb31c5f3b62b5be6655cc2ec0ee7b5d5f86`이다. 이것은 형식 계약의 정적 확인이며 실제 OK-VQA 서버 제출 성공을 검증한 것은 아니다. [VQA API](https://github.com/GT-Vision-Lab/VQA/blob/master/PythonHelperTools/vqaTools/vqa.py).

**진단·기전.** 로컬 metric 계산과 외부 제출 파일 생성은 같은 함수 안에서도 별개 출력이다. 제출 불가가 해결됐다고 모델 정확도가 올랐다고 해석하면 안 된다. 반대로 로컬 점수가 있어도 서버에 평가 가능한 artifact가 있었다고 보장할 수 없다.

**가설 → 최소 실험.** 기존 예측의 답변 문자열과 순서를 고정하고 제출 schema만 변환한다. annotation과의 ID 집합 차이, 누락·중복 ID, 정수형 여부를 검사한 뒤 실제 사용하는 evaluator에서 load smoke test를 수행한다. 공식 loader의 집합 검사만으로 중복 레코드가 없음을 증명하지는 못하므로 uniqueness를 따로 검사한다.

**GO/KILL.** 이전 파일만 실패하고 수정 파일이 로드되면 artifact 호환성 복구로 분류한다. 로컬 정확도가 달라지면 schema 외 변경이나 sample alignment부터 조사한다. 서버 채점이나 새 성능 측정은 이번에 실행하지 않았다.

## 3. E.T. Bench — 새 통합에서도 입력과 metric의 세부 계약을 고정한다

**새로운 것은 adapter다.** VLMEvalKit commit `2f11dc888838404991214cce0358fff815be7ff6`가 E.T. Bench를 추가했다. 원본은 NeurIPS 2024 benchmark이며, 공식 프로젝트는 2024년 코드·모델·데이터 release를 명시한다. 오늘 최초 발표로 다루지 않는다. 공식 문서와 adapter는 전체 7,289개와 상용 모델 평가용 470개 subset을 구분한다. [통합 commit](https://github.com/open-compass/VLMEvalKit/commit/2f11dc888838404991214cce0358fff815be7ff6), [공식 프로젝트](https://github.com/PolyU-ChenLab/ETBench), [공식 평가 안내](https://github.com/PolyU-ChenLab/ETBench/blob/main/docs/BENCHMARK.md).

**입력 조건.** 새 preset에는 전체/subset의 1 FPS·2 FPS와 `_vid` prompt가 있다. 원본 문서도 초 단위 텍스트 timestamp와 `<vid>` token·`src` 값의 두 annotation 형식을 구분한다. adapter는 vid-style ECA를 해당 annotation의 선택지로 채점하며, frame 입력 경로에서는 vid-style을 허용하지 않는다. 같은 benchmark 이름이라도 subset·frame budget·prompt가 다르면 **not strictly apples-to-apples**다. [dataset preset](https://github.com/open-compass/VLMEvalKit/blob/2f11dc888838404991214cce0358fff815be7ff6/vlmeval/dataset/video_dataset_config.py), [adapter·metric 구현](https://github.com/open-compass/VLMEvalKit/blob/2f11dc888838404991214cce0358fff815be7ff6/vlmeval/dataset/etbench.py).

**분모 교차검증.** 원본 evaluator와 adapter 모두 TVG에서는 첫 예측 구간의 IoU를 여러 threshold로 평가하고 파싱 실패도 전체 분모에 남긴다. 반면 EVS의 초 단위 summary F1은 파싱 가능한 응답만 평균하고, 모두 실패하면 0이다. 따라서 task별 실패율이 달라지면 같은 방향의 능력 변화 없이도 집계 해석이 달라진다. “모든 파싱 실패는 0점”이라고 전체 benchmark를 요약하면 부정확하다. [원본 metric 코드](https://huggingface.co/datasets/PolyU-ChenLab/ETBench/blob/main/evaluation/compute_metrics.py).

**동등성의 남은 조건.** adapter의 dense caption 경로는 PTB tokenizer 사용에 실패하면 자체 정규식 tokenizer로 전환한다. 원본은 PTB tokenizer를 사용한다. unmatched caption의 비교 문자열도 adapter는 고정 seed를 사용하고 원본은 전역 random을 사용한다. 원본과 큰 구조가 같다는 사실만으로 모든 caption 점수가 bitwise 일치한다고 결론낼 수 없다. 원본 metric 파일은 웹 도구로 열리지 않아 공식 Hugging Face resolve URL을 직접 읽어 교차검증했다. 실행·성능 차이는 측정하지 않았다.

**진단 → 가설 → 최소 실험.** 첫 단계는 저장된 TVG·EVS raw 응답을 같은 task/source/sample ID로 양쪽 evaluator에 넣어 parsed span·Failed·분모·개별 점수를 비교하는 것이다. 추가로 caption 경로에서 tokenizer 종류·random seed·sentence embedding revision을 기록한다. 가설은 모델 차이 일부가 입력 budget과 파싱·집계 계약 차이로 설명될 수 있다는 것이다.

**GO/KILL.** 동일 입력에서 span이나 분모가 달라지면 모델 비교를 멈추고 evaluator부터 고정한다. 일치하면 frame budget만 바꾸는 후속 실험으로 진행한다. synthetic fixture는 구현 검사로만 쓰고 실험적 성능 향상량으로 제시하지 않는다. 새 모델 추론은 후속 단계다. [회귀 테스트](https://github.com/open-compass/VLMEvalKit/blob/2f11dc888838404991214cce0358fff815be7ff6/tests/test_etbench_metrics.py).

## 동조건 비교와 미확인 항목

오늘은 모델 backbone·pretraining·external data·input resolution·TTA·reasoning effort·context/frame/compute budget을 통일한 새 모델 비교를 확보하지 않았다. 순위 이동량과 실제 모델 향상량은 미확인이다.

재평가에는 dataset revision·train/val/test와 sample ID, evaluator commit, raw prediction, prompt·decoding, judge snapshot·endpoint, 실패 로그를 보존해야 한다. E.T. Bench의 원본/압축 영상과 sampling도 구분한다. 공식 안내의 선택적 영상 압축은 입력 조건이며 이번 통합에서 새로 발표한 데이터 split 변경이 아니다.

공식 테스트는 읽었지만 실행하지 않았다. 채점 모델 변경은 calibration이 필요한 개입이고, 제출 schema 수정은 모델 재학습 근거가 아니다. 이번 보고서의 가설·실험은 제안이며 실행 결과를 만들지 않았다.

## 오늘의 benchmark signal 3개

1. **judge 실패와 정상 오답을 구분한다.** 공식 규칙상 둘 다 0점이어도 운영 원인과 모델 능력의 의미는 다르다.
2. **평가 가능한 artifact를 별도로 검증한다.** 로컬 정확도와 서버 제출 호환성은 각각 검사한다.
3. **task별 분모와 입력 budget을 명시한다.** 같은 benchmark 안에서도 실패 처리·timestamp 표현이 다를 수 있다.

## 내 연구에 바로 연결되는 포인트

- Evidence-grounded VQA·해양 안전 VQA에서는 전체 0점 run을 해석하기 전에 judge 오류율과 endpoint/model 설정을 확인한다.
