## Q1. 반복 OCR의 오류 중 얼마가 모델 불안정성이 아니라 이전 출력의 입력 재유입인가?

**문제·Observation·왜 지금:** #27326의 사실은 detector 뒤 입력 정규화와 annotator에 복사본 전달을 추가한 것이다. PR은 ASCII 페이지를 원본 배열에 그리면 다음 호출이 라벨까지 읽는다고 보고한다. 실제 사진 재현은 maintainer가 별도로 확인했다고 당일 failure가 추적했다. 단어 수 증가는 정확도 향상 근거가 아니다.  
[공식 PR](https://github.com/ultralytics/ultralytics/pull/27326) · [실제 diff](https://github.com/ultralytics/ultralytics/pull/27326/files) · [maintainer 재현](https://github.com/ultralytics/ultralytics/pull/27326#issuecomment-7109921703)

**Gap·Diagnosis·Mechanism:** 같은 장면의 연속 호출이라도 pixel이 달라지면 모델의 반복 안정성 실험이 아니다. 추론상 시각화가 만든 confidence·라벨을 recognizer가 다시 증거로 읽는다. 입력 형식 정규화와 복사 효과가 한 변경에 들어 있어 둘을 분리해야 한다.

**Hypothesis:** BGR uint8에서 drawing copy만 적용해도 원본 mutation에 따른 추가 token 유입이 사라진다. Grayscale·BGRA·uint16의 오류는 후단 정규화가 별도로 설명한다.

**최소 개입·Experimental Design:** base `90248c4a16d7839895de596b7a14e573f36074ea`와 head `4bb478b730290c9ced910677ab2e312c8a68c7ef`를 고정한다. copy 유무 × 정규화 유무의 2×2 ablation을 설계한다. 동일 배열 재호출, 매 호출 새 복사본, drawing 비활성 대조군을 비교하고 detector에는 원래 입력을 유지한다. ASCII·비ASCII는 별도 층화한다.

**Dataset·baseline·metric·GO/KILL:** CPU에서 권한이 있는 문자 사진 한 장으로 시작하고 공개 OCR 개발 subset으로 확장한다. 정확한 이미지 확보·annotation은 미확인이다. baseline은 매번 원본 복사본을 주는 호출이다. 호출 전후 pixel hash, annotation 문자열 재인식률, token·box 차이, 정답이 있는 경우 CER/WER를 측정한다. 원본 보존과 오류 회복이 대응하면 GO. hash가 같아도 결과가 달라지면 입력 오염만의 설명은 KILL하고 내부 상태·비결정성을 조사한다.

**Expected Contribution·negative result:** 인식 오류를 모델과 주변 입력 상태로 분해하는 검사다. 영향이 없으면 해당 경로의 반복 오류는 drawing mutation으로 설명되지 않는다는 경계를 얻는다.

**Compute·Risk·4~8주:** CPU MVP cost **1/5**, 실제 OCR weight·recognizer 의존성은 필요하다. 1~2주 불변성 검사, 3~4주 여러 OCR·시각화 라이브러리, 5~8주 CCTV·계기판 반복 호출로 확장한다. 알려진 버그 하나 재현만으로 novelty는 낮고 여러 도구에서 반복되는 오류 구조가 있어야 논문화 후보가 된다.

## Q2. INT8의 작은 객체 손실은 보정 표본 부족보다 activation 범위의 outlier 민감도 때문인가?

**문제·Observation·왜 지금:** #27340 diff는 TensorRT 11 ModelOpt 호출의 명시적 `calibration_method="max"`를 제거한다. PR은 기본 entropy로 전환했다고 설명한다. 128장 보정에서는 테스트한 모델들이 개선됐다고 보고하지만 소수 보정의 일부 OBB·다른 task는 악화됐다고도 보고한다. TensorRT 7–10 경로는 별개다.  
[공식 PR·측정 조건](https://github.com/ultralytics/ultralytics/pull/27340) · [실제 diff](https://github.com/ultralytics/ultralytics/pull/27340/files) · [최초 제보](https://github.com/ultralytics/ultralytics/issues/27334)

**Gap·Diagnosis·Mechanism:** maintainer는 큰 activation이 max 범위를 늘려 다른 값의 해상도를 낮춘다고 해석한다. 하지만 AP-small 저하나 특정 층의 인과 기전은 이번 근거에서 확인되지 않았다. 전회 calibration 크기·장면 대표성 질문에서 한 단계 나아가 고정 tensor의 범위 추정만 개입한다.

**Hypothesis:** calibration tensor를 고정하면 outlier에 민감한 층에서 max 대비 entropy의 양자화 오차가 커지는 조건을 찾을 수 있다. 그 층만 FP16으로 복원했을 때 small-object recall이 회복되어야 검출 실패와의 인과 연결을 지지한다.

**최소 개입·Experimental Design:** 먼저 저장 activation이나 합성 분포로 최대값·clipping·재구성 오차를 검사한다. 이후 같은 YOLO26n checkpoint·ONNX·TensorRT 11 환경에서 max/entropy/FP16을 paired 비교한다. 고정 subset·순서를 사용하고 반복 build 변동을 별도로 기록한다. 층별 FP16 복원은 한 번에 한 구간만 바꾸며 precision 배치·실제 kernel도 확인한다.

**Dataset·baseline·metric·GO/KILL:** COCO 개발 subset으로 보정하고 고정 val2017 ID에서 AP-small·scale별 recall·전체 AP, activation saturation·재구성 오차, build 시간·추론 latency를 기록한다. calibration과 평가 이미지는 겹치지 않게 한다. 특정 층 개입이 build 변동을 넘어 scale별 오류를 회복하면 GO. 전체 AP만 변하거나 영향이 반복되지 않으면 small-object 기전 주장은 KILL한다.

**Expected Contribution·negative result:** 범위 선택 → 층별 정보 손실 → scale별 오류를 연결하는 진단이다. 작은 객체에 특이적인 영향이 없으면 일반 양자화 오차와 scale-specific 가설을 구분할 수 있다.

**Compute·Risk·4~8주:** tensor CPU 검사는 cost **1/5**, GPU export·평가는 **3/5**의 계획 판단이다. 1~2주 범위 분석, 3~4주 반복 build, 5~8주 소형 detector 간 검증을 계획한다. RTX 5060 Ti 8GB 호환성·VRAM은 미측정이다. 혼합 정밀도·outlier 연구와 중복 위험이 높아 단순 entropy 우월성 주장은 기여가 약하다.

## Q3. VLM 누수 수정은 다른 살아 있는 pipeline의 자원 수명까지 보존하는가?

**문제·Observation·왜 지금:** #4993은 tokenizer 마지막 공유 참조에서 cleanup하고 async warmup을 기다리는 등의 수정 제안이다. 작성자는 반복 reload의 메모리 안정화를 보고한다. **미병합이며 독립 재현은 미확인**이다. 자동 리뷰는 한 instance의 plugin unload가 공유 core의 다른 live pipeline과 충돌할 위험을 지적했고, 작성자는 기존 lifecycle과 일치하는 의도라고 답했다. 합의된 해결로 볼 수 없다.  
[공식 PR·작성자 검증](https://github.com/openvinotoolkit/openvino.genai/pull/4993) · [공유 plugin 반례](https://github.com/openvinotoolkit/openvino.genai/pull/4993#discussion_r4655838005) · [작성자 답변](https://github.com/openvinotoolkit/openvino.genai/pull/4993#discussion_r4662474963)

**Gap·Diagnosis·Mechanism:** 단일 객체 소멸 뒤 메모리 plateau와 여러 객체의 공존 안전성은 서로 다른 속성이다. cache·allocator의 예약 메모리와 live allocation 누수를 구분하지 않으면 teardown 효과를 잘못 읽을 수 있다.

**Hypothesis:** 마지막 참조 cleanup은 tokenizer 복사본의 수명을 보존하지만, per-instance plugin unload가 포함된 전략은 공존 조건에서 재생성 비용·자원 중복을 만들 수 있다. 이는 리뷰에서 도출한 가설이며 실제 장애가 확인됐다는 뜻은 아니다.

**최소 개입·Experimental Design:** base `2de7224b8031aaecf173ed98ecb890dbaac5b2b4`, head `1b694ec2cb76a3616b1fb4dfaa6972d70ae9b62c`를 고정한다. CPU tokenizer 복사·encode/decode·부분 소멸 뒤 생존 복사본을 검사한다. 이후 A pipeline을 유지하며 B를 생성·파괴하고 매회 A의 고정 입력 추론을 확인한다. 전체 patch와 마지막 참조 cleanup만 적용한 ablation, plugin unload 제외 ablation을 비교한다.

**Dataset·baseline·metric·GO/KILL:** tokenizer fixture와 고정 이미지·prompt부터 시작한다. 정확한 tokenizer/model artifact 확보는 미확인이다. warmup 이후 live heap slope·PrivateBytes/RSS·device memory, A의 실패율·결정적 출력 일치·재생성 시간·thread/handle을 측정한다. 단독 loop와 공존 loop 모두 안정화되면 GO. A가 실패하거나 자원 중복이 증가하면 해당 teardown 전략은 KILL한다.

**Expected Contribution·negative result:** 정확도와 메모리 회수를 함께 보존하는 serving 수명 계약이다. 증가가 allocator cache로 설명되거나 공존 문제가 재현되지 않아도 적용 범위를 좁히는 유효한 결과다.

**Compute·Risk·4~8주:** CPU tokenizer cost **1/5**, VLM 공존 실험 **3/5**. 1~2주 tokenizer, 3~4주 두 instance, 5~8주 다른 backend·device로 확장한다. Intel iGPU 제보를 NVIDIA 8GB로 일반화하지 않는다. 시스템 연구 성격이 강하며 CV 논문 기여는 장기 영상 서비스의 오류·가용성과 연결해야 한다.

## Q4. 영상의 Answer–Evidence Gap 중 얼마가 모델 대신 judge의 프레임 누락에서 생기는가?

**문제·Observation·왜 지금:** 최근 Omni adapter의 content judge는 auto 모드에서 video 요청이 특정 HTTP 오류로 거부되고 8프레임 요청이 성공하면 이후 frames를 사용한다. 한 번 video 요청이 수락되면 video를 유지한다. 일시적 서버 오류·rate limit은 입력 모드 전환 사유가 아니다.  
[고정 adapter 코드](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/omni_duplexeval/utils.py) · [입력 모드 계약](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/omni_duplexeval/README.md)

**Gap·Diagnosis·Mechanism:** 모델이 위험 사건을 봤더라도 8개 균등 프레임에 사건이 없으면 judge가 정답 근거를 확인하지 못할 수 있다는 추론이다. HTTP 요청 수락은 endpoint가 local video를 실제 읽었다는 증명이 아니다. 모델 grounding 실패와 judge 관측 실패를 분리해야 한다.

**Hypothesis:** 응답·judge·prompt를 고정하면 사건 프레임 포함 여부가 content 판정 불일치의 일부를 설명한다. 동일 frame budget 안에서 사건을 포함하는 진단 조건은 그 영향을 줄인다.

**최소 개입·Experimental Design:** CPU에서 event 구간 annotation과 8개 sampling 시각의 교집합부터 계산한다. 모델 재추론 없이 저장 응답을 사용해 균등 8프레임과 사건 포함 8프레임을 paired 채점한다. 실제 video 독해를 확인한 endpoint가 있을 때만 video 대조군을 추가한다. 사건 annotation을 쓰는 조건은 **진단용 oracle**이며 실사용 성능 개선으로 보고하지 않는다.

**Dataset·baseline·metric·GO/KILL:** Omni-DuplexEval의 확인 가능한 event subset과 별도 event 구간 annotation을 사용한다. 기본 reminder 시각을 사건의 전체 지속 구간으로 간주하지 않는다. 원본 split·revision·sample ID를 고정하고, 사건 포착률·사람 판정 대비 false rejection·content 점수 차이·judge 실패율을 측정한다. 사건 누락과 오류가 연결되면 GO. judge가 영상을 읽는지 미확인인 조건의 우열 주장은 KILL한다.

**Expected Contribution·negative result:** 모델–judge 증거 접근의 차이를 기록하는 evaluation audit다. 차이가 없으면 해당 clip·응답에서는 균등 sampling 누락이 지배적 원인이 아니라는 결론을 얻는다.

**Compute·Risk·4~8주:** 시각 교집합은 CPU cost **1/5**, 유료 judge 비교는 **2/5**로 계획한다. 이번에는 API를 호출하지 않았다. 1~2주 사건 annotation, 3~4주 재채점, 5~8주 CCTV·해양 안전 clip으로 일반화한다. frame sampling 연구와 중복 위험이 크며 사람 기준과 실제 자연 응답이 필요하다. video/frames 점수는 **not strictly apples-to-apples**다.

## Q5. Streaming VLM은 미디어 시각에는 제때 답해도 실제 사용자에게는 늦게 도착하는가?

**문제·Observation·왜 지금:** 고정 MiniCPM duplex wrapper는 입력을 실제 시간 대기 없이 chunk별로 재생한다고 명시한다. 반환 `current_time`을 adapter가 preamble만큼 보정하고, reminder 시각 뒤의 텍스트 window를 채점한다. 이는 미디어 시각의 적절성과 wall-clock 응답 지연을 같은 것으로 취급할 수 없음을 보여준다.  
[고정 wrapper](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/models/simple/minicpm_o_45_duplex.py) · [정규화·window 코드](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/573a89504132afb6371a43de526b52ed8151b004/lmms_eval/tasks/omni_duplexeval/utils.py) · [원본 데이터의 질문 시각](https://huggingface.co/datasets/Hothan/Omni-DuplexEval)

**Gap·Diagnosis·Mechanism:** offline replay는 chunk 순서에 따른 모델 행동을 평가할 수 있다. 하지만 처리 시간이 chunk 유입 속도를 넘으면 실제 서비스에는 backlog가 쌓일 수 있다는 추론이다. 정확한 시각 출력도 queue 지연·audio 생성·전송 비용을 포함한다는 보장은 없다.

**Hypothesis:** 같은 입력과 출력 의미에서도 처리 속도·queue 정책에 따라 실제 event-to-answer 지연이 달라진다. 미디어 기반 성공과 wall-clock deadline 성공을 함께 보고하면 안전 경보의 숨은 지연을 찾을 수 있다.

**최소 개입·Experimental Design:** 먼저 CPU mock stream에서 미디어 시각·monotonic 수신 시각·처리 완료 시각을 별도로 기록하고 알려진 처리 지연을 주입한다. 이후 같은 checkpoint·decoding·chunk 입력으로 offline replay와 실시간 유입을 비교한다. queue 보존·drop 정책, 첫 token/최종 답/음성 시작 시점을 명시하며 preamble 보정을 따로 감사한다.

**Dataset·baseline·metric·GO/KILL:** 합성 event 시퀀스는 계측 검증에만 쓰고 Omni PR 개발 clip으로 확장한다. baseline은 현재 wrapper의 미디어 시각 점수다. event-to-first-valid-answer 지연·deadline miss·queue 길이·미디어/실제 시각 차이를 기록하고 내용 정확도를 함께 측정한다. 동일 내용 수준에서 지연 차이가 재현되면 GO. monotonic 계측 없이 timestamp 차이만으로 실시간 실패를 주장하면 KILL한다.

**Expected Contribution·negative result:** temporal reasoning과 서비스 처리 지연을 분해하는 protocol이다. 실제 실행이 유입 속도를 충분히 따라가면 해당 장비·부하에서 backlog 설명을 배제할 수 있다. Q4는 judge가 보는 증거, Q5는 응답 전달 시각이 개입 대상이다.

**Compute·Risk·4~8주:** mock cost **1/5**, 실제 streaming VLM은 **4/5**이며 8GB 실행 가능성은 미확인이다. 1~2주 clock 검증, 3~4주 고정 모델 계측, 5~8주 부하·사건 길이·queue 정책을 비교한다. 단순 latency logging으로는 novelty가 낮다. 안전 사건의 내용–시점 성공률이 분리되는 조건을 보여야 논문화 후보가 된다. 새 학습은 첫 실험에 필요하지 않다.

## 공통 비교 조건과 오늘의 선택

dataset revision·split·sample ID·입력 hash, checkpoint·backbone, pretraining·external data, input resolution·TTA, processor·runtime·dtype, reasoning·context/frame budget, compute budget, evaluator commit·judge snapshot을 고정한다. 해당하지 않는 것은 N/A, 확보하지 못한 값은 미확인으로 남긴다. 장비·입력 모드·평가 분모·시간 기준이 다른 비교는 **not strictly apples-to-apples**다.

점수는 조사자의 우선순위 판단이며 실측치나 출판 보장이 아니다. Compute cost는 낮을수록 가볍고 compute efficiency는 높을수록 유리하다.

- **오늘 가장 먼저 테스트할 질문:** Q1. 한 BGR 사진에서 동일 배열 재호출과 새 복사본 호출의 hash·추가 token을 비교한다.
- **RTX 5060 Ti 8GB에서도 시작할 질문:** Q1 CPU 검사, Q2 tensor 범위 검사, Q3 tokenizer 검사, Q4 sampling 교집합, Q5 mock clock 검사. 실제 GPU 단계의 VRAM은 미측정이다.
- **장기 박사주제:** 입력 상태 → 모델 증거 → judge 증거 → 응답 전달 시각의 오류 예산을 연결하는 안전 영상 평가. Q4·Q5를 중심으로 CCTV·해양 위험 사건에서 무엇을 보았고 언제 유효하게 반응했는지 분리한다. 현재는 연구 방향이며 검증된 분야 추세나 완성된 기여가 아니다.

조사 결론은 새 architecture보다 주변 상태·관측·시계의 계약부터 검증하자는 것이다. 질문별 GO/KILL은 모두 제안이며 실행 결과가 아니다.
