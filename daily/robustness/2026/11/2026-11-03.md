## 1. Text→image Arabic shift — 평균 지수로 가려지는 시각 입력 failure cell

- **출처:** [System One Bench v1.13.0 release](https://github.com/alilibx/system-one-bench/releases/tag/v1.13.0), [공식 README](https://github.com/alilibx/system-one-bench).
- **사실:** v1.13.0은 GLiDE를 모든 3,250 text case와 5개 Vision Index dataset에 동일 request body로 실행했고, System One Index 84.1, Vision Index 82.5를 기록했다고 발표합니다.
- **공식 결과:** release는 GLiDE가 text의 동일 Arabic tweet에서 73.5%였으나 이미지 입력에서는 51.5%로 22.0 point 하락했다고 밝힙니다. Calibration error는 3.6%이며, Vision Index rank는 13개 중 7위입니다.
- **해석:** 이 차이는 언어 능력만의 domain shift가 아니라 render/OCR/visual grounding을 포함한 modality shift입니다. text 결과와 image 결과를 하나의 “Arabic capability” 수치로 합치면 failure cell이 숨겨집니다.
- **진단 → 가설 → 최소 실험:** 동일 문장을 text와 rendered-image로 만들고, English·French·Arabic과 280px 이상/이하, clean/compressed 조건을 교차합니다. accuracy, calibration error, abstention 또는 invalid-format rate를 함께 기록합니다.
- **GO/KILL:** 이미지 Arabic cell의 accuracy·calibration guardrail이 통과하면 GO입니다. text score만으로 OCR/vision deployment를 통과시키는 것은 KILL입니다.

## 2. Repeat-run stability — 재현 가능성과 shift robustness의 구분

- **출처:** [System One Bench v1.13.0 release](https://github.com/alilibx/system-one-bench/releases/tag/v1.13.0).
- **사실:** release는 GLiDE의 두 번째 full run이 동일 index 84.13을 기록했고, 4,850 decision 중 7개 답만 달랐다고 보고합니다.
- **해석:** 이는 고정 request·고정 data·동일 API 경로에서의 run-to-run 안정성 신호입니다. 그러나 camera, compression, provider model revision, language distribution이 달라졌을 때도 견고하다는 증거는 아닙니다.
- **진단 → 가설 → 최소 실험:** baseline과 rerun을 같은 data hash에서 최소 3회 실행한 뒤, 별도로 image rendering·언어·provider region을 하나씩 바꿉니다. exact-match disagreement, calibration drift, worst-cell accuracy를 분리해 봅니다.
- **GO/KILL:** same-hash rerun과 shift cell 모두에서 허용 오차를 만족하면 GO입니다. 7/4,850 disagreement만으로 OOD robustness를 주장하는 것은 KILL입니다.

## 3. Latency measurement location — 네트워크 shift를 모델 성능으로 오인하지 않기

- **출처:** [System One Bench v1.13.0 release](https://github.com/alilibx/system-one-bench/releases/tag/v1.13.0).
- **사실:** GLiDE round는 기존 board latency를 측정한 cloud server와 왕복 경로가 다른 장비에서 실행됐습니다. release는 Jev 1.14 control이 그 장비에서 median 521ms였고 board에서는 136ms였다고 기록하며, GLiDE latency를 board에 싣지 않았습니다.
- **해석:** API model의 end-to-end latency는 model compute만이 아니라 region, gateway, queue, concurrency, retry 정책의 함수입니다. 측정 host가 바뀌면 순위 자체가 shift될 수 있습니다.
- **진단 → 가설 → 최소 실험:** 동일 model·prompt·concurrency에서 baseline control model을 매 run에 넣고, host/region을 바꿔 median·p95·timeout rate를 수집합니다. control drift가 사전 한계를 넘으면 해당 run의 cross-run latency 비교를 무효화합니다.
- **GO/KILL:** control이 안정적일 때만 새 model latency를 기존 leaderboard와 비교합니다. control drift가 큰 run의 latency를 다른 round의 품질/비용 Pareto에 넣는 것은 KILL입니다.
