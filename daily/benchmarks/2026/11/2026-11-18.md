## 1. 이미지 표식 배치 — 동일 파일도 chat 입력 계약이 달라진다

**무엇이 바뀌었나·확인 사실.** `ConfigurableMessagesTask._build_user_turn`은 이미지 수와 텍스트의 `<image>` 수가 같을 때 각 표식을 실제 image content로 치환한다. 이전에는 이미지를 앞에 모으고 텍스트의 표식을 그대로 남겼다. 새 경로는 텍스트 segment를 strip하며, 비이미지 media는 앞에 남긴다. 표식이 없거나 개수가 맞지 않으면 기존 경로를 유지한다. 따라서 모든 task·backend에 일괄 적용되는 수정은 아니다. [공식 diff](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/7e25868c14dab6e8a5c2d69463f4d9b2f906d231).

**maintainer 설명과 교차확인.** STARE·MMT·Geometry3K·MathCanvas처럼 자체 `doc_to_messages`가 없는 과제에서 chat processor가 image token과 이미지를 이중 계산하는 오류를 설명한다. 추가 테스트는 두 이미지의 표식 위치 배치, marker-only 입력, video와 image 혼합, 표식 없는 입력, 개수 불일치 fallback을 검증하도록 작성됐다. 테스트의 존재와 내용을 확인했지만 실행하지 않았다. [회귀 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/7e25868c14dab6e8a5c2d69463f4d9b2f906d231/test/eval/test_user_turn_image_placeholders.py).

**관측 → 진단 → 기전·추론.** 평가 실패는 시각 추론 결함 이전에 message 조립 계약에서 생길 수 있다. 실행이 성공하더라도 이미지와 참조 문장의 순서가 바뀌므로 multi-image 비교 결과가 달라질 가능성이 있다. 이중 계산은 processor의 토큰 처리 문제이며 이미지 파일 자체가 두 번 복제됐다는 증거와는 구별한다.

**가설 → 최소 개입 → 실험 제안.** 같은 이미지·질문을 고정하고 parent `60a79fb270e5c712460c533e0a3664c7081c0a7f`와 수정 commit의 serialized content를 비교한다. image count, literal marker count, image-text 순서, processor 성공 여부를 기록한다. 먼저 공식 fixture로 계약을 감사하고, 영향을 받는 실제 과제 표본에 한해서 같은 checkpoint·processor·decode budget으로 paired 추론한다. 완료율과 완료 응답의 정확도를 각각 보고하며 실패를 포함한 전체 분모도 보존한다.

**GO/KILL.** 개수 불일치가 사라져도 정답률 개선을 자동 인정하지 않는다. 직렬화 결과가 같거나 해당 task가 자체 message 함수를 쓰면 영향 대상에서 제외한다. 완료율만 오르면 adapter 복구로 기록한다.

**비교 판정.** 같은 이미지와 모델이어도 message protocol이 달라진 old/new 결과는 **not strictly apples-to-apples**다. 새 dataset split·pretraining·backbone 개선을 보여주는 변경은 아니다.

## 2. median 집계 — 순서에 의존하던 통계를 바로잡는다

**무엇이 바뀌었나·확인 사실.** 공통 `median(arr)`는 `arr[len(arr)//2]`에서 `statistics.median(arr)`로 수정됐다. 이전 구현은 정렬을 하지 않았고 짝수 길이에서 가운데 두 값의 평균도 계산하지 않았다. 같은 commit은 power analysis에서 0·비유한 effect size, alpha/power 범위 위반, correlation 범위 위반, 음수 표준편차, paired difference의 영분산 등에 오류를 내며 CLI가 이를 설명하도록 바꾼다. [공식 diff](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/c33a160d7d08168897051091029aee2d88229232).

**공식 테스트의 구체적 의미.** fixture `[5,1,9]`의 새 median은 5이고 `[3,1,2,10]`은 2.5다. 입력을 바꾸지 않는지도 검사한다. 이는 통계 계약의 예시이며 모델 benchmark 측정값이 아니다. 테스트는 정상 power 입력과 일부 잘못된 입력도 포함한다. [테스트 원문](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/c33a160d7d08168897051091029aee2d88229232/test/eval/test_metrics_median_power.py).

**관측 → 진단 → 기전·추론.** 이전 구현을 호출한 평가는 모델 출력이 같아도 sample ordering에 따라 집계값이 달라질 수 있다. 그러나 median 함수 수정이 모든 accuracy·mAP에 영향을 준다는 결론은 잘못이다. 실제 사용 task 목록·영향 점수·순위 변동은 이번 조사에서 확정하지 못했다. power analysis의 입력 검증도 유효한 모든 설정에서 표본 수가 바뀌었다는 증거는 아니다.

**가설 → 최소 개입 → 실험 제안.** 보유 평가 설정에서 `aggregation: median` 또는 동적 median 호출을 먼저 찾는다. 없다면 이 실험을 중단한다. 있다면 원본 per-sample 값을 고정하고 순서만 여러 번 섞어 parent와 수정 구현으로 집계한다. 순열별 범위, 표준 median 일치 여부, 짝수/홀수 구간 차이를 남긴다. 새 모델 호출은 필요 없다. power analysis는 별도 감사하며, 실제 paired difference 분산과 가정한 correlation을 기록한다.

**GO/KILL.** 수정 전 결과가 순서에 따라 변하면 영향을 받은 평가 결과만 evaluator revision과 함께 재산출한다. 이미 정렬된 홀수 입력처럼 결과가 같으면 해당 데이터에서 영향 없음으로 남긴다. 실제 task 호출 근거 없이 과거 leaderboard를 오류라고 단정하지 않는다.

**비교 판정.** 동일 저장 출력을 사용하는 paired 재집계는 집계기 효과를 분리할 수 있다. 서로 다른 구현에서 나온 과거 headline score를 모델 개선량으로 비교하면 **not strictly apples-to-apples**다. 데이터·학습·입력 resolution·TTA는 이 수정의 개입 대상이 아니다.

## 3. FERMAT-PINK 통합 — 잘못 쓴 내용을 충실하게 읽는가

**실제 새 변화·확인 사실.** 신규성은 PINK 논문의 최초 발표가 아니라 lmms-eval 과제 통합이다. ACL 원문은 2026년 10월 논문으로 표기된다. adapter는 `ai4bharat/FERMAT`의 `train` split을 평가용으로 쓰고, temperature 0·최대 4,096 tokens로 전사를 생성한다. `pink`, `over_correction_rate`, `raw_score_ratio`를 노출하고 `pink-eval` scorer를 호출한다. `train`이라는 split 이름이 이번 모델을 그 표본으로 학습했다는 증거는 아니다. [통합 diff·YAML·utils](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/6dcf31da7b92970fd91a2a7a37f03b36ec112f0c), [ACL 논문 소개](https://aclanthology.org/2026.emnlp-main.476/).

**저자 주장.** 일반 문자열 유사도는 학생 풀이의 오류를 모델이 임의로 바로잡는 over-correction을 충분히 드러내지 못한다. PINK는 모델 전사와 실제 필기 전사를 같은 rubric으로 채점해 개선돼 보이는 부분을 벌점 처리한다. 이 문제 정의는 공식 논문 소개와 원저자 저장소가 일치한다. 기존 논문의 모델 순위는 오늘 새로 측정한 결과로 옮기지 않는다. [공식 PINK 저장소](https://github.com/9115jin/PINK).

**scorer 교차검증·확인 사실.** 공식 `score.py`는 component별 모델 점수가 oracle보다 높을 때 차이가 10 이하면 oracle 점수로 되돌리고, 10을 넘으면 0으로 만든다. PINK는 벌점 적용 점수 합을 oracle 점수 합으로 나눈다. 단순 sample별 비율의 평균과는 다르다. 공식 scorer의 기본 `missing="drop"`은 oracle/model 성공 표본의 교집합을 쓴다. adapter도 judge 성공 row만 model DataFrame에 넣고 `compute_pink(model, oracle)`를 호출한다. 빈 전사는 별도로 성공 row의 0점으로 처리한다. 따라서 **빈 전사와 judge 호출 실패의 분모 정책이 같지 않다.** [공식 scorer, 조회 blob `48311213882dc67a7639e29eb1aaaffea381e42d`](https://github.com/9115jin/PINK/blob/main/src/pink/score.py), [adapter 코드](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/6dcf31da7b92970fd91a2a7a37f03b36ec112f0c/lmms_eval/tasks/fermat_pink/utils.py).

**추가 감사점·정적 코드 추론.** adapter cache key는 sample ID와 prediction의 tuple이며 judge 설정·oracle 파일은 포함하지 않는다. 같은 process에서 같은 응답을 다른 judge나 oracle로 연속 평가하면 cache가 재사용될 가능성이 있다. 실제 오염 실행을 재현한 것은 아니며, 별도 process 실행으로 우선 회피하고 후속 검증할 사항이다.

**관측 → 진단 → 기전·추론.** 이미지 증거와 답의 의미가 다를 때, 언어 모델이 더 그럴듯한 정답으로 바꾸는 것이 OCR 목적에는 실패일 수 있다. 다만 judge 실패가 어려운 표본에 몰리면 교집합 점수도 선택 편향을 받을 수 있다. 이것은 코드에서 도출한 위험 가설이며 실제 편향 크기는 미측정이다.

**가설 → 최소 개입 → 실험 제안.** 저장된 전사·oracle·judge grade가 있다면 모델 재추론 없이 다음을 감사한다.

1. 전체 요청 수, model/oracle judge 성공 수, 교집합 `n`, 빈 전사 수를 함께 기록한다.
2. 공식 drop 점수를 보존하고, 정확히 같은 요청 subset으로 oracle를 제한한 뒤 judge 누락을 0점으로 두는 민감도 분석을 별도 수행한다. 전체 packaged oracle를 무조건 분모로 쓰지 않는다.
3. 같은 전사에 대해 judge/oracle 설정만 바꿀 때 process를 분리한다. 후속 cache 실험은 judge 호출을 mock하여 네트워크 없이 검증한다.
4. over-correction 표본을 사람이 원본 필기와 대조해 의미 보존 오류와 judge 판단 오류를 분리한다.

**GO/KILL.** drop/zero 간 결론이 달라지면 PINK 하나만으로 모델 우열을 정하지 않는다. 표본 수와 judge provenance가 일치하고 인간 감사에서도 오류 은폐가 확인될 때 충실도 평가 실험을 확대한다.

**비교 판정.** judge·oracle·prompt·유효 표본이 다른 PINK 값, BLEU와 PINK의 숫자 자체는 **not strictly apples-to-apples**다. adapter 테스트는 judge 호출을 fake하므로 실제 API 재현이나 논문 순위 검증을 대신하지 않는다. [공식 adapter 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/6dcf31da7b92970fd91a2a7a37f03b36ec112f0c/test/tasks/test_fermat_pink.py).

| dataset revision·split | 이미지 수정은 task별 기존 데이터. PINK YAML은 train split이며 dataset revision은 고정하지 않음 |
| backbone·pretraining·external data | 새 학습이나 backbone 통제 실험 없음. 모델별 학습 오염 여부 미확인 |
| resolution·TTA | 이미지 메시지 순서는 변경되나 resize 동등성은 미확인. PINK는 RGB 변환, TTA 동등성 미확인 |
| inference·reasoning·context | PINK 전사 4,096-token cap과 judge budget은 별개. 백엔드별 유효 설정 기록 필요 |
| compute budget | median은 저장 출력 재집계 가능. PINK 신규 judge 호출에는 별도 비용 발생. 실측 비용·VRAM 없음 |
| evaluator version | 각 항목의 고정 commit과 parent를 구분. 외부 pink-eval 설치 버전·oracle provenance도 보존 필요 |
| 논문·코드·leaderboard 일치 | PINK 문제 정의·벌점 기전은 원문과 코드가 일치. 오늘 새 leaderboard 상승·순위 역전은 확인하지 않음 |

detection·segmentation·OVD·aerial·maritime 전용의 추가 신규 순위 이동은 충분한 직접 근거를 확보하지 못했다. 의미 있는 코드 변화 세 건으로 제한하고 부족한 분야를 placeholder로 채우지 않았다.

## 오늘의 benchmark signal 3개

1. **입력 계약:** image token 수와 image-text 순서를 먼저 감사해야 모델의 multi-image 실패를 해석할 수 있다.
2. **집계 계약:** 중앙값은 sample 순열에 불변이어야 한다. evaluator 변경량과 모델 변경량을 분리한다.
3. **충실도와 분모:** 더 올바르게 보이는 답이 원래 증거에는 불충실할 수 있으며 judge 성공 교집합도 함께 보고해야 한다.

## 내 연구에 바로 연결되는 포인트

- **오늘 먼저:** 현재 평가가 median을 호출하는지 확인한다. 사용한다면 저장 값의 순서 교란 감사부터 수행하고, 사용하지 않으면 multi-image message 감사로 넘어간다.
- **Answer–Region Gap·해양 안전 VQA:** 답이 그럴듯해지는 것과 증거를 충실히 읽는 것을 분리한다. PINK의 수학 rubric을 선박·안개 장면에 그대로 적용하는 것은 검증되지 않았다.
- **CCTV·다중 시점:** 전후 프레임을 비교하는 문장과 이미지 배치를 고정해 temporal reasoning 실험 전에 입력 결함을 배제한다. 정지 이미지 marker 수정 자체는 video memory 개선 증거가 아니다.
- **small/tiny object·P2:** 이번 변경에서 작은 물체 AP 개선 수치는 없다. 모델 개입 전에 message·resize·평가 집계를 고정하는 절차로만 연결한다.
- **RTX 5060 Ti 8GB:** 저장 출력의 집계 감사와 message fixture·mock cache 검사는 대형 모델 적재 없이 설계할 수 있다. PINK judge를 8GB에서 실행할 수 있다는 근거는 없다.

모든 최소 실험은 후속 제안이다. 본 실행은 원문·공식 코드 감사이며 새로운 모델 성능 측정이나 독립 재현을 수행하지 않았다.
