## 1. FramePack-U — 고정 visual-token 예산의 장시간 비디오 평가 코드

**공식 근거:** [GitHub](https://github.com/ZelD0n/framepack-U) · [논문](https://arxiv.org/abs/2610.16118) · [지원 데이터](https://huggingface.co/datasets/ZelD0n/FramePack-U)

1. **새로 나온 내용**  
   공식 README는 2026-10-12에 논문·코드·supporting materials를 공개했다고 기록한다. repository도 같은 날 생성됐고 10월 14일까지 push됐다. 질문 관련성 ReDi와 frame diversity로 프레임을 순위화하고, 서로 다른 해상도로 고정 길이 context에 packing하는 inference-time 방법이다.

2. **논문·프로젝트 연결**  
   NeurIPS 2026 논문은 비디오 길이가 늘어도 visual context 크기를 고정하는 것을 목표로 한다. 저자는 Qwen3.5-35B-A3B의 128-frame budget에서 LongVideoBench, MLVU, Video-MME가 official model보다 각각 12.9, 10.6, 9.7점 높았다고 보고한다. 서로 다른 benchmark 수치를 하나의 우열 척도로 합치지는 않았다.

3. **코드 품질과 재현성**  
   Python·CUDA·Torch·Transformers·vLLM·FlashAttention 버전을 직접 고정했고, local model/dataset path setup과 missing-link 사전 검사를 제공한다. 사전 계산 CLIP score와 frame feature를 공개해 가장 비싼 전처리를 건너뛸 수 있다. 반면 root tree에 CI와 test suite는 보이지 않고, requirements는 transitive lock이 아니라 direct dependency pin이다.

4. **라이선스**  
   코드는 Apache-2.0이다. LongVideoBench, Video-MME, MLVU, Qwen model weight에는 각 원본 라이선스가 따로 적용된다.

5. **pretrained weights/checkpoints**  
   방법 자체는 별도 학습 checkpoint가 없다. Qwen3.5-4B/9B/35B-A3B, Qwen3.6-27B를 외부에서 받고, CLIP feature를 직접 생성하거나 공식 precomputed artifact를 사용한다.

6. **설치 난이도와 의존성**  
   Python 3.10, Linux x86-64, CUDA 12.8, Torch 2.10, vLLM 0.19.1, 별도 FlashAttention wheel을 요구한다. 환경은 명확하지만 버전 결합이 강하고 benchmark video 준비가 무겁다.

7. **GPU/VRAM 요구량**  
   공식 문서는 단일 최소 VRAM을 보장하지 않는다. 4B부터 35B-A3B까지 model size와 packing scheme에 따라 요구량이 달라진다. large scheme 예시는 8개 visible GPU와 data parallel 4를 사용하므로 개인 8GB GPU에서 전체 논문 설정을 재현 가능하다고 단정할 수 없다.

8. **바로 실험에 붙이기 좋은가**  
   전체 VLM 평가보다 frame selection 단계가 바로 유용하다. 해양 장시간 영상에서 uniform, ReDi, event-aware selector가 같은 32/64/128-frame budget에서 작은 선박·부표의 결정적 프레임을 얼마나 보존하는지 먼저 측정할 수 있다.

9. **framework 호환성**  
   VLMEvalKit과 Qwen3.5/3.6 경로를 제공하고 Hugging Face model·dataset storage를 사용한다. MMDetection, Ultralytics, timm의 일반 drop-in adapter는 아니다.

10. **maintenance 가능성과 활동성**  
    공개 후 이틀간 5개 commit이 있었고 issue는 아직 0개다. 초기 문서 품질은 좋지만 사용자 기반과 장기 유지성은 아직 판단하기 이르다.

**진단 → 가설 → 최소 실험**

- **진단:** constant visual context는 GPU token memory를 고정하지만 video decode와 전체 frame scoring 비용까지 고정하지는 않는다.
- **가설:** query-aware ReDi는 uniform sampling보다 같은 token budget에서 evidence recall을 높이지만, candidate frame 수가 커지면 CPU wall-clock이 지배한다.
- **최소 실험:** 항만 CCTV 20개 long clip에 32/64-frame budget을 두고 uniform, ReDi, oracle event sampler를 비교한다. evidence timestamp recall, tiny-object recall, decode+score wall-clock, peak VRAM을 분리해 기록한다.
- **GO:** ReDi가 uniform 대비 evidence recall을 10%p 이상 높이고 end-to-end latency 증가는 25% 이하다.
- **KILL:** frame scoring 시간이 VLM 절감 시간을 상쇄하거나 짧은 이벤트 recall이 uniform보다 낮다.

**평가:** 실험 가치 **5/5** · 재현성 **4/5** · 신규성 **5/5** · 실용성 **4/5**

## 2. Open-o3-Video-v2 — 능동 증거 탐색·grounding을 묶은 공개 학습 스택

**공식 근거:** [GitHub](https://github.com/Multimedia-Semantic-Analytics-Lab/Open-o3-Video-v2) · [논문](https://arxiv.org/abs/2610.17656) · [4B 모델](https://modelscope.cn/models/FDUBay/Open-o3-Video-v2-4B) · [데이터](https://modelscope.cn/datasets/FDUBay/Open-o3-Video-v2-data)

1. **새로 나온 내용**  
   2026-10-12 생성된 공식 repo가 SFT, GRPO 기반 RL, crop_video agent loop, 9개 benchmark evaluator, 4B/8B 및 SFT checkpoint를 공개했다. sparse observation에 증거가 없으면 temporal crop을 요청하고, 반환된 frame에서 timestamp와 object box를 다시 grounding한다.

2. **논문·프로젝트 연결**  
   STGR-v2-CoT-135K에는 52K multi-turn trajectory가 포함되고 STGR-v2-RL-13K는 policy optimization용이다. 저자는 4B가 V-STaR에서 40.4 mAM, 56.3 mLGM을 얻어 Qwen3-VL-4B backbone보다 8.5, 12.6점 높았다고 보고한다. tool 호출·decode frame·reasoning token 예산이 다른 일반 VLM 비교는 **not strictly apples-to-apples**다.

3. **코드 품질과 재현성**  
   SFT, RL, Eval 환경을 분리하고 data preparation의 check-only, dry run, path override를 제공한다. evaluator에는 parser와 dataset pytest가 있으며 9개 benchmark input 계약을 문서화했다. 재현에 필요한 외부 benchmark media와 judge model은 별도 확보해야 한다.

4. **라이선스**  
   project code는 Apache-2.0이다. bundled verl은 자체 license와 notice를 유지하고 source video, benchmark, Qwen weight에는 각 원본 조건이 적용된다.

5. **pretrained weights/checkpoints**  
   4B·8B final model과 4B·8B SFT model을 ModelScope에 제공한다. Hugging Face가 아니라 ModelScope가 공식 배포 경로이며 base Qwen3-VL도 별도로 내려받는다.

6. **설치 난이도와 의존성**  
   Eval은 Python 3.12와 uv, SFT는 Linux·CUDA 12.6·nvcc·C++ compiler·FFmpeg, RL은 Python 3.11·CUDA·nvcc·compiler를 요구한다. 세 환경을 섞지 않도록 한 점은 좋지만 총 설치 범위는 크다.

7. **GPU/VRAM 요구량**  
   SFT 4B/8B 기본 recipe와 RL 기본값은 8 GPU다. two-node RL 예시는 노드당 8 GPU다. 단일 4B eval의 공식 최소 VRAM은 제시되지 않았으므로 RTX 5060 Ti 8GB 가능성을 추정하지 않는다.

8. **바로 실험에 붙이기 좋은가**  
   전체 학습보다 4B evaluator의 VAL_DATASET_SAMPLE=1 경로와 crop_video trace parser가 먼저 유용하다. 항만 영상에서 uniform observation이 놓친 짧은 안전 이벤트를 tool call이 실제로 회수하는지 감사할 수 있다.

9. **framework 호환성**  
   Qwen3-VL, MS-SWIFT, verl, Ray, ModelScope와 연결된다. MMDetection·Ultralytics·timm용 vision backbone adapter는 아니다.

10. **maintenance 가능성과 활동성**  
    repo는 10월 14일까지 push됐고 공개 시점에 issue 1개가 있다. 학습·평가·데이터가 함께 있어 완성도는 높지만 신규 조직·신규 repo라 장기 maintenance는 아직 관찰이 필요하다.

**진단 → 가설 → 최소 실험**

- **진단:** 정답 개선이 더 좋은 evidence acquisition에서 왔는지, 더 긴 generation과 추가 frame budget에서 왔는지 분리해야 한다.
- **가설:** 동일 decode-frame과 token budget을 맞추면 active crop은 특히 짧은 사건·작은 객체에서 uniform sampler보다 높은 evidence recall을 유지한다.
- **최소 실험:** 50개 maritime clip에서 uniform 96-frame, active crop, active crop without object grounding을 동일 총 decode frame으로 비교한다.
- **GO:** active crop의 evidence timestamp recall과 box IoU가 모두 개선되고 answer accuracy가 3%p 이상 높다.
- **KILL:** 이득이 추가 frame 또는 judge prompt 차이로만 설명되거나 tool trace의 25% 이상이 중복 관찰이다.

**평가:** 실험 가치 **5/5** · 재현성 **4.5/5** · 신규성 **5/5** · 실용성 **3/5**

## 3. EOS-Story — training-free visual storytelling의 실행 코드와 failure surface

**공식 근거:** [GitHub](https://github.com/SeungJuCha/EOS-Story) · [논문](https://arxiv.org/abs/2610.22320)

1. **새로 나온 내용**  
   2026-10-15 논문 공개 뒤 공식 repo가 10월 16일 실행 코드로 갱신됐다. identity와 scene prompt를 분리한 뒤 EOS embedding에 appearance residual을 넣고, scene scale에 맞춘 Identity Anchoring과 Identity-Aware Self-Attention을 적용한다.

2. **논문·프로젝트 연결**  
   SDXL-family에서 single/multi-subject storytelling과 pose ControlNet 경로를 제공한다. 저자는 cross-attention mask가 잘못된 영역을 잡거나 SDXL base가 concept를 만들지 못하면 방법도 실패한다고 직접 명시했다.

3. **코드 품질과 재현성**  
   주요 module이 pipeline, attention processor, utilities로 분리돼 있고 requirements가 거의 전부 pin됐다. benchmark YAML과 single/multi/pose smoke command가 있다. test.sh는 assertion 기반 unit test가 아니라 실제 generation을 호출하는 smoke runner이며, CI는 root에서 확인되지 않았다.

4. **라이선스**  
   root에 NOTICE와 THIRD_PARTY_LICENSES는 있지만 project 자체 LICENSE 파일은 확인되지 않았다. Diffusers, Consistory, benchmark upstream의 attribution만으로 EOS-Story 코드 전체의 재사용 권한이 자동 확정되지는 않는다. 재배포·상용 사용 전 maintainer 확인이 필요하다.

5. **pretrained weights/checkpoints**  
   별도 학습 checkpoint가 아니라 SDXL-family checkpoint와 ControlNet을 사용한다. Juggernaut-XL, Playground v2.5, RealVisXL variation을 보여주며 weight는 외부 provider 조건을 따른다.

6. **설치 난이도와 의존성**  
   Python 3.10, CUDA GPU, Torch 2.9, Diffusers 0.29, Transformers 4.55.2 등 구체적인 환경이다. 단일 requirements 설치는 단순하지만 오래된 Diffusers와 최신 Torch의 결합은 별도 environment가 안전하다.

7. **GPU/VRAM 요구량**  
   논문은 5-story 측정에서 EOS-Story가 약 47,777MB GPU memory를 사용했다고 보고한다. 조건이 다른 baseline과 효율 순위를 직접 비교하면 **not strictly apples-to-apples**다. 공식 최소 VRAM은 제공되지 않아 8GB 실행을 보장할 수 없다.

8. **바로 실험에 붙이기 좋은가**  
   pre-generated image와 attention map을 이용한 failure audit가 먼저 가능하다. full generation보다 automatic mask, explicit mask, confidence-gated abstention의 subject misplacement를 비교하는 것이 저비용이다.

9. **framework 호환성**  
   Hugging Face Diffusers와 SDXL pipeline에 직접 연결된다. MMDetection, Ultralytics, timm과는 직접 호환되지 않는다.

10. **maintenance 가능성과 활동성**  
    repo는 10월 3일 생성됐고 논문 공개 뒤 10월 16일까지 push됐다. 공개 issue는 0개다. code surface는 작고 읽기 쉽지만 license 부재와 짧은 history 때문에 maintenance 점수는 보수적으로 본다.

**진단 → 가설 → 최소 실험**

- **진단:** identity feature가 강할수록 좋은 것이 아니라, attention-derived mask가 틀릴 때 오류를 증폭한다.
- **가설:** attention entropy와 layer agreement로 injection confidence를 계산해 낮은 sample에서는 explicit mask 또는 abstention으로 전환하면 misplacement가 줄어든다.
- **최소 실험:** 공개 benchmark 30 prompt의 기존 결과 또는 소수 generation에서 automatic, explicit, gated hybrid를 비교한다.
- **GO:** misplacement 30% 이상 감소, CLIP-I 손실 0.01 이하.
- **KILL:** confidence AUROC가 mask failure 예측에서 0.65 미만이거나 explicit mask 품질에 결과가 전적으로 종속된다.

**평가:** 실험 가치 **4/5** · 재현성 **3/5** · 신규성 **4.5/5** · 실용성 **2.5/5**

## 4. AReA — 고해상도 DiT용 coarse-to-fine receptive-field attention

**공식 근거:** [GitHub](https://github.com/KooroshRH/AReA) · [논문](https://arxiv.org/abs/2610.17227) · [Hugging Face demo](https://huggingface.co/spaces/kooroshrh/AReA)

1. **새로 나온 내용**  
   10월 17일 official repo가 FLUX.1 adapter와 HRGen-1K prompt를 포함하도록 갱신됐다. 초기 denoising에서는 full-resolution query가 pooled KV를 보고, 후반에는 DWT로 나눈 adaptive local window, Halo, global-KV bridge를 사용한다.

2. **논문·프로젝트 연결**  
   training-free이며 추가 parameter나 RoPE extrapolation 없이 attention processor를 바꾼다. 저자는 6144²에서 FLUX.1 full attention 대비 3.2배, Qwen-Image에서 2.9배 가속을 보고한다. 공식 논문 실험은 NVIDIA H100에서 수행됐다.

3. **코드 품질과 재현성**  
   attention, tiling, bridge, backbone adapter가 분리돼 있고 command-line 옵션과 HRGen-1K JSONL이 있다. dependency는 lower bound만 있고 full lockfile·CI·unit test는 보이지 않아 환경 drift 위험이 있다.

4. **라이선스**  
   project code는 Apache-2.0이다. 기본 FLUX.1-Krea-dev checkpoint는 gated Hugging Face license를 별도로 수락해야 한다.

5. **pretrained weights/checkpoints**  
   training-free라 자체 checkpoint는 없다. 실행 시 FLUX.1 weight를 Hugging Face에서 받는다.

6. **설치 난이도와 의존성**  
   Torch 2.4+, Diffusers 0.35+, Transformers 4.45+, Accelerate 0.30+다. 설치 명령은 짧지만 gated model 인증과 수십 GB weight download가 필요할 수 있다.

7. **GPU/VRAM 요구량**  
   README는 60GB 미만 GPU에서 idle model을 CPU로 offload한다고 설명한다. 이는 최소 VRAM 보장이 아니다. 논문 H100 결과를 RTX 5060 Ti 8GB에 직접 적용할 수 없다.

8. **바로 실험에 붙이기 좋은가**  
   고메모리 장비가 있으면 FLUX.1의 2K/4K single-prompt가 간단하다. 개인 장비에서는 Hugging Face demo로 구조 failure를 먼저 확인하고, code-level attention schedule audit를 하는 편이 현실적이다.

9. **framework 호환성**  
   Diffusers pipeline에 attention processor와 hook을 붙이는 형태다. 현재 공식 지원은 FLUX.1이며 Qwen-Image, FLUX.2, Ideogram 4는 README상 coming soon이다. 논문이 여러 모델을 평가했더라도 현재 repo 실행 범위와 구분해야 한다.

10. **maintenance 가능성과 활동성**  
    repo는 10월 3일 생성, 10월 17일 push, 36 stars와 2 open issues를 보였다. 이번 후보 중 초기 관심은 높지만 adapter roadmap의 이행은 후속 관찰이 필요하다.

**진단 → 가설 → 최소 실험**

- **진단:** high-resolution speedup이 attention 절감에서 오더라도 CPU offload와 VAE tiling이 end-to-end latency를 지배할 수 있다.
- **가설:** 작은 구조물·문자 영역은 smooth-region split과 shrinking window에서 먼저 손실되며, DWT threshold를 조정하면 speed–detail Pareto를 개선할 수 있다.
- **최소 실험:** 2K prompt 20개에서 default, no adaptive split, bridge ratio 0/0.5를 비교해 OCR accuracy, object count, seam score, latency, peak VRAM을 측정한다.
- **GO:** baseline보다 latency 20% 이상 감소하면서 OCR/object count 손실 1%p 이하.
- **KILL:** CPU offload 포함 wall-clock 이득이 사라지거나 small-object duplication이 증가한다.

**평가:** 실험 가치 **4.5/5** · 재현성 **3.5/5** · 신규성 **5/5** · 실용성 **3/5**

## 5. MYOPIA — tree-based VLM reasoning의 frozen reproduction archive

**공식 근거:** [GitHub](https://github.com/islammesabah/VLM_Classification) · [논문](https://arxiv.org/abs/2610.21573) · [Hugging Face benchmark](https://huggingface.co/datasets/IslamMesabah/myopia-benchmark)

1. **새로 나온 내용**  
   오래된 development repo가 2026-10-16 논문용 frozen archive, 4개 SQLite result database, derived CSV, table regeneration script, Hugging Face benchmark를 갖추도록 갱신됐다. 논문은 tree traversal이 12개 dataset–model pair 모두에서 direct zero-shot보다 낮았다고 보고한다.

2. **논문·프로젝트 연결**  
   GTSRB, MNIST, CIFAR-10, MSCOCO에서 GPT-4o, Qwen-VL-Max, Llama-3.2-Vision을 비교한다. greedy tree의 early node error가 correct class를 영구 배제하는 문제를 node depth와 path log로 분석한다.

3. **코드 품질과 재현성**  
   paper number는 MYOPIA frozen directory에서 offline으로 재생성할 수 있고, 표별 command와 output path가 문서화됐다. GTSRB legacy row를 deduplicate하지 않으면 denominator가 901에서 최대 915로 부푸는 caveat도 명시한다. 일부 supplement table은 원본 row는 있지만 조립 script가 없어 수동 검사가 필요하다.

4. **라이선스**  
   code·tree·prompt·evaluation harness는 MIT다. GTSRB, MNIST, CIFAR-10, MSCOCO의 원 데이터 권리는 서로 다르며 특히 CIFAR-10은 formal license가 없다고 README가 경고한다.

5. **pretrained weights/checkpoints**  
   자체 checkpoint는 없다. 결과 database와 reference prediction을 제공한다. full collection은 상용 API 또는 self-hosted Llama endpoint를 사용하고, CLIP baseline만 open-weight local model을 선택할 수 있다.

6. **설치 난이도와 의존성**  
   offline table regeneration은 Python venv와 가벼운 scientific stack으로 가능하다. dataset download와 paid API key는 새 inference를 수집할 때만 필요하다. CLIP baseline은 Torch·Transformers를 추가로 설치한다.

7. **GPU/VRAM 요구량**  
   shipped database 분석은 CPU에서 가능하며 GPU VRAM이 필요 없다. API 기반 주요 VLM 재수집은 원격 compute를 쓰고, self-hosted Llama나 CLIP은 선택한 model에 따라 달라 공식 최소 VRAM 하나로 표현할 수 없다.

8. **바로 실험에 붙이기 좋은가**  
   매우 좋다. 먼저 paper table과 tree_error_analysis를 offline으로 재생성한 뒤, GTSRB subset에서 greedy-1, beam-2, confidence backtrack을 result DB 위의 simulation으로 비교할 수 있다.

9. **framework 호환성**  
   OpenAI/OpenRouter, DashScope, Ollama, Hugging Face dataset과 연결된다. MMDetection·Ultralytics·timm용 training framework는 아니며 CLIP baseline은 Transformers 경로다.

10. **maintenance 가능성과 활동성**  
    README는 best-effort research maintenance를 명시한다. 10월 16일 push가 있었지만 stars·open issues가 0이고 CI·test suite는 확인되지 않았다. frozen archive의 자기완결성은 높고 장기 기능 개발 가능성은 낮게 본다.

**진단 → 가설 → 최소 실험**

- **진단:** 해석 가능한 tree가 설명을 늘리지만 greedy early exclusion 때문에 정확도와 호출 비용을 동시에 악화시킬 수 있다.
- **가설:** confidence-triggered 1회 backtrack은 tree 구조를 유지하면서 zero-shot gap의 절반 이상을 회복한다.
- **최소 실험:** shipped GTSRB path log로 greedy-1, oracle backtrack upper bound, confidence proxy를 먼저 offline simulation한다.
- **GO:** zero-shot gap 50% 이상 회복, 평균 call 2배 이내.
- **KILL:** node confidence가 실제 wrong-branch를 구분하지 못하거나 비용 대비 direct zero-shot 우위가 없다.

**평가:** 실험 가치 **5/5** · 재현성 **5/5** · 신규성 **4/5** · 실용성 **5/5**

## 내 연구에 바로 연결되는 포인트

- **small/tiny object:** FramePack-U와 Open-o3-Video-v2는 frame budget이 작을 때 작은 선박·부표가 있는 순간을 보존하는지를 evidence recall로 평가해야 한다.
- **effective receptive field:** AReA의 denoising-stage receptive-field schedule은 CNN/ViT의 고정 receptive field와 비교할 수 있는 직접적인 동적 설계 사례다.
- **VLM Answer–Region Gap:** Open-o3-Video-v2의 timestamp·box trace와 MYOPIA의 path log를 결합하면 정답 실패가 증거 탐색, region grounding, reasoning 중 어디서 시작됐는지 분해할 수 있다.
- **domain shift와 forgetting:** MYOPIA의 greedy exclusion은 rare-class suppression과 유사하게 한 번의 접근 실패가 후속 판단을 닫는 구조다. zero-shot reference와 recovery path를 함께 유지해야 한다.
- **compute-aware evaluation:** constant context, adaptive attention, agentic crop 모두 GPU peak만 보고 끝내면 안 된다. decode, selector, tool call, CPU offload를 포함한 end-to-end wall-clock을 기록한다.
