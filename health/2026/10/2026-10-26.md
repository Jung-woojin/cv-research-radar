## 진단 → 가설 → 최소 실험

### 1. 대량 missing 오탐

- **진단 [사실]**: `radar_health.py`는 로컬 저장소의 최근 commit을 2026-10-22로 보고했고, 연결된 GitHub 앱은 2026-10-26 원격 파일 5개를 반환했다.
- **가설 [추론]**: health script가 원격 contents API보다 stale local clone을 기준으로 누락을 판정해 성공 ledger와 충돌한다.
- **최소 실험**: 임의 3개 날짜 경로에 대해 `(local exists, ledger success, remote exists)` 삼중 값을 비교한다. 성공 기준은 remote가 존재하면 missing 대신 `local_stale`로 분류하는 것이다.

### 2. GitHub 쓰기 승인 실패

- **진단 [사실]**: AI Tool Radar `create_file`은 자동 승인 검토가 workspace credit 부족으로 실행되지 않아 실제 GitHub mutation이 발생하지 않았다.
- **가설 [추론]**: 같은 승인 경로를 쓰는 health report와 후속 자동화도 credit이 복구되기 전까지 쓰기 실패할 가능성이 높다.
- **최소 실험**: credit 복구 후 먼저 `fetch_file`로 부재와 SHA를 재확인하고, 보존된 AI Tool Radar 초안을 정확히 한 번 `create_file`한다. 성공 기준은 원격 본문 일치, file SHA·commit SHA·main 확인, 중복 commit 0개다.

### 3. `github_audit.py` network timeout

- **진단 [사실]**: 두 저장소의 repository·commit·workflow·legacy issue/trigger 조회가 모두 timeout이었지만 GitHub 앱 read는 정상이다.
- **가설 [추론]**: 저장소 장애가 아니라 스크립트가 사용하는 CLI/network 경로의 제한 또는 인증 문제다.
- **최소 실험**: 동일 workflow 경로를 script transport와 GitHub app transport로 각각 3회 조회하고 성공률·지연을 기록한다. app 3/3 성공, script 0/3이면 transport-specific 장애로 확정한다.
