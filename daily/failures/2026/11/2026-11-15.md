## 1. Tile 경계 객체가 다른 class의 큰 box 때문에 누락됨

**확인 사실.** Ultralytics #27188은 병합됐으며 commit은 `5bb105508976ba6b4d1c2b91a0f8c54a46a1f671`이다. diff는 fragment 복구의 coverage 검사에도 NMS와 같은 class offset을 적용한다. 기본 `agnostic_nms=False`가 수정 대상이며 `agnostic_nms=True`는 유지한다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27188) · [코드 변경](https://github.com/ultralytics/ultralytics/pull/27188/files)

- **실패 조건·구성:** `tile=` 추론에서 tile seam에 걸린 fragment의 절반보다 큰 영역을, 유지된 다른 class box가 덮는 경우. 원문 예시는 person 내부 tie, bus와 겹친 person이다.
- **작성자 재현:** CPU, `conf=0.1`, `yolo26n-seg`·`zidane.jpg`·`tile=320`에서 tie 출력이 수정 전 6개, 후 7개라고 보고한다. 이는 정답 기반 recall 개선이나 새 true positive의 증명이 아니다.
- **공식 인정·community 여부:** 공식 저장소의 병합된 수정이다. 작성자 전후 비교가 있으며, 독립 community 재현과 이번 watch의 실행은 없다. 배포 package version은 확정하지 않았다.
- **진단 → 메커니즘:** NMS는 class-aware였지만 후속 fragment coverage는 raw box extent로 계산했다. 앞 단계의 class 계약을 뒷 단계가 지키지 않아 다른 class가 fragment를 제거했다.
- **가설·최소 개입:** encoder나 P2 feature를 바꾸기 전에 coverage 검사만 class-aware로 맞추면 경계 객체의 일부 누락을 회복할 수 있다.
- **후속 최소 실험:** parent와 병합 commit에 같은 합성 box·score·tile geometry를 넣는다. 큰 box의 class만 같음/다름으로 바꾸고 seam fragment 유지 여부를 비교한다. `agnostic_nms=True`와 seam 밖 객체를 대조군으로 둔다. 실제 이미지에서는 정답 label로 precision·recall을 함께 확인한다.
- **GO/KILL:** class가 다른 경우만 fragment가 복구되고 agnostic 대조군이 유지되면 구현 검증 GO. 검출 수만 늘고 false positive가 늘면 task 개선 주장은 KILL.
- **기존 주장과의 관계:** 작은 객체 backbone의 한계나 domain shift를 입증하지 않는다. tile 크기·overlap·confidence·NMS·max_det가 다른 성능 비교는 `not strictly apples-to-apples`다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **4/5** · 연구 아이디어 가치 **4/5**.

## 2. vLLM 다중 이미지 요청의 encoder-cache 대기와 반복 추월

**확인 사실.** #67292는 open이고 연결된 수정 #67385도 미병합이다. PR diff는 encoder 한도 때문에 요청을 미룬 step에서 뒤따르는 encoder 필요 요청을 보류하는 flag와 regression test를 추가한다. 검토한 PR head는 `8835e461c13f588935e9e5e3bd9aff0e94a575ee`다. [공식 저장소 issue](https://github.com/vllm-project/vllm/issues/67292) · [수정 제안](https://github.com/vllm-project/vllm/pull/67385) · [diff와 tests](https://github.com/vllm-project/vllm/pull/67385/files)

- **실패 조건·구성:** chunked prefill off, async scheduling, encoder cache가 빠듯하며 작은 이미지 요청이 지속 유입되는 경우다. 원 issue는 vLLM `73a1377b6`, encoder budget/cache 1,200 embeddings, 이미지당 280 embeddings를 쓰는 weights 없는 scheduler 재현을 제공한다. CUDA 장치는 platform 감지에 필요하다고 명시한다.
- **작성자 재현:** 4-image 요청이 async 조건에서 200 step 동안 미배정됐고 sync에서는 첫 step에 배정됐다고 보고한다. PR은 별도의 Gemma 4 E2B serving 실험과 수정 후 회복을 보고한다. 이는 작성자 결과이며 독립 검증값이 아니다.
- **공식 인정·community 여부:** community 제보와 같은 작성자의 수정 제안이다. 공식 저장소 등록과 PR 존재만으로 maintainer가 원인·수정을 승인했다고 보지 않는다.
- **진단 → 메커니즘:** async 계획 시점에는 이전 step의 encoder-cache 항목이 아직 해제되지 않았다. 전체 요청을 한 번에 prefill해야 하는 큰 요청은 건너뛰고, 들어갈 수 있는 작은 요청이 공간을 다시 차지한다.
- **가설·최소 개입:** 큰 요청을 미룬 step에서 뒤따르는 encoder 할당을 잠시 막으면 다음 배정 기회를 만들 수 있다. 다만 작은 요청의 지연 및 빈 step이 비용이다.
- **후속 최소 실험:** 공개 scheduler fixture로 sync/async × chunked on/off를 고정 비교한다. 큰 요청의 최초 배정 step, 뒤에서 추월한 요청 수, encoder 가용 슬롯, step별 배정량을 기록한다. text-only와 image prefix-cache hit 요청이 계속 진행되는지도 확인한다. 그 뒤 실제 VLM에서 입력·출력 token 수와 도착률을 고정해 요청 크기별 TTFT·완료율·처리량을 측정한다.
- **GO/KILL:** 큰 요청의 유한 대기와 작은 요청 비용을 함께 확인해야 GO. synthetic 회복만으로 실서비스 무한 대기를 확정하거나 throughput 개선으로 일반화하지 않는다. 원 issue도 실제 모델의 지속 부하 대기시간은 측정하지 않았다고 한정한다.
- **기존 주장과의 관계:** VLM reasoning 실패나 encoder 정확도 저하가 아니다. sync/async 또는 chunking 변경은 scheduling 조건 자체를 바꾸므로 성능 비교는 `not strictly apples-to-apples`다.
- **점수:** 심각도 **4/5** · 재현 신뢰도 **3/5** · 연구 아이디어 가치 **4/5**.

## 3. FP16/BF16 mask crop: 재현되는 utility 오류의 production 적용 범위

**확인 사실.** #27179는 **병합되지 않고 종료**됐다. diff는 저정밀 box를 받을 때 pixel grid를 FP32로 만들도록 제안한다. maintainer는 일반 segment predict·val·train이 FP32 box를 사용하므로 해당 production 경로에서는 재현되지 않는다고 설명했다. `fixed` label이나 merge 후보 SHA만으로 병합됐다고 판단하면 안 된다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27179) · [검토 댓글](https://github.com/ultralytics/ultralytics/pull/27179#issuecomment) · [제안 diff](https://github.com/ultralytics/ultralytics/pull/27179/files)

- **실패 조건·구성:** `ops.crop_mask`에 FP16/BF16 box를 직접 전달해 pixel grid도 같은 dtype으로 만드는 경우. 특정 dataset이나 checkpoint가 필요하지 않다.
- **작성자 재현:** FP16 box `[2050,0,2052,1]`과 폭 2054의 전경 mask에서 기존 출력은 x=2050만, 제안 수정은 2050·2051을 유지한다고 보고한다. endpoint 자체는 표현 가능해도 중간 pixel index가 반올림되는 사례다.
- **공식 인정·community 여부:** contributor의 utility 재현에 대해 maintainer가 production 도달 가능성을 검토했다. maintainer는 4320×3240 이미지의 `half=True`, `retina_masks=True` predict에서도 FP32 box가 전달되어 mask가 같다고 보고했다. 독립 community 검증과 이번 watch 실행은 없다.
- **진단 → 메커니즘:** box dtype을 pixel index 생성에 재사용하면 좌표 격자의 정수 구별 능력이 손실된다. FP32 grid는 이미 box 좌표에서 잃은 정밀도까지 복원하지는 못한다.
- **가설·최소 개입:** custom utility 사용자는 grid dtype만 바꿔 이 경로를 검사할 가치가 있다. 일반 predict 사용자는 먼저 실제 `crop_mask` 입력 dtype을 관측해야 한다.
- **후속 최소 실험:** FP16·BF16·FP32 box로 양 축의 crop을 비교하고 FP64 정수 격자를 oracle로 둔다. 이어 같은 실제 이미지의 predict 입력 dtype과 결과 hash를 기록한다. `process_mask`의 upsample 분기도 분리한다. maintainer 댓글에 따르면 기본 dtype에서 `upsample=False`의 ratios 곱셈은 box를 이미 승격시킨다.
- **GO/KILL:** custom half-box 경로에서만 차이가 나면 utility 계약 문제로 범위를 제한한다. production box가 FP32이고 결과가 같으면 일반 segmentation 성능 저하 주장은 KILL.
- **기존 주장과의 관계:** FP16 inference 자체가 대형 이미지 segmentation을 망친다는 근거가 아니다. 직접 helper 호출과 실제 predict 경로는 `not strictly apples-to-apples`다.
- **점수:** 심각도 **2/5** · 재현 신뢰도 **4/5**(utility 범위) · 연구 아이디어 가치 **3/5**.

## 오늘의 실패 패턴 3개

1. **후처리의 의미 계약 누락:** class-aware NMS 뒤의 coverage 검사도 같은 class 구분을 유지해야 한다.
2. **처리량과 대기 공정성의 분리:** 작은 요청의 지속 처리가 큰 요청의 진행을 보장하지 않는다.
3. **재현과 실제 경로 도달 가능성의 분리:** helper의 오류를 모델 전체 성능 문제로 확대하기 전에 dtype과 호출 경로를 확인해야 한다.

## 논문 아이디어로 연결 가능한 빈틈

**추론.** aerial/UAV·maritime의 작은 객체 누락을 연구할 때 feature 해상도보다 먼저 tile seam·다른 class의 포함 관계·후처리 조건별 오류를 나누는 진단이 유용하다. 동일 checkpoint의 candidate box를 고정하고 merge 단계만 바꾸면 표현력 부족과 복구 로직 실패를 분리할 수 있다.

VLM serving에서는 이미지 수별 완료율과 TTFT를 함께 보고해야 전체 처리량에 숨은 다중 이미지 요청의 불이익을 찾을 수 있다. 다만 오늘 근거는 특정 scheduler 조합이므로 다른 backend나 video frame budget까지 일반화하지 않는다.

신규성 위험은 알려진 버그의 재정리에 그치는 것이다. 여러 모델·데이터에서 동일 조건의 실패가 반복되고, 단일 개입이 precision·recall 또는 대기시간 분포에 미치는 영향을 확인해야 연구 주장으로 발전할 수 있다. 현재 이 효과는 측정하지 않았다.

## 직접 재현해볼 최소 실험

첫 실험은 CPU에서 synthetic tile box의 class만 바꾸는 paired test다. 원본 후보·score·geometry·NMS threshold를 고정하고 fragment 유지 여부를 비교한다. 작은 객체가 타 class의 큰 box 안에 놓인 정답 이미지로 후속 precision·recall을 검사한다.

두 번째는 weights 없는 vLLM scheduler fixture다. 작은 요청 유입 수와 큰 요청의 이미지 수를 고정하고, sync·chunked 대조군과 원본/PR head를 비교한다. CUDA platform 감지 요구가 있어 완전 CPU 실행으로 약속하지 않는다.

세 번째는 CPU에서 mask crop dtype fixture를 비교한다. RTX 5060 Ti 8GB에서 대형 VLM serving 전체가 가능하다는 주장은 하지 않는다. 이번 세 실험에는 신규 학습이 필요하지 않으며 실제 VRAM·latency는 미측정이다.

**공통 GO:** 원본에서 조건부 실패가 재현되고 단일 개입 후 회복되며 대조군이 유지된다. **공통 KILL/축소:** 재현되지 않으면 revision·dtype·호출 경로·scheduler 설정을 먼저 맞추고 모델 능력 실패라는 해석을 중단한다.
