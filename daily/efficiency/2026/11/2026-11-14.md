## 1. Edge0 — GPU 한 장과 전체 메모리 요구량을 분리한다

**확인한 사실:** 공식 공지는 11/12, 저장소 News는 11/13을 표시한다. 발표·저장소 공지 날짜이며 동일 시각이라고 단정하지 않는다. 최신 145B/120B 경로는 Linux/Windows, NVIDIA GPU, CUDA 13과 전용 edge0-strata 엔진을 요구한다. [공식 공지](https://edge0.ai/blog/introducing-edge0-145b-frontier-ai-capabilities-on-your-own-computer), [실행 문서](https://github.com/Edge0-AI/Edge0/blob/main/edge0-infer/README.md).

**저자 측정:** 145B Q3_K는 RTX 5090 D 24GB에서 chat decode 99.7 tok/s, NVFP4는 79.6 tok/s다. residency-on 메모리는 각각 VRAM 23.14 GiB + RAM 31.28 GiB, VRAM 23.25 GiB + RAM 38.27 GiB로 기재한다. 이는 해당 설정의 메모리 배치이며 peak 전체 시스템 메모리 보장은 아니다. [모델·측정 문서](https://github.com/Edge0-AI/Edge0/blob/main/docs/models/edge0-145b.md).

**비교 조건:** precision 외에도 weight format·커널 경로가 달라진다. batch·warm-up·정확한 engine commit·host CPU·전력은 해당 표에서 확인되지 않았다. 품질표도 Q3_K/NVFP4를 따로 평가한 표가 아니다. **not strictly apples-to-apples**이며, throughput 순위만으로 품질·에너지 우위를 판단할 수 없다. [조건과 한계](https://github.com/Edge0-AI/Edge0/blob/main/docs/models/edge0-145b.md).

**진단→가설:** active parameter 수보다 expert residency와 host↔GPU 전송이 decode를 제한할 수 있다.

**최소 실험 제안:** 같은 모델 format·prompt·engine commit에서 GPU resident expert budget만 바꾸고 TTFT, prefill/decode, p95 inter-token latency, host RSS, VRAM, PCIe traffic을 기록한다. 품질 비교는 동일 evaluation harness로 별도 수행한다.

**GO/KILL:** residency 변화와 전송량·지연 변화가 반복적으로 연결되면 GO. “24GB GPU에서 실행”을 “RAM 없이 24GB에 상주”로 해석하는 결론은 KILL.

## 2. SAM — RoPE 수학보다 compiler가 보는 연산 표현이 병목인가

**확인한 사실:** #27158은 compile 중 complex multiply를 동등한 real-valued rotation으로 바꾸고 eager의 complex 경로를 유지한다. 11/11 merge된 변경이다. [공식 PR](https://github.com/ultralytics/ultralytics/pull/27158).

**저자 측정:** RTX PRO 6000 Blackwell, torch 2.15.0+cu132, FP16, imgsz=1036, `fullgraph=True, dynamic=False`에서 COCO 20장×5회 encoder median은 SAM 3.1 29.48→26.73 ms, SAM 3 29.44→27.49 ms다. eager에서 real 형태는 CUDA +16%, MPS는 호출당 7.5배 느렸다고 설명한다. [측정·구현 이유](https://github.com/ultralytics/ultralytics/pull/27158).

**비교 조건:** batch·warm-up은 명시 확인되지 않았다. encoder-only이며 전·후처리·mask decoder·compile cold 비용을 포함한 서비스 지연이 아니다. 500장 품질 점검에서 eager mask는 동일했지만 compiled SAM 3에는 severe regression 1건과 recovery 1건이 있었다. 다른 장치·shape 전이는 **not strictly apples-to-apples**다. [검증 범위](https://github.com/ultralytics/ultralytics/pull/27158).

**진단→가설:** complex 연산의 fusion 차단이 launch·메모리 이동 비용을 늘린다는 저자 설명을 검증할 가치가 있다.

**최소 실험 제안:** eager/compiled × 기존/수정 RoPE의 2×2 ablation. 입력·weight·batch를 고정하고 cold compile과 warm latency를 분리하며 profiler kernel 수, p50/p95, mask IoU와 최악 image를 함께 기록한다.

**GO/KILL:** compiled 경로에서만 kernel 수·지연 감소와 품질 허용 범위가 함께 재현되면 GO. eager까지 일괄 치환하거나 encoder 개선율을 전체 서비스 개선율로 쓰면 KILL.

## 3. TQIR — 저장 bit, 계산 bit, 시스템 처리량은 서로 다른 축이다

**확인한 사실:** v1은 11/11 09:23:10 UTC 제출됐다. storage S와 decoded weight W·activation A 정밀도를 분리하고, INT8/INT4로 정확히 복원 가능한 codeword를 사용한다. [논문](https://arxiv.org/abs/2611.15231).

**저자 결과:** TSMC 16nm 합성 decoder는 0.0509 mm², 307.2 Gweights/s를 보고한다. Table V의 43.89 tok/s는 LLaMA-2-7B·76.8 GB/s 이상적 weight bandwidth에 기반한 상한이며 KV·activation·control traffic을 제외한다. Power는 합성 도구 추정이고 비교 공정 간 정규화하지 않았다. [본문 IV-A/B, Tables III–V](https://arxiv.org/html/2611.15231v1).

**조건:** 상용 보드 runtime version·batch·warm-up·실제 입력 shape 기반 wall-clock 결과로 사용할 수 없다. 다른 공정 decoder와의 면적 비교는 정규화 가정을 포함해 **not strictly apples-to-apples**다.

**진단→가설:** 압축률보다 decode·transform 비용과 memory/PE rate의 균형이 실효 이득을 결정할 수 있다.

**최소 실험 제안:** 고정 GEMM shape에서 format별 read bytes·decode cycles·transform cycles를 분리하고 메모리 대역폭을 sweep한다. 이후 같은 KV/context 조건의 end-to-end 측정과 대조한다.

**GO/KILL:** decode 비용을 포함해 bandwidth 절감 이득이 유지되면 GO. decoder 면적 효율을 전체 edge accelerator의 속도·전력 배수로 바꾸면 KILL.
