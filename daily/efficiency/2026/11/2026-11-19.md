## 1. ARM repack — 연산 최적화가 더 좋은 backend를 차단할 수 있다

**사실:** #32142는 dotprod 없는 ARMv8.0의 Q4_0/Q8_0 repack kernel을 추가하는 미병합 PR이다. 현재 head는 `28f615982227e956c15e3d0ce816cfec17b9bbb8`이며 commit 목록의 committer 시각은 11/18 20:58:01 UTC다. 이는 rebase 시각을 포함하며 표의 측정 시각으로 간주하지 않는다. [PR·측정](https://github.com/ggml-org/llama.cpp/pull/32142), [commits](https://github.com/ggml-org/llama.cpp/pull/32142/commits)

**저자 측정:** 11/16 Raspberry Pi 4 Model B, Cortex-A72 4코어 1.5 GHz, gcc 14.2·`-mcpu=cortex-a72`, `-fa 1 -ub 512`, master `2d8a32502` 대비 교대 2회 평균이다. Qwen3.5-0.8B all-Q4_0·4 threads에서 pp128은 16.57→34.02 tok/s지만 tg128은 5.29→5.36 tok/s다. 같은 1-thread tg128은 2.65→3.98 tok/s로 thread 수에 따라 이득도 다르다. [11/16 comments](https://github.com/ggml-org/llama.cpp/pull/32142#issuecomment-)

**새 커뮤니티 제보:** 11/18 Mac mini M4, Metal off·native off·`-mcpu=apple-a7`, build `2d677c3`, SmolLM2-360M-Instruct Q4_0·4 threads에서 repack off/on의 pp512는 1451.15→750.36 tok/s, tg128은 219.27→253.78 tok/s로 보고됐다. 원문 표의 model label은 “llama 3B”지만 params는 361.82M이며 본문 모델명과 label이 충돌한다. 따라서 해당 수치는 제보 조건에만 한정한다. [11/18 측정과 작성자 답변](https://github.com/ggml-org/llama.cpp/pull/32142)

**진단·기전:** 작성자는 repack buffer가 plain host buffer를 요구하는 BLAS 경로보다 우선 선택되기 때문이라고 설명한다. `apple-a7` 빌드도 Accelerate 내부의 M4 matrix unit 사용까지 제한하지 않는다고 명시했다. 따라서 M4 결과는 실제 Cortex-A53·구형 iPhone 실측이 아니다. 기본 macOS dotprod 빌드에 새 회귀가 생겼다고 일반화할 수도 없다.

**조건과 한계:** Pi와 M4는 모델·하드웨어·backend·빌드가 달라 **not strictly apples-to-apples**다. 두 측정의 warm-up, OS 세부 버전, 명시적 batch 크기, KV precision, 전력·peak memory는 미확인이다. pp128/512·tg128은 benchmark 토큰 길이이며 image shape가 아니다. 에뮬레이션의 correctness 확인을 성능 검증으로 쓰지 않는다.

**가설→최소 실험:** 동일 장치·weight hash·commit에서 repack on/off × BLAS on/off, threads 1/4를 교차한다. pp128/512와 tg128, cold load·warm p50/p95, kernel 선택 로그, 출력/PPL을 함께 기록한다. 각 arm의 build flags·batch·ubatch·warm-up을 고정한다.

**GO/KILL:** prefill과 decode가 갈리는 이유를 backend 선택으로 설명할 수 있으면 GO. Pi prefill 개선을 모바일 end-to-end 속도 배수로 확대하면 KILL. 오늘 가장 먼저 볼 사례다.

## 2. CPU NUMA — decode 이득과 prefill 손실을 같은 표에 둔다

**사실:** #32461 head는 `0119ceeb8988bfae87a43ea8506cb75f1946d343`이며 미병합 상태다. node별 CPU device·thread pool·memory binding과 all-reduce를 추가한다. 11/18 maintainer는 virtual CPU devices부터 작은 PR로 나눌 것을 요청했다. 현재 구현은 Linux·OpenMP에 한정되며 repack 미지원, taskset/cgroup 무시, node 메모리 부족 시 fallback 부재를 명시한다. GPU+CPU MoE expert offload 지원도 아니다. [PR·제약·리뷰](https://github.com/ggml-org/llama.cpp/pull/32461)

**커뮤니티 대조:** 11/18 EPYC 7742 단일 socket NPS4, 4 NUMA nodes×16 cores, node당 DDR4 2채널, CPU-only OpenMP에서 PR head와 merge-base `a946eb541`을 비교했다. `llama-bench -p 512 -n 128 -fa 1 -r 3`, master의 최선 4-node 설정은 interleave·64 threads·NUMA distribute다. [측정 comments](https://github.com/ggml-org/llama.cpp/pull/32461)

| 모델·precision | 최선 master pp512 / tg128 | 4-node TP pp512 / tg128 |
|---|---:|---:|
| Qwen3.5-27B Q4_K_M | 41.15 / 5.43 tok/s | 63.92 / 8.06 tok/s |
| Qwen3.6-35B-A3B Q4_K_M | 207.74 / 16.63 tok/s | 167.11 / 30.39 tok/s |

**품질·조건:** wikitext-2, context 512·20 chunks의 PPL/KLD 대조와 env 미설정 control이 있다. MoE의 TP 4-node PPL은 6.6346, master는 6.6422로 보고됐지만 이것만으로 일반 정확도 동등성을 확정하지 않는다. warm-up·OS/compiler 세부 버전·명시적 batch·peak RSS·전력은 미확인이다. 저자의 Graviton4 서버 결과를 이 EPYC 표와 합쳐 배수를 만들면 **not strictly apples-to-apples**다.

**진단→가설:** decode는 node-local weight 읽기 이득을 얻지만 prefill은 repack 부재와 작은 expert slice·all-reduce 비용 때문에 손해일 수 있다. MoE의 2→4-node prefill 정체는 단순 코어 부족 설명과 맞지 않는다. 이 기전은 평가자의 추론이며 causal profiler 결과는 없다.

**최소 실험:** 동일 모델·commit에서 master repack on/off와 TP 1/2/4 nodes를 비교한다. thread 총수·메모리 배치·prompt 길이·batch를 통제하고 remote-memory traffic, all-reduce 시간, PP/TG, PPL/KLD를 기록한다.

**GO/KILL:** 기존 NUMA 장비가 있고 decode 중심 workload이면 조건부 GO. prefill 중심 서비스·제약된 container에 기본 활성화하거나 새 서버 구매 근거로 삼는 것은 KILL. FLOPs 감소 기법이나 edge NPU 결과로 분류하지 않는다.

## 3. Scheduler host memory — 작은 예약량과 안전한 pointer 수명은 함께 검증한다

**사실:** #31274는 11/18 22:06:51 UTC revision을 포함하며 현재 head는 `671887cb8b3ad9f12b757a6a9073c5e4210aad92`다. active graph 크기로 context를 잡고 dependency context를 분리한다. 더 큰 graph가 오면 새 block을 할당하되 이전 block은 scheduler 해제 때까지 보존한다. 따라서 축소·성장 반복에서 메모리가 즉시 줄어드는 정책은 아니다. [PR](https://github.com/ggml-org/llama.cpp/pull/31274), [현재 diff](https://github.com/ggml-org/llama.cpp/pull/31274/files)

**저자 주장과 귀속 제한:** 본문의 RTX 5090 DFlash2-7 4,039 MiB·MTP-7 9,831 MiB host 절감표는 #32043과의 조합이라고 명시한다. 이를 #31274 단독 효과나 GPU VRAM 절감으로 옮기지 않는다. GB300·5090 간 차이도 GPU 자체의 우열을 입증하지 않는다.

**이전 측정과 새 반례:** 11/13 커뮤니티는 이전 head `a85ed2c`에서 Qwen3.8-27B-UD-Q2_K_XL+projector의 두 scheduler 예약량 716.7→123.1 MiB를 보고했다. 이는 오늘 revision의 재측정이 아니다. 11/18에는 C=8 설정의 sizing 테스트 실패와 graph 성장 후 pointer use-after-free를 ASan으로 찾았다는 추가 제보가 나왔다. 현재 diff에서 retired buffer 보존·CMake test define 전달을 확인했지만, 해당 최신 head에서 제보자가 재검증한 결과는 확인하지 못했다. [측정·장애 comments](https://github.com/ggml-org/llama.cpp/pull/31274)

**비교 조건:** 이전 측정은 Debian Docker/Windows 11, CPU·RTX 4090/3080 경로이며 예약량·Windows commit charge를 다룬다. RSS·peak VRAM·실제 보드 전력·latency 개선과 구분한다. 현재 표는 batch·warm-up·입력 shape·driver/runtime 전체 manifest가 부족하고 여러 revision·다른 PR을 포함해 **not strictly apples-to-apples**다.

**진단→가설:** 최대 graph 기반 과다 예약을 줄이면 host memory는 절감되지만 realloc으로 graph가 참조하는 주소가 바뀌면 정합성이 깨질 수 있다. 이전 buffer 보존은 이 위험을 줄이는 대신 graph 성장 이력에 따른 추가 예약량을 남길 수 있다.

**최소 실험:** 최신 head와 base에서 small→large→small graph, alloc→reserve→기존 graph 재실행을 교차한다. C=4/8을 실제 build·test 양쪽에 전달하고 ASan/UBSan, output parity, reserved bytes·RSS·Windows commit charge를 따로 측정한다. 모델 성능 비교 전에 allocator-only regression부터 수행한다.

**GO/KILL:** 작은 graph 회귀 테스트와 메모리 지표 분리가 우선 GO. 최신 head의 안전성과 단독 절감량을 확인하기 전 배포 채택은 KILL. 큰 숫자를 만들기 위해 host 예약량을 VRAM으로 바꾸지 않는다.
