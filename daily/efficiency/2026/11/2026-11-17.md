## 1. HIP MoE — L2 hit rate 개선과 wall-clock 개선은 다르다

**사실:** #32344는 `05db09a4d3c3c1caa7cda31f98eca6ae28d92eb5`로 병합됐다. HIP의 MoE에서 row tiles를 안쪽 순서로 배치하고 dense multiplication에는 column 우선 배치를 유지한다. diff의 설명은 expert별 column tile이 L2 재사용을 개선하지 못하고, 실행 시간이 다른 block들을 묶어 AMD GPU의 작업 배치를 악화시킬 수 있다는 것이다. [PR·diff](https://github.com/ggml-org/llama.cpp/pull/32344/files)

**저자 측정:** GFX906, master `de32b268c` 대비 gpt-oss-20b MXFP4의 pp512/ub512는 1247.01→1319.81 tok/s다. 동일 표의 dense Qwen3-14B Q8_K_XL은 453.00→451.99 tok/s다. 다른 baseline인 pre-#29948 표와 섞어 최대 개선율을 만들지 않는다. [측정표](https://github.com/ggml-org/llama.cpp/pull/32344)

**조건·한계:** prompt 512, microbatch 512는 명시됐지만 해당 PR 표의 전체 batch, warm-up, ROCm/driver version과 정확한 보드 SKU는 미확인이다. 원래 제보는 MI50/MI60·Linux·별도 Qwen 모델과 command를 사용한다. 그 제보의 decode 무변화나 수치를 위 PR 표에 합치면 **not strictly apples-to-apples**다. [원 제보 #31599](https://github.com/ggml-org/llama.cpp/issues/31599)

**진단→가설:** 원 제보는 L2 hit rate가 좋아져도 CU 작업 불균형으로 prefill이 느려질 수 있다고 보고한다. FLOPs·weight 크기를 유지한 채 grid order만 바꿔 이 가설을 분리할 수 있다.

**최소 실험 제안:** 한 GFX906 장치에서 동일 weight·build 옵션·ROCm을 고정하고 merge parent와 merge commit을 비교한다. MoE/dense control × pp512/pp4096 × ub512/ub2048을 실행하고 warm-up·반복 수를 명시한다. kernel 시간, CU별 작업 분포, prefill/decode, 출력 정합성을 기록한다.

**GO/KILL:** MoE prefill 개선과 작업 균형 회복이 함께 반복되면 GO. dense 저하가 측정 잡음 밖으로 재현되거나 다른 AMD 세대에 그대로 일반화해야만 성립하면 해당 배포 판단은 KILL. peak VRAM·전력 개선은 주장하지 않는다.

## 2. STM32용 export — INT8 지원과 보드 성능은 별도 관문이다

**사실:** #27211은 STM32N6 Neural-ART 등을 위한 ST Edge AI Core용 ONNX export 제안이며 아직 open이다. 기존 #27129를 보완한다. box/keypoint를 [0,1]로 정규화하고 QDQ 방식의 per-channel symmetric INT8 weights·asymmetric INT8 activations·MinMax calibration을 사용한다. [현재 PR](https://github.com/ultralytics/ultralytics/pull/27211), [원 제안](https://github.com/ultralytics/ultralytics/pull/27129)

**저자 host 검증:** YOLO26n, imgsz 640, ONNX Runtime CPU, 기본 COCO8 계열에서 segmentation mask mAP50-95는 float 0.541→INT8 0.365, pose mAP50-95는 0.449→0.265다. 작은 calibration/validation 자료의 결과이며 전체 COCO 성능으로 일반화하지 않는다. [표·한계](https://github.com/ultralytics/ultralytics/pull/27211)

**조건·한계:** PR 문서는 batch 1·static shape와 semantic 1/8, depth 1/4 해상도 출력을 명시한다. host CPU 모델·ORT exact version·warm-up은 미확인이다. ST Edge AI Core compile 및 STM32 보드 실행은 검증하지 않았다고 명시한다. 저해상도 출력의 64배/16배 크기 감소는 출력 tensor 요소 수의 관계이며 전체 RAM·latency·전력 감소 배수가 아니다. 원 제안과 보완 PR의 표도 버전·구현이 달라 **not strictly apples-to-apples**다. [제안 문서 diff](https://github.com/ultralytics/ultralytics/pull/27211/files)

**진단→가설:** 좌표·score 범위를 맞춰도 mask coefficient·keypoint를 공유 scale로 양자화하면 특정 task의 품질 손실이 남을 수 있다. graph 밖으로 옮긴 upsampling·NMS의 비용도 시스템 측정에 다시 포함해야 한다.

**최소 실험 제안:** 같은 weight·고정 split에서 float/whole-graph INT8/head-float control을 비교한다. calibration과 평가 이미지를 분리하고 small-object·mask·keypoint cell을 따로 본다. 품질 관문을 통과한 뒤 ST compile 가능 여부, 보드 peak SRAM/외부 메모리, 전후처리 포함 p50/p95, 전력계 기반 energy/frame을 측정한다.

**GO/KILL:** 지금은 export·정합성 검증 계획에만 GO. task별 사전 정의 품질 허용치를 넘으면 전체 INT8 배포를 KILL하고 최소 precision exclusion을 시험한다. host validation만으로 STM32 가속 성공을 선언하는 판단은 KILL.

## 3. CoreML — provider fallback이 먼저 해결해야 할 것은 정확성이다

**사실:** #34166은 padded Conv에서 dilation>1이고 `(kernel-1)*dilation >= 32`이면 CPU EP에 남기는 제안이다. 11/16 추가 commit `f43fbf0bde0786af8e4a3e0b1565932a483b3830`은 symbolic kernel 크기가 -1로 읽혀 guard를 통과하는 경우를 보완한다. PR은 아직 open이다. [PR](https://github.com/microsoft/onnxruntime/pull/34166), [commit 목록](https://github.com/microsoft/onnxruntime/pull/34166/commits)

**저자 재현:** M-series Mac, ORT 1.31.0 wheel, CoreML `CPUOnly`에서 kernel 7·dilation 12·pads 36인 1D Conv의 경계 출력 오류를 보고한다. piper 모델은 main 3/3 crash, 변경 후 5/5 실행됐다고 한다. 이는 latency 개선 실측이 아니다. [실험 본문](https://github.com/microsoft/onnxruntime/pull/34166)

**조건·한계:** 구체적 Mac SKU·macOS·precision·batch·warm-up은 명시 확인하지 못했다. 2D kernel 9×9·dilation 9·pads 36도 저자 보고에 포함되지만 전체 CV 모델 검증은 아니다. static/dynamic 및 NeuralNetwork/MLProgram 경로를 다루며, ANE/GPU나 다른 Mac과 비교하면 **not strictly apples-to-apples**다.

**진단→가설:** 연산 지원 판정이 잘못되면 graph offload 비율이 높아도 유효 추론 throughput은 의미가 없다. fallback의 partition·전송 비용은 correctness를 회복한 뒤 측정할 별도 손익이다.

**최소 실험 제안:** 고정 synthetic 입력에서 padded/unpadded × narrow/wide span × known/symbolic kernel을 비교하고 NumPy/CPU EP reference와 경계 오차를 확인한다. 다음으로 동일 모델에서 provider assignment, partition 수, transfer 포함 p95와 peak memory를 기록한다.

**GO/KILL:** crash 제거와 출력 tolerance를 먼저 통과하면 성능 측정에 GO. 지원 비율을 높이려고 unsafe 연산을 CoreML에 강제하거나 미측정 fallback 속도를 개선으로 표현하면 KILL.
