## 1. DominoBench — 모델 개선처럼 보일 수 있는 데이터·평가 계약 변경

### 공개 시점과 exact revision

**사실:** [공식 history](https://huggingface.co/datasets/emilioferrara/DominoBench/commits/main)의 최초 artifact upload는 11월 12일 19:31:12 UTC, commit `7d11c18c83545f45e92c129f19b4de2ddcf12e18`이다. 이번 조사 창의 사건은 아래 두 cleaned-benchmark commit이다.

- `2567666ba267fdc7896b614bada6fb816dd42c88` — 11월 15일 20:32:22 UTC.
- `0ec02825830840bf03861f61f07d9b7ead4a995f` — 11월 15일 20:32:29 UTC, part 2. KST로 11월 16일 05:32다.

현재 확인한 revision은 `ae78fecced8f8344b3017c1ad8c356920dd1a661`이며 11월 17일 07:39:37 UTC의 마지막 변경은 논문 링크·인용 추가다. 이를 신규 dataset 업로드로 세지 않았다. [논문 v1](https://arxiv.org/abs/2611.20385)은 11월 16일 제출됐다. 논문 제출일, 최초 artifact 공개일, 실질 revision 날짜를 분리한다.

### 무엇이 실제로 공개됐나

**사실:** [고정 card](https://huggingface.co/datasets/emilioferrara/DominoBench/blob/ae78fecced8f8344b3017c1ad8c356920dd1a661/README.md)는 data와 code 모두 MIT로 안내한다. Hub metadata는 public·ungated다. PNG·문항 JSON·simulation trajectory NPZ, generator, evaluation harness가 파일 목록에 있다. 새 model weight release는 아니다.

card는 현재 main set을 **854 items·427 pairs**, ranking subset을 **124 items·62 pairs**, 작은 set을 **38 items·19 pairs**로 안내한다. `1K`라는 이름을 실제 1,000문항 분모로 해석하면 안 된다. item 내부 `split`은 generator label이며 benchmark 구분에는 폴더를 사용하라고 명시한다.

**저자 설명:** 사람의 collision box가 그려진 인물 밖까지 뻗어 있어, 이미지상 접촉 없이 사망으로 라벨된 pair를 제거했다. 원래 500 pairs 중 73 pairs, 작은 set의 25 pairs 중 6 pairs를 제외했고, 큰 set 제외분 중 45 pairs가 ledge였다. [제외 manifest](https://huggingface.co/datasets/emilioferrara/DominoBench/blob/ae78fecced8f8344b3017c1ad8c356920dd1a661/data/excluded_pairs.json)에는 제외 ID와 사유가 있지만, 연결된 audit script·결과 파일은 확인한 현재 siblings 목록에서 찾지 못했다. 따라서 저자의 전수 visibility audit를 독립 검증했다고 말할 수 없다.

### 논문 주장과 artifact 사이의 확인할 간극

**사실:** [가중치 파일](https://huggingface.co/datasets/emilioferrara/DominoBench/blob/ae78fecced8f8344b3017c1ad8c356920dd1a661/data/dominobench1k/dominoscore_weights.json)은 `frozen_on: 2026-11-15`, `items: 854`와 이전 가중치의 `superseded` 항목을 보존한다. 예를 들어 ledge weight가 이전 0.1182에서 현재 0.0925로 달라진다. 이 숫자는 파일의 평가 가중치이며 성능 측정값이 아니다.

card는 chance-corrected·mechanism-weighted DominoScore를 설명하며 `eval/metrics.py`를 가리킨다. 그러나 [실제 해당 파일](https://huggingface.co/datasets/emilioferrara/DominoBench/blob/ae78fecced8f8344b3017c1ad8c356920dd1a661/eval/metrics.py)에서 확인한 `compute()`는 item accuracy, flipped-person accuracy, pair consistency, Brier, parse failure 등을 계산하고 가중치 JSON을 읽거나 DominoScore를 출력하지 않는다. 전체 repository의 다른 경로에 구현이 없다는 결론까지 내리지는 않는다. **card의 점수를 재현하는 정확한 entry point는 추가 확인 대상**이다.

또한 pair consistency는 양쪽 twin 결과가 모두 있는 pair만 분모에 넣는다. 결과 파일 누락 시 item accuracy와 pair consistency의 coverage가 달라질 수 있으므로 `n`과 `n_pairs`를 함께 확인해야 한다.

**추론:** checkpoint가 같아도 ① 제외 문항 구성, ② mechanism weight, ③ 누락 twin 처리만 달라져 순위나 점수가 움직일 수 있다. 정제 전후 평가를 모델의 reasoning 향상으로 해석하면 **not strictly apples-to-apples**다. H3는 이미지에 보이지 않는 양까지 제공하므로 H0 대비 개선 전체를 순수 계산 능력 차이로 단정하는 것도 피해야 한다.

### 설치·자원·무결성·활동

[requirements](https://huggingface.co/datasets/emilioferrara/DominoBench/blob/ae78fecced8f8344b3017c1ad8c356920dd1a661/requirements.txt)는 `numpy>=2.0`, `pymunk>=7.3`, `matplotlib>=3.9`, `Pillow>=10.0`이며 정확한 lock은 아니다. open-weight 실행용 vLLM은 optional이다. CLI/API backend는 별도 계정·인증·호출 비용이 생기므로, metadata와 evaluator fixture부터 분리한다.

CPU manifest·scoring audit에는 GPU가 필요하지 않다. full-model GPU/VRAM은 선택 checkpoint에 따라 달라지며 단일 최소값은 확인하지 못했다. frozen revision은 확보했지만 전체 artifact checksum manifest·attestation 검증은 하지 않았다.

공식 Hub discussions API는 이번 조회에서 count 0을 반환했다. 이는 독립 재현 성공이나 code 안정성을 뜻하지 않는다. 최근 활동은 cleanup·leaderboard 이미지·card 갱신으로 구분했다.

### 진단 → 가설 → 최소 개입 → 10~30분 smoke-test 계획

**관측:** 데이터 제외와 점수 가중치가 함께 바뀌었고, card가 지목한 기본 metrics 파일에서 composite score 계산을 확인하지 못했다.

**가설:** 결과 차이 일부는 representation보다 평가 대상·분모·가중치의 변화에서 발생한다.

**최소 개입 계획:**

1. 고정 revision의 index·subset·제외 manifest를 대조해 twin이 쌍으로 남는지, 제외 ID가 평가 대상에서 빠졌는지 확인한다. 모델은 호출하지 않는다.
2. 이미 보존된 동일 prediction을 retained subset에만 재채점한다. 새 추론 없이 데이터 선택 효과를 분리한다. 기존 prediction이 없으면 이 단계의 실측은 보류한다.
3. evaluator fixture에 완전한 twin 결과와 한쪽 결과가 빠진 경우를 넣어 `n`·`n_pairs`·pair consistency를 확인한다. fixture 결과를 모델 성능으로 보고하지 않는다.
4. DominoScore를 생성한 entry point·가중치 revision·분모를 확인한 뒤 같은 prediction에 이전/현재 weight를 각각 적용한다. 데이터 선택 효과와 가중치 효과를 별도 표로 남긴다.

**GO:** CPU manifest·분모 audit부터 진행할 가치가 있다. exact score entry point가 확보되면 같은 prediction의 재채점으로 확장한다.

**KILL/보류:** incomplete twin coverage나 불명확한 composite-score 경로가 남으면 leaderboard parity 주장을 중단한다. 정제 전후 순위 변화를 새 model gain으로 쓰거나 H3를 H0와 동일 정보량 비교로 해석하지 않는다.

## 오늘의 연구 판단

새 weight·dataset을 억지로 추가하지 않고 **실제 변경 1건**으로 발행한다. 위 실험은 모두 제안이며 실행 결과가 아니다.
