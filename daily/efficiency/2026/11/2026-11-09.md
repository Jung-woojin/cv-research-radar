# Daily Efficiency & Edge Radar — 2026-11-09

## 핵심 요약

1. Ultralytics 8.4.208은 TensorRT 11 FP16 NMS-free export의 최대 3% 속도 향상을 주장하지만, GPU·shape·batch·warm-up이 없는 릴리스 노트 수치라 직접 비교 근거는 아니다.
2. OpenVINO issue #39545는 Arc Pro B70/OVMS weekly build에서 130K context decode가 약 2.7–2.8 tok/s까지 내려간다고 보고했다. 작성자가 제공한 단일 환경 관찰이며, host-memory KV/state 배치가 핵심 가설이다.
3. 같은 보고는 32GB VRAM에 약 15GB가 남은 상태에서도 long-context prefill이 host private memory를 약 5.3GB 늘렸다고 적는다. free VRAM만으로 context capacity를 판단하면 안 되는 사례다.
4. OpenVINO #39613은 stateful INT4 IR의 dynamic KV state가 public reshape 후에도 남아 NPU compilation을 막는다고 재현 코드를 제시한다. edge NPU의 bottleneck은 FLOPs가 아니라 static-shape graph preparation일 수 있다.
5. ONNX Runtime은 Intel GPU용 WebGPU prefill flash-attention kernel을 추가했지만, quantized KV cache는 아직 이 경로에서 지원하지 않는다. 새 kernel은 속도 주장이 아니라 조건부 구현 변화다.
6. 오늘의 결론은 “INT4/FP16/flash-attention” 레이블보다 context length, KV placement, static shape, adapter, cache precision, batch, prefill/decode 분리를 먼저 기록해야 한다는 것이다.

## 핵심 사례

### 1. Ultralytics 8.4.208 — TensorRT 11 FP16 NMS-free export

- **사실:** 11/08 공식 릴리스는 TensorRT 11 FP16 NMS-free export 지원을 포함한다. [release](https://github.com/ultralytics/ultralytics/releases)
- **저자 주장:** 릴리스 노트는 최대 3% faster라고 설명한다.
- **비교 조건:** GPU, TensorRT minor version, model, input resolution, batch, dynamic/static shape, warm-up, transfer 포함 여부, percentile latency가 제시되지 않아 strict apples-to-apples가 아니다.
- **진단:** detection deployment에서는 NMS-free graph의 이득이 host postprocess 제거, GPU graph shape, proposal count에 따라 달라질 수 있다.
- **최소 실험:** 같은 ONNX/model weight로 legacy와 NMS-free TensorRT engine을 build하고 batch 1/4, 고정/동적 shape, FP16에서 p50/p95 end-to-end latency, throughput, peak VRAM, output agreement를 기록한다.
- **GO/KILL:** output agreement와 p95 latency 이득이 실제 target GPU에서 유지되면 GO; decode/transfer/postprocess를 분리하지 않은 평균만 좋아지면 deployment claim은 KILL이다.

### 2. OpenVINO #39545 — long-context KV/state가 host memory에 놓일 때의 decode 붕괴

- **사실(보고자 환경):** 공개 issue는 Windows 11, Intel Arc Pro B70 32GB, OVMS 2026.5.0 weekly, OpenVINO/Qwen3.8-27B-int4-ov(13.9GB int4 weights와 vision modules)를 명시한다. 같은 보고에서 short context MTP-on은 64.5 tok/s, 32K MTP-off는 14.5 tok/s, 64K는 9.1 tok/s, full 130K는 4.1 tok/s 또는 MTP-on 2.7–2.8 tok/s라고 적는다.
- **보고자 관찰:** 130K prefill이 host private memory를 약 5.3GB 증가시키고 VRAM은 약 15GB 남았다고 한다.
- **추론:** KV/linear-attention state의 host placement 또는 memory traffic이 long-context decode를 지배했을 가능성이 있다. 원인 확정이나 다른 GPU/NPU 일반화는 아직 할 수 없다.
- **최소 실험:** 같은 model/build에서 context 50, 32K, 64K, 96K, 130K sweep을 하고 MTP on/off, prefix cache on/off, KV placement/cache size를 교차한다. tok/s, p50/p95 inter-token latency, GPU VRAM, host private memory, PCIe traffic을 함께 기록한다.
- **GO/KILL:** host-memory growth와 throughput collapse의 상관이 반복되면 memory-placement optimization으로 GO; 재현되지 않으면 weekly build/driver/model-specific incident로 KILL한다.

### 3. OpenVINO #39613 — static-shape requirement가 edge NPU를 막는 경우

- **사실:** 11/08 공개 issue는 Qwen2.5-0.5B INT4 stateful IR에서 `Model::reshape()` 후에도 48개의 `ReadValue`/`Assign` KV-state variable이 dynamic shape로 남는 재현 코드와 관찰을 제공한다. issue는 이 상태가 NPU compilation을 막는다고 설명한다.
- **진단:** device가 NPU라도 model IR의 staticization이 실패하면 INT4·저전력 장점은 실행 전 단계에서 무효화된다.
- **최소 실험:** 같은 stateful IR와 prompt length 128/384/512에서 public reshape, GenAI path, stateless export를 비교해 compile success, compile time, peak memory, first-token latency를 기록한다.
- **GO/KILL:** static path가 compile되고 output checksum이 맞으면 NPU benchmark로 GO; dynamic KV state가 남으면 NPU throughput 비교 자체를 KILL하고 export/staticization requirement를 먼저 해결한다.

### 4. ONNX Runtime WebGPU Intel subgroup prefill flash-attention

- **사실:** 11/05 commit은 Intel GPU dense prefill용 `FlashAttentionPrefillProgram`을 추가했다. adapter와 shape에 따라 workgroup/KV step을 선택하며 Intel adapter와 non-quantized KV cache에서 이 경로를 선택한다.
- **명시된 한계:** quantized KV cache(INT8/TurboQuant), TurboQuant LUT, compressed K/V decoding은 이 kernel에서 지원하지 않는다.
- **진단:** prefill kernel 변경은 decode 개선을 의미하지 않으며 quantized cache path와 비교할 수 없다.
- **최소 실험:** Intel adapter에서 prompt length/heads/head size sweep을 해 기존 kernel과 new kernel의 prefill tok/s, compilation time, peak workgroup memory, output checksum을 비교한다. quantized KV cache는 별도 baseline으로 분리한다.
- **GO/KILL:** non-quantized 조건에서 checksum 동등성과 p95 prefill 개선이 함께 나타나면 GO; quantized cache를 섞은 비교는 not apples-to-apples로 KILL한다.

## 오늘의 진단 → 가설 → 최소 실험

- **관찰:** long context에서 VRAM 여유, weight quantization, 새 attention kernel이 있어도 실제 decode/compile 성능은 보장되지 않는다.
- **가설:** edge/consumer deployment 성능은 compute보다 KV/state placement와 shape specialization의 영향을 더 크게 받을 수 있다.
- **최소 실험:** 하나의 manifest에 device/driver/runtime, model/IR hash, context length, cache placement/precision, batch, warm-up, prefill/decode 구분을 저장하고 context sweep을 실행한다.
- **성공:** 동일 manifest에서 p95 latency와 memory curve가 반복된다.
- **실패:** memory curve 또는 compile path가 다르면 TFLOPs/parameter 수로 성능 원인을 해석하지 않는다.

## 오늘의 GO / KILL

- **GO:** target edge GPU/NPU에서 context-length sweep과 host/VRAM 동시 계측을 baseline으로 만든다.
- **GO:** NMS-free TensorRT와 WebGPU kernel은 output equivalence를 먼저 확인한 뒤 latency trial을 한다.
- **KILL:** hardware, runtime version, cache placement, context length가 다른 “tok/s” 또는 “최대 3%” 결과를 직접 순위화하지 않는다.
