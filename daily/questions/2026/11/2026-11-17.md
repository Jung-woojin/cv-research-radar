## Q1. 고해상도 sparse mask의 변환 계약 위반은 작은 객체의 위치·경계 오류로 나타나는가?

**문제·Observation·왜 지금:** #27232 작성자는 3840×2880 입력, YOLO26n-seg, CPU, `retina_masks=True`에서 결과를 FP16으로 변환한 뒤 dense mask에 접근하면 예외가 발생한다고 보고했다. 확인한 diff는 ROI 좌표를 요청 dtype으로 바꾸지 않고 device만 옮기며 dense 출력에 crop dtype을 사용한다. PR은 미병합이고 독립 재현은 이번에 수행하지 않았다. [PR 본문](https://github.com/ultralytics/ultralytics/pull/27232), [공식 diff](https://github.com/ultralytics/ultralytics/pull/27232/files).

**Gap → Diagnosis → Mechanism:** mask 값과 정수 좌표를 같은 방식으로 변환하면 좌표 반올림이 crop 크기와 붙여넣기 위치를 바꿀 수 있다. 이미 계산된 segmentation의 저장 표현 오류를 모델의 작은 객체 인식 실패로 오인할 여지가 있다. 작은 객체에서 상대적인 경계 영향이 더 클 것이라는 부분은 추론이며 원문이 입증한 AP 결과가 아니다.

**Hypothesis·최소 개입:** ROI를 정수로 유지하고 pixel만 변환하면 비어 있지 않은 sparse mask의 dense 변환 결과가 직접 dense tensor 변환과 일치한다. 객체 크기를 고정하고 위치만 이동하면 정밀도 경계와 연관된 오류가 드러날 수 있다.

**MVP·baseline·dataset·ablation:** CPU에서 홀수 좌표·비대칭 crop을 가진 합성 ROI를 만들고 위치·크기를 독립적으로 바꾼다. PR 작성자가 실패를 보고한 base `ef512bfc2`와 head `b48d79b4888afa2eb4e5f7aa4537a891da7b1886`을 사용하되 실행 전 base의 전체 SHA를 확인한다. FP16·FP32·uint8·bool 변환과 dense 직접 변환을 대조한다. 빈 mask, 낮은 좌표, CPU↔device 왕복은 별도 ablation이다. 이후 원문의 bus 이미지와 보유 고해상도 annotation 표본으로 확대한다. aerial·maritime 데이터 전이는 아직 검증하지 않았다.

**Metric·GO/KILL:** 좌표 일치율, dtype 보존, 예외율, pixel equality, mask IoU·경계 차이, peak memory를 기록한다. 정수 ROI 유지로 조건부 실패가 사라지고 dense 대조군이 유지되면 GO. pixel parity만 회복되면 구현 진단으로 한정한다. 실제 작은 객체의 task metric 변화가 없으면 “작은 객체 성능 저하” 가설은 축소한다.

**기여·위험·기간·negative result:** 기대 기여는 고해상도 저장 최적화의 의미 보존 검사와 실패 영역 지도다. 알려진 버그 재현만으로는 신규성이 낮다. 4~8주에는 다른 sparse 구현·좌표 범위·접근 순서에서 반복성과 task 영향을 확인해야 한다. 영향이 없다는 결과도 모델 오류와 후처리 오류의 경계를 정리한다. Compute cost **1/5**: 합성 MVP는 CPU 가능하며 dense materialization 메모리는 별도 기록한다.

## Q2. grounding의 시간적 불안정성 중 얼마가 요청 예약 순서에 의한 상태 혼선인가?

**문제·Observation·왜 지금:** #27233 작성자는 공유 FastSAM 모델에 서로 다른 box prompt의 두 stream을 예약하면 앞 요청이 뒤 prompt의 mask를 반환한다고 보고한다. 확인한 diff는 prompt를 요청 config에 보관하고 inference lock 내부에서 적용한다. PR은 미병합이며 작성자 테스트 보고를 독립 재현으로 간주하지 않는다. [PR 본문](https://github.com/ultralytics/ultralytics/pull/27233), [공식 diff](https://github.com/ultralytics/ultralytics/pull/27233/files).

**Gap → Diagnosis → Mechanism:** 영상·prompt·weight가 같아도 다른 요청의 생성 시점이 공유 predictor 상태를 바꾸면 frame 간 대상 전환이 생길 수 있다. 이를 temporal reasoning 또는 prompt grounding 능력으로만 평가하면 실행 상태라는 교란을 놓친다. FastSAM의 이 현상이 다른 VLM에도 있다는 뜻은 아니다.

**Hypothesis·최소 개입:** 요청별 prompt 격리가 되면 지원되는 예약·소비 순서에서 각 stream이 자기 prompt의 고립 실행 결과를 유지한다.

**MVP·baseline·dataset·ablation:** `FastSAM-s.pt`, 원문의 bus 이미지 두 frame, 동일 `imgsz=320`과 CPU를 사용한다. base `b1cae4a0f30006835d5569d187109d2c15ac4aac`와 head `c21efcbe4866a7910fcddb11dd57c7309caa42ba`에서 A/B 고립 실행을 기준으로 삼는다. A/B 예약 후 순차 소비, 역순 소비, A 첫 frame 뒤 B 예약을 비교한다. A=B prompt와 후속 무prompt 호출도 대조한다. 지원하지 않는 generator 재진입은 상태 혼선과 구분해 기록한다.

**Metric·GO/KILL:** 자기 고립 mask와의 pixel parity·IoU, 다른 prompt의 고립 mask로 바뀌는 비율, frame별 불일치, 오류·완료율을 측정한다. 입력 고정 상태에서 예약 순서 효과가 나타나고 격리 후 사라지면 GO. 고립 실행 자체의 비결정성만으로 설명되면 순서 혼선 가설을 축소한다.

**기여·위험·기간·negative result:** 기대 기여는 grounding 평가에 요청 독립성 검사를 추가하는 것이다. 4~8주에는 다른 prompt 유형·복수 구현에서 검증해야 하며 알려진 PR 하나만으로 논문은 부족하다. Negative result도 안전한 공유 조건과 호출 규약을 제공한다. Compute cost **2/5**: CPU 소규모 추론으로 시작하고 VRAM·지연은 미측정이다.

## Q3. INT8 분류 손실을 logit 동점으로 설명할 수 있는 범위와 남는 오차는 무엇인가?

**문제·Observation·왜 지금:** #27225는 `Classify` 출력의 float 유지와 linear의 dynamic INT8 weight quantization을 추가했고 main에 병합됐다. 작성자·review reproduction은 기존 INT8의 최대 logit 동점과 수정 후 동점 소멸을 보고하지만 FP32와 정확도가 완전히 같아지지는 않는다. 이번 보고서는 그 수치를 재측정하지 않았다. [PR·재현 보고](https://github.com/ultralytics/ultralytics/pull/27225), [공식 diff](https://github.com/ultralytics/ultralytics/pull/27225/files).

**Gap → Diagnosis → Mechanism:** calibration 분포와 마지막 출력 포화가 동시에 달라지면 전체 top-1 손실을 “양자화 일반 문제”로 뭉뚱그리기 쉽다. 동점을 없앤 뒤에도 남는 오차를 분리해야 backbone 오차·calibration 민감도와 head clipping의 기여를 구분할 수 있다.

**Hypothesis·최소 개입:** 기존 INT8에서 FP32 정답을 잃는 사례는 동점·포화 조건에 집중될 수 있다. float-output head가 이 부분을 줄이더라도 비동점 오류는 남을 것이다. 이는 검증할 가설이다.

**MVP·baseline·dataset·ablation:** 동일 YOLO26n-cls checkpoint, 고정 imagenette160 train calibration ID·순서와 val 평가 표본을 사용한다. 모든 출력은 동일한 1,000 class 공간으로 비교한다. FP32 LiteRT, base `b1cae4a0f30006835d5569d187109d2c15ac4aac`의 INT8, 병합 commit `95d2e2a72ff002e81228ea1074d59fb69baa175d`의 INT8을 paired 평가한다. 먼저 작은 고정 표본의 per-image logits를 저장한다. calibration 표본·순서 변경은 별도 요인으로 둔다. 수정은 head activation과 linear recipe를 함께 바꾸므로 한 요소의 효과라고 단정하지 않는다.

**Metric·GO/KILL:** top-1/top-5, 최대 logit 동점률, 포화 빈도, FP32 대비 margin·순위 변화, tie/non-tie별 회복률을 기록한다. 동점 표본의 회복이 집중되면 기전 GO. tie 감소와 정확도 회복이 연결되지 않으면 “동점이 주원인” 가설을 축소하고 잔여 양자화 오차를 분석한다.

**기여·위험·기간·negative result:** 기대 기여는 압축 모델의 의사결정 손상을 표본별로 설명하는 진단이다. 4~8주에 여러 head·calibration domain으로 확대할 수 있으나 단일 exporter 버그는 신규성이 낮다. 효과가 없어도 tie 지표의 한계와 추가 진단 필요성을 보여준다. Compute cost **2/5**: 소형 모델 CPU 평가가 MVP이며 export 의존성 설치 가능성은 미확인이다. CPU 결과를 NPU 정확도·속도 근거로 쓰지 않는다.

## Q4. VLM의 설명 형식 차이가 MCQ 채점에서 가짜 능력 차이를 만드는가?

**문제·Observation·왜 지금:** lmms-eval commit `b0d4d665953d28eaad6243b390c5b024451ddb12`는 WorldSense·AV Odyssey·TOMATO에서 단어 속 대문자를 후보로 읽던 조건을 괄호 선택지 또는 공백 뒤 문자·마침표 형식으로 바꾼다. commit 설명은 Answer의 A·Based의 B 오인을 지적한다. [공식 변경·설명](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/b0d4d665953d28eaad6243b390c5b024451ddb12).

**Gap → Diagnosis → Mechanism:** 모델마다 답 앞 설명·마지막 답의 형식이 다르므로 같은 의미의 정답도 parser 경로에 따라 다르게 읽힐 수 있다. 단순 old/new accuracy보다 형식별 오인과 의미 판단의 일치를 감사해야 한다.

**Hypothesis·최소 개입:** 의미가 같은 답의 괄호·문장형 변환에 대한 판정 불변성이 old/new parser에서 다르며, 일부 apparent model gap은 형식 구성비와 연관될 수 있다. 실제 모델 순위 역전은 아직 확인하지 않았다.

**MVP·baseline·dataset·ablation:** 보유한 위 과제의 저장 원응답·GT·선택지에 parent/new parser만 적용한다. 재추론 없이 paired 재채점한다. 별도로 사람이 의미를 확인한 답에 형식 변형을 적용하고 대문자가 있는 무관 설명·최종 답 위치를 바꿔 본다. 원응답과 합성 형식 변형 결과를 분리한다. 자료가 없으면 공식 fixture로 파서 계약만 검사하며 모델 능력 결론은 내리지 않는다.

**Metric·GO/KILL:** parse label 전환, parse 실패율, 의미 보존 변형 간 일치율, task별 accuracy 차이, 사람 blind 판정과의 일치를 기록한다. random fallback의 seed와 호출 순서를 고정하고 경로를 별도 기록한다. 모델 비교에 쓰려면 충분한 두 모델 원응답이 필요하다. 형식 변형만으로 오채점이 달라지면 GO. 실제 저장 응답에서 영향이 없으면 해당 표본에 한정해 가설을 축소한다.

**기여·위험·기간·negative result:** 기대 기여는 설명형 VLM 평가의 채점 불변성 감사다. 어제의 grounding JSON 복원과 달리 선택지 의미·표현의 분리가 중심이다. 4~8주에는 여러 task parser·출력 스타일에 걸친 체계적 편향이 필요하다. 단순 regex 수정 재현만으로 신규성은 낮다. Negative result는 영향 없는 응답 분포와 evaluator의 안정 범위를 남긴다. Compute cost **1/5**: 저장 응답 기반 CPU 분석이다.

## Q5. 이미지 인코딩 변경의 효과는 alpha 처리인가, 압축으로 작은 증거를 잃은 결과인가?

**문제·Observation·왜 지금:** VLMEvalKit commit `57c8a2e04bd9daacd3d5323f1ff1e93c9a0c9388`는 일부 API wrapper의 기본값을 `convert_rgb=False`로 바꾸며 PNG로 모드·투명도를 보존한다. CMYK는 JPEG이며 shared encoder 자체의 기본값은 여전히 RGB 변환이다. 실제 provider의 alpha 합성 동작과 성능 영향은 미확인이다. [공식 diff](https://github.com/open-compass/VLMEvalKit/commit/57c8a2e04bd9daacd3d5323f1ff1e93c9a0c9388).

**Gap → Diagnosis → Mechanism:** RGB/JPEG→alpha 보존 PNG 전환은 색 모드와 codec을 함께 바꾼다. 작은 문자·윤곽의 응답 차이를 alpha 효과 하나로 해석하면 압축·resize·파일 제한의 영향을 혼동한다. 해당 commit이 small-object AP를 개선했다는 증거는 없다.

**Hypothesis·최소 개입:** 작은 증거가 있는 일부 입력에서 codec 효과와 배경 합성 효과가 독립적이거나 상호작용할 수 있다. 먼저 wire payload가 실제로 달라지는지 확인해야 한다.

**MVP·baseline·dataset·ablation:** alpha 유무·작은 문자·경계 크기를 조절한 합성 이미지와 사용 허가된 보유 OCR/grounding 표본을 사용한다. 동일 원본에서 legacy RGB/JPEG, 명시적 배경 합성 RGB/PNG, alpha 보존 PNG를 만든다. opaque RGB PNG/JPEG 대조로 codec을 분리하고 alpha는 동일 codec 내에서 비교한다. 크기·resize·파일 budget을 고정하고, 제약 때문에 달라진 크기는 별도 strata로 남긴다. CPU payload 역디코드 후에만 같은 endpoint·model ID로 소수 paired 호출을 계획한다.

**Metric·GO/KILL:** mode·MIME·pixel hash·alpha·해상도·payload 크기를 먼저 기록한다. 모델 단계는 OCR exact match, grounding IoU, 실패율과 latency를 분리한다. codec 통제 후 배경 조건에 따른 응답 차이가 반복되면 alpha 관련 가설 GO. provider가 동일 픽셀로 정규화하거나 차이가 없으면 해당 조건에서 가설을 축소한다. provider 내부 입력을 관측하지 못하면 alpha 기전을 확정하지 않는다.

**기여·위험·기간·negative result:** 기대 기여는 작은 시각 증거의 입력 provenance와 조건별 민감도 분석이다. 4~8주에는 복수 provider·증거 크기·불투명 대조에서 일반성이 필요하다. 어제의 RGB/BGR chart 문제와 달리 추론 입력 자체가 대상이다. Negative result도 입력 표현 차이가 실제 성능으로 전파되지 않는 조건을 보여준다. Compute cost **1/5**는 CPU 감사에 한정하며 API 호출 비용·사용 가능성은 별도다.

## 비교 계약과 실행 우선순위

모든 실험에서 dataset revision·split·checkpoint·backbone·pretraining·외부 데이터·해상도·TTA·backend·evaluator commit·decode seed·reasoning/token/frame budget·compute budget을 기록한다. 알려지지 않은 조건은 미확인으로 둔다. Q1~Q3은 weight와 입력을 고정하고 실행 경로만 바꾸는 대조를 우선한다. Q4는 원응답을 고정하고, Q5는 전달 픽셀부터 통제한다.

서로 다른 calibration 표본, ImageNet 전체와 imagenette, parser revision이 다른 과거 점수, JPEG/PNG 기본값이 다른 결과, provider가 다른 응답은 **not strictly apples-to-apples**다. 다른 결과를 단순히 합쳐 모델 우위나 architecture 효과를 주장하지 않는다.

아래 /5 점수는 조사자의 우선순위 판단이며 실측치가 아니다. Compute efficiency는 높을수록 적은 자원으로 검증하기 좋다는 뜻으로, 위 compute cost와 방향이 반대다.
