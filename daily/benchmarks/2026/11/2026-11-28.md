## 1. ParseBench-2 — 공식 scorer 재사용과 실패 분모의 명시

### 실제 변화와 원본 대조

**확인 사실.** commit `1a6181731a23a9afb78c74adfe7a2eb8cdbb6400`은 문서 전사·구조화 layout을 평가하는 `parsebench2` task를 추가했다. task version은 1.3, scorer는 `parse-bench==2.0.1`, 데이터 revision은 `a12c9785cd8cd015b5284e0ad0d74722091762f2`다. PDF 전체 페이지를 `pypdfium2==4.30.0`의 scale 2, 144 DPI, RGB로 렌더링한다. 새 데이터나 새 leaderboard가 이날 처음 공개됐다는 주장은 아니다. [병합 diff](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/1a6181731a23a9afb78c74adfe7a2eb8cdbb6400), [고정 task 설정](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/1a6181731a23a9afb78c74adfe7a2eb8cdbb6400/lmms_eval/tasks/parsebench2/parsebench2.yaml).

추론용 dataset에는 `example_id`, subset, 원본 document 경로만 넣고 reference sidecar는 scoring 단계에서 읽는다. 고정 prompt는 Markdown과 정규화된 layout 좌표를 포함하는 JSON을 요구한다. native bbox를 공식 normalized-layout 구조로 변환한다. 따라서 scorer를 공유해도 provider별 공개 leaderboard의 prompt·렌더링·출력 계약까지 재현하는 것은 아니다. [adapter 전체 코드](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/1a6181731a23a9afb78c74adfe7a2eb8cdbb6400/lmms_eval/tasks/parsebench2/utils.py).

원본 `v2.0.1` 코드와 대조하면, adapter는 `ParseEvaluator.can_evaluate`, `_next_only_result`, `EvaluationRunner.aggregate_metrics`, `combine_next_score`를 호출한다. 공식 집계는 text·formatting·tables·charts·layout·forms의 여섯 dimension을 평균하며, 각 dimension 내부에는 별도의 subset 가중치가 있다. 문서 전체를 단순 평균한 점수와 같지 않다. 필요한 slot이 빠지면 dimension과 overall을 계산하지 않는다. [원본 eligibility](https://github.com/run-llama/ParseBench/blob/v2.0.1/src/parse_bench/evaluation/evaluators/parse.py), [원본 runner](https://github.com/run-llama/ParseBench/blob/v2.0.1/src/parse_bench/evaluation/runner.py), [공식 가중치·결측 규칙](https://github.com/run-llama/ParseBench/blob/v2.0.1/src/parse_bench/evaluation/next_score.py).

### 실패와 분모를 구분해야 하는 이유

| 상태 | 코드에서 확인한 처리 |
|---|---|
| layout 페이지에 예측 layout 없음 | layout에서 0점으로 평가하며 해당 dimension을 생략하지 않음 |
| reference를 공식 evaluator가 평가할 수 없음 | adapter가 evaluation을 `None`으로 두고 공식 집계에서 제외 |
| 적용 가능한 extended metric 없음 | 실패 결과 생성. 같은 product type에서 관측된 metric에 실패를 0으로 보충 |
| evaluator/worker 등 인프라 오류 | 공식 runner가 인프라 실패로 분류한 것은 점수의 zero-padding에서 제외 |
| JSON 파손·잘못된 layout | 가능한 Markdown은 보존해 채점하되 별도 response failure에도 포함 |

**경계:** 실패한 문서만 있고 성공 문서에서 해당 metric이 한 번도 생성되지 않으면, zero-padding할 metric 자체가 없어 slot이 결측으로 남을 수 있다. “모든 실패는 언제나 overall 0점”이라고 일반화하면 틀린다. 인프라 오류가 제외되므로 점수만 보고 정상 완료를 판정해서도 안 된다. [집계 회귀 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/1a6181731a23a9afb78c74adfe7a2eb8cdbb6400/test/tasks/test_parsebench2_eligibility.py).

응답 status의 `missing`, `invalid`, `invalid_layout`은 response failure rate에 포함된다. 복구된 Markdown이 점수를 받아도 형식 실패 기록은 남는다. 반면 일반 `markdown_only` 응답은 이 failure rate에 포함되지 않는다. 따라서 낮은 response failure rate가 완전한 layout JSON 준수를 보장하지 않는다. layout coverage 역시 명시적 layout 채널의 존재를 보는 진단값이므로 grounding 정확도와 별도로 읽어야 한다.

### 작성자 보고와 비교 한계

adapter README는 공개 `azure_di_layout` 저장 출력 4,317건에서 공식 CLI와 subset별 성공 4,315건·실패 1건·skip 1건 및 전체 report가 허용 오차 `1e-12`에서 일치했다고 보고한다. overall 0.6608도 **작성자 보고값**이며 이번 실행에서 재현한 수치가 아니다. 이는 adapter의 저장 출력 재채점 일치 근거이지, 새로운 모델이 더 우수하다는 증거가 아니다. [검증 조건과 제한](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/1a6181731a23a9afb78c74adfe7a2eb8cdbb6400/lmms_eval/tasks/parsebench2/README.md).

같은 README의 Qwen2.5-VL-3B `--limit 13` 실행은 subset당 한 문서의 smoke sample이다. 전체 benchmark 성적으로 취급하지 않는다. 입력 형식·출력 길이·layout 좌표 준수의 영향을 분리하지 않고 architecture 순위를 주장할 수 없다.

### 진단 → 가설 → 최소 실험

- **관측·진단:** 텍스트를 읽었더라도 JSON·좌표 계약을 지키지 못하면 layout 평가가 손상된다. 반대로 Markdown 복구가 전사 점수를 유지할 수 있어 형식 실패와 내용 실패가 일치하지 않는다.
- **기전·가설:** 작은 VLM의 낮은 점수 일부는 시각 인식보다 긴 구조화 출력과 좌표 표기의 부담에서 발생할 수 있다. 현재 README만으로 각 원인의 기여율은 확정할 수 없다.
- **최소 개입:** 기존 저장 응답을 고정하고 status, 복구 Markdown, layout 유무, eligibility, 인프라 오류를 문서 ID별로 기록한다. 임의로 어려운 문서를 분모에서 빼지 않는다.
- **첫 실험:** 공개 replay의 소규모 subset별 표본을 공식 CLI와 adapter로 재채점한다. dimension 값뿐 아니라 성공·실패·skip 수와 실제 score slot의 분모를 비교한다. CPU만으로 시작 가능하지만 전체 문서 렌더링은 오래 걸릴 수 있다.
- **GO:** 동일 저장 record의 값과 상태·분모가 일치하면 새 모델 실험으로 진행한다. **KILL/보류:** 오류가 제외된 상태에서 점수만 일치하거나 결측 dimension을 임의 평균했다면 비교를 중단한다.

Python 3.12 이상과 선택 dependency가 필요하다. `extractbench` extra는 다른 `parse-bench` 버전을 고정하므로 별도 환경이 필요하다. 이번 실행에서는 설치나 replay를 수행하지 않았다.

## 2. MuirBench — 이미지가 어느 선택지에 붙는지도 평가 조건이다

### 실제 변화와 원본 대조

**확인 사실.** commit `757f01500c77fd9043611bcea6ad8b012579426b`은 `doc_to_messages`를 등록했다. 생성된 질문·선택지 텍스트를 `<image>`로 나눠, RGB 이미지 목록을 marker 순서대로 사이에 삽입한다. image 수와 marker 수가 일치할 때 literal marker는 텍스트에서 제거된다. [공식 diff](https://github.com/EvolvingLMMs-Lab/lmms-eval/commit/757f01500c77fd9043611bcea6ad8b012579426b).

질문에 이미지 하나, B·C·D 선택지에 이미지가 하나씩 있으면 입력은 “질문 이미지 → A 텍스트 → B 이미지 → C 이미지 → D 이미지”의 대응을 유지한다. 모든 이미지를 텍스트 앞에 모으면 선택지 문자와 이미지의 인접 관계가 끊긴다는 것이 수정의 취지다.

원본 MuirBench는 질문·선택지에 이미지가 끼어드는 multi-image 평가이며 answerable/unanswerable 쌍을 포함한다. 따라서 입력 위치 수정은 benchmark의 실제 구성과 관련된다. 그러나 원본 prompt는 `(A)` 형식, `Question/Choices/Hint/Answer` 구조를 쓰고, lmms adapter는 `A.` 형식과 별도 지시문을 유지한다. 원본 후처리는 괄호·독립 문자·내용 매칭과 최후 random fallback을 포함하지만 adapter는 다른 filter와 lowercase exact 집계를 쓴다. **입력 위치 개선만으로 원본 평가 전체와 동일해졌다고 볼 수 없다.** [원본 프로젝트](https://muirbench.github.io/), [원본 prompt](https://github.com/muirbench/MuirBench/blob/main/eval/utils/preprocess.py), [원본 parser](https://github.com/muirbench/MuirBench/blob/main/eval/utils/postprocess.py).

### 적용 범위와 남은 경계

- 변경은 custom message callback을 사용하는 chat 경로에 해당한다. 기존 `doc_to_text`와 `doc_to_visual`은 유지돼 simple backend가 같은 수정 효과를 받는다고 단정할 수 없다.
- marker 수가 image 수와 다르면 예외를 내지 않고 images-first + 원래 text로 돌아간다. 이 경우 marker도 원래 text에 남는다.
- 대응은 개수와 순서에 의존한다. 개수 일치만으로 이미지 내용·ID와 선택지의 의미적 대응까지 검증하지 않는다.
- 이번 diff는 입력 callback·YAML 등록·테스트다. dataset split, answer, 집계 metric을 바꾼 수정이 아니다. 실제 정확도 개선량은 제공된 diff에서 확인하지 못했다.

[전체 adapter와 filter](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/757f01500c77fd9043611bcea6ad8b012579426b/lmms_eval/tasks/muirbench/utils.py), [chat callback 호출 경로](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/757f01500c77fd9043611bcea6ad8b012579426b/lmms_eval/api/task.py), [marker·순서·fallback 테스트](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/757f01500c77fd9043611bcea6ad8b012579426b/test/tasks/test_muirbench_messages.py).

### 진단 → 가설 → 최소 실험

**진단·기전:** 선택지 이미지가 분리되면 모델은 시각 관계와 함께 암묵적인 위치 대응도 복구해야 한다. 이 추가 부담은 실제 multi-image reasoning 실패와 섞일 수 있다.

**가설:** 입력 직렬화 수정의 효과는 이미지가 선택지에 들어가는 문항에서 특히 클 수 있다. 코드에서 도출한 가설이며 성능 향상을 확인한 결과가 아니다.

**최소 실험:**

1. 실제 사용하는 backend에서 저장된 question·options·image ID를 고정하고 old/new message를 덤프한다.
2. 질문 내 이미지·선택지 이미지·텍스트 선택지·marker mismatch로 층화한다. 이미지 hash·순서·선택지 경계·fallback 여부를 확인한다.
3. 직렬화 감사가 통과한 뒤에만 작은 paired 재추론을 한다. checkpoint, image processor, 해상도, 이미지 수·token budget, generation, parser를 고정한다.
4. overall accuracy 외에 선택지 이미지 문항 정확도, abstention 정확도, paired outcome 전환 수, mismatch 비율을 보고한다. 저장 답만 다시 채점해서는 입력 변경 효과를 측정할 수 없다.

**GO:** 실제 backend의 이미지–선택지 대응이 복구되고 층화된 paired 결과가 개선되면 확대한다. **KILL/보류:** backend가 입력을 다시 images-first로 바꾸거나 fallback이 섞이면 모델 능력 결론을 중단하고 전송 경로부터 고친다. 첫 두 단계는 GPU 없이 가능하다.

## 동조건 비교와 연구 우선순위

| 조건 | ParseBench-2 | MuirBench |
|---|---|---|
| dataset/split/revision | 고정 snapshot·test 입력. 임의 subset 결과를 전체로 쓰지 않음 | task는 test split. 이번 patch에 dataset revision 고정 추가 없음 |
| backbone/pretraining/external data | 새 matched 모델 비교 미확보 | 새 matched 모델 비교 미확보 |
| input resolution/TTA | PDF 144 DPI·전체 페이지. backend resize와 token 압축은 별도 고정 필요 | patch는 배치를 수정. 해상도·TTA 변경 근거 없음 |
| reasoning/tools/context/compute | 출력 16,384 token 설정. provider별 공개 조건과 동일하다는 근거 없음 | 16 token·temperature 0 설정 유지. 이미지 처리 budget은 backend 확인 필요 |
| evaluator | 공식 2.0.1·task 1.3 | parser·집계 유지, chat 입력 변경 |

같은 저장 출력의 scorer parity 검사는 비교 가능하다. 새 native JSON 생성 결과와 provider 공개 leaderboard, 수정 전후 입력으로 생성한 서로 다른 모델 순위는 **not strictly apples-to-apples**다. 입력·출력 계약을 드러낸 변화는 연구자가 따라갈 가치가 있지만, 그 자체를 SOTA 이동으로 포장하는 것은 leaderboard noise다.

## 오늘의 benchmark signal 3개

1. **공식 scorer 사용과 완전한 평가 동등성은 다르다.** prompt·renderer·response contract까지 고정해야 한다.
2. **분모는 실패 종류에 따라 달라진다.** missing prediction·invalid reference·인프라 오류를 함께 기록해야 한다.
3. **이미지와 선택지의 대응은 benchmark 조건이다.** 모델 성능을 논하기 전에 실제 message serialization을 검사해야 한다.

세 signal은 선정한 두 변경에서 도출한 해석이며 서로 다른 benchmark 세 건을 의미하지 않는다.

## 내 연구에 바로 연결되는 포인트

- Answer–Region Gap에서는 정답 문자열·영역 좌표·입력의 이미지 ID 대응을 분리해 기록한다. 잘못 붙은 이미지는 시각 reasoning 실패와 구별해야 한다.
- 해양·CCTV 다중 프레임 VQA는 시간 순서뿐 아니라 질문·선택지와 프레임의 대응을 감사한다. backend 간 score 차이를 모델 차이로 곧바로 해석하지 않는다.
- 문서 OCR을 evidence pipeline에 쓸 때 Markdown 내용 점수와 layout grounding을 따로 본다. 복구된 텍스트가 존재해도 근거 위치가 유효하다는 뜻은 아니다.
- **오늘 먼저 할 일:** 기존 MuirBench 또는 다중 이미지 VQA 입력의 marker 수·image hash·선택지 경계를 감사한다. RTX 5060 Ti 8GB에서도 첫 단계는 GPU 추론 없이 시작할 수 있다.
