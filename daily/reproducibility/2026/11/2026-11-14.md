[README](https://github.com/NTUMARS/ODE-POLICY/blob/359abc133184c21517cee5ca3eb205672f939c2b/README.md), [설정](https://github.com/NTUMARS/ODE-POLICY/blob/359abc133184c21517cee5ca3eb205672f939c2b/ode_policy/configs/policy_config/ode.yaml)

**재현 조건 / observed gap.** 공식 재현 문서는 논문 조건에 `field_use_s=true cond_use_s=false grip_ode=false solver=rk4`와 raw-command `libero_4suite_50demo_ode_vt.zarr`를 요구한다. 현재 기본 데이터는 gripper ramp가 적용된 별도 경로다. 또한 early epoch만 볼 때도 100-epoch cosine schedule을 유지하고 `stop_at_epoch`를 쓰도록 명시한다. 현재 기본 실행과 논문 실행의 설정 차이는 확인했지만, 이를 독립적인 재현 실패로 측정하지 않았다. [재현 문서](https://github.com/NTUMARS/ODE-POLICY/blob/359abc133184c21517cee5ca3eb205672f939c2b/docs/REPRODUCE.md)

**사실 / mechanism.** PR은 상위 forward가 multimodal 입력을 `self.model`로 전달하도록 바뀌었으나 remote code는 이를 text-only 모델로 교체한다고 진단한다. 따라서 없는 속성만 채우면 audio/video를 무시한 실행이 될 수 있다는 것은 PR 작성자의 분석이다. diff에서 별도 extra와 `transformers>=5.3.0,<5.21.0` 제한을 확인했다. 병합 commit은 `fa8a92ff53dedf7dcd4f21395a842083ec412b40`, 공식 2.27.14 공개는 11/13 10:49 UTC다. [diff](https://github.com/embeddings-benchmark/mteb/pull/5882/files), [릴리스](https://github.com/embeddings-benchmark/mteb/releases/tag/2.27.14)

**진단 → 가설 → 최소 실험.** 이 실패는 weight 손상보다 remote-code와 framework의 호출 계약 변화일 수 있다. 동일 model/remote-code revision과 입력에서 5.20.2·5.22.2를 비교하고 text/image/audio/video가 실제 어느 submodule로 전달되는지 기록한다. 같은 text에서 media를 교체했을 때 embedding이 변하는지도 검사한다. modality sensitivity만으로 올바른 모델임을 입증할 수는 없으므로 고정 reference 출력과 함께 확인한다.

**GO/KILL.** 모델 전용 extra·lockfile로 환경을 분리하고 modality 전달 및 reference parity가 확인되면 GO. `rope_deltas`만 추가해 예외를 없앤 결과나 완료 여부만으로 multimodal 재현을 주장하는 것은 KILL.

**커뮤니티 재현 조건.** issue #50709는 Transformers 5.22.1, Linux/Python 3.13.9, torch 2.15.0+cu132, H100 80GB, kernels 0.17.2, BF16의 tiny MistralLarge4 예제를 제공한다. 일반 `flash_attention_3`는 로드 시 거부하지만 `kernels-community/flash-attn3`는 로드 후 forward에서 TypeError가 난다는 보고다. 이미지 입력의 정확도 재현은 아니다. [이슈](https://github.com/huggingface/transformers/issues/50709)

**사실 / observed gap.** PR #50712의 diff는 Hub kernel 분기에 `_supports_flash_attn` 검사를 추가하고 회귀 테스트를 넣는다. 11/13 13:54 UTC에 main으로 병합됐으며 merge commit은 `e18fcb1b8e2b8f597269887ccf4c5fea1e8f493d`다. 패키지 release 포함 여부는 확인하지 않았다. 이 변경은 미지원 모델에 Flash Attention을 구현한 것이 아니라 로드 단계에서 거부하도록 만든 것이다. [PR](https://github.com/huggingface/transformers/pull/50712), [diff](https://github.com/huggingface/transformers/pull/50712/files)

**진단 → 가설 → 최소 실험.** backend의 다른 이름이 동일한 지원 검사에 도달하지 않으면 로드 성공을 호환성으로 오인할 수 있다. 같은 tiny checkpoint에서 수정 전후 × 일반 FA/Hub kernel을 비교한다. 미지원 모델은 둘 다 로드 시 실패해야 하고, 지원 모델은 기존 로드·고정 forward 동작을 유지해야 한다.

**GO/KILL.** 지원 여부 검사와 지원 모델의 reference parity를 통과하면 GO. 미지원 경로의 forward 결과를 품질·latency 비교에 넣거나 이 fix를 모델 지원 확대라고 해석하는 것은 KILL.

## 사례 4 — Hub cache: 강제 refresh 요청과 실제 artifact 출처가 다를 수 있다

**커뮤니티 재현 조건.** issue #5350은 Hub 2.5.0.dev0의 `2c61ae8c11eedb1b79e262dd9eb5e68962cac063`, Python 3.12.14, macOS arm64에서 HTTP 연결 실패를 모의하고 실제 임시 cache를 사용한다. 작성자는 `snapshot_download(force_download=True)`가 기존 snapshot을 반환하지만 단일 파일 API는 ValueError를 낸다고 보고했다. 실제 Hub outage나 production cache 손상 관측은 아니다. [이슈](https://github.com/huggingface/huggingface_hub/issues/5350)

**사실 / 수정 상태.** 고정 소스의 metadata 실패 fallback은 snapshot 반환 전에 `force_download`를 검사하지 않는다. open PR #5351은 그 앞에 오류 처리를 추가하고 cache/local-directory 회귀 테스트를 제시한다. 작성자는 관련 6개 test 통과와 새 4개 case의 수정 전 실패를 보고했지만 이번 실행에서 독립 검증하지 않았다. PR head는 `7e79a0540e091e8036b11e3e584a46dbd87aa36b`이며 미병합이다. [고정 소스](https://github.com/huggingface/huggingface_hub/blob/2c61ae8c11eedb1b79e262dd9eb5e68962cac063/src/huggingface_hub/_snapshot_download.py), [수정 PR](https://github.com/huggingface/huggingface_hub/pull/5351)

**진단 → 가설 → 최소 실험.** “force 호출 완료”를 fresh checkpoint 확보로 해석하면 artifact 출처 기록이 틀릴 수 있다. weights 없이 임시 config/tree/ref fixture를 만들고 정상 fallback, 강제 refresh+통신 실패, force+local-only를 cache/local-directory 각각에서 검사한다. 반환 경로뿐 아니라 resolved revision·파일 hash·요청 로그를 보존한다. 보류한 #5344의 dry-run 전후 `refs/main` 변경도 별도 fixture로 검사할 가치가 있다.

**GO/KILL.** 실제 revision과 hash를 검증한 artifact만 실험으로 GO. fresh download 여부를 반환 경로만으로 판단하거나 open PR을 배포된 해결책으로 사용하는 것은 KILL.

## 공통 비교 조건과 오늘의 판단

backbone·pretraining·data/split·resolution·hardware·precision·batch·TTA·evaluator를 일치시킨 공통 benchmark는 없다. 위 사례 간 성능 비교는 **not strictly apples-to-apples**다. API 계약 테스트에 dataset/split/TTA가 적용되지 않는 경우와 실제 성능 실험의 미확인 조건도 구분해야 한다.

- **오늘의 1순위 GO:** ODE 논문/default recipe의 resolved config와 데이터 표현을 대조한다. 학습 전에 가장 적은 비용으로 비교 조건의 혼선을 제거할 수 있다.
- **GO:** multimodal embedding에는 modality 전달 검사, kernel 교체에는 지원 검사, 다운로드에는 revision/hash 검사를 preflight로 둔다.
- **GO:** 계약 검사가 통과한 뒤 동일 조건에서 seed 반복과 downstream metric을 측정한다.
- **KILL:** 실행 완료·예외 제거·단일 seed·main 병합을 각각 재현 완료·정확성·안정성·릴리스로 치환하지 않는다.
- **후속 연구 질문:** 설정·호출·artifact 계약 검사가 end-to-end 재현 실패를 얼마나 먼저 걸러내는가? 동일 fixture에서 preflight 실패와 후속 실행 실패를 함께 수집해야 반증 가능하며, 현재는 연구 가설이다.
