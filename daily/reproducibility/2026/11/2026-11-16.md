## 사례 1 — Grounding DINO: seed를 고정하기 전에 head가 로드됐는지 검사

**Claim / 커뮤니티 재현 조건.** #50774 작성자는 Transformers 5.18.0, torch 2.13 CPU, Windows 11, Python 3.12에서 `IDEA-Research/grounding-dino-base` revision `12bdfa31`과 `iSEE-Laboratory/llmdet_base` revision `35378694`를 사용했다. Grounding DINO shared decoder box head가 random initialization으로 남고, LLMDet의 per-layer box head와 class bias는 layer 0 값으로 대체된다고 보고한다. 로드 경고는 없었다는 제보다. [원문·재현 코드](https://github.com/huggingface/transformers/issues/50774)

**Observed gap / 검증 수준.** 작성자는 자체 이미지에서 box가 최대 약 40 px 달라지고, 파일에서 head를 복사한 뒤 독립 C++/HIP 구현과 0.03 px 이내로 일치한다고 주장한다. 이미지·전체 평가 조건이 공개된 benchmark 비교는 아니므로 이 수치를 일반 성능 차이로 사용하지 않는다. 별도 댓글 작성자는 Transformers 5.18.0·torch 2.15.0+cpu에서 shared box head 6개 tensor 모두 파일과 다르며, 세 weight는 load seed에 따라 달라지고 encoder output head 6개 tensor는 파일과 정확히 일치했다고 보고한다. 이는 **weight 수준의 별도 확인이며 LLMDet 전체 추론의 독립 재현은 아니다.** [추가 weight 대조](https://github.com/huggingface/transformers/issues/50774#issuecomment-6894705034)

**사실 / 가능한 mechanism.** v5.18.0 소스에 decoder head와 outer head의 tied-weight mapping, `decoder_bbox_embed_share` 분기, decoder head 재연결 코드가 있다. 이 코드 구조와 제보는 tying/loading 계약 문제라는 가설에 부합하지만, 최초 유입 commit과 확정된 수정 PR은 확인하지 못했다. 이슈는 open이다. [고정 소스](https://github.com/huggingface/transformers/blob/v5.18.0/src/transformers/models/grounding_dino/modeling_grounding_dino.py)

**진단 → 가설 → 최소 실험.** 가설은 “동일 checkpoint의 seed별 출력 차이 일부가 미로딩 head에서 발생한다”이다. 학습 없이 immutable checkpoint revision을 고정하고 두 load seed에서 모든 bbox/class head tensor를 파일과 대조한다. shared/nonshared 모델을 분리하고, encoder head를 양성 대조로 둔다. 그다음 같은 이미지·prompt·processor·FP32 조건에서 head 복원 전후 box/logit을 비교한다. 원문 snippet은 revision 인자를 생략하므로 실제 실험에서는 명시적으로 고정해야 한다.

**GO/KILL.** 파일과 loaded tensor가 선언된 tying 규칙대로 일치하고, 고정 입력 출력이 사전 설정한 허용오차를 통과하면 GO. head 로드 불일치가 남은 상태에서 seed sweep 결과를 모델의 본질적 불안정성이나 새로운 architecture 효과로 해석하는 것은 KILL. 수동 복사는 진단용 우회이며 검증된 공식 수정으로 간주하지 않는다.

## 사례 2 — 멀티모달 pipeline: 요청 순서가 숨은 실험 조건

**Claim / 재현 조건.** #50784는 Transformers `5.24.0.dev0` commit `3a134bc37f7c22c801b618e289b0255425f22647`, torch 2.11.0+cu130, Linux·Tesla T4, `HuggingFaceTB/SmolVLM-256M-Instruct`에서 dictionary 재사용 후 두 번째 요청이 중복 `max_new_tokens` 오류로 실패한다고 보고한다. stop sequence와 image→text mode 누출은 sanitizer 수준 fixture로 확인했다고 구분한다. 실제 모델의 precision·입력 이미지·immutable model revision은 미확인이다. [원문](https://github.com/huggingface/transformers/issues/50784)

**사실 / observed gap.** 고정 소스의 ImageTextToText는 caller dictionary를 `forward_kwargs`에 직접 연결한 뒤 token limit·stop 설정을 쓴다. AnyToAny도 비어 있지 않은 dictionary를 재사용하며, text 요청에서는 기존 image mode 항목을 덮어쓰지 않는 경로가 있다. 요청별 인자만 같아도 이전 호출이 남긴 상태 때문에 실패하거나 실행·후처리 modality가 어긋날 수 있다는 것이 제보의 핵심이다. 이슈는 open이고, 댓글은 수정 의향만 제시한다. 병합·배포는 확인되지 않았다. [ImageTextToText 고정 소스](https://github.com/huggingface/transformers/blob/3a134bc37f7c22c801b618e289b0255425f22647/src/transformers/pipelines/image_text_to_text.py), [AnyToAny 고정 소스](https://github.com/huggingface/transformers/blob/3a134bc37f7c22c801b618e289b0255425f22647/src/transformers/pipelines/any_to_any.py)

**진단 → 가설 → 최소 실험.** 가설은 “요청 순서에 따른 재현 격차가 모델 state가 아닌 caller 설정 객체의 aliasing에서 발생한다”이다. weights 없이 fresh/shared/shallow-copy dictionary로 두 번 호출해 호출 전후 내용을 비교한다. token limit 변경, STOP 후 stop 미지정, image 후 text를 별개 fixture로 둔다. 후속 실제 모델 검증은 동일 image/prompt에서 deterministic generation과 resolved kwargs를 기록한다. sanitizer 대조만으로 전체 cross-modal generation을 검증했다고 쓰지 않는다.

**GO/KILL.** caller dictionary가 불변이고 같은 요청의 resolved configuration이 호출 순서와 무관하면 GO. 누출된 설정으로 얻은 길이·정확도 차이를 VLM 성능 차이로 보고하는 것은 KILL. 임시 우회는 요청마다 새 dictionary를 만드는 것이며, 중첩 객체의 변경까지 shallow copy가 해결한다고 가정하지 않는다.

## 사례 3 — DDPM: noise 생성 dtype보다 계수 계산 순서가 먼저다

**커뮤니티 재현 조건 / gap.** #15277은 Diffusers 0.43.0 및 main `27a5490`, Python 3.12.13, torch 2.15.0+cu132·Linux, CPU와 A100 조건을 제시한다. 기본 linear beta·1,000 train timesteps에서 FP16의 t=0·1, BF16의 t=0~9에 noise 계수가 0이 된다고 보고한다. 별도 댓글의 CPU 측정도 zero clean sample·unit noise 대조에서 FP16의 초기 두 계수가 0, FP32는 약 0.01000·0.01483이라고 보고한다. 이미지 품질·학습 성능의 독립 측정은 아니다. [원문](https://github.com/huggingface/diffusers/issues/15277), [별도 CPU 측정](https://github.com/huggingface/diffusers/issues/15277#issuecomment-6876344451)

**사실 / mechanism / 수정 상태.** PR #15300 diff는 schedule을 sample dtype으로 내린 후 `1-alpha`를 계산하던 순서를 바꾼다. schedule과 sample의 promoted dtype에서 계수를 계산하고 결과 계수만 sample dtype으로 변환한다. 작성자는 FP32/FP64 bitwise 유지와 저정밀 회귀 테스트 통과를 주장한다. 조회 시 PR은 open·미병합이며 head는 `6975de3235fffb41d99a852456f04c56fb48c89d`다. 테스트 결과는 작성자의 보고이며 본 실행에서 재실행하지 않았다. [수정 PR](https://github.com/huggingface/diffusers/pull/15300), [diff](https://github.com/huggingface/diffusers/pull/15300/files)

**진단 → 가설 → 최소 실험.** 가설은 “초기 timestep의 학습 target/input 불일치가 noise schedule의 조기 rounding에서 발생한다”이다. checkpoint 없이 x0=0·noise=1로 전체 timestep의 유효 계수를 FP16/BF16/FP32에서 추출하고, 같은 schedule 값으로 계산한 FP64 reference와 비교한다. `add_noise`와 `get_velocity`를 모두 검사하고 원본/수정 head에서 출력 dtype·FP32/FP64 비회귀를 확인한다. schedule 자체가 이미 저정밀로 생성돼 소실한 정보는 후속 dtype 승격만으로 복구되지 않으므로 schedule 생성 dtype도 기록한다.

**GO/KILL.** 초기 noise 계수가 reference의 출력 dtype 오차 범위에 들고 기존 고정 fixture도 통과하면 소규모 학습 ablation으로 GO. PR의 계수 수정만으로 FID·수렴·학습 재현이 개선됐다고 선언하는 것은 KILL. 초기 timestep loss와 seed 반복은 계약 검사가 통과한 뒤 측정한다.

## 사례 4 — Ultralytics: checkpoint에 적힌 commit이 실제 시작 코드인가

**Claim / 재현 조건.** #27212는 Ultralytics 8.4.214·main `72a356e`, Python 3.13·Linux의 editable/Git 설치를 제시한다. `GitRepo` 생성 후 첫 checkpoint 저장 전에 checkout이 이동하면 checkpoint의 `git.commit`이 나중 HEAD를 기록한다고 보고한다. 작성자는 실제 run 시작 시각과 reflog를 대조했다고 주장하지만 raw run log는 본문에 없다. 학습 없이 임시 Git 저장소의 두 empty commit으로 lazy-read 동작을 검증하는 fixture는 제공된다. [원문](https://github.com/ultralytics/ultralytics/issues/27212)

**사실 / correction.** PR #27213은 `GitRepo.__init__`에서 HEAD·ref·commit을 즉시 읽어 보존하도록 변경한다. 11/15 16:03:43 UTC에 병합됐고 merge commit은 `2a3921c3abc386d8e97dbb9367db33413d5a01de`다. 이슈는 closed다. 버전별 패키지 release 포함 여부는 확인하지 않았으며, main 병합을 PyPI 배포로 해석하지 않는다. [병합 PR](https://github.com/ultralytics/ultralytics/pull/27213), [diff](https://github.com/ultralytics/ultralytics/pull/27213/files)

**진단 → 가설 → 최소 실험.** 가설은 “사후 재현에 사용하는 checkpoint metadata가 시작 당시 코드를 잘못 가리킬 수 있다”이다. 임시 저장소에서 construction→HEAD 이동→commit 조회를 수정 전후 비교하고 branch/detached HEAD/packed ref를 분리한다. 학습 workflow에는 시작 시 resolved commit·dirty diff hash·config·환경 lockfile을 별도 manifest로 기록해 checkpoint metadata와 대조한다. import 이후 지연 import, dirty 파일, 데이터·의존성 변경은 commit snapshot 하나만으로 포착되지 않는다.

**GO/KILL.** snapshot이 시작 commit을 유지하고 독립 실행 manifest와 맞으면 GO. 과거 checkpoint에 기록된 SHA만으로 “이 코드로 실행했다”고 단정하거나 기존 잘못된 metadata가 새 수정으로 소급 복구됐다고 해석하는 것은 KILL. 관측된 문제는 출처 기록 오류이며 모델 정확도 하락의 직접 증거가 아니다.

## 공통 비교 조건과 오늘의 GO/KILL

네 사례는 같은 backbone·data/split·resolution·pretraining·hardware·precision·batch·TTA·evaluator를 맞춘 성능 비교가 아니다. 서로의 수치를 비교하는 것은 **not strictly apples-to-apples**다. tensor/API/Git fixture에는 dataset·split·TTA가 적용되지 않으며, 실제 모델 제보에서 확인하지 못한 조건은 미확인으로 남겼다.

- **오늘의 1순위 GO:** Grounding DINO/LLMDet 실험을 시작하기 전에 checkpoint와 loaded head tensor를 직접 대조한다. 경고가 없었다는 사실만으로 정상 로드를 가정하지 않는다.
- **GO:** 요청별 resolved kwargs, schedule 생성·계산 dtype, 시작 코드 manifest를 함께 보존한다.
- **GO:** 상태·정밀도·artifact 계약이 통과한 뒤 동일 조건의 seed 반복과 downstream metric을 측정한다.
- **KILL:** open issue를 확정 correction으로, open PR을 릴리스로, 병합을 독립 재현 완료로 바꾸어 말하지 않는다.
- **연구 가설:** weight 로드·입력 noise·요청 상태·코드 출처를 검사하는 preflight가 seed sweep 전에 재현 실패를 얼마나 걸러내는가? 현재는 제안이며, 동일 fixture 집합의 preflight 실패와 후속 실험 실패를 함께 수집해야 검증할 수 있다.
