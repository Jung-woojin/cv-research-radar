## 1. Transformers v5.23.0 — weight보다 위치·cache 구현을 먼저 진단

**배포 사실:** 11월 13일 23:10:57 KST 발행. annotated tag가 가리키는 commit은 `52b080b6416a7897e2af90febeb4dfad22b84d19`이다. GitHub release asset은 없고 tag 서명 검증은 `unsigned`다. Inkling2·LFM3-VL 등의 통합과 VLM correctness 수정이 포함된다. [Release](https://github.com/huggingface/transformers/releases/tag/v5.23.0)

**관측과 저자 설명:** [PR #50427](https://github.com/huggingface/transformers/pull/50427)은 기존 cache 뒤 새 image/video를 넣을 때 이전 `rope_deltas`를 재사용해 새 vision token의 위치 계산을 건너뛰던 경로를 수정한다. PR merge는 11월 10일이며 이번 조사 창의 신규 사건은 **11월 13일 package release**다. [PR #50547](https://github.com/huggingface/transformers/pull/50547)은 Step3.7 checkpoint가 기대하는 W/H rotary band 순서와 구현의 H/W 순서를 맞춘다. PR의 테스트 통과 보고는 개발자 검증이지 이 실행의 측정이 아니다.

**논문 주장과 artifact의 간극:** 공개 checkpoint가 같아도 multi-turn cache나 비정사각형 image에서 output이 달라질 수 있다. 이를 새 representation 또는 새 학습의 이득으로 해석할 근거는 없다. library·processor·attention backend가 다른 결과는 **not strictly apples-to-apples**다. 새 통합도 해당 weight가 이날 처음 공개됐음을 뜻하지 않는다.

**배포 조건:** Apache-2.0 코드. 설치 후보는 `transformers==5.23.0`이며 torch·vision backend·tokenizer·processor와 checkpoint revision을 함께 lock해야 한다. package pin 하나는 전체 dependency lock이 아니다. weights는 각 upstream repository에서 별도 확보하며 training data를 이 tag가 제공하지는 않는다. 전체 모델 추론의 GPU/VRAM은 checkpoint·precision·sequence 길이에 따라 달라지고 이번 release의 단일 최소값은 확인하지 못했다. 위치 계산용 작은 CPU fixture를 먼저 사용할 수 있다.

**활동·무결성:** 위 두 closed/merged PR과 release의 연결을 확인했다. 전체 open Issue를 전수 조사하거나 독립 장치 재현을 확인하지는 않았다. source commit은 고정했지만 package 다운로드 checksum·attestation은 검증하지 않았다.

**진단 → 가설 → 최소 개입 → 10~30분 계획:** representation 손실보다 positional bookkeeping이 병목이라는 가설이다. 기존 환경이 준비돼 있다면 v5.22.2/v5.23.0에서 같은 작은 config·seed·processor로 ① text-prefix cache 뒤 image, ② image-prefix 뒤 video, ③ 가로/세로 image fixture를 넣는다. full-history reference와 cache 경로의 position IDs·delta·logits를 비교한다. checkpoint·data·input shape·precision·batch·attention backend는 고정하고 TTA는 사용하지 않는다.

**GO/KILL:** 수정 후 cache 경로가 reference에 일치하면 구현 migration 검토는 GO. 차이가 남으면 최소 fixture를 보존하고 모델 품질 비교는 보류한다. correction 전후 점수 차이를 신규 모델 gain으로 주장하는 것은 KILL이다.

## 2. Ultralytics v8.4.212 — OCR alphabet과 실행 provider의 분리

**배포 사실:** 11월 13일 22:08:32 KST 발행. tag commit은 `24f58a21f979eb90d502ac0f9400bf07c7429f6b`이다. [Release](https://github.com/ultralytics/ultralytics/releases/tag/v8.4.212)는 한국어·키릴·아랍 문자 등 recognizer 선택, ONNX/CUDA 호환성, validation summary 확장을 안내한다.

**공개 artifact와 저자 주장:** [PR #27167](https://github.com/ultralytics/ultralytics/pull/27167)은 11개 PP-OCRv5 mobile ONNX 모델을 기존 `ultralytics/assets`의 `v8.4.0` asset release에 연결했다고 설명한다. 따라서 package tag와 weight가 저장된 release tag는 다르다. 원본 Paddle ONNX export를 `onnxslim` 처리했고 argmax가 같다는 설명은 개발자 검증이다. 언어를 자동 감지하지 않으며 한국어는 `recognizer="korean_PP-OCRv5_mobile_rec"`처럼 직접 선택한다. [버전 고정 OCR 문서](https://github.com/ultralytics/ultralytics/blob/v8.4.212/docs/en/guides/ocr.md)

**실행 조건의 간극:** [PR #27175](https://github.com/ultralytics/ultralytics/pull/27175)는 CUDA 12 torch와 CUDA 13용 ORT wheel의 조합에서 CPU fallback이 발생한다고 설명한다. 비 ARM64 CUDA 12 환경의 자동 설치는 `onnxruntime-gpu[cuda]<1.27`로 제한하지만, 이미 설치된 부적합 build를 자동 교체하지 않는다. 개발자 Windows 11·RTX 4060·torch 2.11.0+cu128 결과는 독립 재현이 아니다. `device=0`만으로 GPU 실행을 입증할 수 없다.

**논문 주장과 artifact의 간극:** 한국어 오류가 줄어도 detection backbone 학습 개선보다 recognizer alphabet 교체가 원인일 수 있다. 속도 변화 역시 GPU provider 복구일 수 있다. recognizer·alphabet·provider가 다른 비교는 **not strictly apples-to-apples**다. 이 tag를 새 YOLO 연구 checkpoint 공개로 분류하지 않는다.

**배포 조건:** code AGPL-3.0, 기본 Python ≥3.8. 설치 후보는 `ultralytics==8.4.212`와 환경에 맞는 ORT 고정이다. PaddlePaddle 설치 없이 CPU/CUDA ORT를 쓰지만 첫 실행은 모델 다운로드·dependency 설치를 유발할 수 있다. weight별 license/source는 ONNX metadata로 확인해야 하며 code license를 모든 weight에 확장하지 않는다. 새 dataset은 없다. CPU smoke test가 가능하고 특정 GPU/VRAM 최소값은 미확인이다.

**활동·무결성:** #27167은 11월 13일 13:07:06 UTC, #27175는 13:03:55 UTC merge됐다. package release asset은 SBOM이다. API의 SBOM SHA256은 `3fe1b4da55557d12b6ed6cfb8825998e4d2d59af8e9d1376ad3cec91424e0ece`이며 weight checksum이 아니다. tag는 unsigned이고 ONNX별 checksum·attestation은 이번 실행에서 검증하지 못했다.

**진단 → 가설 → 최소 개입 → 10~30분 계획:** 첫 단계는 session provider·torch CUDA·ORT version을 기록하는 것이다. 다음으로 같은 detector와 고정 crop을 유지한 채 default recognizer와 Korean recognizer만 바꿔 한글·Latin·혼합 crop의 transcription, character error, confidence를 비교한다. 별도로 같은 ONNX·input shape·batch=1·precision에서 CPU/CUDA provider와 warm-up 이후 지연을 기록한다. detection error와 recognition error를 따로 집계한다.

**GO/KILL:** 기대 provider와 alphabet이 확인되고 고정 crop의 오류 감소가 재현되면 해당 사용 경로는 GO. provider가 CPU인데 GPU latency라고 보고하거나 confidence만으로 한국어 정확도를 판단하는 것은 KILL이다.

## 3. Inkling 2 Small — 발표에서 실제 weight 공개로 전환

**공개 시점 사실:** [공식 발표](https://thinkingmachines.ai/news/inkling-2-small/)는 11월 5일이며, 11월 12일 업데이트가 실제 weight 다운로드 가능을 알린다. Hub의 `upload model` commit은 `78cb6c0ef68e1f089b77e78cfd94783d05b5c41b`, 시각은 11월 12일 19:53:15 UTC다. 오늘 확인한 현재 revision은 `8361e7a31ae7e9966a49a91d3994fde618936c2b`이며 마지막 변경은 README다. 최근 수정 시각을 새 weight 공개 시각으로 대체하지 않았다. [공식 commit 목록](https://huggingface.co/thinkingmachines/Inkling-2-Small/commits/main)

**Artifact·무결성:** 현재 tree에는 24개 numbered safetensors shard, index, 별도 `mtp.safetensors`, config·processor·tokenizer가 있다. 첫 shard의 공식 LFS oid는 `d5e2ab13b8f433da7b2221191c6e254836bd93d9fd3f1ea2cadec1d4a002b69b`다. 이는 전체 checkpoint digest가 아니며 실제 파일 다운로드 대조·attestation 검증은 하지 않았다. [revision 고정 파일 목록](https://huggingface.co/thinkingmachines/Inkling-2-Small/tree/8361e7a31ae7e9966a49a91d3994fde618936c2b)

**저자 주장과 조건:** Apache-2.0 공개 weight다. [모델 card](https://huggingface.co/thinkingmachines/Inkling-2-Small/blob/8361e7a31ae7e9966a49a91d3994fde618936c2b/README.md)는 594B total·17B active, NVFP4 최소 합산 VRAM 500GB, MXFP8 800GB를 안내한다. 실행에는 호환 inference framework와 dependencies가 필요하다. training dataset 전체 공개는 확인하지 못했다.

**Claim과 재현 경계:** 17B active는 메모리 footprint 17B를 뜻하지 않는다. card의 ScreenSpot Pro 평가는 긴 변이 4,096px를 넘는 image와 정답 좌표를 함께 rescale한다. 원본 해상도 평가와는 **not strictly apples-to-apples**다. 공개 weight만으로 저자 평가표의 harness·precision·image 처리 재현이 보장되지는 않는다.

**활동·설치 조건:** Hub history에는 chat-template 인자 순서 수정과 evaluation metadata 추가가 보인다. 이를 모두 weight 교체나 독립 재현으로 해석하지 않는다. card는 SGLang·vLLM 등의 recipe를 연결하지만 이번 조사에서는 정확한 container digest와 전체 dependency lock을 검증하지 못했다. 소형 GPU에서 full inference를 10~30분 내 수행할 수 있다고 약속하지 않는다.

**진단 → 가설 → 최소 개입 → 10~30분 계획:** CPU metadata audit부터 진행한다. 고정 revision에서 index가 참조하는 모든 shard 존재 여부와 LFS manifest, quantization config, processor·chat-template revision을 수집한다. ScreenSpot fixture의 resize 전후 좌표 변환을 검증한다. 충분한 cluster가 이미 준비된 경우에만 고정 image·prompt·precision·token budget으로 1-example load/generate를 후속 실행한다.

**GO/KILL:** 오늘은 manifest와 좌표 변환 audit만 GO. 전체 weight 무결성·runtime lock·GPU 예산이 확보되기 전 full reproduction은 보류한다. active parameter만으로 메모리·비용을 산정하거나 공개 평가표를 독립 검증 수치로 사용하는 것은 KILL이다.

## 오늘의 GO/KILL와 연구 질문

| 우선순위 | 관측 → 가설 | 최소 실험과 판정 |
|---|---|---|
| 1 | ONNX 성능 저하 → provider 선택 실패 가능성 | 같은 graph에서 실제 session provider부터 확인. GPU 미활성 상태의 속도 비교는 KILL |
| 2 | multi-turn VLM 출력 차이 → cache 위치 계산 오류 가능성 | full-history/reference와 cache 경로 비교. 일치하면 구현 수정 채택 GO |
| 3 | 한국어 OCR 오류 → alphabet/readout 불일치 가능성 | detector·crop 고정 후 recognizer만 교체. detection gain으로 해석하지 않음 |
| 4 | open weight가 곧 재현 가능함 → runtime·precision·resize 계약 누락 | shard/processor/harness manifest부터 GO, 자원 미확보 full inference는 보류 |

후속 연구 질문은 “새 weight 없이도 cache·alphabet·provider를 교정하면 어떤 failure cell이 사라지는가?”다. 공통 개입은 backbone 재학습보다 **실행 경로와 readout 조건을 고정하는 것**이다. 실패가 남으면 image shape·multi-turn·script별로 분해해 representation 병목과 구현 병목을 구분한다. 위 계획은 모두 제안이며 실측 결과가 아니다.
