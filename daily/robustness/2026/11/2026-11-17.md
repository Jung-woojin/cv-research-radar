## 1. INT8 calibration: 표본 수보다 출력 포화가 병목일 수 있다

**확인 사실.** merge commit은 `95d2e2a72ff002e81228ea1074d59fb69baa175d`다. diff는 Classify를 float head-output 규칙에 포함하고 fully connected 층의 weight를 dynamic INT8로 처리해 float 입력·logit을 유지한다. [PR 및 diff](https://github.com/ultralytics/ultralytics/pull/27225/files)

**작성자 보고.** ImageNet val 50,000장 CPU 평가에서 yolo26n-cls의 top-1은 기본 12장 calibration으로 52.05→70.60%, 512장 export 1에서는 68.26→70.61%다. 고정 2,000장 subset의 최대값 동률은 각각 874→0, 155→0이다. 표의 5개 구성 모두 수정 뒤 top-1이 개선돼 이 표의 **악화 행은 0/5**다. 이는 자연 shift cell 총수가 아니다. FP32 top-1 71.39%까지 완전히 회복하지는 않는다. [측정 조건·표](https://github.com/ultralytics/ultralytics/pull/27225)

**교차 대조와 남은 failure cell.** 같은 PR의 review reproduction은 M5 Pro CPU·torch 2.14.1·litert-torch 0.10.0·ai-edge-litert 2.3.0·quantizer 0.10.1, imagenette160 val 3,925장을 1,000-class로 평가했다. default→512장 calibration에서 수정 전 top-1은 64.36→35.77%, 수정 후도 68.15→62.83%다. 즉 이 두 표본 설정 비교에서 수정 후에도 **1/1 하락**이다. 표본 수와 표본 분포가 함께 바뀌므로 크기만의 인과효과는 아니다. ImageNet 표와는 **not strictly apples-to-apples**다.

**진단 → 가설.** 저자는 INT8 상한에 잘린 class logit들이 동률이 되고 낮은 class index가 선택되는 mechanism을 제시한다. 평가자 가설은 calibration 분포와 포화율이 top-1 rank를 함께 좌우한다는 것이다. 양자화 range calibration은 확률 calibration과 다르며 ECE·Brier·risk–coverage는 미확인이다.

**최소 intervention·실험.** weights·resize·split·batch·CPU threads·calibration 순서를 고정하고 기존 INT8/float-head/FP32를 비교한다. 대표성이 같은 nested calibration subset과 별도 domain-shift subset을 분리한다. top-1/top-5, tie·clip 비율, class별 오류, ECE·Brier·risk–coverage를 산출한다. 원문에서 개별 입력 해상도·batch·pretraining 통제가 충분히 확인되지 않아 이를 재현의 고정 항목으로 둔다.

**GO/KILL.** 포화·동률이 줄고 untouched worst-cell 정확도와 calibration이 유지되면 float-head를 GO한다. calibration 표본 수만 늘려 배포하는 결정은 KILL한다. review에서 x86 속도 개선이 M5에서는 재현되지 않았고 GPU/NPU delegate 및 실제 NXP board는 미검증이므로 속도·edge 보편 개선도 보류한다.

## 2. mAP가 같아도 이미지별 failure cell은 사라질 수 있다

**확인 사실.** merge commit `54763f10624f1776f43546ea7f4559878f9aab80`은 per-image key를 basename에서 공통 이미지 디렉터리 기준 상대 경로로 바꾼다. `a/0.jpg`와 `b/0.jpg`가 별도 항목으로 보존된다. [PR 및 diff](https://github.com/ultralytics/ultralytics/pull/27222/files)

**작성자 보고·metric.** CPU의 yolo26n/yolo26n-pose 검사에서 복제 coco8 detect·pose는 4/8→8/8 entry, 세 중첩 경로는 1/3→3/3, flat coco8는 4/4 유지다. 네 표 행에서 mAP는 모두 동일하다. 원문 표의 **entry completeness 악화는 0/4**지만 geography별 정확도 악화 cell 수는 미확인이다. per-image precision/recall/F1·TP/FP/FN은 IoU 0.5 기준이며 probability calibration·selective coverage는 제공되지 않았다. entry 보존율을 prediction coverage로 해석하지 않는다. [재현 표·제약](https://github.com/ultralytics/ultralytics/pull/27222)

**진단 → 가설.** dict key 충돌은 집계 mAP 계산과 별개로 진단용 record를 덮어쓴다. 지역·카메라 폴더가 같은 basename을 쓴다면 worst-cell 표본이 사라질 수 있다는 것은 평가자 추론이며, 실제 지리 편향을 발견했다는 뜻은 아니다.

**최소 intervention·실험.** 모델을 바꾸기 전에 image ID를 상대 경로와 content hash에 연결한다. 같은 basename·서로 다른 영상의 작은 split에서 manifest 수와 metric key 수를 맞추고 입력 순서를 뒤집어 cell 집계가 불변인지 검사한다. threshold·weights·resolution·evaluator를 고정해 micro 집계와 지역/카메라 macro 집계를 분리한다.

## 3. HEIC/AVIF: VLM 성능 전에 입력 가용성을 측정한다

**확인 사실.** merge commit `069c841de1b1486fadb0f5ce03d57a07af364102`은 LLM 로컬 파일 경로를 `cv2.imread` 대신 공유 `imread`로 읽도록 바꾼다. URL·data URI·PIL·NumPy 경로는 이번 diff의 변경 대상이 아니다. [PR 및 diff](https://github.com/ultralytics/ultralytics/pull/27221/files)

**작성자 보고·shift cell.** HEIC는 read error에서 JPEG data URI로 바뀌며, OpenCV 4.8.1/4.10/4.11의 AVIF 실패도 Pillow 경로에서 디코딩된다. 최신 OpenCV AVIF와 Pillow 간 평균 절대 pixel 차이는 0.2로 보고되지만 downstream 정확도 차이는 측정하지 않았다. 개별 pixel 계산 조건·전체 실패 cell 분모는 미확인이라 **baseline 대비 악화 cell 총수는 미확인**이다. Windows/Linux AVIF wheel과 실제 LLM API 호출도 검증하지 않았다. [입력 대조표·미검증 조건](https://github.com/ultralytics/ultralytics/pull/27221)

**진단 → 가설.** decoder 가용성이 camera/device별 입력 선택 편향을 만들 수 있다. 디코딩 성공을 분모에서 제외하면 서비스의 end-to-end 성공률이 부풀 수 있다는 것은 평가자 가설이다. 환각·OOD 탐지·ECE·selective coverage 개선 수치는 없다.

**최소 intervention·실험.** 허가된 같은 장면의 JPEG/HEIC/AVIF를 camera ID·OS·decoder 버전별 manifest로 묶는다. 먼저 decode 성공률·shape·방향·pixel 차이를 확인한 뒤, 같은 모델·prompt·해상도로 오류를 포함한 end-to-end 성공률과 성공 디코딩 조건부 정확도를 따로 측정한다. 변환은 손실 압축일 수 있어 형식 간 비교는 **not strictly apples-to-apples**다.

**GO/KILL.** 입력 누락이 줄고 orientation·pixel canary가 통과하면 reader 통합을 GO한다. 변환만 검증한 PR로 hallucination 감소나 Windows 호환 완료를 선언하는 것은 KILL한다. 전일 EXIF 수정과는 별도의 LLM 파일 입력 경로 수정이다.
