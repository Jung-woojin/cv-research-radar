## 1. OpenVINO ARM64 — 오래된 호환성 설정이 현재 병목인가

**사실:** 미병합 #27353은 Linux ARM64 CPU의 `ACCURACY`와 FP32 강제를 제거하고 `LATENCY`만 요청한다. 확인 head는 `815cb26613bff7a26217e42fba8c46f509d40626`이다. FP32 입력·출력 IR이어도 내부 실행 precision은 별개다. [diff](https://github.com/ultralytics/ultralytics/pull/27353/files)

**저자 측정:** Raspberry Pi 5, Ubuntu 25.10 AArch64, Ultralytics 8.4.218, OpenVINO 2026.4.1, COCO128·640 입력, 4 threads·1 stream에서 다음 결과를 보고했다.

| 모델 | 기존 inference ms/image | 변경 후 | mAP50–95 기존→변경 |
|---|---:|---:|---:|
| YOLO26n | 136.79 | 74.56 | 0.4773→0.4774 |
| YOLO26s | 338.14 | 179.37 | 0.5674→0.5665 |

이는 전체 카메라 pipeline 지연이 아닌 benchmark의 inference 값이다. batch·warm-up 횟수·반복 분산·clock/thermal mode는 원문에서 확정하지 못했다. 연산 precision이 달라 **not strictly apples-to-apples**이며, 동일 FLOPs에서 precision dispatch가 바뀐 비교로 읽어야 한다. [측정과 최소 재현](https://github.com/ultralytics/ultralytics/pull/27353)

**교차확인·반례:** `(1,2,32,400)` FP32 입력 두 개의 MatMul probe는 OpenVINO 2026.1.0에서 compile 실패, 2026.2.0과 2026.4.1에서 `gemm_acl_f16`·기대 출력을 보고했다. 연결된 [OpenVINO #35035](https://github.com/openvinotoolkit/openvino/pull/35035)는 실제로 oneDNN MatMul dispatch 수정이며 4/15 병합이다. 새 소식은 이 오래된 수정을 근거로 한 이번 설정 제거와 측정이다.

11/25 03:49 리뷰는 여전히 허용되는 2026.1.0에만 FP32 hint를 유지하자고 요청했다. 따라서 최신 runtime의 속도 개선을 모든 지원 버전의 안전한 변경으로 일반화하지 않는다. COCO128의 유사 점수도 full COCO 품질 동등성을 보장하지 않는다.

**진단→가설:** 과거 compile 오류를 막던 전역 FP32 설정이 최신 runtime의 FP16 kernel 선택까지 차단했을 가능성이 높다.

**최소 실험·GO/KILL:** 같은 Pi·weight·640·고정 batch에서 runtime 2026.1.0/2026.4.1 × 기존/제거/구버전 전용 FP32 guard를 비교한다. compile 성공, 실제 exec type, full holdout 품질, warm p50/p95, sustained thermal 상태를 기록한다. 최신 버전 개선과 구버전 호환성을 함께 통과하면 GO. 버전 guard 없이 전체 ARM64 배포에 적용하면 KILL.

## 2. MNN — INT8 파일이 곧 INT8 계산은 아니다

**사실:** #27355는 package 동작을 바꾸는 PR이 아니라 통합 문서와 측정의 보강이다. 확인 head는 `0dc0c53c017d8deeb47466b994585e5e6f7467c6`이다. 해당 경로의 `quantize=8`은 weight 저장 압축이며 activation quantization이 아니다. MNN 공식 문서도 기본 weight 복원과 dynamic quantization 설정, FP16 저장과 runtime precision을 구분한다. [PR](https://github.com/ultralytics/ultralytics/pull/27355), [MNN 압축 문서](https://mnn-docs.readthedocs.io/en/latest/tools/compress.html)

**저자 측정:** shared AMD EPYC 9655·Ubuntu 24.04, Ultralytics 8.4.218, MNN 3.6.2, PyTorch 2.15.0, ONNX Runtime 1.32.0, `taskset -c 0-7`, batch 1·640×640 조건이다.

| YOLO26n | PyTorch | ONNX FP32 | MNN FP32 | MNN FP16 weights | MNN INT8 weights |
|---|---:|---:|---:|---:|---:|
| inference ms/image | 10.1 | 17.7 | 21.4 | 21.4 | 21.2 |
| 파일 MB, 10⁶ bytes | 5.5 | 9.9 | 9.8 | 5.0 | 2.7 |
| COCO subset mAP50–95, % | 42.0 | 42.0 | 42.0 | 42.0 | 41.7 |

품질은 정렬된 COCO val2017 마지막 500장이다. latency는 전후처리를 제외한 `val` inference 단계의 두 run 평균이며, run 차이는 최대 14%였다. warm-up 횟수는 미확인이다. PyTorch는 다른 세션에서 실행됐고 backend별 thread 설정도 같지 않아 **not strictly apples-to-apples**다. [head 고정 문서](https://github.com/ultralytics/ultralytics/blob/0dc0c53c017d8deeb47466b994585e5e6f7467c6/docs/en/integrations/mnn.md#benchmarks)

**병목 단서:** CPU affinity는 8개지만 Ultralytics가 MNN에 요청한 thread는 서버 전체 logical CPU 절반인 192개다. 직접 MNN의 YOLO26m FP32 forward에서는 `numThread=192` 96ms, 8이면 76ms를 보고했다. 이 raw forward와 위 `val` 평균을 하나의 가속률로 합치지 않는다. 휴대전화·GPU·NPU는 이번 문서에서 실행하지 않았다.

**진단→가설:** 파일 압축은 전송·저장 비용을 줄여도 기본 FP32 kernel의 계산을 줄이지 않는다. 과도한 thread 요청은 작은 affinity 안에서 scheduling 비용을 만들 수 있다.

**최소 실험·GO/KILL:** 동일 host에서 MNN weight precision 32/16/8 × thread 8/192를 같은 세션·같은 wrapper로 교차한다. 실제 kernel precision, load 시간, 파일·RSS·peak allocation, inference p95, holdout 품질을 함께 기록한다. 저장 예산 개선은 품질 관문 통과 시 GO. 속도는 thread와 실행 precision을 통제한 뒤 별도 판단한다. 2.7MB를 peak RAM·VRAM 또는 INT8 연산 증거로 사용하면 KILL.

## 3. Android page cache — 사본 제거와 warm reload의 교환

**사실:** 미병합 #32992는 Linux buffered load 후 tensor byte 범위에 `posix_fadvise(POSIX_FADV_DONTNEED)`를 호출한다. 실패를 무시하는 hint이며 mmap·direct I/O 경로와 구분된다. head는 `318b52449f3eea624b0466a89e6ed0b65f3dbb8f`다. [diff](https://github.com/ggml-org/llama.cpp/pull/32992/files)

**저자 측정:** Pixel 11 Pro·Android 17·kernel 6.12·RAM 11.4GiB, static arm64 CPU binaries, baseline `33aeb17f8`, `-ngl 0 -t 4 -p 0 -n 1 -r 1`이다. granite-4.2-8b Q4_K_M·5.0GiB의 5회 median은 다음과 같다.

| buffered `none` 조건 | master | PR |
|---|---:|---:|
| 실행 후 모델 page cache | 2827–3006 MiB | 210–217 MiB |
| 첫 실행 중 최소 free memory | 0.3 GiB | 3.0–3.1 GiB |
| 파일 cache가 없는 run time | 16.6 s | 13.6 s |
| 직후 같은 build의 run time | 8.5 s | 11.4 s |

같은 Pixel에서 direct I/O는 cold 20.7→20.4초였고 모든 run에 swap이 없었다. 이는 load를 포함한 `llama-bench` 실행 시간이며 steady-state token throughput·TTFT·VRAM 측정이 아니다. [전체 표·한계](https://github.com/ggml-org/llama.cpp/pull/32992)

**중요한 조건 차이:** Galaxy S26 Ultra의 4GiB zram 실험에서는 기존 buffered load 12회 중 3회 swap, 변경 0/12를 보고했다. 하지만 저자가 명시했듯 이 Galaxy 결과는 b11988 기반의 이전 구현이며 현재 tensor별 diff의 재시험이 아니다. 따라서 **not strictly apples-to-apples**다. 시작 free memory 0.7GiB에서는 기존 11/12, 변경 12/12가 swap해 효과가 사라졌다. Galaxy load 시간도 양쪽 7–8초로 같았다.

**진단→가설:** 메모리가 충분한 cold load에서는 page cache 중복과 reclaim 비용을 줄일 수 있다. 반면 다음 load가 재사용할 cache도 버려 warm reload가 느려질 수 있다. 이미 메모리가 부족하면 이 hint만으로 해결되지 않는다.

**최소 실험·GO/KILL:** 동일 폰·동일 revision에서 buffered 기존/patch/direct I/O × cold/warm × 시작 여유 메모리를 비교한다. load 시간, file cache, process RSS·VmSwap, major faults, 이후 decode와 품질을 분리 기록한다. 실제 배포의 메모리 압박과 재로딩 빈도에서 이익이면 GO. 과거 Galaxy 구현의 swap 제거를 최신 diff의 보장 결과로 인용하거나 cache를 process peak RAM과 합치면 KILL. x86·GPU·실측 power는 미검증이다.

## 4. SavedModel — 성공한 INT8 benchmark가 실제로 무엇을 실행했는가

**사실:** #27349는 `saved_model`의 `quantize=8`·`int8=True`를 export 전에 거부하도록 병합됐다. SavedModel 자체는 FP32였고 기존 benchmark는 INT8 요청에도 FP32 결과를 성공 행으로 표시했다. 수정은 새로운 가속이 아니라 잘못된 precision 비교의 차단이다. [구현](https://github.com/ultralytics/ultralytics/pull/27349/files)

**저자 측정·리뷰어 재현:** Linux x86-64 CPU의 YOLO26n에서 동반 생성된 INT8 TFLite 출력은 pixel 단위 box와 class score가 하나의 scale을 공유했다. 리뷰어는 detect scale 2.687, OBB 4.008에서 class score가 0.0으로 복원되고 `bus.jpg`에 box가 없음을 재현했다고 기록했다. FP32 SavedModel의 COCO8 mAP50–95는 양쪽 0.6693으로 같았다. [리뷰 기록](https://github.com/ultralytics/ultralytics/pull/27349)

**조건·한계:** exact CPU·TensorFlow/onnx2tf 버전·batch·input shape·warm-up은 이 재현 기록에서 확정하지 못했다. 따라서 latency 우열을 도출하지 않는다. LiteRT INT8은 별도 경로이며 reviewer COCO8 점수도 run별 0.628/0.654로 달랐다. Edge TPU compile은 reviewer가 수행하지 않았다. 서로 다른 export artifact·calibration·평가 조건은 **not strictly apples-to-apples**다.

**진단→가설:** 상이한 물리 단위의 출력에 같은 quantization scale을 쓰면 큰 box 범위가 작은 score 해상도를 잠식할 수 있다. 동시에 요청 precision과 실제 benchmark artifact가 달라지면 품질·속도 결론 모두 잘못될 수 있다.

**최소 실험·GO/KILL:** 같은 weight·이미지에서 SavedModel FP32와 별도 LiteRT INT8의 실제 입력·출력 dtype/scale, box/score 범위, artifact 경로와 runtime delegate를 먼저 audit한다. 고정 calibration과 holdout 품질을 통과한 artifact만 latency·peak memory 비교에 넣는다. 실제 실행 precision을 증명하면 GO. 옵션 이름이나 export 성공만으로 INT8 가속이라 부르면 KILL.
