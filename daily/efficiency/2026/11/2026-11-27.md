## 1. INT8 segmentation — 정확도 회복이 후처리 비용을 늘릴 수 있다

**사실:** #27376 head `db2953e3b4bfb0c60bfe7e3d3799dac253a7939a`는 Edge TPU/ST Edge AI export에서 mask coefficient를 16으로 나누고 prototype을 16배 한다. float mask 조합에서는 상쇄되지만 quantization 전에 공유 tensor의 범위를 바꾼다. 새 구조나 FLOPs 절감 기법이 아니다. [diff](https://github.com/ultralytics/ultralytics/pull/27376/files)

**저자 측정·리뷰어 재현:** 같은 COCO train2017 300장 calibration, 512 입력·batch 1, COCO val2017 5,000장·confidence 0.001, faster-coco-eval 1.8.1에서 다음 결과를 보고했다.

| YOLO26n-seg 경로 | Box AP 전→후 | Mask AP 전→후 |
|---|---:|---:|
| ST INT8 ONNX, ORT 1.32.0 CPU | 0.1480→0.3246 | 0.1847→0.2934 |
| Edge TPU용 INT8 TFLite, LiteRT 2.4.1 CPU·compile 전 | 0.1492→0.3243 | 0.1857→0.2921 |

공유 output scale은 0.06036→0.00686으로 줄었다고 보고한다. FP32 bus.jpg의 다섯 boxes/masks는 같았다. full-set 평가와 host 실행임을 [리뷰어 댓글](https://github.com/ultralytics/ultralytics/pull/27376#issuecomment-7198271572)에서도 확인했다.

**비용·반례:** bus.jpg의 confidence 0.001에서는 mask 수가 10→107, 후처리 median이 5.54→11.82ms, 반환 uint8 mask tensor가 2.50→26.75MiB였다. confidence 0.25에서는 mask 6→5, inference 13.26→13.75ms, 후처리 3.19→3.13ms였다. 7회 warmed 교대 측정이며 반환 tensor 크기는 peak memory가 아니다.

**조건·한계:** host CPU 모델·OS·timing batch·warm-up 횟수는 해당 측정에서 미확인이다. ST 평가는 worker당 ORT 6 threads, LiteRT는 4 CPU lanes다. backend·thread가 다른 두 행은 **not strictly apples-to-apples**다. confidence별 workload도 다르다. physical Coral/STM32 inference·peak memory·power는 미측정이다. Edge TPU compiler 16.0.384591198의 512 입력에서는 nano만 700/709→701/711 ops mapped였고, large는 activation 크기로 실패, extra-large는 세 partition 시도가 각각 180초 timeout에 도달했다. host AP 회복을 보드 가속으로 해석하지 않는다.

**진단→가설:** 큰 mask coefficient가 boxes/scores와 같은 INT8 scale을 공유하면 좌표의 유효 해상도가 줄 수 있다. 범위 조정이 작은 box를 회복해도 더 많은 후보가 살아남으면 후처리 시간이 증가할 수 있다.

**최소 실험·GO/KILL:** 동일 weight·calibration·512·batch 1에서 scaling on/off × confidence 0.001/0.25를 비교한다. scale·좌표 오차·small-object AP·mask 수·inference/후처리 p95·peak RSS를 분리한다. 보유 보드에서는 실제 partition 경계와 CPU 시간을 추가한다. 품질과 전체 지연 예산을 함께 통과하면 GO. AP만으로 실시간 배포를 승인하면 KILL.

## 2. Edge TPU compiler — compile 성공과 accelerator residency는 다르다

**사실:** #27377 head `1b64671ea26c831fe316ab077b13310b316649c1`의 변경은 `--delegate_search_step` 30→20이다. Linux x86-64·compiler 16.0.384591198에서 YOLO26n-cls 224의 286-op graph와 256-op cut은 실패했으나 266-op cut은 compile됐다. [한 줄 diff](https://github.com/ultralytics/ultralytics/pull/27377/files)

**저자 측정·리뷰어 재현:** YOLO26n-cls/YOLO11n-cls는 step 30 실패→step 20 두 번 시도 후 성공이며 TPU 121/CPU 165 ops였다. AMD EPYC 9655에서 warm-up 후 3회 median의 classifier compile 시간은 step 10의 0.96초→20의 0.70초였다. YOLO26n-seg 320은 기존 step 30의 6.13초, step 10의 10.91초, 최종 step 20의 6.71초다. [리뷰](https://github.com/ultralytics/ultralytics/pull/27377#issuecomment-7198422139)는 아래 PR discussion의 실제 재현 설명과 함께 확인해야 한다. [전체 원문](https://github.com/ultralytics/ultralytics/pull/27377)

**조건·한계:** 같은 INT8 input graph 비교지만 분류와 segmentation은 모델·shape가 달라 **not strictly apples-to-apples**다. compile에는 inference batch·warm inference latency를 적용할 수 없으며 export batch·OS 세부 버전·warm-up 횟수는 미확인이다. physical Coral inference는 미검증이다. CPU op 수와 TPU op 수의 비율은 시간 비율이 아니다.

**진단→가설→실험:** 거친 search step이 유효 cut을 건너뛸 수 있다. 반면 촘촘한 탐색은 compile 비용을 늘리고 CPU fallback 경계가 남는다. 동일 FlatBuffer hash에서 step 30/20/10의 성공 여부·cut·compile 시간·mapped ops를 기록하고 보유 Coral에서 cold load와 warm end-to-end를 측정한다.

**GO/KILL:** 기존 compile blocker의 해소 확인은 GO. compile 성공만으로 “TPU에서 전체 실행” 또는 latency 개선을 선언하면 KILL.

## 3. Paddle fallback — 틀린 결과가 빠른 baseline일 수 있다

**사실:** #27379 head `94e12797835a927a24712e3a39e93eda17a320a6`는 CUDA 요청 여부 대신 `config.use_gpu()`의 실제 상태로 OBB/depth oneDNN workaround 적용 여부를 판단한다. CPU wheel에서는 GPU 요청이 로그만 남기고 CPU 실행을 유지했다. [diff](https://github.com/ultralytics/ultralytics/pull/27379/files)

**리뷰어 재현:** AMD EPYC 9655·RTX PRO 6000 Blackwell host에서 Paddle CPU wheel 3.2.2의 fallback을 확인했다. 같은 YOLO26n FP32 export·640×640·batch 1에서 DOTAv1 val 458장의 AP는 0.072092→0.357689, NYU Depth V2 val 654장의 RMSE는 0.551806→0.546539였다. [재현 댓글](https://github.com/ultralytics/ultralytics/pull/27379#issuecomment-7198125723)

**latency 반례:** EPYC 8 cores에서 5회 교대 fresh-process·warmed inference median은 depth 49.7→84.9ms, OBB 32.7→35.4ms였다. 수정본은 더 정확하면서 더 느리다. 같은 문서의 stack은 Ultralytics 8.4.218, X2Paddle 1.6.0, torch 2.15.0이다. 실제 CUDA 13.0 GPU wheel 3.2.2에서는 작은 dota8/depth8 control 점수가 전후 같았지만 full-val CPU 결과와는 **not strictly apples-to-apples**다.

**조건·한계:** shared host 측정이며 OS·warm-up 횟수·power mode·정확한 baseline benchmark SHA는 미확인이다. inference-stage 값에 전후처리는 포함하지 않는다. GPU가 있는 host의 CPU fallback을 GPU 성능으로 표시하면 안 된다.

**진단→가설→실험:** 잘못된 oneDNN pass가 일부 계산을 잘못 처리하면서 빠른 결과를 만들었을 수 있다. 같은 export에서 CPU wheel `device=0`/명시적 CPU/실제 GPU wheel을 구분하고 effective device·pass 목록·raw output 오차·품질·p95를 기록한다. pass 하나씩 비활성화해 latency와 정확도의 원인을 분리한다.

**GO/KILL:** 속도 비교 전에 정확한 backend와 품질 관문 확인은 GO. 잘못된 출력을 내는 baseline의 낮은 latency를 배포 목표로 유지하면 KILL.

## 4. HIP split-K — 동일 F32 연산도 shape별 병렬성에 좌우된다

**사실:** 미병합 #33167 head `9384a12815111ccfa6fb6c34e1f47edad0dc987d`는 HIP RDNA3 일부 장치에서 작은 출력·긴 K의 F32 GEMM을 분할하고 partial output을 합한다. K≥2048·tile 수 guard, 최대 32 slices, disable 환경변수를 포함한다. gfx1100은 제외한다. 임시 buffer를 쓰므로 VRAM 절감 기법이 아니다. [diff](https://github.com/ggml-org/llama.cpp/pull/33167/files)

**저자 측정:** RX 7700 XT gfx1101·12GB, i5-11600K, Fedora 45, ROCm 10.2.0 TheRock·rocBLAS 5.8.0이다. F32 microbenchmark의 출력 64×256·K4608은 329.9→36.2µs, 128×256·K2304는 160.4→34.4µs였다. NMSE 약 1e-12를 보고한다.

모델 수준에서는 F16 KV·batch 2048·FA auto·5회 반복, `-fitt 1536` 자동 배치에서 Inkling-2-Mini UD-Q2_K_XL의 ub256 pp512가 851→955 tok/s, pp4096은 665→725였다. ub512 pp4096은 634→659다. 같은 ub512의 Qwen3.6-35B-A3B UD-Q4_K_XL pp4096은 1063→1065로 차이가 작았다. [측정 원문](https://github.com/ggml-org/llama.cpp/pull/33167)

**조건·한계:** weight precision은 혼합 quantization이고 수정 대상 GEMM은 F32다. kernel 배수와 모델 throughput은 **not strictly apples-to-apples**다. benchmark baseline exact SHA·driver·warm-up·clock/power mode·자동 offload의 최종 layer 배치는 미확인이다. 저자는 backend tests를 on/off 모두 통과했다고 보고했으나 숫자로 된 full-model 품질 대조는 본문에서 확인하지 못했다. gfx1102/1103/115x는 측정하지 않았다고 명시한다.

**진단→가설:** 작은 출력의 적은 workgroup이 GPU를 충분히 사용하지 못할 때 K 분할이 병렬성을 늘릴 수 있다. attention 비중이나 충분한 tile 수가 커지면 전체 이득은 줄어든다. rocBLAS tuning table 원인 설명은 저자 주장이다.

**최소 실험·GO/KILL:** 같은 build·weight·placement에서 split-K on/off × ub256/512 × prompt512/4096을 교차한다. occupancy·GEMM/합산 시간·temporary peak memory·PP/TG·PPL을 기록한다. 해당 shape가 실제 병목이고 품질이 유지되면 조건부 GO. RX 7700 XT 결과를 모든 AMD·edge APU의 보장 이득으로 쓰면 KILL.
