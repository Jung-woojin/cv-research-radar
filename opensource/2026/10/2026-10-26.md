## 1. AgentVQA

1. **새로운 내용:** `[사실]` Web Agents, Robotics, Egocentric Videos, Games, Spatial Planning의 다섯 영역을 하나의 오프라인 객관식 VQA 형식으로 통합했다. 23개 원천 데이터셋에서 1,000개 수동 검증 문항을 구성하며 각 영역은 200문항이다.
2. **논문·프로젝트:** [논문](https://arxiv.org/abs/2610.31494) · [코드](https://github.com/zlab-princeton/AgentVQA) · [데이터](https://huggingface.co/datasets/AgentVQA/AgentVQA). arXiv v1은 2026-10-22 제출이다.
3. **코드 품질·재현성:** `[사실]` 평가 코드는 lmms-eval 기반이고, 데이터 무결성 검사·dry-run·API 호출 상한·재시작 가능한 실행을 문서화했다. 저장소 루트에는 assets/docs/evaluation과 16개 커밋이 보이지만, 루트 LICENSE 파일은 확인되지 않았다.
4. **라이선스:** `[사실]` 저장소 루트와 Hugging Face 카드에서 단일 통합 라이선스를 확인하지 못했다. 데이터 카드는 23개 원천 데이터셋의 각 라이선스·이용 조건을 따르라고 명시한다. 상업적·재배포 사용 전 하위 데이터셋별 검토가 필요하다.
5. **가중치·체크포인트:** `[사실]` 자체 모델 가중치는 없고 평가 데이터·미디어를 배포한다. Hugging Face 데이터 크기는 25.9GB이며 1,000행이다.
6. **설치 난이도·의존성:** `[사실]` Python 3.10+, CPU용 PyTorch 2.7.1/torchvision 0.22.1, requirements 설치가 공식 경로다. 데이터는 Hub에서 직접 읽는다. 난이도는 **낮음~중간**이며 25.9GB 캐시와 API 키가 병목이다.
7. **GPU/VRAM:** `[사실]` API 평가에는 로컬 GPU나 모델 가중치가 필요 없다고 문서화했다. 로컬 오픈모델을 붙일 경우 자원은 해당 모델에 종속되며 공식 단일 VRAM 수치는 없다.
8. **즉시 실험 적합성:** `[해석]` 매우 높다. GUI·게임·로봇·공간추론 중 한 subset 5문항으로 프롬프트/모델 회귀를 30분 내 점검할 수 있다.
9. **프레임워크 호환성:** `[사실]` Hugging Face Datasets와 lmms-eval을 직접 사용한다. MMDetection·Ultralytics·timm용 어댑터는 제공하지 않는다. OpenAI, Anthropic, Gemini, DashScope, Z.ai, Moonshot, OpenRouter, Together와 호환 API 경로가 문서화돼 있다.
10. **유지보수·이슈/PR:** `[사실]` 확인 시점 저장소는 16개 커밋, 8 stars, 공개 이슈/PR 수는 GitHub 페이지에서 별도 표기되지 않았다. 초기 공개 단계이므로 데이터 revision을 커밋으로 고정해야 한다.

**저자 주장:** 22개 모델 설정 중 최고 전체 정확도는 58.5%이며, 오류의 주원인은 과업 해석보다 UI 위치·움직임·상태 변화·3D 관계의 시각적 grounding과 상태 유지다.

**진단 → 가설 → 최소 실험**

- 진단: 현재 VLM 비교가 일반 이미지 QA에 치우쳐 실제 에이전트의 상태 추적 실패를 숨긴다.
- 가설: GameQA와 ManipBench의 동일 5문항에 간단 추론/고추론 설정을 적용하면 논리보다는 시각 상태 표현에서 일관된 오답이 반복된다.
- 최소 실험: `catalog`와 `validate`를 실행한 뒤 GameQA 5문항을 `--dry-run`, 이어 API 호출 상한 10으로 두 설정에서 평가한다. **측정:** 정확도, 유효 응답률, 문항당 지연, API 오류율, 상태 변화/공간관계 오류 태그 수. 성공 기준은 두 설정 모두 5문항 완주와 오류 태그 재현이다.

## 2. BrickWright / BrickLayer

1. **새로운 내용:** `[사실]` 사전학습 코딩 에이전트가 실제 LEGO 부품만 사용하고 충돌·부유·비연결을 검증하며 텍스트/이미지 프롬프트에서 조립 가능한 3D 구조를 생성하도록 한다.
2. **논문·프로젝트:** [논문](https://arxiv.org/abs/2610.31651) · [프로젝트](https://avalovelace1.github.io/brickwright/) · [코드](https://github.com/AvaLovelace1/brickwright). arXiv v1은 2026-10-22 제출이다.
3. **코드 품질·재현성:** `[사실]` `bricklayer`와 `brickwright` 두 Python 패키지로 나뉘며 pytest, Ruff lint/format, ty type-check 명령과 GitHub 설정이 있다. 9개 커밋의 초기 저장소지만 테스트 경로와 `uv.lock`이 있어 환경 고정성이 좋다.
4. **라이선스:** `[사실]` MIT.
5. **가중치·체크포인트:** `[사실]` 별도 학습 가중치가 없다. 외부 코딩 에이전트를 도구 사용자로 삼고, 실제 부품 카탈로그와 LDraw 내보내기를 제공한다.
6. **설치 난이도·의존성:** `[사실]` 공식 quickstart는 저장소 clone 후 `packages/brickwright` 안내를 코딩 에이전트에 제공하는 방식이다. 개발 명령은 `uv run` 기반이다. 난이도는 **중간**이며 외부 LLM/API와 LDraw 워크플로 이해가 필요하다.
7. **GPU/VRAM:** `[사실]` 로컬 GPU 요구는 명시되지 않았다. 추론 자원은 선택한 외부 코딩 에이전트에 종속된다.
8. **즉시 실험 적합성:** `[해석]` 높다. 3D 생성 자체보다 “생성→검증→수정” 루프가 CAD·로봇 플래닝·합성데이터 검증에 전이 가능한지 확인하는 데 가치가 있다.
9. **프레임워크 호환성:** `[사실]` Python SDK와 LDraw 출력이 핵심이다. MMDetection·Ultralytics·timm·Hugging Face 직접 통합은 없다. 일반 코딩 에이전트와 결합한다.
10. **유지보수·이슈/PR:** `[사실]` 확인 시점 9개 커밋, 11 stars, 0 forks이며 공개 저장소는 막 공개된 단계다. 릴리스 태그보다 커밋 고정 사용이 안전하다.

**저자 주장:** baseline 코딩 에이전트의 물리 유효성이 9~69%인 반면 BrickWright 유도 에이전트는 512개 프롬프트 표본에서 100% 유효성을 달성했고, BrickLayer API는 raw LDraw 작업 대비 추론 비용을 절반으로 줄였다.

**진단 → 가설 → 최소 실험**

- 진단: 자유형 3D 코드 생성은 시각적으로 그럴듯해도 부품 충돌·부유·연결 단절을 놓친다.
- 가설: 동일 텍스트 프롬프트에 raw LDraw와 BrickLayer를 각각 사용하면 BrickLayer 조건에서 validator 오류와 수정 반복 수가 감소한다.
- 최소 실험: “손잡이가 있는 작은 다리” 프롬프트 3개 seed를 두 경로로 생성한다. **측정:** 실제 부품 비율, collision 수, floater 수, connected component 수, 유효 결과까지의 agent turn·토큰·벽시계 시간. 성공 기준은 BrickLayer 3/3 유효 및 raw 대비 평균 수정 turn 감소다.

## 3. OpenTac

1. **새로운 내용:** `[사실]` 자유형 2D 윤곽/DXF/전개 가능한 3D 표면에서 flex-PCB 촉각 피부를 설계하고, Gerber·케이스·manifest를 생성하며 펌웨어·리더·시뮬레이터·센서 간 전이를 연결한다.
2. **논문·프로젝트:** [논문](https://arxiv.org/abs/2610.31661) · [문서/데모](https://opentac.github.io/) · [코드·하드웨어](https://github.com/opentac/opentac). arXiv v1은 2026-10-22 제출이다.
3. **코드 품질·재현성:** `[사실]` Python 패키지, tests, GitHub 워크플로, firmware, hardware, examples, `pyproject.toml`, `uv.lock`, CITATION, 기여 가이드를 포함한다. 확인 시점 131개 커밋으로 이번 선정 중 저장소 성숙도가 가장 높다.
4. **라이선스:** `[사실]` 소프트웨어 MIT, 문서 CC-BY-4.0, 하드웨어 CERN-OHL-P-2.0.
5. **가중치·체크포인트:** `[사실]` 사전학습 비전 가중치 제품이 아니다. 제조 파일·펌웨어·CAD/시뮬레이터 소스가 핵심 산출물이다.
6. **설치 난이도·의존성:** `[사실]` `uv run opentac cad`로 로컬 브라우저 CAD를 열 수 있고 Windows/macOS/Linux launcher가 있다. 설계·시뮬레이션은 **낮음~중간**, 실센서 제작·플래싱은 PCB·재료·USB 권한 때문에 **높음**이다.
7. **GPU/VRAM:** `[사실]` CAD와 센서 읽기 경로에 GPU 요구가 명시되지 않았고, 공식 예제는 노트북에서 약 5초에 200-taxel 깔창 보드를 생성했다고 설명한다.
8. **즉시 실험 적합성:** `[해석]` CAD-only 검증은 즉시 가능하다. 실제 CV 연구에는 촉각 heatmap을 RGB/깊이와 결합한 접촉 이벤트 탐지나 조작 정책 입력으로 연결하는 단계가 추가로 필요하다.
9. **프레임워크 호환성:** `[사실]` Python API, JSON manifest, KiCad/Gerber, SVG/PDF 산출물을 제공한다. MMDetection·Ultralytics·timm·Hugging Face 직접 어댑터는 없다. ROS 연동은 이번 공식 README 범위에서 확인하지 못했다.
10. **유지보수·이슈/PR:** `[사실]` 확인 시점 131개 커밋, 54 stars, 6 forks, 2 open PRs이며 테스트와 기여 문서가 있다. 하드웨어·소프트웨어가 함께 변하므로 manifest/firmware 호환성을 커밋으로 고정해야 한다.

**저자 주장:** 30개 이상 센서를 네 로봇 embodiment에 적용했고, 1,024-taxel 피부에서 16 taxel만 표본화할 때 adaptive acquisition이 full raster 대비 19.2배 빠르며 kHz급 부분 판독을 달성했다.

**진단 → 가설 → 최소 실험**

- 진단: 로봇 비전은 접촉 직전/직후의 시각 모호성을 촉각으로 보완할 수 있지만, 센서 형상·좌표·획득 속도 정의가 프로젝트마다 분리된다.
- 가설: OpenTac manifest를 공통 좌표 계약으로 쓰면 CAD 산출물과 시뮬레이터 heatmap의 taxel 인덱스가 자동 일치한다.
- 최소 실험: 공식 insole 예제를 생성하고 DRC, manifest taxel 수, SVG 위치와 시뮬레이션 frame index를 비교한다. **측정:** 생성 시간, DRC 오류 수, manifest taxel 수(예제 기대 200), 좌표 불일치 수, 재실행 산출물 해시. 성공 기준은 DRC 0, taxel 200, 좌표 불일치 0이다.

## 4. AnyGameRenderer

1. **새로운 내용:** `[사실]` 블록아웃·색상 primitive·semantic map 같은 거친 게임 영상을 입력으로 받아 스타일화된 영상을 생성하면서 프레임별 엔티티 위치·등장/퇴장·개수를 보존하도록 학습한 video-to-video renderer다.
2. **논문·프로젝트:** [논문](https://arxiv.org/abs/2610.31466) · [코드](https://github.com/AlayaLab/AnyGameRenderer). arXiv v1은 2026-10-22 제출이다.
3. **코드 품질·재현성:** `[사실]` 설치·가중치 다운로드·3개 예제·caption skill·단일/배치 추론 명령을 제공하고, musubi-tuner를 특정 커밋에 고정했다. requirements도 버전 고정이지만 공개 테스트 스위트는 저장소 루트에서 확인되지 않았다.
4. **라이선스:** `[사실]` 코드 저장소는 Apache-2.0. 기본 MiniMax-H3 가중치는 별도 Community License 수락이 필요하므로 배포·상업 사용은 두 조건을 함께 검토해야 한다.
5. **가중치·체크포인트:** `[사실]` 기본 가중치 약 123GB와 LoRA 2.4GB를 다운로드한다. LoRA와 처리 파일을 공개한다.
6. **설치 난이도·의존성:** `[사실]` Linux, CUDA 12.8, Python 3.10, torch 2.9.1+cu128, transformers 4.57.6 및 고정 requirements가 필요하다. 난이도는 **매우 높음**이다.
7. **GPU/VRAM:** `[사실]` 공식 요구는 GPU 1장 80GB 이상, CPU RAM 128GB 이상이다. peak는 text encoder 포함 약 50GB, block swap sampling 약 32GB이며 H100급에서 124-frame/20-step clip 약 17분과 load 약 6분을 보고한다.
8. **즉시 실험 적합성:** `[해석]` 현재 로컬 장비에는 부적합하다. 원격 H100 1회로 공식 예제를 실행하거나, 코드·입력 규격만 분석해 small-object/temporal 일관성 평가 설계를 가져오는 것이 현실적이다.
9. **프레임워크 호환성:** `[사실]` PyTorch/Transformers/musubi-tuner 계열이며 전용 mp4+JSONL 파이프라인이다. MMDetection·Ultralytics·timm 직접 어댑터는 없다. Hugging Face에서 MiniMax-H3 라이선스와 가중치를 받는다.
10. **유지보수·이슈/PR:** `[사실]` 확인 시점 28개 커밋, 26 stars, 1 open issue, 0 forks의 초기 공개 저장소다. 고정 해상도 1344×768, 학습 길이 124 frames라는 제약을 유지해야 한다.

**저자 주장:** 59개 held-out case와 753개 GT 엔티티에서 base 대비 temporal match 50.9→62.9%, position match 57.1→61.9%, unrendered 4.1→2.9%, hallucination 52.1→46.0%를 보고한다.

**진단 → 가설 → 최소 실험**

- 진단: 게임 재렌더링 품질 평가는 화질 중심일 때 작은·원거리 엔티티 누락과 잘못된 생성 시점을 놓친다.
- 가설: 동일 primitive clip에서 seed를 바꿔도 entity trajectory/출현 프레임은 외형 변화보다 안정적으로 유지된다.
- 최소 실험: 원격 80GB GPU에서 공식 124-frame 예제 하나를 seed 2개로 실행한다. **측정:** 성공 프레임 수, GT/입력 proxy와의 box temporal match, position match, count-change miss, hallucination, peak VRAM, wall time. 성공 기준은 두 seed 모두 완주하고 base 대비 temporal match가 저하되지 않는 것이다.

## 지금 clone할 3개와 실행 순서

1. **AgentVQA:** 데이터 `validate` → GameQA 5문항 dry-run → 제한된 API 평가. 가장 작은 비용으로 VLM 상태 추적 오류 지도를 만든다.
2. **BrickWright:** `uv run pytest` → 단일 프롬프트 생성 → validator 오류 로그 비교. 검증 루프를 다른 3D/CAD 에이전트로 옮길 수 있는지 본다.
3. **OpenTac:** `uv run opentac cad` → 공식 insole 스크립트 → manifest/DRC 검증. 하드웨어 구매 전 CAD-only 경로를 닫는다.

AnyGameRenderer는 clone과 코드 검토까지만 수행하고, 80GB GPU·128GB RAM·약 125GB 가중치 저장 공간을 확보한 뒤 공식 예제 1개로 go/no-go를 판단한다.

## 공통 결론

- `[사실]` 네 프로젝트 모두 완성 모델의 단일 점수보다 평가기·검증기·manifest·엔티티 수준 지표를 공개했다.
- `[해석]` 이번 주의 유의미한 변화는 “생성 결과를 더 그럴듯하게 만드는 것”보다 에이전트가 놓치는 상태·물리 구조·접촉·개체 일관성을 구조화하고 자동 검증하는 쪽이다.
- `[전망]` 연구 우선순위는 AgentVQA로 시각 상태 실패를 계측하고, BrickWright의 validator loop를 일반화한 뒤, OpenTac처럼 센서 입력 계약까지 확장하는 순서가 효율적이다. 이 전망은 제안이며 실험 결과가 아니다.
