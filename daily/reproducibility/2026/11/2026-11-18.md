## 사례 1 — Qwen3-VL: 실제 padding 이후 token budget을 검사해야 한다

**Claim / 커뮤니티 재현 조건.** #50871 작성자는 Transformers 5.8.0과 main `528c2671`, Python 3.11.16, torch 2.13.0+cu130, Linux·NVIDIA L20을 제시한다. downstream은 vLLM 0.28.0의 Qwen3.6-35B-A3B-FP8 serving이다. 핵심 resize 재현에는 모델 weights가 필요 없다. [원문](https://github.com/huggingface/transformers/issues/50871)

**Observed gap.** 57×720×1280 입력, temporal factor 2, spatial factor 32, pixel budget 50,331,648에서 작성자는 704×1248 출력과 padding 후 58 frames를 보고했다. 이때 총 50,958,336 pixels, 24,882 tokens로 선언된 24,576-token budget을 넘는다. vLLM encoder cache 오류도 제시했지만 이는 제보자의 serving 결과다. 별도 사용자는 main `42cd3d9b5c7be7adc3e0578a9a7cb1c4b40b0e55`에서 weights 없이 함수를 실행해 57-frame 사례와 1,532개 조건 중 34개 위반을 확인했다고 보고했다. [별도 재현](https://github.com/huggingface/transformers/issues/50871#issuecomment-6945097001)

**확인된 소스 / mechanism.** 고정 revision의 GLM4V 공통 함수는 `t_bar`에 `round`를 사용하면서 resize scale인 `beta`에는 원래 `num_frames`를 사용한다. 실제 temporal padding 길이와 검사·축소 기준이 달라질 수 있다. 별도 사용자의 5×64×64 예제는 `round(5/2)*2=4`와 실제 6-frame padding의 차이만으로도 문제를 분리한다. 수정 source of truth는 GLM4V image processor이며 복사·modular 파일도 동기화해야 한다는 분석에 maintainer가 동의했다. 조회 시 이슈는 open이며 연결 검색에서 수정 PR은 찾지 못했다. [고정 소스](https://github.com/huggingface/transformers/blob/42cd3d9b5c7be7adc3e0578a9a7cb1c4b40b0e55/src/transformers/models/glm4v/image_processing_glm4v.py), [maintainer 응답](https://github.com/huggingface/transformers/issues/50871#issuecomment-6947666045)

**진단 → 가설 → 최소 실험.** 가설은 “모델이나 seed가 아니라 padding 전후 shape 계약이 serving 재현을 깨뜨린다”이다. 5-frame·57-frame fixture와 인접한 짝수 frame 대조에서 실제 processor의 `video_grid_thw`, pixel 수, merged token 수를 저장한다. 원본, `ceil`만 적용, `ceil`과 padded-count scale을 함께 적용한 세 경로를 비교한다. sampling index·input tensor는 고정한다. 최소 spatial factor에 clamp되는 극단 입력과 upscale branch도 별도로 검사한다.

**GO/KILL.** 실제 processor 출력이 적용 가능한 budget 범위를 만족하고 짝수 frame 대조가 보존되면 serving smoke test로 GO한다. resize 함수만 통과했는데 full processor나 serving cache까지 해결됐다고 선언하는 것은 KILL한다. 현재 독립 확인은 함수 수준이며 영상 QA 정확도 개선 근거는 없다.

## 사례 2 — Textual Inversion: 같은 embedding도 prompt 대소문자로 사용 vector 수가 달라질 수 있다

**Claim / 재현 조건.** #15313은 Diffusers `0.44.0.dev0@1dabc292d`, Transformers 5.22.2, torch 2.15.0 CPU, Python 3.12.11·macOS 조건이다. `tiny-sd-pipe`에 3-vector embedding을 `MyToken`과 `neg`로 넣고 prompt를 비교한다. 작성자는 Transformers 4.57.1에서는 기존 확장이 작동했다고 보고한다. [원문·재현 코드](https://github.com/huggingface/diffusers/issues/15313)

**Observed gap / 검증 한계.** 작성자 출력에서 `MyToken`은 `['mytoken']`, `neg`는 세 vector token, `Neg`는 `['neg']`로 처리된다. 실제 EasyNegative의 8-vector 예제도 버전별 토큰 수 차이로 제시하지만 독립 댓글이나 이미지 품질 측정은 없다. 조회 시 이슈는 open이고 댓글은 없었다.

**확인된 소스 / mechanism.** 고정 Diffusers 소스는 `tokenizer.tokenize(prompt)` 결과를 `added_tokens_encoder`에서 그대로 찾고 `prompt.replace(token, replacement)`를 수행한다. 이 경로의 문자열 lookup·replace는 대소문자를 구분한다. v5 tokenizer가 추가 토큰을 소문자로 반환한다는 제보와 결합하면 lookup 실패와 원문 prompt 치환 실패라는 두 경로를 설명할 수 있다. tokenizer 자체의 모든 v5 버전 동작을 이번 조사에서 실행 검증한 것은 아니다. [고정 소스](https://github.com/huggingface/diffusers/blob/1dabc292d/src/diffusers/loaders/textual_inversion.py)

**진단 → 가설 → 최소 실험.** 가설은 “seed 변화로 보이는 conditioning 차이 중 일부가 multi-vector token의 미확장에서 발생한다”이다. 동일 embedding tensor를 파일로 고정하고 Transformers 4.57.1/5.22.2 × 등록 token 대소문자 × prompt 대소문자를 교차한다. 확장 문자열, input IDs, 각 vector token의 출현 수와 text-encoder hidden state를 먼저 비교한다. 이후 checkpoint·prompt·initial latent를 고정해 생성 대조를 한다. 임의의 전체 prompt lowercasing은 다른 토큰의 의미를 바꿀 수 있으므로 해결책으로 가정하지 않는다.

**GO/KILL.** 의도한 모든 vector가 중복 없이 들어가고 무관한 prompt 구간이 보존되면 생성 검증으로 GO한다. embedding load 성공이나 경고 부재만으로 conditioning parity를 승인하는 것은 KILL한다. tiny token fixture를 이미지 품질 개선 또는 전 v5 회귀의 증거로 확대하지 않는다.

## 사례 3 — PE Audio/Video: dependency buffer가 weight tying 경로에 들어온다

**Claim / 재현 조건.** #50860 작성자는 Transformers 5.22.2, timm 1.0.31, torch 2.16.0.dev, Python 3.12·Linux에서 `facebook/pe-av-large` 로드를 제시한다. CPU/CUDA/XPU에서 재현됐고 timm 1.0.30은 정상이라고 주장한다. `ignore_mismatched_sizes=True`는 별도 `num_labels` mismatch와 분리하기 위한 조건이다. [이슈·traceback](https://github.com/huggingface/transformers/issues/50860)

**Observed gap / 주장 구분.** 해당 옵션으로 로드하면 tied-weight 초기화 단계에서 `bands is not an nn.Parameter`가 발생한다는 traceback이 있다. 옵션을 끄면 tying이 건너뛰어져 약 130개 tensor가 missing·재초기화된다는 것은 작성자의 추가 주장이다. 이번 실행은 실제 checkpoint tensor나 load log를 검사하지 않았으며 독립 재현 댓글도 없었다. 이슈는 open이다.

**확인된 소스 / mechanism.** Transformers v5.23.0의 PE tying regex는 `.rope.pos_embed`만 제외하고, 초기화 함수는 tied key에 `get_parameter()`를 호출한다. timm 두 tag를 비교하면 1.0.30도 동적 embedding 모드에는 `bands` buffer가 있었지만 고정 shape cache 모드에는 없었다. 1.0.31은 공통 base에서 두 모드 모두 non-persistent `bands`를 등록한다. 따라서 “bands가 timm 전체에 처음 도입됐다”보다 “고정 shape 모드에도 bands가 생겨 regex의 예외 범위 밖으로 들어왔다”가 소스에 맞는 진단이다. [PE regex](https://github.com/huggingface/transformers/blob/v5.23.0/src/transformers/models/pe_audio_video/modeling_pe_audio_video.py), [초기화 함수](https://github.com/huggingface/transformers/blob/v5.23.0/src/transformers/modeling_utils.py), [timm 1.0.30](https://github.com/huggingface/pytorch-image-models/blob/v1.0.30/timm/layers/pos_embed_sincos.py), [timm 1.0.31](https://github.com/huggingface/pytorch-image-models/blob/v1.0.31/timm/layers/pos_embed_sincos.py)

**진단 → 가설 → 최소 실험.** 가설은 “동일 checkpoint라도 dependency의 parameter/buffer 집합 변화가 로드 계약을 바꾼다”이다. 먼저 작은 module에서 고정 shape RoPE의 `named_parameters`·`named_buffers`·expanded tied keys를 tag별 비교한다. 다음 동일 checkpoint revision에서 timm 1.0.30/1.0.31과 mismatch 옵션 on/off를 교차해 missing/unexpected key, 초기화 tensor, 실제 tied tensor의 identity·값을 기록한다. loader의 buffer 처리 변경과 모델 regex 변경은 별도 intervention으로 비교한다.

**GO/KILL.** 예상 tensor가 checkpoint와 일치하고 tying·buffer 재생성·고정 입력 forward가 기준을 통과하면 GO한다. `ignore_mismatched_sizes`로 오류가 사라졌거나 로드가 끝났다는 사실만으로 재현 완료를 선언하는 것은 KILL한다. timm pin은 임시 비교 조건이며 수정 릴리스나 성능 동등성의 증거가 아니다.

## 공통 비교 조건과 오늘의 GO/KILL

세 사례는 video preprocessing, SD text conditioning, audiovisual checkpoint loading으로 서로 다른 작업이다. backbone·data/split·resolution·pretraining·hardware·precision·batch·TTA·evaluator를 맞춘 성능 비교가 아니므로 **not strictly apples-to-apples**다. 함수·토큰·로드 검사는 benchmark metric 측정이 아니며, 확인하지 않은 학습·평가 조건은 미확인으로 남긴다.

- **오늘 첫 GO:** Qwen odd/even-frame processor budget 검사. weights 없이 실패 조건을 분리할 수 있다.
- **다음 GO:** embedding hash와 tokenizer 버전을 고정하고 multi-vector expansion을 검사한다.
- **조건부 GO:** PE 실험은 dependency 버전과 load audit를 확보한 뒤 시작한다.
- **KILL:** seed sweep으로 전처리·token expansion·weight loading 계약 오류를 덮지 않는다. open issue를 수정·릴리스로, closed issue를 검증 완료로 해석하지 않는다.
- **후속 연구 가설:** shape·token·parameter/buffer manifest를 seed 반복 전에 검사하면 일부 재현 실패를 더 작은 실험으로 분리할 수 있다. 이는 이번 조사에서 검증한 실측 결론이 아니라 후속 평가 과제다.
