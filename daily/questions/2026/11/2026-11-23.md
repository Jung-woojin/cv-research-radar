**Hypothesis:** 최종 이미지·annotation·tile 설정을 같게 맞추면, 수정 후 재사용 출력은 새 디렉터리의 clean rebuild와 같은 tile–label manifest를 만든다. 수정 전에는 foreground→background 전환에서 이 불변성이 깨진다.

**최소 개입·Experimental Design:** base `96041a27bf4f258fd3bff511ee24cfb1661b21fb`와 head `244994ad8e9b43239254454a2bac6060f4354ff0`을 고정한다. CPU에서 변경·불변 이미지 두 개로 시작하고, 처음 분할→원본 annotation 수정→같은 디렉터리 재분할을 수행한다. 동일 최종 원본을 새 디렉터리에 분할한 결과가 baseline이다. foreground→background, background→foreground, 불변 tile, 이미지 쓰기 실패를 분리한다. 실패 실행의 부분 결과는 학습에 사용하지 않는다.

**Dataset·Metric·GO/KILL:** 합성 fixture 뒤 DOTA의 별도 개발 subset으로 확장한다. sample별 이미지·label hash, stale label 수, clean rebuild와의 manifest 차이, 실패 시 기존 쌍 보존을 측정한다. 수정 후 정상 실행의 이력 의존성이 사라지면 GO. tile 설정·이미지 내용이 달라지거나 annotation 누락을 진짜 background로 오인하면 성능 인과 해석은 KILL한다.

## Q2. 표현 분석의 차이는 시각 표현 때문인가, embedding API가 다른 출력을 반환했기 때문인가?

**문제·Observation·왜 지금:** #27316은 음수 index를 실제 층 번호로 변환한다. 이전 구현은 음수 요청이 층 index와 맞지 않아 head 출력으로 진행할 수 있었다. 작성자는 detection·classification 등에서 이 차이를 보고했다. 확인한 diff는 네 predict 경로의 index 정규화이며, 모든 head 출력을 embedding으로 바꾸는 수정은 아니다.  
[공식 PR](https://github.com/ultralytics/ultralytics/pull/27316) · [공식 diff](https://github.com/ultralytics/ultralytics/pull/27316/files)

**Gap·Diagnosis·Mechanism:** tensor가 반환됐다는 이유만으로 의도한 층의 표현이라고 볼 수 없다. 분류 확률이나 검출 head 출력을 embedding으로 사용하면 retrieval·clustering·domain separation 해석이 달라질 수 있다는 것이 추론이다. 실제 기존 논문이 영향을 받았다는 증거는 없다.

**Hypothesis:** 같은 층을 가리키는 양수·음수 요청은 명시적 forward hook과 일치해야 한다. API index 정규화로 이 동등성이 회복되지만, head 층 자체의 출력 구조와 pooling 가능성은 별도 계약이다.

**최소 개입·Experimental Design:** base `a431d144646a7fb7a0993323290e4ea84b5c245b`와 head `b3432ed7232209905cc5201e559a473de0349f5b`를 비교한다. 먼저 CPU mock layer에서 양수·음수·혼합·범위 밖 요청을 검사한다. 이후 동일 소형 YOLO checkpoint와 동일 이미지에 대해 API 출력, 같은 층의 forward hook+동일 pooling을 대조한다. `None`·빈 요청·head 요청은 별도 대조군이다. 작은 객체 crop과 전체 장면은 후속 representation 분석에서 분리한다.

**Dataset·Metric·GO/KILL:** 첫 입력은 합성 tensor와 COCO8, 후속은 고정 UAV subset을 사용한다. 출력 type·shape·층 provenance, 최대 절대 오차, cosine similarity와 retrieval 이웃 변화를 기록한다. 대응 층의 API–hook 동등성이 회복되면 GO. 서로 다른 층·pooling·정규화를 비교하면 표현 우열 주장을 KILL한다. Head의 `-1` 요청이 항상 유효하다고 가정하지 않는다.

**Expected Contribution·negative result:** 표현 연구의 층 provenance 검증과 silent fallback 탐지다. downstream 차이가 없으면 해당 데이터·표현 사용법에서 API 오류의 실질 영향이 작다는 결론을 얻는다.

**Compute·Risk·4~8주:** mock은 cost **1/5**, 소형 checkpoint 비교는 **2/5**. RTX 5060 Ti 8GB에서 시작할 후보지만 실제 VRAM은 측정하지 않았다. 1~2주 동등성 감사, 3~4주 여러 task·API, 5~8주 retrieval·domain shift 결론의 변화까지 검증한다. 버그 하나에 한정하면 출판 가능성은 낮고, CNN/ViT의 본질적 차이라고 일반화하면 안 된다.

## Q4. CCTV 점유 집계의 초기 누락은 검출 실패인가, 신규 track을 배제하는 집계 규칙 때문인가?

**문제·Observation·왜 지금:** #27314는 QueueManager가 이전 위치가 있어야 객체를 세던 조건을 제거하고 현재 box 중심으로 점유 여부를 검사한다. 작성자는 실제 영상에서 신규 track의 첫 프레임 누락을 보고했다. OBB end-to-end와 다른 tracker는 검증하지 않았다고 명시했다.  
[공식 PR](https://github.com/ultralytics/ultralytics/pull/27314) · [공식 diff](https://github.com/ultralytics/ultralytics/pull/27314/files)

**Gap·Diagnosis·Mechanism:** 점유와 선 통과는 다른 사건이다. detector가 객체를 찾았어도 tracker 확인 지연과 후처리 이력 요구로 집계가 늦을 수 있다. 이번 수정은 후처리 지연을 겨냥하며 실제 인원 recall 전체를 해결하지 않는다.

**Hypothesis:** tracker 출력을 고정하면 수정 전의 점유 누락은 ROI 안 신규 ID와 대응하며, 현재 box 중심 집계로 그 추가 지연이 사라진다. ID reset·재진입에서 같은 효과가 반복될 수 있다는 것은 후속 가설이다.

**최소 개입·Experimental Design:** base `c747ded440c5bf8d7a4da40f33f084976c60da9e`와 head `e5629a7c07f727f819444277470ad94f67bf123e`를 비교한다. CPU에서 고정 box·ID 시퀀스로 첫 프레임·신규 진입·재진입·ID 변경을 검사한다. baseline은 현재 box 중심의 직접 occupancy oracle이다. 실제 CCTV에서는 annotation 대비 detector, detector 대비 tracker, tracker 대비 집계를 단계별로 분리한다. ROI 경계의 `contains` 정책도 고정한다.

**Dataset·Metric·GO/KILL:** 합성 track 뒤 공개 영상 또는 권한이 있는 CCTV 개발 clip을 사용한다. 구체적 clip 확보는 미확인이다. 프레임별 count MAE, 신규 ID 첫 집계 지연, onset 누락률과 detector·tracker recall을 기록한다. 고정 track에서 추가 지연만 제거되면 GO. tracker가 객체를 내보내지 않은 프레임까지 집계 수정의 실패·성공으로 해석하면 KILL한다.

**Expected Contribution·negative result:** 인식–추적–사건 집계의 오류 예산 분해다. 실제 영상에서 효과가 작으면 장기 확인 지연이나 detector miss가 더 큰 원인일 수 있다는 결론을 얻는다. 해양 안전 감시로 확장하려면 중심점 점유 정의가 적절한지도 별도로 검증해야 한다.

**Compute·Risk·4~8주:** 고정 track은 cost **1/5**, 소형 detector 영상은 **2/5**. 1~2주 시퀀스 검사, 3~4주 tracker·ROI 교차 비교, 5~8주 안전 사건의 onset 지연 평가를 계획한다. 알려진 집계 규칙 수정만으로 novelty는 낮다.

## Q5. 수치적으로 올바른 metric 수정은 언제 실제 모델 평가에 영향을 주는가?

**문제·Observation·왜 지금:** #27315는 SILog의 difference-of-moments 계산을 중심화된 제곱 오차로 바꾸는 제안이다. PR은 **미병합 종료**됐다. Maintainer는 정렬하지 않은 합성 입력에서 cancellation을 재현했으나, 기본 median alignment와 실제 depth 평가에서는 보고 자릿수 수준의 효과가 없었다고 설명했다. 확인한 validator는 `DepthMetrics(max_depth=...)`를 생성하고, metric 기본값은 `align="median"`이다.  
[제안·반대 근거 댓글](https://github.com/ultralytics/ultralytics/pull/27315) · [고정 validator](https://github.com/ultralytics/ultralytics/blob/c747ded440c5bf8d7a4da40f33f084976c60da9e/ultralytics/models/yolo/depth/val.py) · [고정 metric](https://github.com/ultralytics/ultralytics/blob/c747ded440c5bf8d7a4da40f33f084976c60da9e/ultralytics/utils/metrics.py)

**Gap·Diagnosis·Mechanism:** 단위 계산의 오차와 전체 평가 결론의 오류는 다르다. 추론상 log-depth 오차의 평균이 분산보다 클 때 cancellation 위험이 커지지만, alignment·clamp·mask가 실제 도달 범위를 바꾼다. 따라서 합성 반례만으로 benchmark 신뢰성 문제를 주장할 수 없다.

**Hypothesis:** 두 계산식의 차이는 평균 log-scale bias 대비 잔차 분산이 작은 조건에 집중되며, 기본 median alignment의 실제 예측에서는 보고 정밀도보다 작다. 이 가설은 개선을 기대하기보다 영향이 없는 범위를 먼저 검증한다.

**최소 개입·Experimental Design:** 같은 base와 proposal head `a55f28fa8f1a30943433405f2bff4eb6939047bf`의 계산식을 사용한다. CPU에서 scale bias·잔차 분산·dtype·alignment를 교차하되, clamp 전후를 구분한다. float64 계산을 reference로 삼고 sample별 계산 후 동일 집계를 적용한다. 이후 depth8과 고정 NYU 저장 prediction으로 실제 범위를 확인한다. CLI가 지원하지 않는 `align` 설정을 정규 val 옵션처럼 쓰지 않는다.

**Metric·GO/KILL:** reference 대비 절대 오차, 음수 분산 clamp 발생, 최종 표시 문자열 변화와 모델 순위 변화를 기록한다. 실제 모델·공식 경로에서 표시 정밀도를 넘는 재현 가능한 차이가 있어야 영향 연구 GO. 합성 비정렬 조건에서만 차이가 있으면 성능 개선 주장을 KILL하고 수치 경계 결과로 종료한다.

**Expected Contribution·negative result:** 수치 반례가 실제 평가로 전파되는지를 판정하는 절차다. 영향 없음은 maintainer의 반대 근거를 지지하는 유효한 결과다. 이미 알려진 안정적 분산 공식 자체를 신규 기여로 주장하지 않는다.

**Compute·Risk·4~8주:** 합성·저장 예측 분석 cost **1/5**. 실제 prediction 확보는 미확인이다. 1~2주 경계 분석 후 실제 영향이 없으면 조기 종료한다. 4~8주 연구로 확장하려면 여러 CV metric에서 반복되는 영향 전파 조건이 필요하며, 현재 단독 논문화 가능성은 낮다.
